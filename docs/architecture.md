# Squirmy architecture

This is the technical contract for the codebase. [plan.md](./plan.md) says what the product does; this says how the code is laid out and which conventions every module follows. When code and this document disagree, fix one of them in the same change.

## Workspace

```
apps/mobile            @squirmy/mobile        Expo app
apps/web               @squirmy/web           Vite + React web app
apps/server            @squirmy/server        Fastify API, worker, realtime
packages/contracts     @squirmy/contracts     zod schemas and types for every API
packages/client-core   @squirmy/client-core   session reducer, session client, API client
adapters/kit           @squirmy/provider-kit  the provider side of the acquisition protocol
adapters/cold-storage  @squirmy/adapter-cold-storage  reference provider: a folder of your own files
adapters/mock          @squirmy/adapter-mock  provider for tests and demos: quiet tagged tones
```

npm workspaces, Node 22.13 or newer, TypeScript 6, ESM everywhere except the Expo app. `contracts` and `client-core` compile to `dist` with `tsc`; consumers import the built output, so run `npm run build:packages` (or the packages' `dev` watchers) before typechecking or running anything else. The adapters build the same way (`npm run build:adapters`); the root `typecheck`, `test` and `build` scripts build both. The server image installs only the server's workspaces; `adapters/cold-storage` and `adapters/mock` are separate services with their own READMEs, and `adapters/kit` is the library they share (a workspace package, not published to npm).

## Code conventions

- Relative imports end in `.js` in server and packages (NodeNext). No path aliases in server or packages.
- **Contracts first.** Every request and response body is a zod schema in `packages/contracts/src/<domain>.ts`, exported with its inferred type under the same name. Routes parse input with the schema and return objects that satisfy the response type.
- **Units.** Durations are integer milliseconds. Timestamps on the wire are ISO 8601 strings; the session protocol uses epoch milliseconds. Gains are dB; peaks are linear.
- **IDs.** UUIDv7 from `newId()`. Artwork asset ids are UUIDv4 from `newPublicId()`.
- **Errors.** Throw `AppError` (or the helpers in `lib/errors.ts`). The response body is `{ error: { code, message, details? } }`. Codes are stable snake_case strings.
- **Names in the API.** A *track* is a recording. `TrackSummary.id` is the recording id. An *album* is a release group. Clients never see files, releases or recordings as separate concepts, except `fileId` in the playback descriptor.
- **Text matching.** Use `matchKey`, `creditKey` and `sortKey` from `lib/text.ts` for every normalized comparison and for the `*_key` columns.
- **No module-level side effects.** Nothing connects, listens, schedules or reads config at import time. `db` connects on first use.
- **Comments** explain why, not what. No commented-out code.

## Server

```
apps/server/src/
  index.ts              entry: migrate, then start API and/or worker by SQUIRMY_ROLE
  app.ts                buildApp(): Fastify instance, plugins, auth hook, module routes
  config.ts             zod-parsed environment
  database/             client.ts (lazy db), locks.ts (session locks), schema.ts, migrate.ts
  lib/                  auth, errors, ids, text, crypto, settings, version, ffmpeg, http
  jobs/                 pg-boss wrapper: jobs.define, enqueue, schedule
  realtime/             socket.io server, rooms, publish/invalidate/publishChanges
  modules/<name>/       one folder per module; see the table below
  test/                 database harness, audio fixtures, factories, http fixtures
```

- **Boot.** `index.ts` migrates, runs each module's `jobs` hook in worker roles, starts jobs, then in API roles builds the app, attaches realtime and runs the `realtime` hooks, then runs every module's `start` hook and listens last. A failure at any step, a migration included, logs `[squirmy] failed to start` and undoes the steps done so far. SIGTERM and SIGINT undo them in reverse. A worker-only process opens no HTTP port.
- **HTTP.** Helmet with a Content-Security-Policy that allows scripts, connections and media from the server only (no inline scripts, no `eval`: the web app sets zod's `jitless` in `zod-config.ts`), cookies, multipart (streamed, up to 16 GiB per file), and CORS only for the Vite dev origins outside production. Each module's `routes` is registered in its own encapsulated scope under `/api/v1`.
- **Compression and revalidation.** `@fastify/compress` sends brotli (quality 4) or gzip for JSON, XML, JavaScript, CSS, SVG and text of 1 KiB or more; audio, images and ranged responses go as they are. `lib/conditional.ts` gives every successful JSON GET under `/api/v1` a weak `ETag` (a hash of the body) and `Cache-Control: private, no-cache`, unless the route set its own, and answers a matching `If-None-Match` (compared weakly) with an empty 304.
- **Web app.** When `SQUIRMY_WEB_DIST` is set the built app is served, with `index.html` as the fallback for unknown GET paths outside `/api`, `/rest`, `/socket.io`, `/health` and `/ready`. Hashed files under `assets/` are cached as immutable.
- `GET /health` answers without touching anything; `GET /ready` checks the database.
- **Database connections.** Each process has a query pool of `SQUIRMY_DB_POOL_SIZE` connections (10; 4 under test, so tests catch work that assumes more), pg-boss's own pool of 6 (3 under test), and one connection for session locks. Nothing keeps a pooled connection while it waits for other work that needs one: a transaction runs only its own statements (no network call, file copy, job or query on `db` inside it), and a lock that outlives a statement (an import run, an organize batch in a root, the inbox watcher) is taken with `withSessionLock` or `trySessionLock` from `database/locks.ts`, on the lock connection. Holders used to reserve a pooled connection each, and an import keeps its lock while identification waits for probe, ingest and matching jobs, so four imports took a 4-connection pool and waited forever for connections they held themselves. A second take of a key this process holds fails at once, as it would in another process. Work that keeps a connection for hours (the search index import's COPY) opens a client of its own. Transaction-scoped advisory locks are taken in one order: `squirmy:library-catalog` before `squirmy:matching:apply` or `squirmy:search-stubs`.

### Modules

Each module is a folder under `modules/` that exports one `ServerModule` from its `index.ts`. `modules/index.ts` lists them all statically. A module only edits files inside its own folder, its own contracts file, and its own tests.

```ts
export type ServerModule = {
  name: string
  /** HTTP routes. Called with an instance already prefixed with /api/v1. */
  routes?: (app: FastifyInstance) => void | Promise<void>
  /** Routes that need their own prefix (Subsonic's /rest). Called with the root instance. */
  rootRoutes?: (app: FastifyInstance) => void | Promise<void>
  /** Job handlers. Called in processes whose role includes the worker. */
  jobs?: (jobs: JobRegistry) => void | Promise<void>
  /** Socket handlers. Called in processes whose role includes the API. */
  realtime?: (realtime: Realtime) => void | Promise<void>
  /** Long-running loops (file watchers, schedulers). `stop` must undo `start`. */
  start?: (context: { role: 'all' | 'api' | 'worker' }) => void | Promise<void>
  stop?: () => void | Promise<void>
}
```

### Seams between modules

Modules reach each other in three ways, in this order of preference:

1. **Database state.** A module finds its own work by querying for rows that need it (files with no loudness, albums still `pending`). Sweeps make this robust to ordering and restarts. A module may also hold off on work by another module's recorded state: scans skip `_Incoming` folders of imports still moving files, and matching waits for an import to decide its duplicates.
2. **Jobs by name.** A module may enqueue another module's job (`enqueue('loudness.measure', { fileId })`). The job name and payload are that module's public interface.
3. **Seam functions.** A few direct calls are declared up front as seams: `enrichment/detail.ts` (`ensureAlbumDetail`, `ensureArtistDetail`, `artistRadioTracks`), `acquisition/coverage.ts` (`onDemandRecordings`, `requestRecording`), `radio/suggest.ts` (`suggestAutoplay`). The owning module fills them in; callers never change. In the other direction, sessions exports `onPlayStart` (`sessions/plays.ts`), a subscription to plays opening on the active device, which scrobble uses for "now playing".

Beyond those, modules call each other's exported functions directly where sharing beats a copy: the catalog read helpers (`catalog/sql.ts`, `catalog/availability.ts`, `catalog/redirects.ts`, `catalog/summaries.ts`), `library/cleanup.ts`, `matching/merge.ts`, organize's planner and mover, and `search/keys.ts` are used across modules. Import them from the owning module and keep their signatures stable; the owner changes them with their callers.

### Configuration

Environment variables are parsed in `config.ts`; see that file for the full list. The ones a self-hoster sets: `DATABASE_URL` (required), `SQUIRMY_DATA_DIR`, `SQUIRMY_LIBRARY_PATHS` (read-only roots) and `SQUIRMY_MANAGED_LIBRARY_PATHS` (managed roots), `SQUIRMY_INBOX_PATH`, `PORT`, `PUBLIC_URL`, `TRUST_PROXY`, `SQUIRMY_ROLE`. `SQUIRMY_SECRET` is generated into the data directory on first boot when unset.

Operator settings that change at runtime (provider toggles, API keys, thresholds) live in the `server_settings` table and are edited in the admin UI. Shape: `ServerSettings` in contracts. Secrets are stored encrypted under separate keys and never returned. Feature switches clients need before signing in, such as `wantlistEnabled` (default off), are also reported by `GET /setup/status`; changing one invalidates `queryKeys.setupStatus()` and what it changes for every client.

### Artwork

Images are rows in `assets`. `storeImage(bytes)` stores an image now, de-duplicates by content, and queues `artwork.render` for a new one, which writes the 96, 300 and 600 px renditions from one read of the original. `GET /art/:id/:size` also answers `:size.webp`, which the web app uses so a CDN that caches by extension (Cloudflare) keeps art at the edge; responses are `public, max-age=31536000, immutable` with an `ETag` matched weakly. `remoteImage(url)` only records where an image lives; it is downloaded the first time `GET /art/:id/:size` asks for it, so search results for music you do not own can show covers without downloading every one. A failed download answers 404, is not cached, and is retried after an hour. A sized Cover Art Archive front (`.../front-500`) that answers 404 is fetched as the original (`.../front`, `coverart.originalFront`): archive.org derives the thumbnails some time after an upload, so a release of the last few days has only the original. When the source answers 404 or 410 (a release group the Cover Art Archive has no cover for), the asset is also unassigned from the albums and artists showing it, so their summaries stop handing out an id that cannot be served, `invalidate` names those albums and artists (from whichever process asked for the image), and each album gets `enrichment.cover`, which picks another cover; the discography does not offer that cover again for a week. Summaries leave out an asset that is `missing`, or `failed` and not yet due for a retry (`servable` in `catalog/summaries.ts`); Subsonic applies the same rule to its `coverArt` fields, image URLs and `getCoverArt` by entity id (`servableArt` in `subsonic/sql.ts`).

Lost originals rebuild themselves (`artwork/recover.ts`). When a file under `assets/` is gone, `readOriginal` (used by renditions and Subsonic's `getCoverArt`) reads it back from disk while the request waits: the folder image of a `folder:` source, or the pictures of the source file and of any present file whose `embedded_art_asset_id` it is. Only bytes with the stored SHA-256 are accepted, so an id never shows a different picture. A URL source is queued as `artwork.recover` and the request answers 404 without cache headers; the job downloads it again (a `remote_url` asset goes back to `remote` and is fetched as on its first request; any other must match its hash). An asset nothing rebuilds is `missing`, answers 404 at once, and is left alone. `artwork.sweep` (daily, 04:40) queues assets whose file is gone, `missing` assets whose file is back, and `missing` assets last tried a week ago.

### Authentication

- A session token is 32 random bytes, base64url. Only its SHA-256 is stored (`auth_sessions.token_hash`). Sessions last 180 days, sliding.
- Browsers get it in the `squirmy_session` cookie (httpOnly, SameSite=Lax, Secure when the request is HTTPS). Native clients send `Authorization: Bearer <token>`. The socket takes the same token from the cookie or from `auth.token`.
- Setup, login and register return `{ user, token }` to every client. A request with the header `X-Squirmy-Client: web` also gets the cookie; `GET /auth/me` renews it. Passing a `device` upserts the `devices` row.
- An `onRequest` hook resolves the token for `/api` routes and sets `request.user` (or null) and `request.authSessionId`. `/rest` authenticates each request with Subsonic credentials instead. Route code calls `requireUser(request)` or `requireAdmin(request)` from `lib/auth.ts`.
- **CSRF.** A cookie-authenticated request that is not GET/HEAD/OPTIONS must carry the header `X-Squirmy-Request: 1`. Bearer requests are exempt.
- Passwords are argon2id. Login is rate limited per address. Failed logins are counted before the password check (and taken back on success) per username and address, per username and IPv6 /48, and per username overall, where addresses with a recent success are exempt (`lib/failures.ts`); so concurrent attempts cannot slip past, a correct login never uses a budget, and one client cannot lock an account out for everyone. At most two argon2 runs at once (`withHashSlot`), with a bounded queue. Setup and register are limited per address, password changes per user. Subsonic has no lockout. Addresses are keyed by `lib/proxy.ts` `addressKey` (IPv6 per /64). Counters live in the API process's memory.
- Logging out, changing a password (other sessions), and an admin disabling a user or resetting their password end the affected sessions and close their sockets.
- App passwords for Subsonic clients are random secrets stored AES-GCM encrypted (Subsonic token auth needs the clear text) plus a SHA-256 `key_hash` for `apiKey` lookups. `modules/auth/service.ts` exports `verifyAppPassword` and `findAppPasswordByKey`. Creating one needs the account password, at most `APP_PASSWORD_LIMIT` (50) per user; a password change, an admin reset and disabling the account delete them (`revokeAppPasswords`). Devices are recorded through `rememberDevice`. Recording a new device also forgets the user's devices not seen for 180 days (as long as a session lasts) and keeps at most the 100 most recently seen.
- `lib/crypto.ts` derives purpose-specific keys from the root secret with HKDF and exposes `hashToken`, `sign`/`verify` (HMAC-SHA256) and `encrypt`/`decrypt` (AES-256-GCM, base64url output).

### Jobs

`jobs/` wraps pg-boss. Modules never import pg-boss directly.

```ts
jobs.define('library.probe', { concurrency: 4 }, async (data: ProbeJob) => { … })
await enqueue('library.probe', { fileId }, { singletonKey: fileId, priority: 0 })
await schedule('library.scan-all', '0 4 * * *')
```

- Queue names are `<module>.<verb>`.
- Handlers are idempotent: running one twice leaves the same result.
- `enqueue` accepts a transaction (`{ tx }`) so a row and its job commit together. It goes through pg-boss's Drizzle adapter, so the job insert runs on the caller's transaction; there is no outbox.
- `singletonKey` makes a duplicate a no-op while a job with that key is queued, retrying or active. Queues use pg-boss's `exclusive` policy and keyless jobs get a unique key, so only keyed jobs are deduplicated.
- A definition can choose `policy: 'stately'` instead: one queued and one active job per key, so a request made while a job runs is kept as a single follow-up (`library.ingest` uses it). The policy is fixed when the queue is created.
- `enqueueMany(name, items)` inserts many jobs in one statement with the same deduplication.
- Each concurrency slot is its own pg-boss worker and is woken as soon as its job finishes, so a backlog drains continuously rather than waiting out pg-boss's 30 second notify backstop between jobs.
- NOTIFY wakes workers when a job is inserted, not when a deferred one (`startAfter`) becomes due, so `enqueue` also wakes this process's workers for that queue just after the start time; a deferred job enqueued by another process still waits for the next poll.
- Failures retry with exponential backoff (default 3 retries). `timeoutSeconds` fails a job that runs too long.
- Every process starts pg-boss: `index.ts` calls `startJobs({ work })` with `work` true for worker roles. Modules' `jobs` hooks run only in worker roles; a process that enqueues a job it has no definition for creates the queue on first use.
- `getQueueStats()` counts jobs live; `GET /admin/jobs` returns it.
- Tests call `startJobs({ work: true })` and then `drainJobs()`, which resolves once no job of a defined queue is ready or active, running retries without waiting out the backoff.
- Priority orders jobs within one queue only. Each queue has its own worker slots, so heavy queues are bounded by their `concurrency` (loudness 1, analysis 2) rather than by priority. Background sweeps and safety-net jobs use negative priorities so on-demand jobs of the same queue run first.

### Realtime

`realtime/` owns the socket.io server. The session protocol is specified in `packages/contracts/src/session.ts`.

- `startRealtime(app)` attaches to the Fastify server before it listens; closing the app closes the socket server. Messages of 1 KiB or more are deflated (`perMessageDeflate`), mostly for `session:queue`, which carries the whole queue.
- The heartbeat is socket.io's ping, every `HEARTBEAT_INTERVAL_MS` (5 s), with `HEARTBEAT_TIMEOUT_MS` (10 s) to answer (both in the session contract), so a socket that stops answering closes 10 to 15 seconds after its last answer, rather than after socket.io's default 45. Clients take the timings from the handshake, older ones included. Device presence rides on it (see "Sessions").
- The handshake takes the session token from `auth.token` or the `squirmy_session` cookie and is refused without a valid one. With the cookie, an `Origin` header must match the request's `Host`, `PUBLIC_URL`, or (with `NODE_ENV=development`) the Vite dev server. A socket is disconnected when its session expires; messages are capped at 1 MB.
- Each socket joins the room `user:<id>`. Admin sockets also join `admins`. Handlers passed to `onConnection` run after that; register socket listeners before the first `await`.
- `publish(target, event)` and `invalidate(target, keys)` are callable from any process. They `NOTIFY squirmy_events` with a JSON payload; the API process `LISTEN`s on a dedicated connection and forwards to rooms. `target` is `{ user: id }`, `'admins'`, `'all'`, or a list of them, which reaches each socket once however many of them it is in (an admin is in their own room and in `admins`). Keys that do not fit in one notification (8000 bytes) are split across several. `disconnectSockets(userId, { only | except })` closes sockets of revoked sessions the same way.
- `time:sync` is answered here; the `session:*` events belong to the `sessions` module.
- Two kinds of message tell open screens what changed, both from any process and both dropping the API process's cached reads (see "Catalog read side") at once in the calling process and in the API process when the NOTIFY arrives, before the clients are told:
  - `invalidate(target, keys)` names lists whose members or order changed (the library's lists, Home, Liked Songs, the playlists, admin screens), with keys from `queryKeys`; clients refetch them.
  - `publishChanges(target, changes)` names entities and what changed about them (`EntityChange`, `packages/contracts/src/realtime.ts`), sent as `changes`: `availability` (new availability of tracks and albums, to `all`), `patch` (a user's `liked`, `wanted`, `inLibrary` or `library` on one entity, to that user only), `updated` (only the entities' own pages show it) and `deleted`. Clients set what a change carries on every cached copy of the entity in place, refetch the entity's own page for `updated`, and drop a `deleted` one's; no list moves and no search runs again. Changes that do not fit in one notification are split. `changeKeys` names the cached reads each drops.
- Every mutation that changes what another open screen shows says so with one of them, as narrowly as it can:
  - **Availability.** Whatever changes whether a recording plays (a delivery, a miss, a job that failed for any `EntryFailure`, a request nothing covers, a provider answering, recovering or being reconfigured, an eviction) calls `announceAvailability` (`acquisition/resolve.ts`), which publishes the tracks' and their albums' new availability. It never invalidates search, lists or Home: cache is in no library.
  - **Deliveries.** Placing one (matching's `announce`) sends `updated` for the albums and artists whose pages changed. The library's lists and Home are invalidated for everyone only when those albums hold collection files (`holdsCollection`; files still in an import's incoming folder do not count, and a finished upload announces the lists itself); otherwise only for the users who saved the album or recording (`saversOf`), whose songs list a cached file joins. Enrichment of an album announces its cover the same way (`albumChanged`).
  - **Hearts** (saves to the library; `userdata/changes.ts`, `announceUserChange`) send the entity's new `liked` and membership (`inLibrary`, `library`) as a `patch`, an album's also its songs' `inLibrary`/`library` and its artists' `inLibrary` (from `membership` in `catalog/availability.ts`), and invalidate only that user's likes lists, library lists and Home.
  - **Playlists** invalidate the playlists (everyone's for a public one); deleting one also sends `deleted`.

### HTTP API

All native routes are under `/api/v1`. Lists are paginated with `PageQuery` and return `{ items, nextCursor }`; short lists (users, invites, app passwords, roots, devices, acquisition providers, an import's albums) return every item with `nextCursor: null`. `GET /admin/jobs` returns a bare array; `GET /admin/albums/:id/candidates` returns `{ items, files }` and the acquire routes `{ items }`, unpaginated. `createApiClient` in client-core has one method per route below, and its response schemas are the reference for each route's shape. `apiRoutes` next to it names each method's route; `client-routes.test.ts` fails when the server registers a native route that no method calls and that is not on its short list of routes clients never call (stream and art URLs, the Last.fm callback, provider deliveries), and when a method calls a route the server lacks, unless that route is listed as awaiting the server. Uploads go through `XMLHttpRequest`, which reports progress.

### Availability

Two separate questions, both answered in `modules/catalog/availability.ts`: can this be played (availability), and is it in this user's library (membership). A file existing answers the first and, on its own, never the second.

**Availability**, which every list and page uses:

- Track: `server` if a present (not missing) `media_files` row has its `recording_id`, whatever its source. Otherwise `on_demand` if an enabled acquisition provider covers it (coverage `assume_available`, or a cached positive resolve) and it has no miss from that provider that counts (see "Acquisition"). Otherwise `none`.
- Album: counts owned tracks on its track list (`albumTrackList`, below): the canonical release (else the album's release with the most tracks), plus owned recordings filed under the album that the release does not list. All owned is `full`, some is `partial`; none owned is `on_demand` when any of its tracks would be (an album is dimmed only when nothing on it plays: one track a provider missed must not gray out an EP), else `none`. `trackCount` and `ownedTrackCount` count the same list, so an album with a present, linked file is never `none`.
- Clients present it by viewer with `isPlayable` and `albumPresentation` from client-core: for a *requester* (an admin, or a member with `canAcquire`) `on_demand` looks and plays like `server`; for anyone else it is unavailable. Requesters see no badge or count telling the two apart.

**Membership.** A user's library is the server's *collection* plus what that user *saved*:

- **Collection**: a present file whose `source` is not `provider:*` (scanned, uploaded, from the inbox). Shared: it is in every user's library, and only an admin takes it out, by deleting files. `collectionFile(alias)` is the condition.
- **Cache**: a file a provider delivered. `media_files.cached` is generated from `source like 'provider:%'`, so it cannot drift. Cache makes a track `server` and puts nothing in any library: a song sampled by pressing play stays out of Albums, Songs, Artists and Recently added.
- **Saved**: a row in `likes (user_id, entity_type 'album' | 'recording' | 'artist', entity_id, created_at)`, written by the heart, `PUT /me/likes/:type/:id`, and deleted by `DELETE` (owner: userdata). There is one control: liking is saving, Liked Songs lists the saved recordings, a Subsonic star and a Last.fm love are the same row. A save needs no file, so a saved album is in the library at once. Removing deletes the row only: files stay as cache; playlists and history stay. For a requester an album or track save also asks acquisition for what is missing, as the `userdata.fetch-saved` job, best effort: the save never waits for it or fails on it. Nothing else writes a save: fetching (`POST /albums/:id/acquire`, playback, downloads, radio) never does. A collection item is in the library whatever its heart says; the heart only shows the viewer's own save.
- **Album** in a user's library: a collection file is linked to it (`media_files.album_id`), or the user saved it (`inLibraryAlbum`).
- **Track**: a collection file links its recording, or the user saved the recording, or a present file (cache included) links it and that file's album is saved by the user (`inLibraryRecording`). Songs of a saved album therefore appear as their files arrive.
- **Artist**: the user saved the artist, or it is credited (`album_artists`) on an album in the user's library. Being featured on a track, or credited on cached music, does not count.
- Merges move saves (the older row wins a collision), and the library's orphan cleanup and `search.cleanup` keep saved rows.
- The migration that introduced this turned completed album fetches with a requester into saves (with a track-only provider, seven or more track fetches of one album by one requester within a second, more than playing ever starts at once); other single-track fetches came from pressing play and were not carried over. On a server whose files all came from a provider, every library starts empty. Saves used to live in a table of their own, `library_items`, beside likes; migration 0018 unioned the two into `likes` (an entity in both keeps the earlier time) and dropped it.

### Catalog read side

- `catalog/summaries.ts` builds every `TrackSummary`, `AlbumSummary` and `ArtistSummary`, in batches with a fixed number of queries. They leave out artwork the art route would answer 404 for: a `missing` asset, or a `failed` download inside the hour before it is tried again. Other modules (search, sessions, userdata) use these rather than writing their own. Subsonic builds its own, because its objects describe files (size, codec, path), but takes availability and redirects from the catalog. Summaries are per viewer: `TrackSummary.inLibrary` and `ArtistSummary.inLibrary` follow the viewer's membership (`artistSummaries` without a user answers for the collection alone); `AlbumSummary` carries none, and `AlbumDetail.library` is `collection` (which wins when the album is also saved), `saved` or null. `TrackSummary.library` says why a track is a member, the first of `collection`, `album` (a present file of it is on an album the viewer saved) and `saved`, or null (`recordingLibrary` in `availability.ts`): only a `saved` track leaves the library when its save is removed.
- Ids that come from clients follow `merged_into_id` redirects (`catalog/redirects.ts`, one primary-key lookup per hop, at most 16); the summary builders do it themselves, so stored queue and playlist ids keep working after a merge. `POST /tracks/summaries` answers a merged id with the row it was merged into and lists, in `requestedIds`, the id each summary was asked for, so `TrackStore` files it under the id the queue holds.
- **Cached reads** (`lib/read-cache.ts`). `GET /home`, `/library/*`, `/albums/:id`, `/artists/:id`, `/playlists` and `/playlists/:id` keep their serialized answer and its ETag in the API process, per user and URL, within `SQUIRMY_READ_CACHE_MB` (default 64, least recently used out first; off under test unless set). Each route names the `queryKeys` roots it depends on; an `invalidate` for one of them drops that user's entries (a user target) or everyone's (`all`, `admins`), a root the cache does not know drops everything, and `admin`, `settings`, `scrobbling`, `me` and `lyrics` drop nothing. A read that overlaps a drop is not stored. Entries expire after five minutes, which bounds what nothing announces; catalog searches (stubs credit artists and fill covers) and provider changes drop everything explicitly. Writes made in the background go through `invalidate` like any other, so a worker's reach the API process: an unassigned cover, album stubs a discography adopts (`upsertDiscography` names them, whichever job wrote it), an album hydration (announced even when a later step fails) and `search.cleanup` (each kind it deleted from, by root). Home is computed again two seconds after a drop when it was read in the last 15 minutes.
- Lists use keyset cursors (`catalog/pagination.ts`): opaque, tied to one ordering, and stable under ties and concurrent inserts. Title and artist orderings are `sortKey` over the stored `*_key` columns, backed by expression indexes in `schema.ts`.
- **Library lists** (`catalog/library.ts`) take the user and list their membership (above). Title, artist and year pages (and tracks by year, which place each library track by its newest present file, so a saved track waits for its file) have two shapes, picked per request by `libraryShape`, which counts members up to 2,000 on the membership indexes. A small library is read from its members (collection files by album or recording through the `media_files_collection_*` indexes, plus the user's saves) and sorted, so a catalog full of search stubs costs nothing. A large one walks the catalog's sort index and keeps members, about `limit` rows when most of the catalog is library.
- `recent` places an item at the later of its newest collection file's `added_at` and its save's `created_at` (for a track, also the save of an album holding a present file of it). It is a union of one walk per way in, each on its own index and keeping only the items whose time it holds, so each item appears once. Songs that entered at the same time (one scan, one saved album) follow their file paths, which is track order under every naming template, then the id. Its orderings are `albums:recent2` and `tracks:recent3`; cursors from an older order are refused with `invalid_cursor`. `performance.test.ts` (10,000 albums, 150,000 tracks) and `stubs-performance.test.ts` (200,000 stubs around a library of 50 albums) check every page with EXPLAIN.
- Home's sections come in decision 30's order: `recently-played`, `most-played`, `playlists`, `recently-added` (the user's library albums by `recent`), `new-releases`, `wantlist`. `new-releases` (`enrichment/releases.ts`) is per user: albums from the last 120 days whose main artist is credited on an album in the user's library or was hearted by them, leaving out what the user has and cover acts' releases (karaoke, tributes, string-quartet and similar renditions, by title or artist name). `enrichment.new-releases` keeps the discographies of every user's such artists current; music fetched for playing makes nobody's artist.
- A track's album in a summary is the album context, else an album of a present file, else an album of a release it is on, preferring the artist's own release (the album's primary artist is the recording's), then albums, EPs, singles, soundtracks, live albums and compilations, the album's canonical edition, the earliest year; else its search hint. So a song on an album and on its single shows the album, wherever the single sits in the catalog. Its artwork is that album's cover, else the cover of another of those albums.
- **The artist page** (`artistDetail`) lists the releases the artist leads (primary artist or first credit) and those of others that credit it, on the release or on a track of one of its editions, newest first. Rows of one release (the same `releaseKey` and type) show once, as the owned, MusicBrainz, stated-type, most complete row (`standingRows`); a row whose type is a guess gives way to any row of its title. The enrichment module merges such rows where it can; this keeps the page right meanwhile and where MusicBrainz has two groups of one title and type. The releases are split into `sections` in the order of `ARTIST_SECTION_KEYS` (`sectionOf`): by type, except that mixtapes (MusicBrainz's "Mixtape/Street", typed `album` so older clients still parse them) are `mixtape`, soundtracks are listed with the albums of an artist who has more albums than soundtracks (The Beatles' Help!, not Hans Zimmer's scores), and others' releases are `appears_on`. Each section carries its first `ARTIST_SECTION_PREVIEW` (12) releases and its `total`; `GET /artists/:id/releases` pages the rest, with a cursor naming the last release listed (followed through merges), so a discography that grows meanwhile neither repeats nor skips one. `releaseCount` and `ownedReleaseCount` count the artist's own releases and those with a file on the server. `albums` and `appearsOn` carry the same previews for clients that predate `sections`: Bach's page was 3.8 MB with 6,169 releases. **Top tracks** are the artist's stored list (`artist_top_tracks`) in its order, each song once (by recording, then by title); without one (music only in the library) the artist's tracks rank by completed plays here, then popularity. MusicBrainz's placeholder artists (Various Artists) have no top tracks, radio, similar artists or bio.
- An album's track list is `albumTrackList` (`catalog/pages.ts`), for the album page and Subsonic's `getAlbum`: the canonical release's tracks, then owned recordings filed under the album that the release does not list (bonus tracks, files matched with no track) in path order on the last disc, with no position. Subsonic numbers those after the disc's last track.

### Search

`modules/search/`. Both routes return `SearchResults` built with the catalog summary builders, so availability comes out the same as everywhere else. Queries whose `matchKey` is shorter than two characters answer nothing.

- **Ranking** (`rank.ts`, both routes): every result gets a 0..1 score, `relevance × (0.5 + 0.5 × prominence)`, returned best first across kinds as `ranked`. Relevance compares the name with the query by `matchKey` (a leading "the", "a" or "an" ignored on either side, edition suffixes dropped by `editionFreeKey`, spacing and punctuation ignored for "acdc", `$` read as `s`): 1 the whole name or artist and title together, 0.97 once an article is ignored, 0.95 compact, 0.8 a prefix of whole words, 0.7 any prefix, 0.6 a later word, 0.62 to 0.45 an album's or song's artist, 0.5 one typo from five characters, 0.3 what the provider found for its own reasons. Prominence is the provider's (Deezer fans on a log scale, a song's rank, the local index's popularity; carried from `materialize` by catalog id) or the stored song popularity, passed from songs to their album and from artists to their music, raised for what is in the viewer's library (at least 0.55), played among their last 1,000 plays, or liked; unknown, it falls back to the result's place in its list. Prominence at most doubles a score, so an exact name loses only to a prefix match about a hundred times better known, and an artist's songs found through the artist alone never bury another artist named as typed. `rank.test.ts` holds Deezer-shaped fixtures for the cases this was tuned on (tate, mgmt, kid a, AC/DC, $uicideboy$, …). The catalog route also ranks the library answer's page for the same query (the provider may know how popular those are), so its `ranked` can name ids only that answer lists; clients take an item's higher score. **`top`** is the best ranked result whose own name matches at least by a typo, with `score` 1..3 for older clients (3 the whole name, 2 with an article or spacing ignored, 1 less); the catalog's names an item of its own lists. Both fields are optional in the contract.

- **`GET /search/library`** (`library.ts`): owned music (artists credited on an owned track or an album with a present file, albums with a present file, owned tracks) plus the user's saves, file or not, so the Library's search finds a hearted album before it arrives. An optional `genre` keeps the results to albums of that genre, their tracks and their artists, filtered before `offset` cuts the page, so a search inside a genre chip stays in it. Candidates per kind come from bounded index lookups, and one walk of the user's saves (prefix or trigram match, its own `union` branch so the owned lookups keep their plans): a byte-order prefix btree on `name_key`/`title_key`; every split of the query into "artist title" or "title artist", looked up from that artist's rows; albums and tracks whose primary artist's name starts with the query; and, from three characters, trigram word similarity on `name_key` or the whole `match_key` (artist and title, so typos and word order are tolerated). Ranking: exact, then prefix (title, name or artist), then similarity; ties go to the user's plays among their last 1,000, then likes. `type` limits the answer to one kind and `offset` skips that many of each, for a client's filter. Each kind is one query run with `enable_seqscan` off, because the planner prices `word_similarity` too low. `performance.test.ts` measures it on 10,000 albums and 150,000 tracks.
- **`GET /search/catalog`**: one provider per request (`providers.ts`), asked only for the kinds `type` names and from `offset` (Deezer's `index`, MusicBrainz's `offset`; the local index reads the rows before it), in this order: the local index when `isCatalogIndexReady()`, Deezer when enabled, MusicBrainz when enabled. A provider that throws falls through to the next; `provider` names the one that answered. Identical queries in flight share one provider call, and `cachedFetch` keeps search responses for a day. MusicBrainz free text matches titles only, so "artist title" queries are only understood by the other two. The route runs the library search for the same query, kinds and `offset + limit` alongside the provider call and leaves out of its answer every artist, album and track that the library answer lists on this page or an earlier one, so owned music the provider also found is not shown twice. It also lists one artist per name (`namesakes.ts`): an artist without an MBID is left out when the library answer, an artist of the answer with an MBID, or an earlier one has its name. Deezer has duplicate pages for some artists ("Boards of Canada" 1098 and 412310471), which are rows of their own until enrichment merges them; artists with MBIDs always stay. Albums are listed once per artist and name (`oncePerTitle`, both routes): Deezer lists one edition several times (the explicit and the clean "SOS Deluxe: LANA"), each a row of its own; the first stands for the others, and a copy the library answer shows leaves the catalog's out. Its `top` is picked from what is left, with the same function and scale as the library's, so the client's comparison is between two separately ranked hints. After answering, it starts detail in the background: `warmDetail` for a top artist, and through `warm.ts` for up to five albums (a top album, then the first albums with no track list yet), two at a time across the process, a newer search's ahead of what an older one left waiting. Their pages are complete and their tracks playable by the time a user opens one.
- **Stub rows** (`materialize.ts`): results are stored before they are returned, in one transaction per response under the advisory lock `squirmy:search-stubs`. Each result is matched to an existing row by its `external_ids` row (`deezer`, or `musicbrainz` for MusicBrainz and local-index ids), then by MBID, then by key: for artists the one artist with that `name_key`, if exactly one exists and it has no other id from the provider; for albums and tracks the same artist (credit text or primary artist) and the same title, owned rows first, then MusicBrainz rows: for a track once edition suffixes are dropped, for an album once only store labels are dropped (`labelFreeKey`), since "OK Computer (Deluxe Edition)" is another edition with its own songs. A provider that names no album type (Deezer's album of a track, the local index's albums) matches any type; one that names a type matches that type, unless the row is owned or its own type is a guess. Track lengths must be within 10 s. Only then is a stub inserted:
  - artist: `name`, `name_key`, `detail_level` 0, `mbid` when known, an `external_ids` row, `image_asset_id` from `remoteImage`;
  - album: `title`, `artist_credit`, `primary_artist_id` and `album_artists`, `type`, `year`/`release_date`, `title_key`, `match_key`, `detail_level` 0, `mbid` (release group) when known, an `external_ids` row, `artwork_asset_id` from `remoteImage`, no releases. Without a type from the provider the type is guessed (`guessAlbumType`: a single when the album is titled like one of the response's tracks, else an album) and `type_guessed` is set;
  - recording: `title`, `artist_credit`, `primary_artist_id` and `recording_artists`, `duration_ms`, `title_key`, `match_key`, `explicit`, `popularity` (0..1), `isrcs`, `mbid` when known, an `external_ids` row, and `album_hint_id`, an album it appears on. Summaries use the hint only when no file or release track names an album.

  Existing rows only gain a missing external id, image or album hint, and a guessed album type (with a missing year and date) once the provider lists the album itself. A row found by its provider id that gives way to an owned row found by key is merged into it when it has no MBID and no files (its provider id moved before, and the stub stayed beside the owned row on the artist's page). A response that inserted album stubs queues `enrichment.reconcile` for their artists. A Deezer artist id no row carries, named like a row that has another Deezer id, is that row's when what the response credits it with (its albums and tracks) shares a release or two songs with what the row is credited with (`sameArtist`, an album titled like the artist excepted): Deezer keeps second pages for some artists. Otherwise it is stored as an artist of its own and `enrichment.reconcile { artistCopy }` looks again with Deezer's and MusicBrainz's data. Credits without any provider id (the local index names some artists only as text) reuse the artist with that name and otherwise become a stub without an external id.
- **Release keys** (`keys.ts`, `releaseKey`): `editionFreeKey` once store labels of a release's kind or origin are dropped too ("(From F1® The Movie)", "(Original Motion Picture Soundtrack)", "- Single", "E.P."). Used to tell whether two album rows of an artist are one release (`enrichment/reconcile.ts`, the artist page), never for search.
- **Edition suffixes** (`keys.ts`): a bracketed or dashed suffix is ignored for matching when all its words describe an edition (deluxe, expanded, remastered, anniversary, explicit, clean, bonus tracks, numbers…) and at least one is a strong word, so "OK Computer (Deluxe Edition)" and "Let It Be - Remastered 2009" find the plain titles while "(Live)", "(Remixes)", "(Radio Edit)" and "(Taylor's Version)" stay different albums and songs. Stored keys keep the full title. A catalog query that ends in edition words with at least one strong word ("ok computer deluxe") is also sent without them, and those results follow the whole query's: providers match every word, so an edition they name differently would otherwise find nothing.
- **`search.cleanup`** (daily): deletes stubs older than 30 days that never gained detail (albums and artists at `detail_level` 0 with no MusicBrainz releases, recordings on no release) and that nothing keeps: files, likes, ratings, wants, playlist items, plays, ids in stored playback sessions, acquisition jobs still running, album hints of kept recordings, credits, merges. Their `external_ids` go too; `assets` stay. The library's orphan cleanup leaves stubs alone.

### Playback and streaming

- Clients ask `GET /tracks/:id/playback` and receive a signed URL. The stream route accepts the signature instead of a session so `<audio>`, AVPlayer and downloads need no headers. Signatures bind the file id, profile, user id and an expiry of 12 hours.
- File choice: files of the recording that belong to the requested album first, then lossless over lossy, then higher bitrate. Both ids follow merges, so a queue entry that names an album merged away still gets that album's file.
- `chooseProfile` (`streaming/select.ts`) maps a quality to a profile. `original` serves the file when the client decodes its codec. Otherwise the target is the first profile the client decodes from the quality's preference list (`original` and `high`: `aac_256`, then `mp3_320`, `opus_128`, `mp3_192`; `data_saver`: `opus_128`, then `mp3_192`, `aac_256`, `mp3_320`). A lossy file at or below the target bitrate that the client decodes is served as is; one it cannot decode gets the smallest playable profile at or above its own bitrate. Encoder settings are in `streaming/profiles.ts`.
- Signed URLs carry `exp` (epoch seconds), `uid` and `sig`, an HMAC from `sign('stream', …)`. A request without a valid signature may use the session instead.
- A URL names the file, not its path, so it keeps working when organize files it: a file not at its row's path is looked for at the other end of a move that is running (organize renames on disk before it updates the row), and is marked missing only when it is in neither place. When the library root itself is not a readable folder (an unmounted drive or share) the request answers 503 `root_unavailable` and nothing is marked missing, as the scanner does.
- A transcode is written to the cache while it is streamed to the first requester; later requests get the cached file with Range support. A cached transcode is used only while the source's size and mtime are the ones it was made from, so a file replaced or retagged in place is encoded again. ffmpeg writes to a pipe, so every streamed byte is final: AAC 256k in ADTS (`.aac`), Opus 128k in Ogg, MP3 at constant bitrate without a Xing frame. Encoders: `aac`, `libopus`, `libmp3lame`.
- Requests for the same transcode share one ffmpeg per process; a client that leaves does not stop it. At most half the CPU cores (at least two) encode at once.
- Transcodes are built when a stream first asks for them; nothing is converted ahead of time. `streaming.evict` runs hourly and at worker start: it reconciles rows with files on disk and deletes least-recently-used transcodes beyond `transcodeCacheMaxBytes`, sparing those used in the last half hour so a track being played keeps answering Range requests.
- Normalization values: prefer measured loudness (`-18 − loudness_lufs` gives the gain); fall back to the file's ReplayGain tags. Album values come from `release_loudness`.
- Loudness is EBU R128 from ffmpeg's `ebur128` filter. `loudness.measure` `{ fileId }` stores a file's integrated loudness and true peak, then queues `loudness.album` `{ releaseId }`, which decodes the release's present files in track order through one concat filter, so gating covers the album as a whole. `loudness.sweep` (every 10 minutes and at worker start) queues files with no loudness in batches of 500 and releases whose file set changed. Silent and very short files store -70 LUFS, which yields no gain.

### Sessions

The server holds one shared session per user in memory, loaded on first use and persisted to `playback_sessions` on change (debounced one second, and flushed on shutdown), plus one session of its own for each detached device (see "Detaching" below). This assumes one API process: the copy in memory is the truth, so functions that change sessions (`markRecordingReady`, `replaceQueue`) must run in that process. Commands arrive on the socket, run through `reduceSession` from client-core, and the result is broadcast to the sockets in that session (socket.io room `session:<user>` for the shared one, `session:<user>/<device>` for a device's own): `session:state` on every change, `session:queue` only when the queue half changed (`queueChanged`), emitted just before the `session:state` of the same version. A socket joins a session room when its hello is answered; device lists and invalidations go to the `user:<id>` room as before.

- **Commands.** The server passes the envelope's `commandId` to the reducer (new entry ids derive from it), remembers recent command ids (the last hundred are stored with the session, so they survive a restart along with their effect) and acks a duplicate without applying it again, and acks a command before broadcasting its result. Server-issued commands use a fresh id. A user's commands, reports and hellos run one at a time, in arrival order, so each socket has a budget (`sessions/socket.ts`): 20 commands a second in bursts of 40, past which commands are acked `rate_limited`; 5 reports a second in bursts of 20; 5 hellos, then one every 5 seconds; 10 detaches and attaches together, then one every 2 seconds, past which they are acked `rate_limited`. Excess reports and hellos are dropped.
- **Queue model.** `reduceSession` (client-core) follows streaming apps; the rules are on `SessionCommand` in the contract. A collection started from one of its tracks keeps the tracks before it behind the current one in `playedInCycle` (played or skipped, oldest first), which is what `previous` steps back through and what repeat all plays again; `history` is only the record of what was heard. Entries added with `enqueue` are marked `queued`: they stay put when the queue is shuffled or jumped past (`playQueueEntry` skips everything else between) and repeat all leaves them out. While shuffled, `playOrder` holds the collection order of the queue and of what lies behind, so shuffle off can continue in order after the current entry. Every field added for this is optional or keeps its old shape, so stored sessions and older apps (whose optimistic reducer the server's answer corrects) keep working.
- **Trusted entries.** For `playTracks` and `enqueue` (and Subsonic's `savePlayQueue`) the server keeps only the track ids the client sent: it follows merges, takes durations from the database, drops tracks the user cannot play, and sets `ready` or `preparing` itself. Rows merged after an entry was made are followed too (`updateTracks`, a server command): when a session loads, each time its current entry changes (for it and the next five), and when acquisition answers for a recording a waiting entry holds under an id merged into it. Requests made under the old id carry over to the new one. Owned tracks are kept for everyone; `on_demand` ones only for a requester (an admin, or a member with `canAcquire`), so no one else gets an entry that would sit preparing and then fail.
- **Limits.** A session is copied and sent whole on every queue change, so it stays bounded. `playTracks` and `enqueue` carry at most `COMMAND_TRACK_LIMIT` (5,000) tracks, and the queue holds at most `QUEUE_LIMIT` (10,000) entries: an `enqueue` that would grow it past that, counted after untrusted tracks are dropped, is acked `queue_full` and the reducer ignores it, so optimistic clients agree. `replaceQueue` considers at most 5,000 ids from the current one on.
- **Device list.** The live devices (see "Presence" in the session contract), sent on every hello and whenever one comes, goes or changes; `GET /me/devices` answers the same from memory. The `devices` table keeps every device ever signed in, for names and history; no list reads it. A device is live while one of its sockets is open, and a socket stays open only while it answers the heartbeat (see "Realtime"), so a device that went silent leaves within 15 seconds and one whose socket closes cleanly leaves at once. Each socket gets the list as its own device sees it: `isCurrent` marks that device (over HTTP, the device the sign-in was made from). `lastSeenAt` is when the device last sent a hello, command, report, move or heartbeat answer; it moves on in memory and the list goes out again when what the others have is a minute or more behind, so each live device costs at most one list a minute, and no listed device is ever a few minutes quiet, which clients would show as "Active … ago".
- **Active device.** The first device that can play and sends a command that starts playback while no device is active becomes active. `transfer` changes it, and only to a connected device that can play. Only the active device may send `trackEnded` and engine reports. A report that is more than a second off the computed position, or changes whether playback is stalled, becomes `syncPosition`.
- **Disconnects.** If the active device's last socket closes while playing, the server stops the session's clock at once (a `syncPosition` that marks it stalled, so every client, older ones included, holds the position), waits 20 seconds, then applies `deviceLost` as of the moment it went away (pause at the position it had then, or at a later change's, and clear the active device), so neither the resume point nor the play counts the grace period, and nothing jumps back. A device that returns within the grace period most likely only lost its connection and played on, so its hello restarts the clock where it would be by then, unless the session changed meanwhile; its next report corrects the rest. A session loaded after a restart gives its absent active device the same grace. During the grace the device is not listed, so no client offers it; the session still names it as active, which is how clients tell (client-core's `away`) and say "Reconnecting to …". After a restart every client reconnects within socket.io's reconnection backoff (at most five seconds), each hello adds its device to the list, and nothing leaves it meanwhile, so it only grows back.
- **Plays.** A play row opens when an entry is current and running on the active device and closes when the entry changes or stops at its end. Listened time comes from the session's position arithmetic, so pauses and seeks add nothing. The open play is stored with the session (and written at shutdown under the id it was given when it opened), so a listen across a restart stays one row. Plays under five seconds are skips and leave no row; one counts as completed after half the track or four minutes. A play is written under the recording and album the track's summary resolves to when it closes (merges followed; the album of its file, else of a release), not the entry's ids, so it never lands on a merged-away row or on the catalog stub album an on-demand track was queued from. Writing one invalidates history and home.
- **On demand.** The current entry and the next five (`PREPARE_AHEAD`) that are `preparing` are requested from acquisition with `requestRecording`, current first and one after another, so jobs are created in queue order. Each request carries an origin, `play` for the current entry and `prefetch` for the rest (passed through for job ordering; acquisition does not read it yet); a prefetched entry that becomes current is asked for again as `play`, which joins the job in flight, and a queued request the session no longer wants by its turn is not sent. An entry stays `preparing` until the file is linked, then `setEntryState` flips it to `ready` or `failed`. Every failure comes with why (`EntryFailure`: `unavailable`, `outage` or `error`, from acquisition's outcome), and the sockets in the session get `playback.failed` with it just before the state that marks the entries failed. A failed entry further down is only marked, without any notice, and skipped when reached. A failed current entry (a failure that comes after a current entry became ready leaves that entry playing) is handled by why:
  - `unavailable` (the provider does not have it): skipped. The session keeps the distinct tracks it skipped so (`skippedTracks`: this one and the failed entries the reducer passes over with it), cleared when anything is delivered for the session (a current entry ready, any of its fetches done) or the user starts something new. When nothing after it is playable the reducer stops on it; if that ends a run (others were left in the queue, or more than one track was skipped to get there), the session publishes `playback.unavailable` with `kind: 'exhausted'`. When the run reaches five tracks (`UNAVAILABLE_BEFORE_PAUSE`) with more still ahead, the session pauses on it instead, with `kind: 'unavailable'`: that many in a row more likely means a provider wrongly answering that it has nothing.
  - `outage` (the provider is failing or could not be asked, see "Acquisition"): the session pauses on the first such current entry and publishes `playback.unavailable` with `kind: 'outage'` and the `reason` for clients to show.
  - `error` (anything else): skipped, except the third in a row with no current entry ready in between (`FAILURES_BEFORE_PAUSE`; a new `playTracks` also restarts the count), which pauses with `kind: 'failures'`, so a server that fails everything does not run down the queue.

  A pause keeps the rest of the queue and requests nothing more until the user plays again, when `play` moves on from it. The event goes only to the sockets in that session, before the state that stops, so client-core's `SessionClient` puts it in the same snapshot as the stop (`outage`, cleared once the session plays or moves on). Every request gets an answer, so an entry never waits forever; see "Acquisition". A request that throws instead fails the session's entries of that recording as an `error`; a session that loads with a preparing entry whose track is `none` by then fails it as `unavailable`.
- **Autoplay.** When the queue is nearly empty and autoplay is on, the radio module supplies `setAutoplayQueue`. `playTracks` empties the autoplay queue, so suggestions always follow what is playing rather than an earlier queue.
- **Detaching.** `session:detach` gives a device that can play a session of its own, copied from the shared one with `forkSession` (client-core); `session:attach` discards it, and with `bringQueue` first makes the shared session what it was (`bringSession`). The rules are in the "Detaching" section of `packages/contracts/src/session.ts`; the server's side of them:
  - Own sessions are rows of `detached_sessions` (one per device, cascading with the `devices` row), written before the device moves and then like shared ones, with `last_seen_at`. Once loaded, one stays in memory like a shared session (so it keeps its recent command ids) until shutdown or until it is discarded. Its device leaving while it plays gets the same grace period and `deviceLost`.
  - Which session a device is in is decided by its first socket's hello: the stored own session when there is one and the hello carries `detached` (either value), else the shared one. A hello without `detached` is from a client that cannot detach and discards a stored own session. Later sockets of a connected device join whichever session it is in, and when it moves, its other sockets get `session:moved`.
  - All of a user's sessions share the user's one serial queue, so detaching and attaching change both sessions in one step. The `detached_sessions` row is written (detach) or deleted (attach) before anything in memory changes, so a database error leaves the device where it was; the shared session is then written at once rather than a second later. The open play moves with the device: detaching while active carries it into the own session, bringing the queue back carries it into the shared one (closing the play the shared session had), and attaching without it closes it.
  - An own session runs everything above as the shared one does (trusted entries, fetching ahead, the pause after failed fetches, autoplay, plays), and its `playback.unavailable` goes to its device alone.
  - A device in its own session can transfer only to itself, and the shared session cannot transfer to a detached device. `DeviceInfo.detached` lists what each detached device plays, and the list is sent again when that changes.
  - Limits: eight own sessions per user. Detaching drops sessions unseen for seven days, then, if eight remain besides the device's own, the one whose device was seen longest ago among those not connected; with eight connected it is refused. Sessions unseen for seven days are discarded at the user's next returning hello or detach. There is no background sweep, so a user who never connects again keeps their rows until the user is deleted.

### Scrobbling

- **Connections** live on the user row under `settings.secrets.<listenbrainz|lastfm>`: the credential (ListenBrainz user token, Last.fm session key) encrypted with `encrypt('scrobble-credential', …)`, the account name, `since`, `needsAttention` and `lastError`. Connecting verifies the credential (`listenbrainz.validateToken`, Last.fm's web auth flow) and switches the user's `scrobbleListenBrainz`/`scrobbleLastFm` on; disconnecting switches it off and drops unsent rows. Reconnecting the same account keeps `since`, so plays waiting for it are still sent.
- **Last.fm web auth.** `POST /me/scrobbling/lastfm/start` returns Last.fm's approval URL with a callback carrying `state` = user id, expiry (10 minutes) and `sign('lastfm-connect-state', …)`. The callback base is `PUBLIC_URL`, else the request's origin.
- **Sweep.** `scrobble.sweep` (every minute and at worker start) inserts one `scrobble_deliveries` row per service for each completed play of the last 14 days that started at or after `since`: `pending` when the service is switched on, `skipped` when off. It then queues `scrobble.deliver` `{ userId, target }`, keyed by both, where rows are ready.
- **Delivery.** `scrobble.deliver` locks the oldest ready rows (`for update skip locked`) in the service's batch size (ListenBrainz 1000, Last.fm 50), submits them with the MusicBrainz recording, release, release group and artist ids when known, track number, duration, album and start time, and marks them `sent`. A failure counts an attempt and the row waits 1, 2, 4… minutes (at most 6 hours) for the next sweep; after 10 attempts it is `failed` and left alone. A rejected credential (ListenBrainz 401, Last.fm error 9) sets `needsAttention` instead, and rows wait for the user to reconnect.
- **Guarantees.** The row is the idempotency record: one per play and service, submitted while locked, so overlapping sweeps and deliveries send a play once. The one gap is a crash after a service accepted a batch and before the commit, which resends that batch once.
- **Now playing** is sent from the API process when `onPlayStart` fires, best effort and without retries.

### Radio

- `suggestAutoplay` (the seam) and the radio routes rank with `radio/ranking.ts`: profile the seeds (artists, album and artist genres, years, similar artists, and Deezer's radio of the two most recent seed artists), gather a few hundred candidates in one query from bounded pools (seed artists, similar artists, Deezer's radio, albums sharing a genre or era, tracks the user played within half an hour of a seed, liked tracks and artists, a few random albums), score them with the weights in `ranking.ts` plus noise, and pick under variety rules over any ten consecutive tracks, seeds included: two per artist, one per album, three by seed artists, no artist twice in a row.
- A candidate is *related* when it is by a seed or similar artist, in Deezer's radio, shares a genre with the seeds (cosine at least `GENRE_RELATED`), or the user played it near a seed on at least two different days (one day is one session, or several people testing one account). Likes, popularity and owning a file only order candidates. Related ones are picked first, under the strict rules and then relaxed ones; unrelated ones (the random albums, a liked song of another genre) only fill a batch up to one window (`FILL_UP_TO`, ten), and past that the batch ends early: a radio that runs out continues through autoplay from its own last tracks. The rules drop last. An artist's tracks, in the pools and in the seed profile, are those it is credited on plus those it leads (`primary_artist_id`), since older rows and catalog stubs can lack credit rows. `suggestAutoplay` follows merge redirects of its seeds and exclusions first, so a queue entry holding a merged id still keeps its track out.
- For a requester (an admin, or a member with `canAcquire`), `on_demand` tracks from the seed-artist, similar-artist, radio and liked pools are gathered too and ranked together with the owned ones. What is on the server is mostly whatever was played lately, so having a file is no reason to suggest a track: it only breaks a near tie for the first pick (within `INSTANT_MARGIN`, the noise's range), so playback after the seeds starts without a fetch. The rest are fetched ahead while the first ones play. Everyone else gets owned tracks only, and nothing when none qualifies.
- Deezer's radio comes from enrichment's `artistRadioTracks` seam (`enrichment/radio.ts`): Deezer's `artist/<id>/radio` (the artist's Deezer id from `external_ids`, else an exact-name search, not linked), each track mapped to the row a page's popular tracks would use (`deezerRadioTrackRow`: by Deezer id, ISRC or the artist's title, else a provider-only stub with its album hint; its artist by `deezerArtistRow`'s rule). That brings artists the catalog has never heard of into a radio, and the artists it names count as similar artists (0.5, unless `similarArtists` ranks them higher). It runs before the similar-artist lookup so that lookup maps to the rows it wrote. The seam answers within the ranking's wait with the rows written so far and writes the rest in the background; one artist's rows are reused for an hour per process.
- Random sampling in SQL uses `uuid_hash_extended` with a salt drawn from the injected random source, so a seeded source repeats a result exactly.
- `similarArtists(artistId)` merges Deezer related artists (of the artist's Deezer page with the most fans, since search can link a namesake's page by name; else an exact name search) and ListenBrainz similar artists (with a server token and an artist MBID), mapped to catalog artists by MBID, else `name_key`. Deezer's suggestions the catalog lacks become artist stubs with their page and picture (`enrichment/deezer-rows.ts` `deezerArtistRows`, the rule search uses), so the rail does not depend on what someone happened to search; ListenBrainz's are left out. A source that is off or fails is skipped; lookups during ranking (Deezer's radio, then similar artists) share a 2.5-second wait, with at least half a second left for similar artists.
- A radio is up to 50 tracks starting with the seed track (fewer when the related ones run out) with context `{ type: 'radio', id: 'track:<id>' | 'artist:<id>' }`. Nothing is stored: when the radio runs out and autoplay is on, the session's history (the radio's last tracks) seeds the next batch, so it continues in the same direction.
- The seed obeys the queue's rule: a track with a file for everyone, an `on_demand` one for a requester, else 409 `not_playable`. An artist radio starts from the artist's playable track the user played most, then liked, then one with a file (so it plays at once), then the most popular; for a requester that includes its top tracks and discography on demand, so an artist with nothing on the server still has a radio. When nothing of the artist has a track list yet (albums found by search) and an `assume_available` provider would play them, it first fetches the track lists of two albums (studio albums, newest first) through `ensureAlbumDetail`, each within the page budget. Nothing playable is 409 `nothing_playable`.
- `canStartArtistRadio` answers the same question without fetching, for `ArtistDetail.radio`: clients offer an artist radio only when it is true.

### Subsonic

`modules/subsonic` serves OpenSubsonic under `/rest` over the same services; [subsonic.md](./server/subsonic.md) lists what it supports.

- `router.ts` answers every method on GET and form POST, with or without `.view`. Handlers return plain objects that `serialize.ts` writes as XML or JSON(P). Failures are Subsonic error codes in a 200; service `AppError`s map to the closest code (404 is 70, 403 is 50).
- Every request authenticates with an app password (token, password or `apiKey`); there is no lockout, since app passwords cannot be guessed and are cheap to check.
- Ids carry their kind (`ar-`, `al-`, `tr-`, `pl-`, `ca-` for an artwork asset) and are checked on the way in. Music folders are library roots, numbered by a hash of the root id.
- Lists show the user's library restricted to tracks with a present file (`sql.ts`): a library file is a present collection file, or a present cached file whose recording or album the user saved (for a recording, that is the catalog's `inLibraryRecording` plus a present file); a library album is `inLibraryAlbum` with a library file, and its songs are its library files; artists are credited on a library album or track. Library albums are found from the library files, so search stubs cost nothing. Lookups by id (`getSong`, `stream`), starred songs and playlist entries need only a present file. `songs.ts`, `albums.ts` and `artists.ts` build response objects in batches with a fixed number of queries (`albums` and `artistRows` return only library rows); a song is shown through the present file `selectFile` would stream.
- `search3` and `search2` rank a query with the search module's library search (`searchLibrary`), so typos are tolerated as in the apps, and keep what is in the user's library. Sync clients page through everything with an empty `search3`. The page that starts where the user's previous one ended continues from its last key, so deep pages cost what the first does.
- `stream` serves originals and the streaming profiles through `openStream`; a bitrate below every profile, or a `timeOffset`, is a live ffmpeg encode that is not cached. A live encode takes a streaming encoder slot without waiting (`tryAcquireSlot`) and at most `LIVE_ENCODES_PER_USER` (3) run per user; a refusal is `transcoder_busy` (503) or `too_many_live_encodes` (429), sent as a Subsonic error before any header.
- The play queue is the session queue (`getSnapshot`, `replaceQueue`). The songs a client saved before its current one are remembered in memory while the session's current entry and queue are unchanged.

### Library pipeline

Jobs, in order. Each is idempotent and keyed by file or album group.

1. `library.scan` `{ rootId, paths? }` walks a root, or just the given paths, and compares `(rel_path, size, mtime)` with `media_files`: new files are inserted at `probe_stage 0`, changed ones reset to it, vanished ones get `missing_since` and returning ones lose it. A row is marked missing only while it still has the path the scan read and nothing is at that path when the scan writes: files move during a scan (Organize filing a delivery out of `_Incoming` while the watcher's scan of that folder runs), and a row marked missing by mistake makes its recording unplayable for a moment, long enough for the acquisition job checking that delivery to fail it. Probes are queued in bulk. The walk (sorted by UTF-8 bytes) and the rows (read in pages, `collate "C"`) are merged like two sorted lists, so memory and queries stay flat whatever the library size. Hidden entries, `@eaDir`, recycle bins and partial downloads are skipped; symlinks are followed only to files inside the root, also when the scanned path itself is a link or lies under a linked folder. Serving and every ffmpeg read resolve a file's links (`libraryPath`) and refuse one whose real path is outside its root's (403 `path_outside_root`). A root that cannot be read is skipped rather than marked missing. One scan per root at a time (the root id is the singleton key); `library.scan-all` runs nightly. A full scan asked for while a watcher or import scan of some paths holds the key is not dropped: a queued partial scan becomes the full scan, and a running one is followed by `library.scan-after`, which the partial scan's job runs as soon as it finishes (or, failing that, which queues the full scan on its own 15 minutes later).
2. `library.probe` reads tags and technical details with `music-metadata` (ffprobe fills gaps and takes over when it cannot parse), normalizes them into `FileTags`, reads ReplayGain (and Opus R128) into the `tag_*` columns, stores the embedded picture, sets `probe_stage 1` and the group key, then queues ingest for the group. A file nothing can read gets `probe_error` and is left alone until it changes.
3. `library.ingest` `{ rootId, groupKey }` creates or reuses local-only catalog rows (artists, album, release, recordings, release tracks) from the group's tags and links the files, in one transaction. Rows the files already use are reused unless another group has more files on them (or as many and an older file), so a group that loses a file keeps its rows whichever of the two is ingested first; rows with a MusicBrainz id in the tags are found by it or created with it, and are never renamed from tags afterwards. The album type comes from a release-type tag (`RELEASETYPE`, "MusicBrainz Album Type"), else a compilation flag, else a lone file without an album name is a single; otherwise it is "album" with `type_guessed` set, so a single delivered before its catalog row is known is not taken for an album. Files a provider delivered (their import belongs to an acquisition job) take their artists from the request, and tags only fill gaps: a delivery of one requested recording is credited as that recording (and its album as the requested album), whatever its tags spell; for other deliveries each tag credit resolves to the requested recordings' and album's artists by name, by the whole credit, or split into them when every part is one ("Grimes, VADAKIN"). A store's spelling used to mint a second artist beside the catalog's. A group with a matched or locked file is only relinked. Rows that end up unused (no files, no user data, no MusicBrainz id) are removed. Then album and artist art from the folder and files, lyrics (embedded or a `.lrc` sidecar), and `matching.match-album`. After this step the music is browsable and playable.
4. `library.analyze` (low priority) computes the audio hash and sets `probe_stage 2`. A new file whose hash matches a row whose file is gone is that row moved: the old row takes the new path and keeps its id, links and match state. Then `loudness.measure`.
5. `matching.match-album` `{ rootId, groupKey }` (singleton key `<rootId>:<groupKey>`) upgrades local-only rows to MusicBrainz rows, opens a review, or leaves the files `unmatched`. It applies under the catalog lock, like ingest. `matching.sweep` re-queues groups still `pending` every ten minutes and at worker start. When `PATCH /admin/settings` switches MusicBrainz on, `queueNewlyPossibleMatching` (`matching/retry.ts`) queues a sweep at once; when an AcoustID key appears it queues `matching.retry-fingerprints`, which sets unlocked `unmatched` files with no known AcoustID back to `pending` in groups the matcher would fingerprint (no album artist and title to search by), then sweeps. Groups searched by their tags are not retried: the key could not change their answer. Both leave alone files in `_Incoming/<importId>/` while that import is processing and has no `duplicates_decided_at`, so no provider is asked about copies about to be deleted or about half an album; the import queues their matching once it has decided.
6. `enrichment.album` and `enrichment.artist` (queued by the match) fill in covers, images, bios, Deezer ids and lyrics; see "Enrichment".

Every ffmpeg and ffprobe call that reads a library, staged or delivered file puts `INPUT_GUARD` (`lib/ffmpeg.ts`, through `audioInput`) before the input: the `file` protocol only, and only the demuxers of the scanner's audio extensions, because ffmpeg picks a demuxer by content and a concat script, playlist or SDP named `x.flac` would otherwise open other files or sockets. fpcalc has no such options, so `acoustid.fingerprint` pipes samples from a guarded ffmpeg into `fpcalc -format s16le` and takes the duration from the guarded probe.

`library.purge-missing` runs daily and deletes files missing longer than `missingFileGraceDays`. The grouping and album artist rules are written out at the top of `modules/library/grouping.ts`. In short, the album grouping key is root id, parent directory (ignoring `CD1`/`Disc 2` subfolders), and `matchKey` of album artist and album. An album artist tag that is a track's several artists run together ("A, B", where the multi-value artists tag names A and B) credits those artists, never one artist named "A, B". Because the folder is part of the key, every acquisition delivery is a group of its own; acquisition places delivered files on the requested album itself (see "Acquisition") instead of leaving them to ingest and matching.

Watching: roots with `watch` on are watched while a worker runs, and changed paths are scanned after two quiet seconds. macOS and Windows use one recursive watch per root; Linux uses one inotify watch per folder. Network mounts and exhausted inotify limits fall back to the nightly scan.

Scans skip `_Incoming/<importId>` folders while that import is extracting or moving files into them, and organize leaves `_Incoming` out of its plans unless `includeIncoming` is set. Organize plans provider deliveries (`cached`) under `_Fetched/` with the root's template inside, and other files out of it. A filed delivery is moved again only when a path component the template fills from an artist credit is no longer what its credits give (`refileCredits`, `organize/refile.ts`): the acquisition repair runs it for each managed root on full runs and after placing anything, the batch is dropped when it moves nothing, and the mover removes the folders it empties. A file a scan finds under a managed root's `_Fetched/` with no row gets `source = 'provider:unknown'`, so a database restored without it keeps it as cache; nothing in a read-only root is ever cache. When move detection reconnects a cached row to a file moved out of `_Fetched/` (or into another root), the row takes the new file's source: the owner moved it to keep it.

### Imports

`modules/imports` brings music in through the server: web uploads, the inbox folder, and acquisition deliveries (which call `createImport`, `addImportFile`, `commitImport` and `failImport` from `modules/imports/index.ts`). Whatever the origin, an import is a row in `imports` and goes through the same steps:

```
receiving ──commit──▶ processing: extracting → moving → identifying → filing ──▶ completed
    │                                                                       └──▶ failed
    └── cancel, provider failure, or a day without files ──▶ failed
```

- **Receiving.** Files stream into `<data>/staging/<importId>/` through a byte counter, as a temporary dot file, and are linked into place in the same transaction that bumps the import's counters, so a concurrent commit or cancel sees all of a file or none of it. Names are checked first (`imports/paths.ts`): audio by the scanner's extension list, `cover.*` and `folder.*` images, `.lrc`, `.cue`, `.log` and `.zip`; relative paths are normalized and must not be absolute or contain `..` or control characters, at most 8 levels and 1024 bytes. `importMaxFileBytes` and `importMaxBytes` bound files and imports (413). Nothing follows or creates a symbolic link. An upload that would leave less than 1 GiB free on the staging disk (`imports/space.ts`; the request's Content-Length counts, and a file is checked again every 256 MiB) is refused with 507 `insufficient_storage`, and `createImport` refuses a member's upload past `importMaxActivePerUser` receiving or processing ones (429 `too_many_imports`; admins exempt).
- **Target root.** `importRootId`, else the only enabled managed root; otherwise creating an import fails with `no_managed_root` or `import_root_not_set`.
- **`imports.process`** runs the steps; each is idempotent and records its outcome before the import moves on, so a retried job carries on after a crash. *Extracting* reads each zip in two passes with yauzl (check every entry, then extract into a temporary folder renamed into place); an archive with an unsafe path, a symbolic link, encryption, more than 10,000 entries, more bytes than the import may hold, or more than 20 times its own size (beyond 64 MiB) is refused whole, and one the disk has no room for fails the import, and nested zips are skipped. *Moving* uses organize's mover (rename, or copy, verify and delete) into `<root>/_Incoming/<importId>/`. *Identifying* queues a scan of that folder and watches `media_files`: it marks rows with `source` and `import_id`; once every file has its audio hash (or an error), it decides in one transaction which files are duplicates and deletes them, recording `imports.duplicates_decided_at` and the paths in `work`. A file is a duplicate when the library already has its audio, when an older import still processing has it, or when an earlier path in the same import does, so the outcome does not depend on the order analysis finished in. For an upload or inbox import, a provider delivery (cache) never counts as the library having the audio: the owner's copy is kept. For an acquisition import it also records the library files its duplicates were copies of (`work.copies`; only earlier provider deliveries not locked by "Fix match") and, on every pass from then on, hands the delivery to acquisition (`settleDelivery` in `acquisition/delivery.ts`), which checks it against the request and places what fits on the requested album before matching is awaited. Then it waits until the rest is ingested and matched, or for an hour, after which duplicates are decided from the hashes known by then and the rest is left for review. *Filing* plans and applies one organize batch for the import's own files still in its folder that are identified with confidence (matched, or placed by acquisition), removes the folder when no audio is left in it, refreshes wants and records the counts. `refileImport` runs the filing step again for a completed import, for files identified after it ended.
- **Completion** is read from the row; every status and step change publishes `import.updated` to the owner and admins.
- **Inbox.** One worker (an advisory lock) polls the inbox (`inboxPath`, else `SQUIRMY_INBOX_PATH`) and takes each top-level item once it has been unchanged and readable for five seconds, moving it into staging. What an import does not take, and failed inbox imports, go to `Not imported/<importId>/` in the inbox. The inbox may not overlap a library root or the data folder.
- **`imports.sweep`** (every 15 minutes and at worker start) expires imports stuck receiving, re-queues processing ones and removes orphaned staging folders.

### Acquisition

`modules/acquisition` implements the server side of [provider-protocol.md](./provider-protocol.md). Nothing happens until an admin adds a provider.

- **Providers** are rows in `acquisition_providers`; the secret is encrypted with `encrypt('acquisition-provider-secret', …)`. A provider counts once it is enabled and has answered `capabilities`, which the server asks for when the provider is added, tested or given a new address or secret, and every five minutes for enabled providers (`acquisition.check`, `checkProviders`; an answer sets `last_ok_at` and clears `last_error` unless the provider is failing, a failure is kept as `last_error` as a failed resolve is, a busy answer is ignored, and none of it touches the failing streak). The enabled list is cached in memory for 30 seconds (and dropped on every change in that process), so `onDemandRecordings` costs nothing without one. Every call goes through `client.ts`: timeouts, the bearer secret, redirects only within the provider's origin, at most 4 MiB read, contract validation; failures are `ProviderCallError` and end up in `last_error` or the job's `error`.
- **Policy** is the `acquisition_policy` row of `server_settings` (`AcquisitionPolicy`): lossless preference, per-file limit, the cache limit (`storageQuotaBytes`), timeout, target root, and the delivery base URL (the policy's, else `PUBLIC_URL`, else localhost).
- **Coverage** (`onDemandRecordings`). An `assume_available` provider covers every recording without a miss that counts (below). A `must_resolve` provider covers recordings with a positive resolve newer than 30 days (`acquisition_offers`, free offers only). Recordings it has never answered for are collected in memory for a quarter second, queued as `acquisition.resolve` jobs of up to 100, and remembered for ten minutes so lists do not queue them again; when the answers arrive, the tracks that lit up and their albums are announced with `announceAvailability`. A provider's coverage is the admin's `coverage_override` when set (`PATCH` of the provider), else what it declared; a `capabilities` refresh only rewrites the declared one. `albumCoveredWithoutTracks` (the seam availability uses for albums with no track list, such as search results) is true while an `assume_available` provider is active.
- **Misses** (`misses.ts`). An empty resolve, a refusal, a failed or mismatched delivery, or a timeout after the provider took a job writes a row to `acquisition_misses` (one per provider and recording), and a miss grays the recording out for that provider for a day. It describes the provider as it was, so each row carries the provider's `miss_epoch` (`provider_epoch`) and `identity` (`provider_identity`, for the history), and only rows at the current epoch and younger than a day count (`currentMisses`, which coverage and the choice of provider for a request read). The epoch moves on (`forgetMisses`), so the older rows stop counting while staying until they expire, when: the provider's identity changes, that is its declared `version` (optional in `ProviderCapabilities`) and a hash of everything else it declares (`providerIdentity`), so a provider without a version still changes identity when an update changes its capabilities; it is turned back on; it is given a new address or secret; or an admin retries its unavailable tracks (`clearProviderMisses`). The first three also end its failing streak (below); a retry leaves the streak alone. The first identity recorded for a provider (also on upgrading to a server that records it) counts as a change. The tracks those misses grayed out are announced with `announceAvailability`, and the process that made the change forgets which of the provider's recordings it asked about recently, so a `must_resolve` provider is asked again at once. `AcquisitionProvider.unavailableTracks` counts the misses that count.
- **Requests** (`requestRecording` from sessions, the acquire routes). The user must be an admin or have `can_acquire` (checked before anything about other users' jobs is looked at), a provider without a recent miss must remain, there must be a root to file into, and a member may have at most 100 unfinished jobs (`acquire_limit_reached`, 429; joining a job in flight is free; admins have no limit). The cache limit never refuses a request. Each job stores its `origin`: `play` (the current entry), `prefetch` (one further down the queue), `download` (a device downloading) or `library` (an explicit request or a library save; the route default). Joining a job in flight with a sooner origin moves it up. An album request leaves out tracks another job is already fetching. Acquisition never adds to a library, whatever the origin: only the heart does (userdata's `PUT /me/likes`, which asks for the files itself as origin `library`). Fetched files are cache. One job per target is in flight: the `idempotency_key` is `recording:<id>` or `album:<id>` and gets the job id appended when the job ends. A request that cannot go ahead is answered as failed straight away, unless another job is fetching that recording.
- **Jobs.** `acquisition.start` picks an offer (fresh cached offers, else a resolve, providers in priority order), waits for a slot under the provider's `maxConcurrent`, claims the job with a new random token (only its SHA-256 is stored) and calls `acquire`. Counting the slots and claiming one happen under an advisory lock per provider, and a job claimed but not yet answered holds its slot, so jobs started together never overshoot. A provider that is busy gets the job again after 5 s, doubling up to a minute (or after its `Retry-After`, up to five minutes), with no miss and nothing counted against its health: busy is an acquire declined with `reason: "busy"`, a resolve or acquire answered 429 (or 503 with `Retry-After`; a bare 503 is more often a proxy in front of a provider that is down, so it counts as a failure), or a job the provider took and then failed as busy before any file arrived (`reason: "busy"` on `complete` or the job status). Older providers' wording counts too: an error starting "Provider is busy", or saying it was rate limited or got too many requests (`saysBusy` in `client.ts`). A job failed as busy goes back to `resolving` with its offer and is handed over again after a wait as long as its age, so the waits double; one that failed busy after files arrived fails without misses. A resolve job refused as busy is queued again the same way, five times at most. The policy's timeout ends a job no provider ever takes, also with no miss. An album job asks with the whole track list and marks tracks the server has, or that the job does not need, `wanted: false`. An album no provider offers whole, declines, or fails without delivering anything is fetched track by track instead (one recording job per missing track, the album job ends `failed` without misses). Deliveries stream into an import of kind `acquisition` (created on the first upload, filed into the policy's root) under the policy's per-file limit. `complete` commits the import, and `acquisition.finish` follows it: while it identifies, every delivered file that is ingested, hashed and not a copy of another library file is checked against the request (`verify.ts`, rules in the protocol document, merging rows with `mergeRecording` where a delivered file is plainly the requested recording) and what it satisfies is announced ready at once; when the import ends the check runs again and decides the job. A delivered file the import dropped as a copy of an earlier delivery counts through that file (`work.copies`), so a second request for a song the library has under another row succeeds and merges the two rows instead of failing with a miss. Free slots go to waiting jobs in start order (`play`, `prefetch`, `download`, `library`, oldest first within one): a job leaves a slot to the waiting jobs ahead of it, and a job ending wakes the first in line. Each upload is held to the job's budget: 1.25 × `maxFileBytes` per requested recording in all and four files per recording plus two (413 past either, which fails the job); empty audio is refused.
- **Placing deliveries** (`place.ts`, the one place that links a delivery to its request). A delivered file that is a requested recording goes on the album the request named (else, for a request without one, the album its file is already on when that is more than its tags, another album listing the recording, or the album a search stub hints at; with no hint either, as for Deezer's popular tracks, the album the file's own album tag names among its artists' albums, by edition-free title), on that album's own track for the recording. An album with no track list from a source has its detail fetched first; while a source could still answer, a young file waits (it plays meanwhile) and the sweep tries again, and without one the file goes on a track list built from the files in their own numbers (on an album its tags named that lists no track for it, a regional edition's bonus track, beside the album's own track list; on a requested album, as an extra with no track). A requested search stub that lists the recording only on a track list built from files gives way to the same album's other row (same artist, type and edition-free title) that lists it from a source, and is merged into that row once empty (`sameAlbumIds`). When the album lists the song under another row (a search stub and the MusicBrainz recording), the two are merged, but only when exactly one track is plainly the same recording and two catalog rows that carry ISRCs share one. `matching.placeFiles` (owned by matching) then links the files (`matched`, source `request`), removes or redirects the tags-built rows they left (never an album with a MusicBrainz id or a track list from a source, nor one with an id at another source unless the caller names it as the same album) and the credits of redirect recordings, so artists their tags ran together go, and resolves the group's review once every file in it is identified; the import files them as it files matches. Placement runs when the import has decided its duplicates (`settleDelivery`), while `acquisition.finish` follows a one-file delivery, at the end of the job, and from the repair.
- **Repair** (`repair.ts`). `acquisition.repair` (at worker start and daily at 04:25) and the sweep (over jobs of the last two hours) place deliveries of completed jobs that are still on rows built from their tags, as left by servers before placement existed, or on a file-built track list while their album, or another row that lists the recording from a source, has one by now, then file them with `refileImport`. The tags-built albums they leave become redirects, so likes, wants, playlist items and plays move to the real album (`mergeAlbum`). Only files a provider delivered for a job that completed, still linked to a recording it asked for, not locked and not matched by the matcher, are touched; jobs it could not place are skipped for five minutes. Groups of deliveries whose album is credited to a run-together artist are ingested again under today's grouping rules. A recording matching later links to another MusicBrainz id fails then: it gets a miss and its entries fail, except a current entry that is already playing. `acquisition.sweep` (every minute and at worker start) fails jobs past the timeout, polls providers of jobs quiet for a minute, re-queues the start of jobs stuck in `resolving` and the finish of jobs in `importing`, deletes expired misses and offers, and runs the repair over recent jobs.
- **The cache** (`evict.ts`). Every delivered file is cache (`media_files.cached`): Organize files it under `<root>/_Fetched/<template>`, matching never opens a review for a group of cached files only, Admin → Library stats count only collection files (a root's `cachedFileCount` says how many of its `fileCount` are cache), and `GET /admin/acquisition/usage` reports `cachedFiles`, `cachedBytes`, `pinnedBytes` and `limitBytes`, shown under Admin → Providers → Cache. When a job's import has ended, `discardUnrequested` deletes its delivered files that are not a requested recording (after merges), unless one is the only file of its recording and is pinned, counted by another import as a copy, or wanted by another job; the sweep repeats it for jobs ended in the last two hours. `acquisition.evict` (hourly at :17, and queued after a completion or upload while the cache is over its limit) deletes least recently used cached files (the later of the recording's last play and the file's arrival) until the cache is under 90% of `storageQuotaBytes`; 0 is unlimited. Never deleted: pinned files (`userdata/pins.ts`: a saved album or recording, a recording on a saved album's track list, a playlist item, a stored queue entry, a play in the last 24 hours, checked again for each file just before it goes), files in their first hour, files of imports still running, and anything outside a managed root. Deleting removes the file, its row and the local-only catalog rows it leaves (`removeOrphans`), then sidecars and empty folders inside `_Fetched/` or `_Incoming/` only; catalog albums and recordings stay, so the track is `on_demand` again.
- **Health** (`health.ts`). Failures a provider is answerable for count against it: a `ProviderCallError` while a job resolves, starts or is polled, a job it reports `failed`, and a job it took that times out (not a delivery the server's own checks refuse, and never a busy refusal, see "Jobs"). `noteProviderFailure` keeps the message in `last_error`, sets `failing_since` on the first one after a delivery, and adds the job's recordings to `failing_recordings`. With three different recordings there (`FAILING_AFTER`) the provider is failing: the misses recorded for them since `failing_since` are deleted and their tracks invalidated, failed jobs record no more misses, their outcomes carry `outage`, and `AcquisitionProvider.failingSince` is set for the admin page. Jobs still go to it, so the first job that completes with a delivery (`noteProviderDelivered`) ends the streak, clears `last_error` and sets `last_ok_at`. A change to the provider (another identity, turned back on, a new address or secret) also ends it, with its misses (see "Misses"): those failures were the provider before the change.
- **Outcomes reach the sessions** through the `squirmy_acquisition` NOTIFY channel, which the API process applies with `markRecordingReady` / `markRecordingFailed`. A failed outcome carries its `cause` (`EntryFailure`), with the outage reason for `outage`:
  - `unavailable`: the provider does not have it. Every provider asked answered without a free offer, it declined or reported the job failed (both record a miss), the delivery was not the track, a miss that counts left no provider to ask (`not_available`), the track is gone, or the user may not fetch.
  - `outage`: the provider is failing (health), a provider could not be asked while resolving, the call to start the job failed, or no provider is enabled any more.
  - `error`: anything else: the server's own import failed, nothing was delivered in time, the job limit, a missing import root.

  Because sessions ask once per load, the API process also reconciles every 30 seconds while a provider is active: recordings of jobs that ended in the last ten minutes are marked ready when owned, and failed when not owned and no job is still on them (`unavailable` when a miss counts for them, else `error`).
- **Events.** Every status change publishes `acquisition.updated` to the requesting user and to admins.

The reference providers live in `adapters/`. `@squirmy/provider-kit` is the protocol's provider side (HTTP, secret, validation, idempotent jobs, streaming uploads; `ProviderBusyError` thrown from `resolve` answers 429 and from `fetch` fails the job with `reason: "busy"`, and a job that failed busy runs again when the server sends it again); `adapters/cold-storage` indexes a folder's tags and resolves by MusicBrainz id, ISRC, then artist, title and length; `adapters/mock` synthesizes quiet tones and can be slow, failing, wrong or priced. The server's tests run the mock in-process.

### External metadata

All clients live in `modules/metadata/` and go through `lib/http.ts`:

- `cachedFetch(provider, url, { ttlSeconds, … })` stores responses in `http_cache` and serves them until they expire. 404s are cached for at most six hours, 5xx never; 429/503 are retried honoring `Retry-After`. `cache: 'reload' | 'no-store'` bypasses the cache for one call.
- Bodies over 8 MiB fail the call with `ProviderError` and are not cached.
- Image links come from provider data, so `fetchImage` downloads through `requestPublic`: https only, at most three redirects followed by hand and checked the same way, and connections only to public addresses. `publicDispatcher` (an undici `Agent`) filters what each name resolves to at connect time, so a name cannot pass a check and then resolve to a private address; `lib/address.ts` has the list (loopback, RFC 1918, link-local, unique local, CGNAT, multicast, reserved, and IPv4-mapped and NAT64 forms of those). A refused URL is treated as an unusable image.
- `rateLimit(key, intervalMs)` reserves the next slot in the `rate_limits` table, so the limit holds across processes. MusicBrainz uses 1100 ms (only against `musicbrainz.org` and its subdomains, such as `beta.`; a mirror is not limited).
- User-Agent: `Squirmy/<version> ( https://github.com/IsaacThoman/squirmy )`, with the version from `lib/version.ts`: `SQUIRMY_VERSION` (release images), else `dev+<short commit>` from `SOURCE_COMMIT` (a build argument, or set at run time by Coolify) or read once at start from git, else `dev`.
- Every provider checks its toggle or key in `ServerSettings` and returns null or an empty list rather than throwing when it is off. `fetchImage` (`metadata/images.ts`) downloads an image for any provider and checks the switch of the source that owns the image's host (`imageSourceEnabled`), so a lazily listed remote image is not downloaded after its source is turned off. "Not found" is null too; a provider failure (network, timeout, 5xx, bad key) throws `ProviderError`.
- Album types: MusicBrainz's release-group types map through `musicbrainz.albumType` (a soundtrack, live or compilation secondary type wins over an album primary type; a single or EP stays one, so a song from a film is listed with the artist's singles), Deezer's `record_type` through its client (`compile` is a compilation).
- Other modules import the clients from `modules/metadata/index.ts`, e.g. `musicbrainz.getRelease(mbid)`.
- Tests never touch the network. `useHttpFixtures(provider)` from `src/test/http.ts` serves recorded responses from `src/test/http/<provider>/` and fails on any unrecorded request. `SQUIRMY_RECORD_HTTP=1` records missing fixtures from the real service.

### Enrichment

The catalog is a lazy cache of MusicBrainz. `enrichment/detail.ts` completes a row when a page opens it; jobs decorate owned music in the background.

- **Album detail** (`ensureAlbumDetail`). An album at `detail_level` 2 fetched in the last 30 days is left alone. With a release-group MBID the group is fetched, the canonical release chosen (`canonical.ts`: best status present, then the most common track count, then the album's own mix before another (Dolby Atmos, spatial, instrumental: MusicBrainz lists those songs as recordings of their own, which no store copy or delivered file matched), uncensored before clean or edited pressings, CD or digital media, then the earliest date) and written through matching's `upsertRelease`. An album whose files are on a MusicBrainz edition keeps it as canonical; one whose files sit on a local edition (a local album merged into the group's row) takes the chosen release, and its files' recordings are fitted to the release's tracks. Without an MBID a Deezer id is bridged, most reliable first: the MusicBrainz URL relation of the Deezer page, the UPC as a barcode (accepted when its releases share one group), then a release-group search accepted only for one hit scoring 90 or more with the same title and artist. The bridge keeps the release too when the link or the barcode names one. The stub adopts the MBID, or is merged into the row that has it, unless it is another edition of the group: its track count differs from the group's own edition's, and a release of the group has its track count or its title names an edition the group's does not ("SOS Deluxe: LANA", "Midnights (3am Edition)", a deluxe "Watch the Throne"). Such a store album stays a row of its own with `edition_of_id` set to the group's row (created at level 1 when missing), the group's type, year and credits, and as its track list the group's release with its track count (link, then barcode, then track count) when there is one, else Deezer's; a release the group's row had shown moves to it, and the group's row picks its own again when next opened. A store copy that only lacks a track is the group's own edition. Of several Deezer albums on one row (the explicit and the clean version) the explicit one is built. With no match the track list comes from Deezer (provider-only rows with ISRCs); the album stays at level 1 and the bridge is retried after a day. A song is one row however many sources list it. Which track of the album a row from another source is follows `track-identity.ts`: a shared ISRC (with the title or the place, and lengths within 15 seconds, unless the ISRC is a source's own against rows without files), else the same edition-free title (`matchKey` folds case, curly and straight quotes and punctuation; guest credits and edition suffixes are dropped) with lengths within five seconds, at the same place or with no ISRC the other lacks entirely, else the same place with lengths within two seconds when neither title names another version and the track there is not listed elsewhere on the other list; each step counts only when exactly one track fits. A MusicBrainz release written onto an album that already lists the songs (Deezer's track list, one built from a delivery's tags, files filed under it) takes over those MBID-less rows (`standInsFor`, a track and a row that pick each other), so likes, plays and queue entries keep their ids. Recordings without an MBID that still stand in for a track of the canonical release are merged into its recording (`fit.ts`) when the release or a Deezer track list is written: tracks of the album's other track lists and the recordings of present files filed under it by those rules (an ISRC never alone), a recording with files on another album (the song's single) sharing an ISRC and the title with one track, a stub with no file sharing an ISRC with one track, and a loose stub of the album's artists (Deezer top tracks carry no ISRC) with the same edition-free title and a length within five seconds. A detail run that writes nothing fits the album's files too, only when an indexed check finds a file on a stand-in, so a track fetched onto a complete album is folded in on the next visit. Deezer's track list is matched to the canonical release the same way (an ISRC counts alone): each match links the Deezer track id; a match that was not by ISRC adds Deezer's ISRC to a recording that carries other codes unless the track is a clean edit (Deezer marks it edited, or the album is not the explicit version), so a delivered stereo file of a song whose canonical release has codes of its own is the track that was asked for; and Deezer's explicit flag is copied onto recordings that have none when the ISRC matches or the Deezer album is the explicit version. Merges keep a flag the winner lacks. A track list only Deezer has gets each track's featured artists from the track's own entry (`creditDeezerTracks`; the album's track list names only the main artist), a collaboration album every main artist Deezer lists (`/album/{id}` contributors), and the album Deezer's year and date. Deezer's text is decoded of HTML entities.
- **Artist detail** (`ensureArtistDetail`, `hydrateArtist`). MusicBrainz answers a request a second and a big discography is many pages (Bach's is 62), so the run writes in the order a page can use it and tells the page when it has something worth showing (`usable`, see Bounds):
  1. **Deezer first.** With a Deezer page, its newest 200 albums become stubs with Deezer's date, type and cover, and rows that already carry a Deezer id gain a missing date, a stated type for a guessed one, or a cover: search names neither, so a first visit was yearless and alphabetical. For an artist with an MBID the MusicBrainz profile is fetched alongside; the pass waits up to 1.5 s for it to name the artist's own Deezer pages, else uses the row's page with the most fans. That is the first answer.
  2. **Profile.** The profile and genres, adopting the MBID (or merging into the row that has it). The name stays the one the row has when MusicBrainz lists it among the artist's names ("Kanye West" for Ye, "Hikaru Utada" for 宇多田ヒカル), takes MusicBrainz's spelling of the same name ("JAY‐Z" for "JAŸ-Z"), and is MusicBrainz's otherwise (`displayName`). Every Deezer page MusicBrainz links is linked. A page the row had by name alone that MusicBrainz does not list, when it lists others, is a namesake's: it moves to a stub of its own with the albums the first pass made from it (`detachDeezerArtist`). A Deezer stub bridged by name search to an artist whose Deezer pages are others is not bridged.
  3. **Image, bio, popular tracks.** The picture is chosen from the artist's own Deezer page (most fans), else fanart.tv, else Wikidata, as a lazy remote image, replacing one taken from a page search linked by name; a picture from the user's folders stays. `artists.image_picked_at` records a choice made with the profile; merges clear it. The bio is the English Wikipedia summary, with the separators of dropped parentheticals cleaned out (`wikidata.cleanExtract`). Popular tracks are Deezer's top tracks (a store's hits, with their albums), else ListenBrainz's most listened recordings (with a token), stored as the artist's ranked list in `artist_top_tracks` with a 0..1 `popularity` on each, with stubs for tracks the catalog lacks.
  4. **Discography.** The official discography (`release-group-status=website-default`), written a page of 100 groups at a time as level-1 album rows with a lazy Cover Art Archive cover (`/release-group/<mbid>/front-500`; none for MusicBrainz's placeholder artists, `musicbrainz.specialPurposeArtists`: Various Artists is credited on hundreds of thousands of compilations), adopting the album stubs search or Deezer made for the same groups (no MBID, no files, not an edition row, led by the group's first credit, else by another artist it credits, since Deezer lists an artist's features among its albums without their owner; the same title once store labels are dropped, `labelFreeKey`, so a deluxe or 3am edition stays its own; compatible type: EP and single are compatible, a stub typed album fits any long-form group since Deezer calls soundtracks, live albums and compilations albums, and a guessed type fits any; a title two groups share adopts nothing). Open pages are told after the first page and at most every 15 s after. Remix albums and DJ mixes are compilations (`musicbrainz.albumType`).

  A Deezer artist is bridged by URL relation, else an unambiguous exact-name search, where a Deezer namesake hint ("Nirvana (UK)") is not part of the name: the hit must be named like the part before it and fit the hint by country or disambiguation (`bridge.ts` `confidentArtist`). Otherwise Deezer's albums are its discography (up to 1,000).
- **One row per release** (`reconcile.ts`). Rows of one release arrive from writers that cannot see each other: search stubs written while the discography was fetched, stubs credited to a second row of the artist that the namesake bridge merges later (Grimes on the test instance), stubs of a track's album reference, rows built from a delivery's tags that a play kept alive after the file moved. `reconcileArtistAlbums` groups the albums an artist leads by `labelFreeKey`, so a deluxe or 3am edition never joins the standard album; a row with neither MBID, files nor `edition_of_id` merges into the row with one of those of the same type, else of the same family (EP and single; the rest), else any when its type is a guess, with years at most one apart; rows that no such row takes merge into the best of them. Rows with an MBID, files or `edition_of_id` are never merged here. It runs at the end of artist detail, after a namesake merge, from `enrichment.reconcile { artistId }` (queued by search when it writes album stubs), and as the release repair (`repair.ts`, `enrichment.reconcile` without an artist, at worker start and daily at 04:50): first editions merged into their group's row by older code are split off again (`editions.ts`: a Deezer album on a group's row whose track count differs and whose title names another edition moves to the row it was merged from, un-merged, or to a new edition row, with the track list Deezer built for it; up to 100 group rows a run), edition rows of one group that are one edition (the same name, track count and ISRCs in order, from their track list or Deezer's) are merged (`mergeDuplicateEditions`; the explicit and the clean version differ in ISRCs and stay apart), artists bridged by name to the wrong MusicBrainz artist are unlinked (`unlinkContradictedBridges`, below), then second Deezer pages are merged into their artists (below), then every artist with a loose row; artist rows built from a delivery's tags that only rows merged away still credit (no MBID, no provider id) are merged into the one other artist of their name, or removed when none or several share it and no like or rating points at them (`foldTagBuiltArtists`); names and titles stored with HTML entities are decoded and their keys recomputed; albums with a date get the year; up to 200 albums a run whose MusicBrainz recordings lack Deezer's explicit flag read their Deezer track list again; up to 200 artists whose popular tracks have no album fetch their top tracks again, so they get one, and up to 200 fetched artists with no ranked list get one; up to 100 artists with an MBID whose picture was not chosen from their profile (`image_picked_at` null) and is not from the user's folders have it chosen again; and up to 500 albums that list a song twice, the canonical track and, below it, a stand-in of another track list or a filed file with its title, an ISRC of it, or its place and length (`album-tracks.ts`), are fitted again, and with Deezer on those where that merged something read their Deezer track list again (up to 100), so a song's single carrying the store's code folds in too. Merges go through `mergeAlbum`, which moves files, editions, external ids, album hints, likes, ratings, wants, library saves, playlist items and plays.
- **Popular tracks from Deezer** keep the album Deezer names for them as their album hint: the row with its Deezer id, else the album artist's row of the same `releaseKey` (owned and MusicBrainz first), else a stub with the track's cover and a guessed type. ListenBrainz's popular recordings take the artist's album of the release name it gives. Popularity is the last ranking's: recordings that left it lose theirs, so a song Deezer ranks under another track id is not listed twice. A featured artist is the row of that name when it is the only one and has no Deezer id yet, as search decides, rather than a second row beside the artist the discography credited.
- **Wrong bridges** (`namesakes.ts`, `unlinkContradictedBridges`). An artist with an MBID whose Deezer page carries a namesake hint the MusicBrainz artist does not fit (`contradictsHint`, `confidentArtist`'s rule: "Nirvana (UK)", the 1970s band, had become "Nirvana UK", a tribute band), or whose MusicBrainz disambiguation says tribute, cover band or karaoke while the page does not, is unlinked unless MusicBrainz itself links the page: the MBID moves to a row of its own with what MusicBrainz credits to it, and the row takes the page's name back at `detail_level` 0, to be bridged again. Candidates are artists whose name ends in a country word or whose disambiguation says they play others' music, up to 100 a run.
- **Second Deezer pages** (`artist-copies.ts`). Rows with an MBID are compared by what MusicBrainz credits them with (albums and recordings with an MBID) only: their other credits may be a namesake's, and counting them let one wrong merge pull in the next. A Deezer-only artist row that shares its name with another row is merged into it (`mergeArtist`: credits, likes, ratings, its Deezer id; the winner keeps its disambiguation and takes the loser's when it has none) when MusicBrainz links its Deezer page to that row's MBID, or the two share a release or two songs, counting the rows' credits and what each row's Deezer pages list (albums, popular tracks). A page MusicBrainz links to another artist, an empty page, or one with nothing in common is a namesake and stays apart; of several fitting rows only a sole MBID row is taken. It runs from `enrichment.reconcile { artistCopy }` (queued by search) and in the release repair, up to 300 rows a run.
- **Warming.** `warmDetail` (the seam's background form) starts a row's run without waiting for it; a catalog search warms its top result when that is an artist, so the page a user opens next joins a run already under way. At most two warm-ups run at once; more are skipped. Albums from a catalog search go through search's own queue instead (`search/warm.ts`), which keeps the ones it cannot start yet rather than skipping them.
- **Bounds.** One run per row is in flight per process and concurrent callers share it. A page waits at most four seconds from when the run started (so a visit that joins a run an earlier visit started waits only for what is left), then renders what is known with `detailPending: true` on `AlbumDetail`/`ArtistDetail`; the run carries on, invalidates the page when it lands, and `enrichment.album`/`enrichment.artist` is queued a minute later as a safety net. An album with a Deezer id and no track list yet gets Deezer's first: the page renders it (pending) while MusicBrainz is asked, and the Deezer edition becomes the MusicBrainz release when it is written. A release group with no Deezer id and no track list (one an artist page's discography listed) looks its Deezer copy up first (an album search for its credit and title: the same artist, the same title, else the same `releaseKey`, single or EP only for one) and takes the same path (`deezerStandIn`). An artist page renders once the Deezer pass is written, and the MusicBrainz discography fills in behind it with invalidations as it goes. The seam never throws: a `ProviderError` leaves what was written, and an optional source failing (image, bio, top tracks) only keeps the row below level 2 so the next visit retries.
- **Owned albums** (`enrichment.album`). After detail: a stored cover unless the album has one at least 500 px on its short side (Cover Art Archive release front, then release-group front, then Deezer), Deezer ids by UPC and ISRC, a Wikipedia description, and `enrichment.lyrics` for owned recordings without lyrics. `albums.enriched_at` records success.
- **Fallback covers** (`enrichment.cover`, `covers.ts`). An album whose cover the art route unassigned gets the first of: a folder image or embedded picture of a present file (as a scan picks them), then the cover of its Deezer page as a lazy image. The archive is not asked for another release of the group: the group front is one of theirs. The sweep queues albums without a cover that have files or a Deezer page, each once a day per process.
- **Lyrics** (`enrichment.lyrics`, and `GET /tracks/:id/lyrics` on demand): LRCLIB by title, artist, album and duration; no match stores a `none` row that is retried after 30 days. Lyrics from files are never replaced.
- `enrichment.sweep` (every 30 minutes and at worker start) queues owned albums without `enriched_at`, their artists below level 2, and owned recordings without lyrics, 200 of each per run. While MusicBrainz is on, it then bridges up to 20 Deezer-only artists that share a name with another row (`namesakes.ts`, each tried once a day per process), by URL relation or an unambiguous exact-name search only, so Deezer's duplicate page of an artist is merged into the artist with the MBID without anyone opening it, and a real namesake stays apart.
- **Sources switched on later.** When `PATCH /admin/settings` switches a source on, `markEnrichmentStale` (`stale.ts`) clears `enriched_at` on owned albums (MusicBrainz, Cover Art Archive, Deezer, Wikidata) and drops artists of owned albums from level 2 to 1 (those, a fanart.tv key, a ListenBrainz token), and the sweep redoes them in its batches. Lyrics need nothing: no LRCLIB lookup is made or stored while it is off. `enrichment.new-releases` (weekly) refreshes library artists' discographies; Home's `new-releases` section lists albums from the last 120 days by library artists that have no present file. Neither counts MusicBrainz's placeholder artists (Various Artists on an owned compilation) as library artists.

## Clients

`client-core` holds everything both clients share and has no React, DOM or React Native imports:

- `reduceSession(state, { command, now, commandId, deviceId })`: the pure session reducer, also run by the server.
- `SessionClient`: owns the socket (through `createSocketTransport` from `@squirmy/client-core/socket`), the clock offset, optimistic commands and reconciliation; exposes a store (`getSnapshot`, `subscribe`) for `useSyncExternalStore`. `save()` and the `restore` option carry the last server state and the unsent commands across a relaunch; a restored session this device was playing comes back paused, at the saved position unless the server changed the session after the save (it paused it when the device went away), whose position is then kept rather than rewound to the save. On reconnect, commands made offline are followed by the engine's position, and tracks the device ended offline after the server gave up on it are preceded by a transfer back to it, so the server accepts them. `forgetPlayback(trackId?)` drops resolved descriptors (one track's, or all) so entries resolve again; the entries the engine holds keep their gain, and the preload is aimed again only when it is that track. An entry that only just became current loads at 0 rather than the few milliseconds its clock has run, since an exact seek that short makes a streaming player rebuffer; a preload the server refused is not asked for again until the target changes or playback is forgotten. `prepareTakeover()`, on a device that does not play, resolves the current entry and preloads it into the engine; a transfer here then loads from that buffer, and it is dropped when another entry becomes current. A load that failed for want of a connection starts, when it is retried, where its first try would have: the time spent offline is not time played. The snapshot's `outage` is the last `playback.unavailable` while the session is still paused on that failed entry: kept unseen until the pause arrives, forgotten once it plays or moves on. Its `away` is the active device while the live list leaves it out (online clients only), with that device as it was last listed (the client remembers the last 32 it saw), or none when it never was.
- `PlayerEngine`: the interface each platform implements (`load`, `preload`, `play`, `pause`, `seek`, `setGain`, `stop`, status events), with a `FakeEngine` for tests. `SessionClient` drives it when this device is active.
- `createApiClient({ baseUrl, getToken })`: typed fetch wrapper for every route, returning contract types.
- `TrackStore`: batched, cached `TrackSummary` hydration for queue entries. `refresh(trackId, albumId)` fetches one again while the cached copy stays on screen (asked while an answer is on its way, it asks again once that is in, since the answer may predate the change); `refreshTrack(trackId)` does that for every album the track is cached under, and `refreshInvalidated(keys)` for the tracks an `invalidate` names (`queryKeys.track`). `refreshFetchedTracks(client, store)` refreshes an entry once it turns from `preparing` to `ready`: an on-demand track gains its album and cover with its file; `patch` sets values the server announces on every cached copy.
- `planChanges`, `patchEntities` and `RealtimeBatch` (`changes.ts`): what a client does with the socket's `changes` and invalidations, shared by both apps.
- `PlaybackNoticeWatcher`, `skipNotice`, `stopNotice` (`session/notices.ts`): what both apps tell a listener when songs cannot be had, from each snapshot and `SessionClient.failureOf(trackId)` (the last `playback.failed` for it). A song that was current or next and failed as `unavailable` joins the run of such songs since one last played, counted with the failed entries passed over to get there; the run is one notice that each skip replaces ("Skipped “Title” — not available", then "Skipped 3 songs — not available"; the web app replaces its toast by key, iOS's notice shows one at a time). Any other failure is a notice of its own: "Couldn’t play “Title”" / "Skipped.". One notice for a stop the server explains (the snapshot's `outage`), which takes the run's place: "None of the remaining songs are available" for `exhausted`, "Several songs in a row aren’t available" / "Playback is paused." for `unavailable`, else "Can’t load music right now" with the reason and "Playback is paused."; after it nothing per song until playback resumes. Failures further down the queue are quiet, and nothing is told offline.
- `isPlayable(track, viewer)`, `albumPresentation`, `albumNote` and `canFetch`: the one rule for what a viewer can play and how unavailable music looks. `mergeSearch(library, catalog, viewer, options)` turns the two search answers into one result set: `items`, one list of every kind ordered by the answers' `ranked` scores (what the viewer cannot play scored down, the viewer's playlists matched by name on the same scale, an older server's answers ordered by name match), with identical albums and songs under different ids listed once. `searchQueue` is what plays from a result list; `recent-searches.ts` is the recent searches both apps keep on the device.
- Formatters (`formatDuration`, `formatTotalDuration`, `formatRemaining`, `formatReleaseDate` for calendar dates at the precision they have) and `creditParts(artistCredit, artists)`, which splits a credit into its artists and the words between them so both apps link each artist in the credit as written; the web app has no copies of them. Normalization math (`gainFor(mode, normalization, context)`), and artwork and stream URL helpers.

**Web** (`apps/web`): Vite, React 19, Tailwind 4, Radix primitives, TanStack Query, react-router. Colors are shadcn-style tokens declared as CSS custom properties in `src/index.css`: `background`, `foreground`, `card`, `popover`, `primary`, `secondary`, `muted`, `accent`, `destructive` (each surface with its `-foreground`), `border`, `input`, `ring`, and `sidebar` with `sidebar-foreground`, `sidebar-accent`, `sidebar-accent-foreground` and `sidebar-border`. A color theme replaces their values at runtime, so components style with the tokens; fixed colors are only for content (text over artwork, genre tiles, playlist covers). Two colors are mixed in `index.css` from the tokens rather than set by a theme: `faded-foreground` (gray text of music that does not play, 3:1) and `tint-muted-foreground` (secondary words over a collection header's artwork tint, 4.5:1); `headerTints` keeps a cover's color from going too light to tint a dark header. `input` is derived as the quietest color 3:1 off every surface a control sits on (`CONTROL_SURFACES`): it draws the edge of text fields and selects and the track of sliders. `color-themes.test.ts` checks those ratios, and 4.5:1 for text, in every theme and appearance. The palette is the web app's own and does not follow `apps/mobile/src/theme.ts`. - **Bootstrap.** One API client (same origin, `client: 'web'`) and one `QueryClient`. Before any route renders, `GET /setup/status` and `GET /auth/me` load. Guards: a server without an admin shows the setup wizard on every route; signed-out visitors go to `/login?next=…`; admin routes need the admin role. Signing in or out only changes the cached `me`, and the guards navigate. A 401 from any request signs out; other failures become a toast with the server's message, unless the query or mutation says it shows them itself (`meta: { silent }`, `meta: { inline }`).
- **Appearance.** `lib/appearance.ts` owns this browser's choice: a mode (`light`, `dark` or `system`, the default) and a color theme id (default `squirmy`). It is kept in `localStorage` under `squirmy.appearance`, per browser and not in the account, and applied to the page: the class `dark` on `<html>` (what Tailwind's `dark:` variant tests) and, for every theme but the default, a `<style id="squirmy-color-theme">` in `<head>` that sets the tokens. `startAppearance()` runs in `main.tsx` before the first render, then follows the system's scheme and changes made in other tabs. The saved value carries the theme's stylesheet too (saved again at start when a release changed the theme's colors), and `public/appearance.js`, loaded blocking from `index.html` before the bundle, applies the class and that stylesheet, so a reload does not flash the wrong colors. - **Color themes.** `COLOR_THEMES` in `lib/color-themes.ts`: Squirmy (the default), Pulpo, Ocean, Forest and Ember, each with `light` and `dark` colors named by role. Now Playing is a full-screen dialog. The player bar is a row of the layout, not fixed over the page, so pages leave no room for it; `--player-height` on `<html>` tells toasts and notices where the player ends. The sidebar has the navigation, the playlists (songs dropped on one of the user's own are added to it, on Liked Songs saved) and the account menu: Settings, Admin panel for admins, Log out. From 768 px the queue panel floats over the page's right side, modal over a scrim (a press on the page or Escape closes it), and from 1280 px it is a column beside it. Now Playing gives focus back to the control that opened it, and on a phone on its side (`short-landscape`, in `index.css`) puts its controls beside the artwork, lyrics or queue. - **Forms** validate with the contract schemas (`useFormSubmit`), show issues under their fields, and map known error codes onto fields.
- **Realtime.** `RealtimeProvider` opens one socket per signed-in user. `invalidate` and `changes` are collected for 100 ms (client-core's `RealtimeBatch`, which also drops keys a shorter one covers), then `applyChanges` (`realtime/apply-changes.ts`) patches every cached answer from the changes, keeping when it was loaded, and the named queries are refreshed once each. The player's `TrackStore` takes the same values (`useFreshSummaries` in `PlayerProvider`), so the queue and the player follow them too. Every reconnect refreshes all of them, and the shell shows a notice when the socket has been down for three seconds. The socket is in the context for `SessionClient`. It follows the page: `pagehide` and `freeze` close it, so the tab leaves the device list at once, and `pageshow` from the back/forward cache and `resume` open it again. A hidden tab stays connected and keeps answering the heartbeat, which runs from the socket's message handler rather than a throttled timer. When the page becomes visible or the browser comes online with no ping heard for 15 seconds (a laptop that slept), the socket is renewed.
- **Audio.** `WebPlayerEngine` alternates two `<audio>` elements, each through its own `GainNode`, so normalization can boost. When the browser refuses to start audio the entry goes to `error`, the player shows Play (its play/pause and Space call `unlock()`) and the shell offers "Enable audio", which does the same from the click. `EngineProvider` calls `warm()` on the first pointer or key press of the page, which opens the `AudioContext` before anything plays, so the first song is not held up by the output starting. `/dev/engine` drives it with tones from `scripts/dev-audio.mjs`; `scripts/e2e-engine.mjs` checks it against the contract in Chromium, `scripts/e2e-auth.mjs` walks the account flows against a fresh server, `scripts/e2e-admin.mjs` the admin flows (setup with a real folder, scans, reviews, Fix match, Organize on disk, the search index), `scripts/e2e-playback.mjs` playback on the demo library (transport, queue, likes, playlists, lyrics, gapless ends, two devices, a second user), `scripts/e2e-polish.mjs` a server started like the Docker image (setup with its configured folder, naming templates, search's top result, the queue showing a fetch as loading), and `scripts/e2e-imports-providers.mjs` adding music (uploads, the inbox, duplicates) and acquisition providers against the mock provider.

- **Data.** Pages read through the hooks in `api/queries.ts`, keyed by `queryKeys`, so the server's invalidations refresh whatever is on screen. Page queries are `silent` and the page shows its own skeleton, error and "Nothing here" (404, and an id that is not a UUID, which is never sent). A read's three states go through `QueryState` (`components/ui/query-state.tsx`): the skeleton until the first answer, then `LoadError` (what did not load, the server's message and **Try again**) in the place of the page (`variant="page"`, a level 1 heading) or of the one panel that failed (`section`, the default), so the rest of the screen stays usable; a failed refetch keeps the last answer. Views that take data as props get the error from `loadFailure` (`load-failure.tsx`). An album whose songs are being looked up asks again every 3 s for a minute (`useAlbum`), and its `refetch` starts another minute. Library lists page by cursor as they scroll. Hearts and wants are optimistic. A heart applies as the same `patch` change the server then sends the user's devices (`applyChanges`), so every cached copy of the entity shows it, and a failure sets it back; the lists it moves (the library's, Liked Songs, Home) follow the server's invalidation. Wants set `wanted` with `patchEntity`. While the server has the wantlist off (`SetupStatus.wantlistEnabled`, read by `useWantlistEnabled` and carried in `LibraryActions.wantlistEnabled`), no sidebar item, search destination, bookmark, menu entry or album-page line mentions it, and `/wantlist` goes home.
- **Cache and prefetch.** `api/persist.ts` keeps the query cache in IndexedDB (`squirmy-cache`), one record per origin and user for 7 days, at most 250 queries, paged lists cut to their first page, and only allowlisted roots (home, library, albums, artists, tracks, likes, playlists, wants, settings, history; never `me`, search, lyrics, admin or playback URLs). It is restored before the first render and every restored query is marked stale, so screens show the last answer and refetch at once. The record names its user, who seeds `me` and the setup status as placeholders (`updatedAt: 0`) that are refetched straight away; a null `me`, any 401 or signing out deletes it. A new build discards old records. `api/prefetch.ts`: `usePrefetch` starts an album's or artist's request on a 100 ms hover, a focus or a press (cards, track-row links, search results, the ⌘K highlight), and `AlbumPreview`/`ArtistPreview` draw the real header from a summary already cached while the detail loads.
- **Session.** `PlayerProvider` (inside the signed-in routes) runs one `SessionClient` on the realtime socket with the page's engine. `resolvePlayback` asks for the user's `qualityWifi` and the codecs `canPlayType` confirms (Opus only in Ogg); `setNormalization` follows the user's mode. A `TrackStore` hydrates queue, history and autoplay entries; the current track also has its own query so its heart follows likes. Commands send track ids, album ids and durations only, never `none` tracks; `on_demand` ones go as `preparing`. What can be heard comes from `player/listening.ts`: on the playing tab only the engine playing the current entry is sound, so `PlayerState.waiting` (the spinner) covers a fetch, the stream being resolved or buffered and a load that fails offline, and `blocked` a play the browser held back; on other devices it follows the session's `stalled`. Playback position is a `PositionClock` that reads `Listening.position()` on animation frames while there is sound, so only the clocks and the lyrics re-render; while waiting it stands where the music will start instead of counting through silence. A seek made while the current entry is `preparing` (the session ignores those) is kept there and sent once the entry is ready. Clear history hides the history at once and tells the session 5 s later, so its toast can undo it. Space and the arrow keys are left to a focused field, slider or menu, and to any dialog but Now Playing (`data-player-keys`). The provider also drives the Media Session (while this tab plays), the tab title, Space and the arrow keys, tells failures as toasts with client-core's `PlaybackNoticeWatcher` (a skipped song's notice waits 1.5 s and is dropped if the session stops meanwhile, so an outage shows only its stop notice; and skips a track the browser cannot play), and keeps the `TrackStore` fresh with `refreshFetchedTracks` and `refreshInvalidated`, so the queue, the player and the Media Session show a fetched song's album and cover.
- **Devices.** Each tab claims its device with a Web Lock on the id kept in `localStorage`: the first tab is the browser's device, a second one `<id>-2` under the same name, so tabs never play at once; a reloading tab waits briefly for its old page's lock and comes back as the same device. Names never carry a tab number: client-core `devices.ts` (`listedDevices`, `deviceLabel`) shows one row per browser, this browser's other tabs as "Another tab", the viewer's own device as "This browser" or "This iPhone", and a short id hint for two devices nothing else tells apart; web and iOS pickers both use it. The name (default from the user agent) is editable in the settings dialog and sent with a fresh hello (`SessionClient.rename`). While another device is active the shell shows "Playing on …" with "Play here", and the volume controls change that device's entry in `volumes`; the strip says "Paused on …" while the session is paused, and unmute goes back to the last volume heard on that device, whichever control muted it. Pointing at "Play here" (or this tab in the picker) calls `SessionClient.prepareTakeover()`, which resolves the current entry and has the engine buffer it as its preload, so the transfer that usually follows starts from that buffer. The devices picker (`components/player/Devices.tsx`) detaches this tab and rejoins (`detach`, `attach({ bringQueue })`), hides that where `canDetach` is false, and lists detached devices under "Playing separately" and never as transfer targets; while detached the player shows "Only on this device" where "Playing on …" would be.
- **Admin.** Pages in `pages/admin.tsx` (lazy) feed views in `components/admin/`. `AdminLayout` is one `PageHeader` titled Admin whose links are the sections (the review queue's carries the count of open reviews), with the server's version under each page. Scan progress comes from `scan.progress` events and invalidations; Organize and index imports report progress only in the database, so those screens poll while one runs. `components/admin/FixMatch.tsx` is the entry point other screens use for Fix match (the album page's menu offers it to admins); it loads its dialog on demand. Settings fields save on blur through `DraftField`, which shows the server's refusal under the field. Providers (`/admin/providers`) lists providers, the acquisition policy and every request, refreshed by `acquisition.updated`.
- **Adding music.** `/imports` (lazy, `pages/imports.tsx`) is for admins and members who may upload. `lib/upload.ts` sends the files picked or dropped (folders walked through directory entries, paths kept) a few per request through `imports.addFiles`, which uses `XMLHttpRequest` for progress and reads each file from disk as it goes; it pauses by aborting the request in flight, and a file the server already had is counted as sent on resuming. The upload belongs to the tab, not the page, and the page follows the import through `import.updated` to its albums (`GET /imports/:id/albums`).
- **Artist pages.** `ArtistView` draws each of `ArtistDetail.sections` as one `Rail` row with **See all** when its `total` is larger than its items (a key the app does not know shows under the section's `title`, with no link); a server that sends no `sections` gets `albums` grouped by type. **See all** opens `/artist/:id/releases/:section` (`ArtistReleasesView`), an infinite grid over `GET /artists/:id/releases` (`useArtistReleases`, under `queryKeys.artist(id)`). While `detailPending`, `useArtist` refetches every 5 s (at most 120 times) and the page says "Loading discography…".
- **What plays.** Every row, card and page uses client-core's rules (`isPlayable`, `albumPresentation`, `albumNote`, re-exported by `lib/catalog.ts`) with the viewer from `useViewer()`, which `OnDemandProvider` provides. Music that plays looks the same wherever its file is: no badge, no count, no word for fetching. What does not play is gray and says "Not available". A current entry that is `preparing`, or any the tab is still waiting to hear, looks like buffering (the spinner on its row and the play button) and after 8 s of waiting the player's subtitle says "Still loading…" (`use-still-loading.ts`). `OnDemandProvider` refreshes a track's own query when its fetch ends; its rows everywhere follow the server's availability `changes`, and the row of a current entry that failed is unavailable at once (`NowPlaying.failed`) rather than highlighted. The heart is the one library control (`SaveHeart`, and `librarySaveEntry` for the menu entry that mirrors it, both worded by client-core's `librarySave`): `LibraryActions.setSaved` patches `liked` (and `inLibrary` when saving) in every cached answer at once, offers Undo, and puts it back when refused. A collection item has the heart too; it only shows the viewer's own save. Track rows, the player bar and Now Playing link each credited artist to its own page (`ArtistLinks`).
- **Search.** `api/use-search.ts` runs `/search/library` (60 ms after typing pauses) and `/search/catalog` (250 ms) and merges them with client-core's `mergeSearch`, for the search page and ⌘K alike. The two are ranked together, so the list waits for the catalog's answer, or `CATALOG_WAIT_MS` (700 ms) after the library's, then shows what it has with a spinner at its end, and a later catalog answer joins where its rows rank. An answer is shown only for the query it answers; meanwhile the last results stay, faded, with nothing Enter would open. A filter's list is `useSearchPages`: pages of 30 of one kind (`type`, `offset`) from both routes, ranked together page by page, which end when a page adds nothing new (an older server ignores both parameters).

Catalog data reaches views through props typed with the contracts; session state and user actions come from `PlayerContext` and `LibraryContext`, whose providers are the only code that talks to `SessionClient` and the API. `/dev/kitchen-sink` shows every component state on the fixtures; the `/dev` pages exist only in development builds.

**Mobile** (`apps/mobile`): the existing Expo app. `expo-audio` implements `PlayerEngine`. The token lives in SecureStore. Screens read through TanStack Query with a persisted cache.

  src/streamingCache/    StreamingCache (prefetch, eviction), its plan (model.ts), SQLite index and file adapters, the provider, Settings' Storage section

- **Accounts.** `AccountProvider` owns the auth state: it restores the stored session and opens the app from it at once (the `me` query confirms it in the background), creates the API client with the bearer token, and returns to sign-in on a 401. The token and device id go through `Keychain` (`src/account/keychain.ts`), which never rejects: what the keychain refuses is kept in memory for the launch, and the app says once that the next launch will need a sign-in. The server's name, version, invite rule and wantlist switch are read again from `GET /setup/status` whenever a server is chosen, and when the server invalidates it, so they stay current. While the wantlist is off (`useWantlistEnabled`), no screen, menu or Home row mentions it.
- **Data.** Query keys come from `queryKeys`; lists are infinite queries over the cursor pages. The cache is saved to app storage (expo-sqlite, through its async API, ten seconds after data changes and when the app leaves the screen) per server and user, and removed on sign-out. It keeps the first page of each list and the 40 most recent album, artist, playlist and track pages from the last day, one line of JSON per query in two values: the lists, read before the splash hides, and the detail pages, read one per task after the first screen shows. A query over 512 KB is not saved, and the detail pages stay within 4 MB together. Every response that carries track summaries primes one `TrackStore`, which hydrates queue entries and the lock screen. Hearts apply at once through a queue kept in app storage (`LikeQueue`): every cached answer that shows the item is patched through `applyChanges`, as the server's `patch` will be (and Liked Songs gains or loses the track), the lists that move follow the server's invalidation, one that cannot reach the server is sent again on the next connection or, after a server error, with backoff, only the last change to an item is sent, and one the server refuses rolls back with a notice. The playback session is saved in two halves, the queue half only when it changed.
- **Realtime.** `RealtimeProvider` opens one socket per signed-in session with `auth.token`, over WebSocket with a fallback to long-polling. `invalidate` refreshes the named queries, collected for 100 ms (and refetches a changed track's like); the echo of a change this device made only marks them stale. `changes` are applied at once (`data/changes.ts`, the web app's rule) and patch the `TrackStore` too; a heart `patch` from another device replaces the heart `LibraryProvider` remembered for that item (`remembersToDrop`), unless a change made here is still on its way, and a heart it sent is forgotten once the server has it, so later changes from other devices show. A reconnect marks everything stale and refetches what is on screen; lists not on screen keep their first page. Returning to the app refetches nothing by itself. The socket is renewed when the app returns after being suspended (no server ping for 15 seconds) and when the network type changes. In the background it stays open only while this phone plays (`BackgroundPresence`, `data/presence.ts`): with nothing playing it closes 1.5 seconds after the app leaves the foreground, since iOS is about to suspend it and a suspended app should not be listed, and opens again when the app returns or playback starts here from the lock screen. A socket closed that way is not offline. A refused handshake rechecks `me`, so a revoked session signs out. The app is *offline* once the socket has been down for 2.5 seconds (a new socket gets 6 seconds to connect, unless a request fails first) and no request sent since it went down was answered; an answered request keeps the app online for 30 seconds more (`offlineAt`, `src/data/reachability.ts`).
- **Playback.** `PlaybackProvider` runs a `SessionClient` on that socket with `ExpoAudioEngine` (`canBoost: false`) and the user's normalization mode. `resolvePlayback` asks for the entry's album, the quality setting for the current network (Wi-Fi or cellular) and the codecs AVPlayer decodes. Components read the session through `usePlaybackState`; the position is polled with `usePosition` by the few components that show it. While another device is active the engine is stopped and the lock screen cleared. An engine error skips the track with a notice, or pauses when the next one fails too.
- **Volume.** On iOS this phone's volume is the system output volume. `SessionPlayer.systemVolume` keeps this device's `volumes` entry out of the engine's gain (only normalization applies), the local `SquirmySystemVolume` module (in `modules/now-playing`) gives the level, its changes and an `MPVolumeView`-backed slider and setter, and `syncSystemVolume` (`src/player/systemVolume.ts`) keeps the session in step: button and slider changes are reported (throttled), a change from another device moves the system volume while this phone plays (not within a second of the phone's own report, so late answers do not pull it back), and becoming the playing device reports the system level. Where the module is missing (Android, an older build) the session volume drives the engine as before.
- **Fetched songs.** A summary taken while its song was on demand has no album or cover; when an entry turns from `preparing` to `ready` the provider refreshes it in the `TrackStore` (client-core's `refreshFetchedTracks`), so the mini-player, Now Playing and the lock screen show the cover.
- **Tab bar.** With the system's glass tab bar, `BrowseStack` draws `TabBarEdge` over its pages: content scrolling under the tab bar and the mini-player blurs and fades into the page colour, so their labels stay legible. `useTabChrome` (`src/tabChrome.ts`) gives the bottom padding a page needs to scroll its last row clear of both.
- **Lock screen.** Buttons arrive through `connectNowPlaying` as callbacks; the provider turns them into session commands, never engine calls. The system's own pause (calls, unplugged headphones) becomes a session `pause`. The star (MPRemoteCommandCenter's `likeCommand`, which iOS draws as Apple Music's favorite) is the track's heart: `favoriteState` gives its state from the track summary and the provider's changed hearts, it is sent again when either changes (only the command, never the now playing info, so the elapsed time stays put), and a tap goes through `setLiked`, as the in-app heart does.
- **Downloads.** `DownloadManager` keeps each recording once per account, whatever albums, playlists, Liked Songs or single-song downloads list it, and drops it when none does. Files come from `GET /tracks/:id/playback?download=1` with the user's download quality, through `expo-file-system` background download tasks, into `Documents/downloads/` under a fresh UUID name; a completed file must match the announced size. Three run at a time; failures retry after 15 s, doubling, and are marked failed after five tries (a 404 at once); on cellular with Wi-Fi only they pause, keeping their resume data, and say so. The index is `downloads.db` (expo-sqlite): one row per account and recording with its file, quality, size, album context and times, plus the track summary, the descriptor (normalization) and retry state as JSON; collections keep their track ids and the album or playlist as last seen, so their pages open offline. Covers are kept at 600 px. Rows are written before files are deleted, and a launch sweep deletes files no row names and re-queues rows whose file is missing or short. Syncs (on reconnect, every six hours, and after `invalidate` of playlists, likes or albums) add tracks new to a downloaded collection, drop removed ones, flag what the server no longer has, and, at most daily per file, re-download a file the server replaced (`fileId` changed) while the old one keeps playing. Sign-out and switch-server remove the account's downloads after saying so.
- **Downloading what the server does not have.** A download takes whatever plays for the user (`isPlayable`): for a requester (`canFetch`) an `on_demand` song gets a row in state `fetching`, and the manager asks for it with `POST /tracks/:id/acquire?origin=download` (an album downloaded whole is asked for once with `POST /albums/:id/acquire?origin=download`), which fetches without adding to the library and waits behind play and prefetch on the server. Requests go one at a time, 600 ms apart (the routes allow 120 a minute), and stop for 30 s when the server answers 429. The server announces an arrival or a miss with an `invalidate` of the track; `DownloadsProvider` gathers those for a second and `refreshTracks` reads their summaries: a `server` song is queued and downloads, a `none` one becomes `unavailable`. With no word the song is asked for again after a minute, doubling to 15 minutes (the answer says it is there, `409 already_available`, or that it cannot be had, 403 or 404 or a job that already failed), and it becomes `unavailable` after eight requests. These states, the request count and the next time to ask are in the row's JSON, so a relaunch carries on. Asking needs only a connection; Wi-Fi only and the storage limit hold back the download after it. Someone who may not fetch downloads only what the server has, as before. A collection keeps every track id it lists, also those with no row, so its status counts every song: "Downloading 2 of 3" while a song is being got, "Downloaded" only when all of them are on the phone, and otherwise "2 of 3 downloaded · 1 not available" (`downloadStatus`, `model.ts`), with Retry when a request could change it. A sync queues an `unavailable` song once the server has it.
- **Streaming cache.** `StreamingCache` keeps what was streamed and the next two `ready` entries in `Caches/streaming/` under a per-device limit (default 2 GB), indexed per account, recording and quality in `streaming-cache.db`. `plan` (`model.ts`, pure) chooses fetches once the outlook from `followSession` has been still for a second: on Wi-Fi also the stream being played, fetched a second time because `expo-audio` exposes no bytes; on cellular one at a time at the cellular quality, none with Data Saver; nothing while another device plays. Eviction is least recently played first and spares the entries about to play. `resolvePlayback` (`resolve.ts`) tries a download, a cached copy of at least the quality that would stream, the server, then a lesser copy; offline it takes a lesser copy without asking the server. Copies near the front are checked against the server daily. A launch drops purged rows, stray files and other accounts' rows; sign-out and switch-server empty it.
- **Search.** The Search tab is a `FlatList` of the ranked list (`useSearchList`, `src/library/useSearchList.ts`): song rows are the song lists' own, other results are `CollectionRow`s with a long-press menu and an ellipsis (`actions`). It waits for the catalog's answer or `catalogWaitMs` after the library's, keeping the last results on screen, and `keepOrder` keeps rows already shown for a query in place when the same query is answered again, so nothing moves under the finger. The segmented filters page one kind through `useSearchPages`. Recent searches and results opened from Search are kept in the app's local storage per server and account (`useRecentSearches`).
- **On demand.** `useAvailability().canPlay` is client-core's `isPlayable` plus the phone's own files (downloads and the streaming cache); offline only those play. A playable track looks the same wherever its file is (no mark); a gray one says "Not available", or offline "Not downloaded" (`unavailableReason`). Fetching looks like buffering: `ExpoAudioEngine` counts a player that says it plays while its clock has stood still for 1.5 s as buffering (AVPlayer does that for a stream that has only begun to arrive), and `watchLoading` (`src/player/loading.ts`) follows how long the current entry has waited for audio (`preparing`, or the session `stalled`) and gives `useLoading`/`useTrackLoading` a phase: after 300 ms the play buttons and the current row show the spinner, after 8 s the subtitle reads "Still loading…". Queue rows show the artist whatever their state, "Not available" when failed. Failures are told with client-core's `PlaybackNoticeWatcher`, in the same words as the web app, through the top notice (its quieter second line carries a notice's `detail`).
- **Browse pages.** An artist or album page draws its header at once from the summary of the tile or row that opened it (`findArtistSummary`, `findAlbumSummary` in `src/data/`), and an artist page answered with `detailPending` is asked for again every 3 s for a while. Rails are virtualized horizontal lists (`CollectionRail`), since each tile is a native view of its own; an artist page shows the server's `sections` (`releaseGroups`, `src/data/artists.ts`; from an older server, `albums` grouped by type, at most 20 tiles per heading) and 5 top songs. **See all** opens the `releases` or `songs` page of the tab's stack: a section's releases page from `GET /artists/:id/releases` (`useArtistReleases`), an older server's from the cached answer. Release tiles say `releaseSubtitle` (year and type, from client-core, as on web). Album pages put a heading over each disc of a multi-disc album and end with `formatReleaseDate` and a ℗ line; rows by the album's artist leave the artist out, and the menu leaves out Go to album. Library's **Find in your library** asks `/search/library` and keeps only songs and artists with `inLibrary` (albums carry no such flag yet).
- **Library.** The library is the server's collection plus what the user hearted, and only the heart adds: on track rows, album and artist pages and the player, plus one menu entry worded by client-core's `librarySave` ("Save to library" / "Remove from library"), the same rule as the web app's. A collection item has the heart too. A track's menu has a **Go to** entry for each credited artist. `LibraryProvider.setLiked` shows the change at once on every cached copy, confirms it with an Undo notice, queues it while offline, sends the changes for one item in order, and sets it back with a notice when refused. Album tiles are dimmed per `albumPresentation`, artist tiles never online; album pages show `albumNote` to viewers who can't fetch music, and the wantlist only on what the viewer can't play.
- **Offline.** `resolvePlayback` returns a downloaded file's descriptor (with its normalization) before asking the server, so downloads never stream; `SessionClient.forgetPlayback()` runs when a download arrives or goes, and `forgetPlayback(trackId)` when a cached file does. Offline, only downloads and cached tracks are playable (`canPlay`): other tracks are gray, as are albums, artists and playlists with nothing downloaded, actions that need the server are hidden, and a current entry that is neither downloaded nor cached is skipped. The session is saved (`SessionClient.save()`) with the summaries of its entries, and a relaunch restores it paused; commands made offline reach the server on reconnect.

## Testing

- `vitest` everywhere. A test file sits next to the code it tests as `*.test.ts`.
- **Database tests** call `useTestDatabase()` from `src/test/database.ts`, which clones a migrated template database for the file. They need `SQUIRMY_TEST_DATABASE_URL` (default `postgres://localhost:54329/postgres`). CI provides a Postgres service.
- **Audio fixtures** are generated with ffmpeg by `src/test/audio.ts`: short, very quiet tones with real tags. No real music is committed.
- **HTTP fixtures** for external services are recorded JSON; no live calls in tests. A hand-written fixture may list `request.headers` that must match too, for requests that differ only in a header.
- **Before a change is done:** `npm run build:packages && npm run typecheck && npm run lint && npm test` all pass.

## Git

- Conventional Commits: `type(scope): imperative summary`. `feat` and `fix` drive releases.
- Branches are named like commits: `feat-library-scan`, `fix-range-requests`.
- Pull requests target `dev`. `main` receives merges from `dev`; semantic-release tags a version on every push to `main`.
- Every push to `main` is deployed to the test environment at once, without waiting for CI. So `main` changes only through a `dev` → `main` pull request whose checks have passed, never by a direct push. A fix made on `main` anyway is merged back into `dev` right away.
- When CI fails on `main`, it opens an issue. Either fix the problem on `dev` and open another `dev` → `main` pull request, or revert the merge commit on `main` (and merge that revert back into `dev`).
