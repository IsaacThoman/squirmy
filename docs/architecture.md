# Squirmy architecture

This is the technical contract for the codebase. [plan.md](./plan.md) says what the product does; this says how the code is laid out and which conventions every module follows. When code and this document disagree, fix one of them in the same change.

## Workspace

```
apps/mobile            @squirmy/mobile        Expo app
apps/web               @squirmy/web           Vite + React web app
apps/server            @squirmy/server        Fastify API, worker, realtime
packages/contracts     @squirmy/contracts     zod schemas and types for every API
packages/client-core   @squirmy/client-core   session reducer, session client, API client
adapters/kit           @squirmy/provider-kit  the provider side of the acquisition protocol
adapters/cold-storage  @squirmy/adapter-cold-storage  reference provider: a folder of your own files
adapters/mock          @squirmy/adapter-mock  provider for tests and demos: quiet tagged tones
```

npm workspaces, Node 22.13 or newer, TypeScript 6, ESM everywhere except the Expo app. `contracts` and `client-core` compile to `dist` with `tsc`; consumers import the built output, so run `npm run build:packages` (or the packages' `dev` watchers) before typechecking or running anything else. The adapters build the same way (`npm run build:adapters`); the root `typecheck`, `test` and `build` scripts build both. The server image installs only the server's workspaces; `adapters/cold-storage` and `adapters/mock` are separate services with their own READMEs, and `adapters/kit` is the library they share (a workspace package, not published to npm).

## Code conventions

- Relative imports end in `.js` in server and packages (NodeNext). No path aliases in server or packages.
- **Contracts first.** Every request and response body is a zod schema in `packages/contracts/src/<domain>.ts`, exported with its inferred type under the same name. Routes parse input with the schema and return objects that satisfy the response type.
- **Units.** Durations are integer milliseconds. Timestamps on the wire are ISO 8601 strings; the session protocol uses epoch milliseconds. Gains are dB; peaks are linear.
- **IDs.** UUIDv7 from `newId()`. Artwork asset ids are UUIDv4 from `newPublicId()`.
- **Errors.** Throw `AppError` (or the helpers in `lib/errors.ts`). The response body is `{ error: { code, message, details? } }`. Codes are stable snake_case strings.
- **Names in the API.** A *track* is a recording. `TrackSummary.id` is the recording id. An *album* is a release group. Clients never see files, releases or recordings as separate concepts, except `fileId` in the playback descriptor.
- **Text matching.** Use `matchKey`, `creditKey` and `sortKey` from `lib/text.ts` for every normalized comparison and for the `*_key` columns.
- **No module-level side effects.** Nothing connects, listens, schedules or reads config at import time. `db` connects on first use.
- **Comments** explain why, not what. No commented-out code.

## Server

```
apps/server/src/
  index.ts              entry: migrate, then start API and/or worker by SQUIRMY_ROLE
  app.ts                buildApp(): Fastify instance, plugins, auth hook, module routes
  config.ts             zod-parsed environment
  database/             client.ts (lazy db), locks.ts (session locks), schema.ts, migrate.ts
  lib/                  auth, errors, ids, text, crypto, settings, version, ffmpeg, http
  jobs/                 pg-boss wrapper: jobs.define, enqueue, schedule
  realtime/             socket.io server, rooms, publish/invalidate/publishChanges
  modules/<name>/       one folder per module; see the table below
  test/                 database harness, audio fixtures, factories, http fixtures
```

- **Boot.** `index.ts` migrates, runs each module's `jobs` hook in worker roles, starts jobs, then in API roles builds the app, attaches realtime and runs the `realtime` hooks, then runs every module's `start` hook and listens last. A failure at any step, a migration included, logs `[squirmy] failed to start` and undoes the steps done so far. SIGTERM and SIGINT undo them in reverse, so module `stop` hooks run before the job system stops and can still enqueue; the process exits after 20 seconds whatever is left, inside the 30 second stop grace period `compose.yaml` sets (Coolify's default too; plain `docker stop` waits only 10). A long job that cannot finish in that time checkpoints instead and is resumed by the next worker: the search index import does (see [Restarts](./local-search-index.md#restarts)). A worker-only process opens no HTTP port.
- **HTTP.** Helmet with a Content-Security-Policy that allows scripts, connections and media from the server only (no inline scripts, no `eval`: the web app sets zod's `jitless` in `zod-config.ts`), cookies, multipart (streamed, up to 16 GiB per file), and CORS only for the Vite dev origins outside production. Each module's `routes` is registered in its own encapsulated scope under `/api/v1`.
- **Compression and revalidation.** `@fastify/compress` sends brotli (quality 4) or gzip for JSON, XML, JavaScript, CSS, SVG and text of 1 KiB or more; audio, images and ranged responses go as they are. `lib/conditional.ts` gives every successful JSON GET under `/api/v1` a weak `ETag` (a hash of the body) and `Cache-Control: private, no-cache`, unless the route set its own, and answers a matching `If-None-Match` (compared weakly) with an empty 304.
- **Web app.** When `SQUIRMY_WEB_DIST` is set the built app is served, with `index.html` as the fallback for unknown GET paths outside `/api`, `/rest`, `/socket.io`, `/health` and `/ready`. Hashed files under `assets/` are cached as immutable.
- `GET /health` answers without touching anything; `GET /ready` checks the database.
- **Database connections.** Each process has a query pool of `SQUIRMY_DB_POOL_SIZE` connections (10; 4 under test, so tests catch work that assumes more), pg-boss's own pool of 6 (3 under test), and one connection for session locks. Nothing keeps a pooled connection while it waits for other work that needs one: a transaction runs only its own statements (no network call, file copy, job or query on `db` inside it), and a lock that outlives a statement (an import run, an organize batch in a root, the inbox watcher) is taken with `withSessionLock` or `trySessionLock` from `database/locks.ts`, on the lock connection. Holders used to reserve a pooled connection each, and an import keeps its lock while identification waits for probe, ingest and matching jobs, so four imports took a 4-connection pool and waited forever for connections they held themselves. A second take of a key this process holds fails at once, as it would in another process. Work that keeps a connection for hours (the search index import's COPY) opens a client of its own. Take `squirmy:library-catalog` before `squirmy:matching:apply` or the exclusive `squirmy:search-stubs` cleanup lock. Search takes the stub lock in shared mode, then artist identity locks, then album and recording identity locks. Each set of identity locks is sorted by lock number.

### Modules

Each module is a folder under `modules/` that exports one `ServerModule` from its `index.ts`. `modules/index.ts` lists them all statically. A module only edits files inside its own folder, its own contracts file, and its own tests.

```ts
export type ServerModule = {
  name: string
  /** HTTP routes. Called with an instance already prefixed with /api/v1. */
  routes?: (app: FastifyInstance) => void | Promise<void>
  /** Routes that need their own prefix (Subsonic's /rest). Called with the root instance. */
  rootRoutes?: (app: FastifyInstance) => void | Promise<void>
  /** Job handlers. Called in processes whose role includes the worker. */
  jobs?: (jobs: JobRegistry) => void | Promise<void>
  /** Socket handlers. Called in processes whose role includes the API. */
  realtime?: (realtime: Realtime) => void | Promise<void>
  /** Long-running loops (file watchers, schedulers). `stop` must undo `start`. */
  start?: (context: { role: 'all' | 'api' | 'worker' }) => void | Promise<void>
  stop?: () => void | Promise<void>
}
```

### Seams between modules

Modules reach each other in three ways, in this order of preference:

1. **Database state.** A module finds its own work by querying for rows that need it (files with no loudness, albums still `pending`). Sweeps make this robust to ordering and restarts. A module may also hold off on work by another module's recorded state: scans skip `_Incoming` folders of imports still moving files, and matching waits for an import to decide its duplicates.
2. **Jobs by name.** A module may enqueue another module's job (`enqueue('loudness.measure', { fileId })`). The job name and payload are that module's public interface.
3. **Seam functions.** A few direct calls are declared up front as seams: `enrichment/detail.ts` (`ensureAlbumDetail`, `ensureArtistDetail`, `artistRadioTracks`), `acquisition/coverage.ts` (`onDemandRecordings`, `requestRecording`), `radio/suggest.ts` (`suggestAutoplay`), `sonic/profile.ts` (`sonicPoints`, `sonicNeighbours`, `fileTimings`, `sonicProgress`) with `sonic/vectors.ts` (`sonicIndex`) and `sonic/sweep.ts` (`analyzeSoon`), and `radio/sonic.ts` (`artistSoundAffinity`: how alike artists sound, for the mixes; null for now). The owning module fills them in; callers never change. In the other direction, sessions exports `onPlayStart` (`sessions/plays.ts`), a subscription to plays opening on the active device, which scrobble uses for "now playing".

Beyond those, modules call each other's exported functions directly where sharing beats a copy: the catalog read helpers (`catalog/sql.ts`, `catalog/availability.ts`, `catalog/redirects.ts`, `catalog/summaries.ts`, `catalog/explicit.ts`), `library/cleanup.ts`, `matching/merge.ts`, organize's planner and mover, and `search/keys.ts` are used across modules. Import them from the owning module and keep their signatures stable; the owner changes them with their callers.

### Configuration

Environment variables are parsed in `config.ts`; see that file for the full list. The ones a self-hoster sets: `DATABASE_URL` (required), `SQUIRMY_DATA_DIR`, `SQUIRMY_LIBRARY_PATHS` (read-only roots) and `SQUIRMY_MANAGED_LIBRARY_PATHS` (managed roots), `SQUIRMY_INBOX_PATH`, `PORT`, `PUBLIC_URL`, `TRUST_PROXY`, `SQUIRMY_ROLE`. `SQUIRMY_SECRET` is generated into the data directory on first boot when unset.

Operator settings that change at runtime (provider toggles, API keys, thresholds) live in the `server_settings` table and are edited in the admin UI. Shape: `ServerSettings` in contracts. Secrets are stored encrypted under separate keys and never returned. Feature switches clients need before signing in, such as `wantlistEnabled` (default off), are also reported by `GET /setup/status`; changing one invalidates `queryKeys.setupStatus()` and what it changes for every client.

### Artwork

Images are rows in `assets`. `storeImage(bytes)` stores an image now, de-duplicates by content, and queues `artwork.render` for a new one, which writes the 96, 300 and 600 px renditions from one read of the original. `GET /art/:id/:size` also answers `:size.webp`, which both apps use (client-core's `artworkUrl`) so a CDN that caches by extension (Cloudflare) keeps art at the edge; responses are `public, max-age=31536000, immutable` with an `ETag` matched weakly. `remoteImage(url)` only records where an image lives; it is downloaded the first time `GET /art/:id/:size` asks for it, so search results for music you do not own can show covers without downloading every one. A failed download answers 404, is not cached, and is retried after an hour. A sized Cover Art Archive front (`.../front-500`) that answers 404 is fetched as the original (`.../front`, `coverart.originalFront`): archive.org derives the thumbnails some time after an upload, so a release of the last few days has only the original. When the source answers 404 or 410 (a release group the Cover Art Archive has no cover for), the asset is also unassigned from the albums and artists showing it, so their summaries stop handing out an id that cannot be served, `invalidate` names those albums and artists (from whichever process asked for the image), and each album gets `enrichment.cover`, which picks another cover; the discography does not offer that cover again for a week. Summaries leave out an asset that is `missing`, or `failed` and not yet due for a retry (`servable` in `catalog/summaries.ts`); Subsonic applies the same rule to its `coverArt` fields, image URLs and `getCoverArt` by entity id (`servableArt` in `subsonic/sql.ts`).

Lost originals rebuild themselves (`artwork/recover.ts`). When a file under `assets/` is gone, `readOriginal` (used by renditions and Subsonic's `getCoverArt`) reads it back from disk while the request waits: the folder image of a `folder:` source, or the pictures of the source file and of any present file whose `embedded_art_asset_id` it is. Only bytes with the stored SHA-256 are accepted, so an id never shows a different picture. A URL source is queued as `artwork.recover` and the request answers 404 without cache headers; the job downloads it again (a `remote_url` asset goes back to `remote` and is fetched as on its first request; any other must match its hash). An asset nothing rebuilds is `missing`, answers 404 at once, and is left alone. `artwork.sweep` (daily, 04:40) queues assets whose file is gone, `missing` assets whose file is back, and `missing` assets last tried a week ago.

### Authentication

- A session token is 32 random bytes, base64url. Only its SHA-256 is stored (`auth_sessions.token_hash`). Sessions last 180 days, sliding.
- Browsers get it in the `squirmy_session` cookie (httpOnly, SameSite=Lax, Secure when the request is HTTPS). Native clients send `Authorization: Bearer <token>`. The socket takes the same token from the cookie or from `auth.token`.
- Setup, login and register return `{ user, token }` to every client. A request with the header `X-Squirmy-Client: web` also gets the cookie; `GET /auth/me` renews it. Passing a `device` upserts the `devices` row.
- An `onRequest` hook resolves the token for `/api` routes and sets `request.user` (or null) and `request.authSessionId`. `/rest` authenticates each request with Subsonic credentials instead. Route code calls `requireUser(request)` or `requireAdmin(request)` from `lib/auth.ts`.
- **CSRF.** A cookie-authenticated request that is not GET/HEAD/OPTIONS must carry the header `X-Squirmy-Request: 1`. Bearer requests are exempt.
- Passwords are argon2id. Login is rate limited per address. Failed logins are counted before the password check (and taken back on success) per username and address, per username and IPv6 /48, and per username overall, where addresses with a recent success are exempt (`lib/failures.ts`); so concurrent attempts cannot slip past, a correct login never uses a budget, and one client cannot lock an account out for everyone. At most two argon2 runs at once (`withHashSlot`), with a bounded queue. Setup and register are limited per address, password changes per user. Subsonic has no lockout. Addresses are keyed by `lib/proxy.ts` `addressKey` (IPv6 per /64). Counters live in the API process's memory.
- Logging out, changing a password (other sessions), and an admin disabling a user or resetting their password end the affected sessions and close their sockets.
- App passwords for Subsonic clients are random secrets stored AES-GCM encrypted (Subsonic token auth needs the clear text) plus a SHA-256 `key_hash` for `apiKey` lookups. `modules/auth/service.ts` exports `verifyAppPassword` and `findAppPasswordByKey`. Creating one needs the account password, at most `APP_PASSWORD_LIMIT` (50) per user; a password change, an admin reset and disabling the account delete them (`revokeAppPasswords`). Devices are recorded through `rememberDevice`. Recording a new device also forgets the user's devices not seen for 180 days (as long as a session lasts) and keeps at most the 100 most recently seen.
- `lib/crypto.ts` derives purpose-specific keys from the root secret with HKDF and exposes `hashToken`, `sign`/`verify` (HMAC-SHA256) and `encrypt`/`decrypt` (AES-256-GCM, base64url output).

### Jobs

`jobs/` wraps pg-boss. Modules never import pg-boss directly.

```ts
jobs.define('library.probe', { concurrency: 4 }, async (data: ProbeJob) => { … })
await enqueue('library.probe', { fileId }, { singletonKey: fileId, priority: 0 })
await schedule('library.scan-all', '0 4 * * *')
```

- Queue names are `<module>.<verb>`.
- Handlers are idempotent: running one twice leaves the same result.
- `enqueue` accepts a transaction (`{ tx }`) so a row and its job commit together. It goes through pg-boss's Drizzle adapter, so the job insert runs on the caller's transaction; there is no outbox.
- `singletonKey` makes a duplicate a no-op while a job with that key is queued, retrying or active. Queues use pg-boss's `exclusive` policy and keyless jobs get a unique key, so only keyed jobs are deduplicated.
- A definition can choose `policy: 'stately'` instead: one queued and one active job per key, so a request made while a job runs is kept as a single follow-up (`library.ingest` uses it). The policy is fixed when the queue is created.
- `enqueueMany(name, items)` inserts many jobs in one statement with the same deduplication.
- Each concurrency slot is its own pg-boss worker and is woken as soon as its job finishes, so a backlog drains continuously rather than waiting out pg-boss's 30 second notify backstop between jobs.
- NOTIFY wakes workers when a job is inserted, not when a deferred one (`startAfter`) becomes due, so `enqueue` also wakes this process's workers for that queue just after the start time; a deferred job enqueued by another process still waits for the next poll.
- Failures retry with exponential backoff (default 3 retries). `timeoutSeconds` fails a job that runs too long.
- Every process starts pg-boss: `index.ts` calls `startJobs({ work })` with `work` true for worker roles. Modules' `jobs` hooks run only in worker roles; a process that enqueues a job it has no definition for creates the queue on first use.
- `getQueueStats()` counts jobs live; `GET /admin/jobs` returns it.
- Tests call `startJobs({ work: true })` and then `drainJobs()`, which resolves once no job of a defined queue is ready or active, running retries without waiting out the backoff.
- Priority orders jobs within one queue only. Each queue has its own worker slots, so heavy queues are bounded by their `concurrency` (loudness 1, analysis 2, sonic analysis 1) rather than by priority. Background sweeps and safety-net jobs use negative priorities so on-demand jobs of the same queue run first.

### Realtime

`realtime/` owns the socket.io server. The session protocol is specified in `packages/contracts/src/session.ts`.

- `startRealtime(app)` attaches to the Fastify server before it listens; closing the app closes the socket server. Messages of 1 KiB or more are deflated (`perMessageDeflate`), mostly for `session:queue`, which carries the whole queue (older clients get it on every queue change; current ones only as a checkpoint, see "Sessions").
- The heartbeat is socket.io's ping, every `HEARTBEAT_INTERVAL_MS` (5 s), with `HEARTBEAT_TIMEOUT_MS` (10 s) to answer (both in the session contract), so a socket that stops answering closes 10 to 15 seconds after its last answer, rather than after socket.io's default 45. Clients take the timings from the handshake, older ones included. Device presence rides on it (see "Sessions").
- The handshake takes the session token from `auth.token` or the `squirmy_session` cookie and is refused without a valid one. With the cookie, an `Origin` header must match the request's `Host`, `PUBLIC_URL`, or (with `NODE_ENV=development`) the Vite dev server. A socket is disconnected when its session expires; messages are capped at 1 MB.
- Each socket joins the room `user:<id>`. Admin sockets also join `admins`. Handlers passed to `onConnection` run after that; register socket listeners before the first `await`.
- `publish(target, event)` and `invalidate(target, keys)` are callable from any process. They `NOTIFY squirmy_events` with a JSON payload; the API process `LISTEN`s on a dedicated connection and forwards to rooms. `target` is `{ user: id }`, `'admins'`, `'all'`, or a list of them, which reaches each socket once however many of them it is in (an admin is in their own room and in `admins`). Keys that do not fit in one notification (8000 bytes) are split across several. `disconnectSockets(userId, { only | except })` closes sockets of revoked sessions the same way.
- `time:sync` is answered here; the `session:*` events belong to the `sessions` module.
- Two kinds of message tell open screens what changed, both from any process and both dropping the API process's cached reads (see "Catalog read side") at once in the calling process and in the API process when the NOTIFY arrives, before the clients are told:
  - `invalidate(target, keys)` names lists whose members or order changed (the library's lists, Home, Liked Songs, the playlists, admin screens), with keys from `queryKeys`; clients refetch them.
  - `publishChanges(target, changes)` names entities and what changed about them (`EntityChange`, `packages/contracts/src/realtime.ts`), sent as `changes`: `availability` (new availability of tracks and albums, to `all`), `patch` (a user's `liked`, `wanted`, `inLibrary` or `library` on one entity, to that user only), `updated` (only the entities' own pages show it) and `deleted`. Clients set what a change carries on every cached copy of the entity in place, refetch the entity's own page for `updated`, and drop a `deleted` one's; no list moves and no search runs again. Changes that do not fit in one notification are split. `changeKeys` names the cached reads each drops.
- Every mutation that changes what another open screen shows says so with one of them, as narrowly as it can:
  - **Availability.** Whatever changes whether a recording plays (a delivery, a miss, a job that failed for any `EntryFailure`, a request nothing covers, a provider answering, recovering or being reconfigured, an eviction) calls `announceAvailability` (`acquisition/resolve.ts`), which publishes the tracks' and their albums' new availability. It never invalidates search, lists or Home: cache is in no library.
  - **Deliveries.** Placing one (matching's `announce`) sends `updated` for the albums and artists whose pages changed. The library's lists and Home are invalidated for everyone only when those albums hold collection files (`holdsCollection`; files still in an import's incoming folder do not count, and a finished upload announces the lists itself); otherwise only for the users who saved the album or recording (`saversOf`), whose songs list a cached file joins. Enrichment of an album announces its cover the same way (`albumChanged`).
  - **Hearts** (saves to the library; `userdata/changes.ts`, `announceUserChange`) send the entity's new `liked` and membership (`inLibrary`, `library`) as a `patch`, an album's also its songs' `inLibrary`/`library` and its artists' `inLibrary` (from `membership` in `catalog/availability.ts`), and invalidate only that user's likes lists, library lists and Home.
  - **Playlists** invalidate the playlists and the Library's All (everyone's for a public one); deleting one also sends `deleted`.
  - **Smart playlists** follow what they are evaluated from: `invalidate` with a `library`, `likes` or `history` key also sends, beside it, `queryKeys.playlist(id)` of each smart playlist it stales (`userdata/smart-refresh.ts`): every one for a change to everyone (a scan, an import), the owner's for one user's (a heart, a play, a rating), to everyone for a public one. Only those pages refetch, never playlists of songs.
  - **Collection plays** invalidate the user's Library All (`queryKeys.libraryItems()`), so it reorders on their other devices.
  - **Library pins** (`userdata/library-pins.ts`) invalidate the same key for the user who pinned or unpinned.

### HTTP API

All native routes are under `/api/v1`. Lists are paginated with `PageQuery` and return `{ items, nextCursor }`; short lists (users, invites, app passwords, roots, devices, acquisition providers, an import's albums) return every item with `nextCursor: null`. `GET /admin/jobs` returns a bare array; `GET /admin/albums/:id/candidates` returns `{ items, files }` and the acquire routes `{ items }`, unpaginated. `createApiClient` in client-core has one method per route below, and its response schemas are the reference for each route's shape. `apiRoutes` next to it names each method's route; `client-routes.test.ts` fails when the server registers a native route that no method calls and that is not on its short list of routes clients never call (stream and art URLs, the Last.fm callback, provider deliveries), and when a method calls a route the server lacks, unless that route is listed as awaiting the server. Uploads go through `XMLHttpRequest`, which reports progress.

|---|---|---|
| `GET /setup/status`, `POST /setup` | auth | create the first admin; the status carries `wantlistEnabled` |
| `POST /auth/login`, `/auth/logout`, `/auth/register`, `/auth/password`; `GET /auth/me` | auth | |
| `GET/POST /auth/app-passwords`, `DELETE /auth/app-passwords/:id` | auth | the secret is returned once, on create; create needs `currentPassword` |

### Share links

The `share` module (`modules/share/`) gives signed-in users public links to an album, a playlist they can see, or a track. A link is a row in `shares`: who made it, what it points at (catalog ids, followed through merges when read), an optional expiry (`1d`, `7d`, `30d` or `never`), and how often it was opened.

- **Tokens.** 32 random bytes, base64url, from `randomToken`. Only `hashToken`'s SHA-256 is stored (`shares.token_hash`), as with sessions, so the link is returned once, on create, as the path `/s/<token>`; clients put their server's origin in front.
- **One 404.** `shareForToken` answers 404 `share_not_found`, with the same body, for a malformed or unknown token, an expired or revoked link, a creator who is disabled, a playlist its creator can no longer see (someone else's made private, or deleted, which also deletes the link), and every link while `sharingEnabled` is off. Revoking deletes the row; turning sharing off deletes nothing.
- **The public page.** `GET /share/:token` builds `PublicShare` field by field from the catalog summaries, as the creator sees them, so nothing a summary carries for a viewer (hearts, library state, artist ids, credits) leaves the server. It has no usernames, no playlist description, no file ids or paths. A playlist shows its current songs, not a copy from when the link was made: `playlistTrackRefs` (userdata) reads its items, or evaluates a smart playlist's rules for its owner, on every page load, playback request and audio request. A track is `available` only when the server has a present file (`server` availability); on-demand music is never fetched for a link.
- **Explicit content.** The visitor has no account, so the creator's rule applies (`explicitAllowed(share.userId)`): with explicit content off for them, an explicit track is not `available`, and both the playback request and every audio request refuse an explicit file with the same 404 `not_available` as any song that does not play. Albums list their own tracks; clean versions are not substituted on a link.
- **Audio.** `GET /share/:token/tracks/:id/playback` refuses a track the item does not hold now (404 `not_available`) and, with `sharePlayback` `off`, everything (403 `share_playback_off`). Otherwise it picks the file with streaming's `selectFile` at `high` quality and seals `{ share, file, profile, expiry }` with `encrypt('share-stream', …)` into the URL `/api/v1/share/stream?key=…`, valid for three hours. Sealing rather than signing keeps the file id out of the page, and the key is in the query because Fastify allows path parameters only 100 characters. Each request to it opens the key, checks the link is still live, that the mode still allows the profile (a whole-file key under `previews` is 403 `share_previews_only`), and that the file's recording is still in the item, then serves through streaming's `openStream` with the share as the encoder's user (`share:<id>`), so listeners of one link share one user's encoder allowance.
- **Previews.** With `sharePlayback` `previews` (the default) the key's profile is `preview`: ffmpeg writes the first `SHARE_PREVIEW_MS` (30 s), faded out over its last two seconds, to a 160 kbps MP3 under `<data>/previews/`, renamed into place when done, then served with Range like any file. Cutting the audio is what makes the limit hold; limiting bytes would not, since bytes do not map to time in a VBR or lossless file and a client can ask for any range. At most two previews are cut at once per process, one per file however many ask, and 32 more wait before 503 `transcoder_busy`.
- **Limits.** The three public routes are rate limited per `addressKey` (60 page loads, 120 playback requests and 600 audio requests a minute), in the API process's memory like the sign-in limits. Unknown tokens count against the same budget.
- **Housekeeping.** `share.sweep` (daily, 04:35) deletes links that expired more than 30 days ago (until then their creators see them marked expired) and previews not played for a week; a served preview's mtime is refreshed at most hourly.
- **Clients.** `SetupStatus.sharingEnabled` tells clients whether to offer Share; changing it invalidates `queryKeys.setupStatus()` and `queryKeys.shares()` for everyone. Creating and revoking invalidate `queryKeys.shares()` for the creator and `queryKeys.adminShares()` for admins. The web app's public page is the route `/s/:token`, outside the signed-in shell and its session, with an `<audio>` element of its own; it runs under the server's Content-Security-Policy like the rest of the app.

### Availability

Two separate questions, both answered in `modules/catalog/availability.ts`: can this be played (availability), and is it in this user's library (membership). A file existing answers the first and, on its own, never the second.

**Availability**, which every list and page uses:

- Track: `server` if a present (not missing) `media_files` row has its `recording_id`, whatever its source. Otherwise `on_demand` if an enabled acquisition provider covers it (coverage `assume_available`, or a cached positive resolve) and it has no miss from that provider that counts (see "Acquisition"). Otherwise `none`.
- Album: counts owned tracks on its track list (`albumTrackList`, below): the canonical release (else the album's release with the most tracks), plus owned recordings filed under the album that the release does not list. All owned is `full`, some is `partial`; none owned is `on_demand` when any of its tracks would be (an album is dimmed only when nothing on it plays: one track a provider missed must not gray out an EP), else `none`. `trackCount` and `ownedTrackCount` count the same list, so an album with a present, linked file is never `none`.
- Clients present it by viewer with `isPlayable` and `albumPresentation` from client-core: for a *requester* (an admin, or a member with `canAcquire`) `on_demand` looks and plays like `server`; for anyone else it is unavailable. Requesters see no badge or count telling the two apart.

**Membership.** A user's library is what that user *saved*, plus the server's *collection* for a user who includes it:

- **Collection**: a present file whose `source` is not `provider:*` (scanned, uploaded, from the inbox). Shared: everyone finds and plays it, `/collection/*` and Home's `recently-added` list it, and uploaders and admins take it out by deleting uploads (see "Imports"). `collectionFile(alias)` is the condition.
- **Included**: the collection counts toward a user's library only when their `UserSettings.libraryIncludesServerMusic` is on (off by default, for existing users too). `collectionCounts(userId)` in `availability.ts` is that one condition, and every collection branch of a membership query (`inLibraryAlbum`, `inLibraryRecording`, `recordingLibrary`, `membership`, the library lists, All, Subsonic's `libraryFile`, an album page's `library`) is gated by it. It reads the user row without depending on the row being tested, so Postgres runs it once per statement (an InitPlan) and skips the gated branches when it is false. The same helpers with `userId: null` answer for the collection alone, which is how `/collection/*` lists the server's music.
- **Cache**: a file a provider delivered. `media_files.cached` is generated from `source like 'provider:%'`, so it cannot drift. Cache makes a track `server` and puts nothing in any library: a song sampled by pressing play stays out of Albums, Songs, Artists and Recently added.
- **Saved**: a row in `likes (user_id, entity_type 'album' | 'recording' | 'artist', entity_id, created_at)`, written by the heart, `PUT /me/likes/:type/:id`, and deleted by `DELETE` (owner: userdata). A finished `upload` import also saves its albums for the uploader (`saveUploadedAlbums`), without asking for missing files, so uploads are in the uploader's library. There is one control: liking is saving, Liked Songs lists the saved recordings, a Subsonic star and a Last.fm love are the same row. A save needs no file, so a saved album is in the library at once. Removing deletes the row only: files stay as cache; playlists and history stay. For a requester an album or track save also asks acquisition for what is missing, as the `userdata.fetch-saved` job, best effort: the save never waits for it or fails on it. Nothing else writes a save: fetching (`POST /albums/:id/acquire`, playback, downloads, radio) never does. For a user who includes the collection, a collection item is in the library whatever its heart says; the heart only shows the viewer's own save.
- **Album** in a user's library: the user saved it, or a collection file is linked to it (`media_files.album_id`) and the collection counts for them (`inLibraryAlbum`).
- **Track**: the user saved the recording, or a present file (cache included) links it and that file's album is saved by the user, or a collection file links it and the collection counts (`inLibraryRecording`). Songs of a saved album therefore appear as their files arrive.
- **Artist**: the user saved the artist, or it is credited (`album_artists`) on an album in the user's library. Being featured on a track, or credited on cached music, does not count.
- Merges move saves (the older row wins a collision), and the library's orphan cleanup and `search.cleanup` keep saved rows.
- The migration that introduced this turned completed album fetches with a requester into saves (with a track-only provider, seven or more track fetches of one album by one requester within a second, more than playing ever starts at once); other single-track fetches came from pressing play and were not carried over. On a server whose files all came from a provider, every library starts empty. Libraries were the collection plus saves until `libraryIncludesServerMusic` came in; an existing user's library then shrank to their saves unless they turn it on. Saves used to live in a table of their own, `library_items`, beside likes; migration 0018 unioned the two into `likes` (an entity in both keeps the earlier time) and dropped it.

### Explicit content

`modules/catalog/explicit.ts` holds the rules; every surface below calls it.

- **Who.** A user allows explicit content unless their `UserSettings.allowExplicit` is false or an admin set `users.explicit_restricted` (`explicitAllowed`; `User.allowsExplicit` is the same answer for clients, `User.explicitRestricted` the admin's switch). A restricted user cannot turn the setting on (`explicit_restricted`), and lifting the restriction leaves their own choice. Both changes invalidate the user's cached reads and `me`, so their clients read the user, and pages, again.
- **What.** A song is explicit as its summary says (`trackExplicit` in `credits.ts`): a present file's advisory tag (`ITUNESADVISORY`, MP4 `rtng`, `EXPLICIT`, read by `library/tags.ts`), else `recordings.explicit`, which only Deezer fills (on materialize, enrichment and `repair`; merges carry it). Unknown is not explicit. A single file is judged by its own tag first (`fileExplicit`), so a file tagged clean plays though its recording is flagged.
- **Gray.** Album pages, playlists, Liked Songs, the library lists, artist top tracks, history and the queue keep explicit songs; clients gray them for a viewer whose `allowsExplicit` is false (client-core's `isPlayable`, `explicitBlocked`, `unavailableLabel` says "Explicit content is off"). Lists stay whole, so positions, counts and cursors mean the same for everyone.
- **Hidden.** Search (both routes, before ranking, songs found by lyrics or credits too), Home's `most-played` and `rediscover`, the user's mixes (when made and when read), radio and autoplay candidates (`suggest` drops them; a track radio from one is 409 `not_playable`; an artist radio starts from a song the user may hear) and every Subsonic song (`subsonic/songs.ts`; Subsonic clients cannot gray) leave them out.
- **Never played.** Trusted entries (`playTracks`, `enqueue`, `savePlayQueue`) drop them or put a clean version in their place, and the playback descriptor, `GET /stream/:fileId` and Subsonic `stream` and `download` answer 403 `explicit_not_allowed` for an explicit file, for an entry queued before the setting changed, an older app or a URL signed earlier. Queues are not rewritten when the setting changes; such an entry is refused when it is reached. A member of someone else's jam is refused the host's explicit songs the same way: their device sits the song out (client-core `sitOutNotice`; the app neither skips nor pauses, which are the host's), and `savePlay` and the scrobble module's now playing leave out a song the user may not hear (`explicitBlockedFor`).
- **Clean versions** (`cleanVersions`): recordings of the same primary artist whose title matches once edition words are dropped (`editionFreeTitle`: "(Clean)", "(Edited)"), within 15 s of the explicit one's length, not merged away, and *known* clean (a file tagged clean, or Deezer's `false`); one whose flag is unknown is not taken, since it may be the same explicit recording under another row. Owned versions first, then the more popular. They come from Deezer's clean editions and clean files in the library. Trusted entries take the first one that plays for the user (with no album context), and the album page shows it in the explicit song's place (`cleanTrackList`), under that album, so an album with a known clean edition reads as that edition. The artist page and album versions are not filtered: which edition a discography lists is the same for everyone.
- **Caches.** Every read that differs by this is already per user in the read cache (Home, album pages); search and radio are not cached.

### Catalog read side

- `recording_artists` holds the ordered display artist credit. `recording_credits` stores additional role-typed credits with optional instruments and an index on artist and role. `works` identifies MusicBrainz compositions by MBID and tagged compositions by title and composer. `recording_works` links each performance to a work and can carry movement name, number and total. MusicBrainz relationships attach to recordings and are refreshed with their release lookup. Tagged relationships attach to files and follow their current recording links through rematches and merges. Catalog reads combine the credits and prefer a present file's work and advisory when available. A composer or producer can have contributed tracks on their artist page without being in the display credit.

- `catalog/summaries.ts` builds every `TrackSummary`, `AlbumSummary` and `ArtistSummary`, in batches with a fixed number of queries. They leave out artwork the art route would answer 404 for: a `missing` asset, or a `failed` download inside the hour before it is tried again. Other modules (search, sessions, userdata) use these rather than writing their own. Subsonic builds its own, because its objects describe files (size, codec, path), but takes availability and redirects from the catalog. Summaries are per viewer: `TrackSummary.inLibrary` and `ArtistSummary.inLibrary` follow the viewer's membership (`artistSummaries` without a user answers for the collection alone); `AlbumSummary` carries none, and `AlbumDetail.library` is `collection` (when the collection counts for the viewer; it wins when the album is also saved), `saved` or null. `TrackSummary.library` says why a track is a member, the first of `collection` (the collection counts for the viewer), `album` (a present file of it is on an album the viewer saved) and `saved`, or null (`recordingLibrary` in `availability.ts`): only a `saved` track leaves the library when its save is removed.
- Ids that come from clients follow `merged_into_id` redirects (`catalog/redirects.ts`, one primary-key lookup per hop, at most 16); the summary builders do it themselves, so stored queue and playlist ids keep working after a merge. `POST /tracks/summaries` answers a merged id with the row it was merged into and lists, in `requestedIds`, the id each summary was asked for, so `TrackStore` files it under the id the queue holds.
- **Cached reads** (`lib/read-cache.ts`). `GET /home`, `/library/*`, `/collection/*`, `/albums/:id`, `/artists/:id`, `/playlists` and `/playlists/:id` keep their serialized answer and its ETag in the API process, per user and URL, within `SQUIRMY_READ_CACHE_MB` (default 64, least recently used out first; off under test unless set). Each route names the `queryKeys` roots it depends on; an `invalidate` for one of them drops that user's entries (a user target) or everyone's (`all`, `admins`), a root the cache does not know drops everything, and `admin`, `settings`, `scrobbling`, `me`, `lyrics` and `uploads` drop nothing. A read that overlaps a drop is not stored. Entries expire after five minutes, which bounds what nothing announces. Catalog search evicts cached answers containing an entity it edited and artist pages or release lists whose credits or releases it changed. A newly materialized release can enter a cached Home feed on its next refresh. Provider changes drop everything explicitly. Writes made in the background go through `invalidate` like any other, so a worker's reach the API process: an unassigned cover, album stubs a discography adopts (`upsertDiscography` names them, whichever job wrote it), an album hydration (announced even when a later step fails) and `search.cleanup` (each kind it deleted from, by root). Home is computed again two seconds after a drop when it was read in the last 15 minutes.
- Lists use keyset cursors (`catalog/pagination.ts`): opaque, tied to one ordering, and stable under ties and concurrent inserts. Title and artist orderings are `sortKey` over the stored `*_key` columns, backed by expression indexes in `schema.ts`.
- **Library lists** (`catalog/library.ts`) take the user and list their membership (above); with `null` for the user they list the collection alone, nobody's saves, which is `/collection/*` (summaries still for the viewer). Title, artist and year pages (and tracks by year, which place each library track by its newest present file, so a saved track waits for its file) have two shapes, picked per request by `libraryShape`, which counts members up to 2,000 on the membership indexes. A small library is read from its members (collection files by album or recording through the `media_files_collection_*` indexes, plus the user's saves) and sorted, so a catalog full of search stubs costs nothing. A large one walks the catalog's sort index and keeps members, about `limit` rows when most of the catalog is library.
- `recent` places an item at the later of its newest collection file's `added_at` (when the collection counts) and its save's `created_at` (for a track, also the save of an album holding a present file of it). It is a union of one walk per way in, each on its own index and keeping only the items whose time it holds, so each item appears once. Songs that entered at the same time (one scan, one saved album) follow their file paths, which is track order under every naming template, then the id. Its orderings are `albums:recent2` and `tracks:recent3`; cursors from an older order are refused with `invalid_cursor`. `performance.test.ts` (10,000 albums, 150,000 tracks) and `stubs-performance.test.ts` (200,000 stubs around a library of 50 albums) check every page with EXPLAIN.
- **All** (`catalog/library-items.ts`, `GET /library/items`) merges one branch per kind, each in the same keys and cut to `limit + 1` after the cursor: albums through the album list's queries, artists through the artists index or (by time) one walk per way in (the newest collection file on an album crediting them, the latest save of such an album, their own save, the collection winning a tie), and the playlists the user can see with Liked Songs, few enough to be listed whole with their sort keys computed by `sortKey`. An item's added time is its album time, the latest of an artist's own save and its library albums' times, a playlist's creation, or Liked Songs' latest liked song. `played` lists `collection_plays` newest first, keeping only library members (and visible playlists), then everything else by added time; a played item's second key and a never-played item's first are `-infinity`, so a cursor says which part it is in. **Pins** (`library_pins`, written by userdata) head the first page whatever the sort, most recently pinned first, beyond its `limit`, and are marked `pinned`; only those the list holds show (`listsEntry`, and under a genre only its albums). The merged query leaves every pinned item out, and each branch reads as many rows more as the user has pins, so a page still fills. Merges move pins (the earlier pin wins). `title` orders by name, `artist` by creator (an artist's name ahead of its albums, a playlist's owner, the user for Liked Songs), and under `year` only albums have one. `performance.test.ts` and `stubs-performance.test.ts` time every order.
- Home (`catalog/home.ts`) has two layouts. The classic one, for app builds that do not ask for `layout=personal`, comes in decision 30's order: `recently-played`, `most-played`, `playlists`, `recently-added` ("New on this server": the collection's albums by `recent`, whatever the user's library), `new-releases`, `wantlist`. `new-releases` (`enrichment/releases.ts`) is per user: albums from the last 120 days whose main artist is credited on an album in the user's library or was hearted by them, leaving out what the user has and cover acts' releases (karaoke, tributes, string-quartet and similar renditions, by title or artist name). `enrichment.new-releases` keeps the discographies of every user's such artists current; music fetched for playing makes nobody's artist.
- The personal Home (`layout=personal`): `jump-back-in`, then `made-for-you`, `because-you-listened`, `top-artists`, `rediscover` and `most-played` in an order set by the time of day, then `playlists`, `new-releases`, `recently-added` and `wantlist`. Sections of the new kind `items` hold cards of several kinds (`HomeItem`: album, artist, playlist, Liked Songs, mix, radio); apps skip a section kind they do not know, so older apps take a newer server. Jump back in reads the context of the latest 500 plays (a playlist, artist, Liked Songs, mix or radio; else the play's album) with the user's `collection_plays`, newest first, each place once. Plays count as `listened` (not an early skip) or `completedPlay` (also past the scrobble threshold) from `catalog/sql.ts`, the same predicates Subsonic's `recent` and `frequent` lists use.
- **Home picks** (`catalog/home-picks.ts`, table `home_picks`) are what would cost months of plays on every Home: the mixes (radio's `makeMixes`, stored in `mixes`), Because you listened to (radio's `becauseYouListened`: one of the month's three most played artists, a different one each day, and its similar artists with a present file on the server), the month's top artists, Rediscover (songs with three or more completed plays six to 24 months ago and no play in 90 days) and `hourly`, each top artist's completed plays per UTC hour over 90 days. `catalog.home-picks` makes one user's and invalidates their Home; `catalog.home-picks-all` (daily, 05:00) queues everyone who played in the last 90 days and has none from today, and reading Home queues a user's when they listened since an earlier day's (or since a run an hour ago that made no mixes). With the client's `tz`, the time-of-day order (`daypartFit`, `fitOf`, `byTimeOfDay`) takes, for each artist, the share of its plays in the current part of the day there (morning 05–11, afternoon 12–16, evening 17–21, night 22–04), scores each rail by the mean over its cards, and sorts in quarters so only a clear difference moves a rail; the mixes are ordered the same way. The partial index `plays_user_completed` (user, start, recording, album where completed and not skipped) keeps Most played and the picks' scans on the index; `home-performance.test.ts` times them on 500,000 plays.
- A track's album in a summary is the album context, else an album of a present file, else an album of a release it is on, preferring the artist's own release (the album's primary artist is the recording's), then albums, EPs, singles, soundtracks, live albums and compilations, the album's canonical edition, the earliest year; else its search hint. So a song on an album and on its single shows the album, wherever the single sits in the catalog. Its artwork is that album's cover, else the cover of another of those albums.
- **Album versions** (`albumVersionIds`, `AlbumDetail.versions`). Since the artist page lists each release once, an album page names the album's other versions itself: the other rows of its release group (the group's row and its edition rows: a deluxe kept from MusicBrainz's titles or a store's, the standard edition from one of them) and its lead artist's other rows of the same `releaseKey` and kind (a deluxe that MusicBrainz lists as a group of its own, a store's deluxe found by search), found by `title_key` prefix. Each edition once: of rows with the same `labelFreeKey`, kind and track count (or no track list yet) the one `standsBefore` picks, and a row with no track list yet gives way to an edition row titled as it is without edition words (a store's "SO CLOSE TO WHAT??? (deluxe)" to "SO CLOSE TO WHAT???", `printedTitleKey`); the album itself stands for its own; the group's row first, then by date, at most 20. Clients show them as **Other versions** with the discography's releases of the same title key (client-core `relatedAlbums`, which also keeps them out of **More by**).
- **The artist page** (`artistDetail`) lists the releases the artist leads (primary artist or first credit) and those of others that credit it, on the release or on a track of one of its editions, newest first. Rows of one release (the same `releaseKey` and type) show once, as the owned, MusicBrainz, stated-type, most complete row (`standingRows`); a row whose type is a guess gives way to any row of its title. The enrichment module merges such rows where it can; this keeps the page right meanwhile and where MusicBrainz has two groups of one title and type. The releases are split into `sections` in the order of `ARTIST_SECTION_KEYS` (`sectionOf`): by type, except that mixtapes (MusicBrainz's "Mixtape/Street", typed `album` so older clients still parse them) are `mixtape`, others' releases are `appears_on`, and studio soundtracks can be albums. **Soundtracks:** a single, EP or "Other" release from a film is typed that, not `soundtrack` (`musicbrainz.albumType`), so it is under Singles, EPs or Other releases. A soundtrack whose only secondary type is Soundtrack and on which no other artist is credited (a studio soundtrack of the artist alone) is listed under Albums when the artist's albums outnumber such soundtracks: The Beatles' Help!, Yellow Submarine and A Hard Day's Night. Never on a placeholder artist's page: Various Artists is the only credit of its soundtracks only because MusicBrainz names no one, so GTA, Cyberpunk 2077 and Sing are its Soundtracks. Every other soundtrack is under Soundtracks: a film composer's scores (Hans Zimmer has more of them than albums), one credited to Various Artists or shared with other artists (The Lion King for Elton John), and compilations or remixes of film music (Yellow Submarine Songtrack, Love). The rule is the same on the page and on **See all**. Each section carries its first `ARTIST_SECTION_PREVIEW` (12) releases and its `total`; `GET /artists/:id/releases` pages the rest, with a cursor naming the last release listed (followed through merges), so a discography that grows meanwhile neither repeats nor skips one. `releaseCount` and `ownedReleaseCount` count the artist's own releases and those with a file on the server. `albums` and `appearsOn` carry the same previews for clients that predate `sections`: Bach's page was 3.8 MB with 6,169 releases. **Top tracks** are the artist's stored list (`artist_top_tracks`) in its order, each song once (by recording, then by title); without one (music only in the library) the artist's tracks rank by completed plays here, then popularity. MusicBrainz's placeholder artists (Various Artists, `musicbrainz.specialPurposeArtists`) have no top tracks, radio, similar artists, bio, genres or disambiguation (MusicBrainz's is a note to its editors), and their summaries carry no picture from the web (stores show a stock photo); a picture from the user's folders shows. Clients draw their placeholder.
- An album's track list is `albumTrackList` (`catalog/pages.ts`), for the album page and Subsonic's `getAlbum`: the canonical release's tracks, then owned recordings filed under the album that the release does not list (bonus tracks, files matched with no track) in path order on the last disc, with no position. Subsonic numbers those after the disc's last track.

### Smart playlists

A smart playlist is a `playlists` row with `rules` (jsonb, `SmartPlaylistRules` in the userdata contract) and no `playlist_items`. `userdata/smart.ts` evaluates it on every read, for its owner whoever reads it: `GET /playlists/:id` (its items, summarized for the reader, `itemId` the track's id and `addedAt` its file's arrival), its summary's count, length and covers, Subsonic's `getPlaylists` and `getPlaylist`, and the editor's preview.

- **Safe by construction.** The rules are a zod tree (conditions on text, numbers, decades, dates and booleans, groups one level deep, at most 50 conditions) compiled into drizzle `sql` fragments. Every value typed is a bound parameter; the only text written into the statement comes from fixed tables keyed by the enums the schema checked. Text matches compare `matchKey` of the value with the `*_key` columns by `strpos` (no LIKE, so `%` and `_` are characters); genres and codecs compare lowercase. `smart.test.ts` checks that hostile values reach the statement only as parameters.
- **What it reads.** The present files of the source, each with its recording and album: for `server` the collection (`collectionFile`), for `library` the three ways in of `libraryRecordingIds` tested on the file itself (a collection file while `collectionCounts`, a file of a hearted recording, a file on a hearted album), which is `inLibraryRecording` without a lookup per row. A song passes when one of its files, with that file's album, passes, and is listed once, through the newest such file. Play counts and last plays (one aggregate of the owner's plays), ratings and hearts are joined only when a rule or the order reads them; artist, album artist and liked rules are hashed sets found once. Random order is `md5(recording id || playlist id and UTC day)`, the same for every reader that day.
- **Cost.** It is one pass over the files, never an index walk, so it costs about the same for every rule set: a hash join of files and recordings, a sort to keep one file per song, then a top-N sort, at most `PLAYLIST_ITEM_LIMIT` songs. The statement runs with `work_mem` of 32 MB for itself, so the sort stays in memory on 150,000 files. `SQUIRMY_PERF=1 npx vitest run src/modules/userdata/smart.performance.test.ts` times five rule sets on 10,000 albums and 150,000 tracks.
- **Refresh.** See "Realtime": the invalidations of the library, hearts and plays also name the smart playlists they stale. Cached reads of `/playlists/:id` depend on `library` and `likes`, as the list does.

### Search

`modules/search/`. Both routes return `SearchResults` built with the catalog summary builders, so availability comes out the same as everywhere else. Music and lyric queries whose `matchKey` is shorter than two characters answer nothing.

- **Saved albums and artists**: both routes set `liked` on the album and artist summaries they return (`withLiked` in `top.ts`, one query), which other answers leave out; rows' menus offer Save to library or Remove from library by it, and the ranking reads it as the like signal.
- **Ranking** (`rank.ts`, both routes): every result gets a 0..1 score, `relevance × (0.5 + 0.5 × prominence)`, returned best first across kinds as `ranked`. Relevance compares the name with the query by `matchKey` (a leading "the", "a" or "an" ignored on either side, edition suffixes dropped by `editionFreeKey`, spacing and punctuation ignored for "acdc", `$` read as `s`): 1 the whole name or artist and title together, 0.97 once an article is ignored, 0.95 compact, 0.8 a prefix of whole words, 0.7 any prefix, 0.6 a later word, 0.62 to 0.45 an album's or song's artist, 0.5 one typo from five characters, 0.3 what the provider found for its own reasons. Prominence is the provider's (Deezer fans on a log scale, a song's rank, the local index's popularity; carried from `materialize` by catalog id) or the stored song popularity, passed from songs to their album and from artists to their music, raised for what is in the viewer's library (at least 0.55), played among their last 1,000 plays, or liked; unknown, it falls back to the result's place in its list. Prominence at most doubles a score, so an exact name loses only to a prefix match about a hundred times better known, and an artist's songs found through the artist alone never bury another artist named as typed. `rank.test.ts` holds Deezer-shaped fixtures for the cases this was tuned on (tate, mgmt, kid a, AC/DC, $uicideboy$, …). The catalog route also ranks the library answer's page for the same query (the provider may know how popular those are), so its `ranked` can name ids only that answer lists; clients take an item's higher score. **`top`** is the best ranked result whose own name matches at least by a typo, with `score` 1..3 for older clients (3 the whole name, 2 with an article or spacing ignored, 1 less); the catalog's names an item of its own lists. Both fields are optional in the contract.

- With `scope=server`, the library route includes visible playlists, matching stored lyrics and credits. `type=playlist`, `type=lyrics` and `type=credits` page those lists separately. Playlists are scoped to the viewer's own and other users' public playlists. Lyrics use a GIN-indexed `simple` full-text vector over plain text, with timestamps stripped from synced lyrics when plain text is absent. A lyric match returns the track summary and a plaintext excerpt. Credit search starts with names of composers and producers, then follows locally stored recording relationships and tags on present files. Its track results carry the matched credits.
- The `quality`, `decade` and `liked` facets constrain local music, lyrics and credits before candidates and pages are cut. Quality uses a present file, decade uses album metadata and likes are per viewer. The catalog route returns empty while a facet is active.
- Non-ASCII names use indexed character bigrams whose extraction is independent of PostgreSQL's character classification. ASCII queries keep their existing trigram indexes. The canonical index also looks up both orders of an artist and a title, or a recording's title and release. Remote providers supplement weak whole-query answers with composite readings and verify the returned credits or release titles before merging.

- **Index upgrades.** Boot migrations install search functions and create library search indexes on empty tables. The `catalog-index.upgrade` job builds missing library indexes on populated tables and adds the Unicode and composite indexes to a previously imported canonical catalog. It runs on a worker at low queue priority, one concurrent index build at a time on its own database connection. It keeps valid indexes on restart and drops invalid ones before retrying. Prefix and ASCII trigram lookups stay available while Unicode and composite lookups wait for their indexes. Lyric results become available when the lyric index is valid. A fresh canonical import builds its indexes on the staging table before the swap. See [Upgrading an existing index](./local-search-index.md#upgrading-an-existing-index).


- **`GET /search/library`** (`library.ts`): uses the same membership rules as the Library lists. A saved album can appear before its files arrive, and its tracks with present files can appear even when those files are provider-cached. The global search screen asks both routes for `scope=server` so the local answer also includes any present file and its credits, regardless of the user's setting. Subsonic uses this scope before applying its own file filters. An optional `genre` keeps the results to albums of that genre, their tracks and their artists, filtered before `offset` cuts the page, so a search inside a genre chip stays in it. Candidates per kind come from bounded index lookups, and one walk of the user's saves (prefix or trigram match, in its own `union` branch): a byte-order prefix btree on `name_key`/`title_key`; every split of the query into "artist title" or "title artist", looked up from that artist's rows; a track title and album title pair looked up from the album's recordings; albums and tracks whose primary artist's name starts with the query; and, from three characters, trigram word similarity on `name_key` or the whole `match_key` (artist and title, so typos and word order are tolerated). Ranking: exact, then prefix (title, name or artist), then similarity; ties go to the user's plays among their last 1,000, then likes. `type` limits the answer to one kind and `offset` skips that many of each, for a client's filter. Each kind is one query run with `enable_seqscan` off, because the planner prices `word_similarity` too low. `performance.test.ts` measures it on 10,000 albums and 150,000 tracks.
- **`GET /search/catalog`**: one provider per request (`providers.ts`), asked only for the kinds `type` names and from `offset` (Deezer's `index`, MusicBrainz's `offset`; the local index reads the rows before it), in this order: the local index when `isCatalogIndexReady()`, Deezer when enabled, MusicBrainz when enabled. A provider that throws falls through to the next; `provider` names the one that answered. Identical queries in flight share one provider call, and `cachedFetch` keeps search responses for a day. MusicBrainz free text matches titles only, so "artist title" queries are only understood by the other two. The route runs the library search for the same query, kinds and `offset + limit` alongside the provider call and leaves out of its answer every artist, album and track that the library answer lists on this page or an earlier one, so owned music the provider also found is not shown twice. It also lists one artist per name (`namesakes.ts`): an artist without an MBID is left out when the library answer, an artist of the answer with an MBID, or an earlier one has its name. Deezer has duplicate pages for some artists ("Boards of Canada" 1098 and 412310471), which are rows of their own until enrichment merges them; artists with MBIDs always stay. Albums are listed once per artist and name (`oncePerTitle`, both routes): Deezer lists one edition several times (the explicit and the clean "SOS Deluxe: LANA"), each a row of its own; the first stands for the others, and a copy the library answer shows leaves the catalog's out. Its `top` is picked from what is left, with the same function and scale as the library's, so the client's comparison is between two separately ranked hints. After answering, it starts detail in the background: `warmDetail` for a top artist, and through `warm.ts` for up to five albums (a top album, then the first albums with no track list yet), two at a time across the process, a newer search's ahead of what an older one left waiting. Their pages are complete and their tracks playable by the time a user opens one.
- **Stub rows** (`materialize.ts`): results are stored before they are returned, in one transaction per response. Search writers share the cleanup lock and lock the identities they can match: artist names and ids first, then album and recording ids and normalized titles paired with the credit text or primary artist. Identities include provider ids and MBIDs. Each result is matched to an existing row by its `external_ids` row (`deezer`, or `musicbrainz` for MusicBrainz and local-index ids), then by MBID, then by key: for artists the one artist with that `name_key`, if exactly one exists and it has no other id from the provider; for albums and tracks the same artist (credit text or primary artist) and the same title, owned rows first, then MusicBrainz rows: for a track once edition suffixes are dropped, for an album once only store labels are dropped (`labelFreeKey`), since "OK Computer (Deluxe Edition)" is another edition with its own songs. A provider that names no album type (Deezer's album of a track, the local index's albums) matches any type; one that names a type matches that type, unless the row is owned or its own type is a guess. Track lengths must be within 10 s. Only then is a stub inserted:
  - artist: `name`, `name_key`, `detail_level` 0, `mbid` when known, an `external_ids` row, `image_asset_id` from `remoteImage`;
  - album: `title`, `artist_credit`, `primary_artist_id` and `album_artists`, `type`, `year`/`release_date`, `title_key`, `match_key`, `detail_level` 0, `mbid` (release group) when known, an `external_ids` row, `artwork_asset_id` from `remoteImage`, no releases. Without a type from the provider the type is guessed (`guessAlbumType`: a single when the album is titled like one of the response's tracks, else an album) and `type_guessed` is set;
  - recording: `title`, `artist_credit`, `primary_artist_id` and `recording_artists`, `duration_ms`, `title_key`, `match_key`, `explicit`, `popularity` (0..1), `isrcs`, `mbid` when known, an `external_ids` row, and `album_hint_id`, an album it appears on. Summaries use the hint only when no file or release track names an album.

  Existing rows only gain a missing external id, image or album hint, and a guessed album type (with a missing year and date) once the provider lists the album itself. A row found by its provider id that gives way to an owned row found by key is merged into it when it has no MBID and no files (its provider id moved before, and the stub stayed beside the owned row on the artist's page). A response that inserted album stubs queues `enrichment.reconcile` for their artists. A Deezer artist id no row carries, named like a row that has another Deezer id, is that row's when what the response credits it with (its albums and tracks) shares a release or two songs with what the row is credited with (`sameArtist`, an album titled like the artist excepted): Deezer keeps second pages for some artists. Otherwise it is stored as an artist of its own and `enrichment.reconcile { artistCopy }` looks again with Deezer's and MusicBrainz's data. Credits without any provider id (the local index names some artists only as text) reuse the artist with that name and otherwise become a stub without an external id.
- **Release keys** (`keys.ts`, `releaseKey`): `editionFreeKey` once store labels of a release's kind or origin are dropped too ("(From F1® The Movie)", "(Original Motion Picture Soundtrack)", "- Single", "E.P."). Used to tell whether two album rows of an artist are one release (`enrichment/reconcile.ts`, the artist page), never for search.
- **Edition suffixes** (`keys.ts`): a bracketed or dashed suffix is ignored for matching when all its words describe an edition (deluxe, expanded, remastered, anniversary, explicit, clean, bonus tracks, numbers…) and at least one is a strong word, so "OK Computer (Deluxe Edition)" and "Let It Be - Remastered 2009" find the plain titles while "(Live)", "(Remixes)", "(Radio Edit)" and "(Taylor's Version)" stay different albums and songs. Stored keys keep the full title. A catalog query that ends in edition words with at least one strong word ("ok computer deluxe") is also sent without them, and those results follow the whole query's: providers match every word, so an edition they name differently would otherwise find nothing.
- **`search.cleanup`** (daily): deletes stubs older than 30 days that never gained detail (albums and artists at `detail_level` 0 with no MusicBrainz releases, recordings on no release) and that nothing keeps: files, likes, ratings, wants, playlist items, plays, ids in stored playback sessions, acquisition jobs still running, album hints of kept recordings, credits, merges. Their `external_ids` go too; `assets` stay. The library's orphan cleanup leaves stubs alone.

### Playback and streaming

The replacement of this core (a native iOS and tvOS engine, fragmented MP4 transcodes with exact gapless numbers, transcode priorities, a Media Source Extensions engine on the web) is designed in [audio-engine.md](./audio-engine.md); until its pull requests land, this section describes what runs.

- Clients ask `GET /tracks/:id/playback` and receive a signed URL. An explicit file is 403 `explicit_not_allowed` there and on the stream route for a user who has explicit content off ([Explicit content](#explicit-content)). The stream route accepts the signature instead of a session so `<audio>`, AVPlayer and downloads need no headers. Signatures bind the file id, profile, user id and an expiry of 12 hours.
- File choice: files of the recording that belong to the requested album first, then lossless over lossy, then higher bitrate. Both ids follow merges, so a queue entry that names an album merged away still gets that album's file.
- `chooseProfile` (`streaming/select.ts`) maps a quality to a profile. By default, `original` serves the file when the client decodes its codec. Otherwise the target is the first profile the client decodes from the quality's preference list (`original` and `high`: `aac_256`, then `mp3_320`, `opus_128`, `mp3_192`; `data_saver`: `opus_128`, then `mp3_192`, `aac_256`, `mp3_320`). A lossy file at or below the target bitrate that the client decodes is served as is; one it cannot decode gets the smallest playable profile at or above its own bitrate. Clients can opt into fragmented MP4 with `containers=fmp4`. Encoder settings are in `streaming/profiles.ts` and the opt-in profiles are described in [Playback](./server/playback.md#fragmented-mp4).
- Signed URLs carry `exp` (epoch seconds), `uid` and `sig`, an HMAC from `sign('stream', …)`. A request without a valid signature may use the session instead.
- A URL names the file, not its path, so it keeps working when organize files it: a file not at its row's path is looked for at the other end of a move that is running (organize renames on disk before it updates the row), and is marked missing only when it is in neither place. When the library root itself is not a readable folder (an unmounted drive or share) the request answers 503 `root_unavailable` and nothing is marked missing, as the scanner does.
- A transcode is written to the cache while it is streamed to the first requester; later requests get the cached file with Range support. A cached transcode is used only while the source's size and mtime are the ones it was made from, so a file replaced or retagged in place is encoded again. ffmpeg writes to a pipe, so every streamed byte is final: AAC 256k in ADTS (`.aac`), Opus 128k in Ogg, MP3 at constant bitrate without a Xing frame. Encoders: `aac`, `libopus`, `libmp3lame`.
- Fragmented MP4 carries FLAC, Opus or AAC encodes, or compatible packets from the source (`copy_mp4`). FFmpeg writes the init segment and media fragments without edit lists. `streaming/mp4.ts` restores the coded duration of the last AAC and Opus packet before its fragment reaches readers or the cache, preserving byte offsets. The descriptor reports `gapless` from measured source frames (rounded up if resampled) and the delivered codec's priming. Remuxes report source priming.
- A fragmented MP4 request can append the unsigned `start` parameter in milliseconds. The scheduler starts a separate ffmpeg using an input seek and returns `X-Squirmy-Start-Frame` in frames at the delivered rate. Remuxes start at an earlier packet for decoder preroll and report that packet's actual position. Seek output uses a temporary file, is discarded when its readers leave, and never replaces the full cached encode. Byte-range requests use the whole file.
- Requests for the same transcode share one ffmpeg per process. Encoder slots go to `play`, `next`, `cache` and `download` in that order, then by arrival. Clients can append the unsigned `intent` query parameter to the stream URL or request it on the playback descriptor. Missing intent means `play`, including Subsonic streams. The highest-priority reader sets the shared encode's priority while attached.
- At most half the CPU cores (at least two) encode at once, and each user can start up to four concurrent encodes, counting Subsonic live encodes. A fifth transcode can replace the user's lowest-priority background encode or returns 429 `too_many_live_encodes` if all four are playing. When the encoder pool is full, a waiting `play` can interrupt the lowest-priority `cache` or `download` encode. Interrupted work discards its temporary file and starts again on request.
- When the last reader disconnects, `cache` and `download` requests and encodes at least halfway through the track finish and populate the cache. Other running encodes have 10 seconds for a reader to return, and can give up their slot sooner for waiting playback. Abandoned requests still in the queue are removed immediately unless requested as `cache` or `download`.
- Transcodes are built when a stream first asks for them; nothing is converted ahead of time. `streaming.evict` runs hourly and at worker start: it reconciles rows with files on disk and deletes least-recently-used transcodes beyond `transcodeCacheMaxBytes`, sparing those used in the last half hour so a track being played keeps answering Range requests.
- A descriptor describes what its URL delivers and, in `source`, the file it is made from (codec family, bit depth, channels, size), with `transcodeReason`: `codec` when the client does not decode the file, `quality` otherwise. Both are absent from older servers; client-core then takes an original's own fields as the file and knows nothing of a transcode's.
- Normalization values prefer measured loudness (`-18 − loudness_lufs` gives the gain), then the file's ReplayGain tags. For a file awaiting measurement with no tagged gain, the playback descriptor uses the median track gain of the present library and marks it `estimated`. Album values come from `release_loudness` or the file's tags.
- Loudness is EBU R128 from ffmpeg's `ebur128` filter. `loudness.measure` `{ fileId }` records integrated loudness, true peak, and the exact decoded frame count and sample rate after applying source priming and padding. It records the trim values from the same decode. Original playback descriptors expose the count, rate and priming in `gapless`. A stream request for audio awaiting measurement queues the job at high priority or raises the priority of its waiting singleton. When track loudness changes and the release’s present files have all been measured, measurement queues `loudness.album` `{ releaseId }`. A running album job may have read older measurements, so it cannot suppress this follow-up. The album job streams decoded audio from one track at a time into a continuous meter and stores the maximum measured track true peak. Silent and very short files store -70 LUFS, which yields no measured gain. A final decode failure sets `probe_error` and clears the file's measurement and its release's album measurement. Scanning a changed file clears stale measurements and the error. `loudness.sweep` runs every 10 minutes and at worker start, queuing present, probed files without a measurement or exact length in batches of 500 and releases that need an updated measurement. Files with recorded errors are skipped until a scan detects a change.

### Sessions

The server holds one shared session per user in memory, loaded on first use and persisted to `playback_sessions` on change (debounced one second, and flushed on shutdown), plus one session of its own for each detached device (see "Detaching" below). This assumes one API process: the copy in memory is the truth, so functions that change sessions (`markRecordingReady`, `replaceQueue`) must run in that process. Commands arrive on the socket, run through `reduceSession` from client-core, and the result is broadcast to the sockets in that session (socket.io room `session:<user>` for the shared one, `session:<user>/<device>` for a device's own): `session:state` on every change, and when the queue half changed (`queueChanged`), just before the `session:state` of the same version, the queue: as `session:queueOps` to sockets whose hello accepts `queueOps`, as `session:queue` to the others. A socket joins a session room when its hello is answered; device lists and invalidations go to the `user:<id>` room as before.

- **Queue diffs.** The rules are under "Queue diffs" in the session contract. `commit` keeps the queue half it replaced; `broadcast` diffs it against the new one with client-core's `diffQueue` (only lists whose identity changed, so most changes compare one or two lists) and sends the operations to the session room's `#ops` sub-room, which sockets accepting `queueOps` join with it, and the whole queue to the rest of the room only when someone is in it. When the operations would inline more than 256 entries, reorder more than 2,000 or pass 64 KB (`QUEUE_OPS_LIMITS`: a new `playTracks`, a reshuffle), everyone gets the whole queue instead. A track end on a 10,000-entry queue is about 400 bytes this way, against 2 to 3 MB whole. Diffing the result rather than replaying commands covers every way a session changes (server commands, `heldOn`, `replaceQueue`, detach and attach) and does not depend on the server and an app running the same reducer. `session:sync` answers with the snapshot of the session the device is in, in order with its updates; it has the hello budget, and past it is acked `rate_limited` (the client tries again three seconds later).

- **Commands.** The server passes the envelope's `commandId` to the reducer (new entry ids derive from it), remembers recent command ids (the last hundred are stored with the session, so they survive a restart along with their effect) and acks a duplicate without applying it again, and acks a command before broadcasting its result. Server-issued commands use a fresh id. A user's commands, reports and hellos run one at a time, in arrival order, so each socket has a budget (`sessions/socket.ts`): 20 commands a second in bursts of 40, past which commands are acked `rate_limited`; 5 reports a second in bursts of 20; signal paths one a second in bursts of 10; 5 hellos, then one every 5 seconds; 10 detaches and attaches together, then one every 2 seconds, past which they are acked `rate_limited`. Excess reports, signal paths and hellos are dropped.
- **Queue model.** `reduceSession` (client-core) follows streaming apps; the rules are on `SessionCommand` in the contract. A collection started from one of its tracks keeps the tracks before it behind the current one in `playedInCycle` (played or skipped, oldest first), which is what `previous` steps back through and what repeat all plays again; `history` is only the record of what was heard. Entries added with `enqueue` are marked `queued`: they stay put when the queue is shuffled or jumped past (`playQueueEntry` skips everything else between) and repeat all leaves them out. While shuffled, `playOrder` holds the collection order of the queue and of what lies behind, so shuffle off can continue in order after the current entry. Every field added for this is optional or keeps its old shape, so stored sessions and older apps (whose optimistic reducer the server's answer corrects) keep working.
- **Trusted entries.** For `playTracks` and `enqueue` (and Subsonic's `savePlayQueue`) the server keeps only the track ids the client sent: it follows merges, takes durations from the database, drops tracks the user cannot play (explicit ones too for a user who has explicit content off, unless a known clean version plays in their place; see [Explicit content](#explicit-content)), and sets `ready` or `preparing` itself. Rows merged after an entry was made are followed too (`updateTracks`, a server command): when a session loads, each time its current entry changes (for it and the next five), and when acquisition answers for a recording a waiting entry holds under an id merged into it. Requests made under the old id carry over to the new one. Owned tracks are kept for everyone; `on_demand` ones only for a requester (an admin, or a member with `canAcquire`), so no one else gets an entry that would sit preparing and then fail.
- **Undo.** The rules are under "Undo" in the session contract. `runCommand` keeps an `UndoStep` (`sessions/undo.ts`) for each undoable command that changed the session, made from the sessions before and after it (ids and anchors, plus the removed entries), on `SessionRecord.undo` in memory only. `undo` is answered by `applyUndo` instead of the reducer and committed like any change; the client's reducer leaves it a no-op, so nothing is applied optimistically.
- **Limits.** A session is copied on every change and sent whole to older clients and on large changes, so it stays bounded. `playTracks` and `enqueue` carry at most `COMMAND_TRACK_LIMIT` (5,000) tracks, and the queue holds at most `QUEUE_LIMIT` (10,000) entries: an `enqueue` that would grow it past that, counted after untrusted tracks are dropped, is acked `queue_full` and the reducer ignores it, so optimistic clients agree. `replaceQueue` considers at most 5,000 ids from the current one on.
- **Device list.** The live devices (see "Presence" in the session contract), sent on every hello and whenever one comes, goes or changes; `GET /me/devices` answers the same from memory. The `devices` table keeps every device ever signed in, for names and history; no list reads it. A device is live while one of its sockets is open, and a socket stays open only while it answers the heartbeat (see "Realtime"), so a device that went silent leaves within 15 seconds and one whose socket closes cleanly leaves at once. Each socket gets the list as its own device sees it: `isCurrent` marks that device (over HTTP, the device the sign-in was made from). `lastSeenAt` is when the device last sent a hello, command, report, move or heartbeat answer; it moves on in memory and the list goes out again when what the others have is a minute or more behind, so each live device costs at most one list a minute, and no listed device is ever a few minutes quiet, which clients would show as "Active … ago".
- **Signal path.** The active device says what it plays with `session:signal` (servers list the `signal` capability): the file, the stream it receives (profile, transcode reason, a copy on the device) and the normalization it applies (with its target and, from an engine with a limiter, how far that turns the song's loudest peak down), built by client-core's `signalReport` from its descriptor. The server keeps the latest per session in memory only, accepts it only from the active device about the current entry, passes it to the sockets in that session, and puts it in hello and move answers while it still describes the current entry on the active device. Clients show it under the same condition (`SessionClientSnapshot.signal`), so nothing ever clears it. `SessionClient` sends it once the server's state has the entry current on this device, again when it changes (normalization mode, album or song gain) and after every hello.
- **Active device.** The first device that can play and sends a command that starts playback while no device is active becomes active. `transfer` changes it, and only to a connected device that can play. Only the active device may send `trackEnded` and engine reports. A report that is more than a second off the computed position, or changes whether playback is stalled, becomes `syncPosition`.
- **Disconnects.** If the active device's last socket closes while playing, the server stops the session's clock at once (a `syncPosition` that marks it stalled, so every client, older ones included, holds the position), waits 20 seconds, then applies `deviceLost` as of the moment it went away (pause at the position it had then, or at a later change's, and clear the active device), so neither the resume point nor the play counts the grace period, and nothing jumps back. A device that returns within the grace period most likely only lost its connection and played on, so its hello restarts the clock where it would be by then, unless the session changed meanwhile; its next report corrects the rest. A session loaded after a restart gives its absent active device the same grace. During the grace the device is not listed, so no client offers it; the session still names it as active, which is how clients tell (client-core's `away`) and say "Reconnecting to …". After a restart every client reconnects within socket.io's reconnection backoff (at most five seconds), each hello adds its device to the list, and nothing leaves it meanwhile, so it only grows back.
- **Collection plays** (`sessions/collection-plays.ts`). A `playTracks` from a client whose context is an album, playlist or artist with its id, or Liked Songs, upserts `collection_plays (user_id, entity_type, entity_id, played_at)` (Liked Songs under the nil uuid), following album and artist merges and skipping ids that do not exist, and invalidates `queryKeys.libraryItems()` for the user unless it was already their latest. Pages send their own context for Play, Shuffle and their rows, so a song started from Search, Home, a radio or the history counts for no collection; `play`, `next`, `previous`, `trackEnded`, autoplay, transfers and server commands record nothing. The table holds the last play only and was not backfilled: `plays` never recorded a context. Adding to the library counts as a play (`recordCollectionAdd`): a new save (not an Undo, which passes `savedAt`) of an album or artist, or of a track for Liked Songs, a created playlist and an upload's saved albums upsert the row at `now()`, so what was just added heads Recently played. Merges move its rows (the later play wins).
- **Plays.** A play row opens when an entry is current and running on the active device and closes when the entry changes or stops at its end. Listened time comes from the session's position arithmetic, so pauses and seeks add nothing. The open play is stored with the session (and written at shutdown under the id it was given when it opened), so a listen across a restart stays one row. A closed play with under five seconds listened is stored as a skip. Plays also store the session context type and id, when present, from when they opened. A non-skip counts as completed after half the track or four minutes, whichever comes first. History and Home’s Recently played exclude skips. Home’s Most played counts completed plays from the last 90 days. A play is written under the recording and album the track's summary resolves to when it closes (merges followed; the album of its file, else of a release), not the entry's ids, so it never lands on a merged-away row or on the catalog stub album an on-demand track was queued from. Writing a non-skip invalidates history and home.
- **On demand.** The current entry and the next five (`PREPARE_AHEAD`) that are `preparing` are requested from acquisition with `requestRecording`, current first and one after another, so jobs are created in queue order. Each request carries an origin, `play` for the current entry and `prefetch` for the rest (passed through for job ordering; acquisition does not read it yet); a prefetched entry that becomes current is asked for again as `play`, which joins the job in flight, and a queued request the session no longer wants by its turn is not sent. An entry stays `preparing` until the file is linked, then `setEntryState` flips it to `ready` or `failed`. Every failure comes with why (`EntryFailure`: `unavailable`, `outage` or `error`, from acquisition's outcome), and the sockets in the session get `playback.failed` with it just before the state that marks the entries failed. A failed entry further down is only marked, without any notice, and skipped when reached; clients tell it then, as playback passes over it, not when it fails (client-core's `PlaybackNoticeWatcher`). A failed current entry (a failure that comes after a current entry became ready leaves that entry playing) is handled by why:
  - the entry the user just started by name (`SessionRecord.picked`: set by `playQueueEntry`, or `playTracks` with `startedFrom: 'song'` and no shuffle, a row clicked; a list played whole, a header's Play or Shuffle, a card, a radio, or an older client that does not say, moves on past a first song it cannot have), for any reason but `outage`: the session pauses on it, marked failed, without `playback.unavailable`, rather than start a song the user did not pick. Clients tell it as a song that could not play (client-core's `skipNotice` with `held`), and `next` or `play` moves on.
  - `unavailable` (the provider does not have it): skipped. The session keeps the distinct tracks it skipped so (`skippedTracks`: this one and the failed entries the reducer passes over with it), cleared when anything is delivered for the session (a current entry ready, any of its fetches done) or the user starts something new. When nothing after it is playable the reducer stops on it; if that ends a run (others were left in the queue, or more than one track was skipped to get there), the session publishes `playback.unavailable` with `kind: 'exhausted'`. When the run reaches five tracks (`UNAVAILABLE_BEFORE_PAUSE`) with more still ahead, the session pauses on it instead, with `kind: 'unavailable'`: that many in a row more likely means a provider wrongly answering that it has nothing.
  - `outage` (the provider is failing or could not be asked, see "Acquisition"): the session pauses on the first such current entry and publishes `playback.unavailable` with `kind: 'outage'` and the `reason` for clients to show. An entry further down that fails in an outage is not marked: it stays `preparing` and is not asked for again until the current entry changes or the user plays (`deferred`), so a failing provider is not asked over and over, and nothing the outage touched reads as unavailable or is skipped later. When the provider is marked failing, the tracks whose misses that clears come as `restored` in an outcome, and `markRecordingRestored` puts their failed entries back to `preparing` (deferred the same way): the songs skipped as not available before the outage was recognised are playable again.
  - `error` (anything else): skipped, except the third in a row with no current entry ready in between (`FAILURES_BEFORE_PAUSE`; a new `playTracks` also restarts the count), which pauses with `kind: 'failures'`, so a server that fails everything does not run down the queue.

  A pause keeps the rest of the queue and requests nothing more until the user plays again, when `play` moves on from it. The event goes only to the sockets in that session, before the state that stops, so client-core's `SessionClient` puts it in the same snapshot as the stop (`outage`, cleared once the session plays or moves on). Every request gets an answer, so an entry never waits forever; see "Acquisition". A request that throws instead fails the session's entries of that recording as an `error`; a session that loads with a preparing entry whose track is `none` by then fails it as `unavailable`.
- **Autoplay.** Whenever something plays with autoplay on and there are no suggestions, the radio module supplies `setAutoplayQueue` (`sessions/autoplay.ts`), however long the queue, so a device can show what plays after it from the start. A batch is seeded from the ten tracks that play just before it (the end of the queue, reaching back into the history for a short one) and leaves out the last 500 of the queue and the last 100 played. It is asked for at most once per current entry, and only the latest ask's answer is used. `playTracks` empties the autoplay queue, so suggestions always follow what is playing rather than an earlier queue.
- **Sleep timer.** `SessionState.sleepTimer` (see "Sleep timer" in the session contract), offered to clients with the `sleepTimer` capability. The end-of-song and end-of-queue kinds are the reducer's: `trackEnded` moves on and pauses, so they hold wherever the reducer runs, older active devices included. A `time` one is the server's: `armSleepTimer` keeps one timer per session (through `configureSessions`' timers) at its `endsAt`, scheduled again whenever a commit changes the field and when a session loads (one that ended while the server was down fires at once), and cancelled when the session is discarded or the server stops; it applies `endSleepTimer`, which pauses at that moment. The device that plays fades its own gain over the last `SLEEP_FADE_MS` (client-core's `SessionClient`, from `sleepFade`), and one playing offline pauses itself two seconds past the end. Detaching takes the timer with the active device (`leftBehind` drops it from the shared session); a device that was not playing detaches without it, and `bringQueue` brings the own session's.
- **Listen together** (`sessions/service.ts`, "Listen together" in the session contract, `session/jam.ts` in client-core), offered with the `jam` capability over `session:jam` (a budget of its own: 10, then one every 2 seconds). A jam is the host's shared session with `SessionState.jam` (`role: 'host'`, the members, `queuePolicy`, a 22-character `randomToken` id the invite link carries); each member's shared session follows it (`role: 'member'`). `commit` runs a member's next session through `withHost`, which copies the host's (`followJam`: everything but the member's active device and volumes, and no sleep timer), so whatever changes a member's session (their transfer, a device lost, a mirror) lands in step; a host's commit (`noteJam`) keeps the in-memory jam index and queues a mirror in each member's serial queue, members just removed included, who leave (`jam.left`, then paused where it was, `leaveJam`). A member's session does none of a session's own work (`following`: no fetching ahead, autoplay, catalog refresh, failure handling, clock stop on a lost device, or re-anchoring from reports): the host's session does it, under the host's permissions. A member's command goes by `memberCommandRoute`: `transfer` and `setVolume` apply to their own session; `enqueue` (with `queuePolicy` `everyone`, tracks trusted for the member and then for the host, stamped `addedBy`), `removeFromQueue` (of their own additions) and `trackEnded` (within `JAM_END_SLACK_MS` of the end, so the first device to finish moves everyone on) run on the host's session in the host's queue and are acked from the member's queue once it has the result; anything else is `jam_host_only` (`setSleepTimer`: `jam_unsupported`). Cross-user work never awaits another user's queue from inside one (a join, a leave and a forwarded command chain the host's and then the member's), so two users' queues never wait on each other. While in a jam the host's reports re-anchor past `JAM_DRIFT_MS` rather than a second, and members' devices seek back to the anchor past it (`SessionClient`'s jam alignment). Membership lives in the sessions' stored state, so it survives a restart: a member's session that loads first loads the host's (`refollow`). A joining device becomes the member's active device when it can play; a detached device can't join (`jam_detached`), a host can't join another (`jam_hosting`), and a jam holds `JAM_MEMBER_LIMIT` (16) people. Detaching leaves the jam with the shared session (`withoutJam`), and `bringQueue` keeps it. Subsonic's `savePlayQueue` leaves a member's session alone. `invite` publishes `jam.invite` to the invited users' rooms. The host's session holds the sleep timer, whose end pauses everyone through the mirror. Only the host undoes: forwarded member edits are not pushed on the host's stack, a member's `undo` is `jam_host_only` (`SessionClient.canUndo` is false while following, so clients offer none), and joining empties the member's own stack. Each member's session counts its own `version` and `queueVersion`, so `commit` diffs a mirror against that member's previous queue and its sockets get `session:queueOps` (or the whole queue) like any session's; signal paths are kept per listener's session, from its own active device.
- **Detaching.** `session:detach` gives a device that can play a session of its own, copied from the shared one with `forkSession` (client-core); `session:attach` discards it, and with `bringQueue` first makes the shared session what it was (`bringSession`). The rules are in the "Detaching" section of `packages/contracts/src/session.ts`; the server's side of them:
  - Own sessions are rows of `detached_sessions` (one per device, cascading with the `devices` row), written before the device moves and then like shared ones, with `last_seen_at`. Once loaded, one stays in memory like a shared session (so it keeps its recent command ids) until shutdown or until it is discarded. Its device leaving while it plays gets the same grace period and `deviceLost`.
  - Which session a device is in is decided by its first socket's hello: the stored own session when there is one and the hello carries `detached` (either value), else the shared one. A hello without `detached` is from a client that cannot detach and discards a stored own session. Later sockets of a connected device join whichever session it is in, and when it moves, its other sockets get `session:moved`.
  - All of a user's sessions share the user's one serial queue, so detaching and attaching change both sessions in one step. The `detached_sessions` row is written (detach) or deleted (attach) before anything in memory changes, so a database error leaves the device where it was; the shared session is then written at once rather than a second later. The open play moves with the device: detaching while active carries it into the own session, bringing the queue back carries it into the shared one (closing the play the shared session had), and attaching without it closes it.
  - An own session runs everything above as the shared one does (trusted entries, fetching ahead, the pause after failed fetches, autoplay, plays), and its `playback.unavailable` goes to its device alone.
  - A device in its own session can transfer only to itself, and the shared session cannot transfer to a detached device. `DeviceInfo.detached` lists what each detached device plays, and the list is sent again when that changes.
  - Limits: eight own sessions per user. Detaching drops sessions unseen for seven days, then, if eight remain besides the device's own, the one whose device was seen longest ago among those not connected; with eight connected it is refused. Sessions unseen for seven days are discarded at the user's next returning hello or detach. There is no background sweep, so a user who never connects again keeps their rows until the user is deleted.

### Scrobbling

- **Connections** live on the user row under `settings.secrets.<listenbrainz|lastfm>`: the credential (ListenBrainz user token, Last.fm session key) encrypted with `encrypt('scrobble-credential', …)`, the account name, `since`, `needsAttention` and `lastError`. Connecting verifies the credential (`listenbrainz.validateToken`, Last.fm's web auth flow) and switches the user's `scrobbleListenBrainz`/`scrobbleLastFm` on; disconnecting switches it off and drops unsent rows. Reconnecting the same account keeps `since`, so plays waiting for it are still sent.
- **Last.fm web auth.** `POST /me/scrobbling/lastfm/start` returns Last.fm's approval URL with a callback carrying `state` = user id, expiry (10 minutes) and `sign('lastfm-connect-state', …)`. The callback base is `PUBLIC_URL`, else the request's origin. An app passes `returnTo`, an address in one of `lastFmReturnSchemes` (`squirmy://`, `squirmy-dev://`); it rides on the callback as `return`, the signature covers it, and the callback redirects there with `lastfm=…` instead of to the web app. The iOS app opens the approval in an `ASWebAuthenticationSession` (`openAuthSessionAsync`), which closes on that redirect.
- **Sweep.** `scrobble.sweep` (every minute and at worker start) inserts one `scrobble_deliveries` row per service for each completed play of the last 14 days that started at or after `since`: `pending` when the service is switched on, `skipped` when off. It then queues `scrobble.deliver` `{ userId, target }`, keyed by both, where rows are ready.
- **Delivery.** `scrobble.deliver` locks the oldest ready rows (`for update skip locked`) in the service's batch size (ListenBrainz 1000, Last.fm 50), submits them with the MusicBrainz recording, release, release group and artist ids when known, track number, duration, album and start time, and marks them `sent`. A failure counts an attempt and the row waits 1, 2, 4… minutes (at most 6 hours) for the next sweep; after 10 attempts it is `failed` and left alone. A rejected credential (ListenBrainz 401, Last.fm error 9) sets `needsAttention` instead, and rows wait for the user to reconnect.
- **Guarantees.** The row is the idempotency record: one per play and service, submitted while locked, so overlapping sweeps and deliveries send a play once. The one gap is a crash after a service accepted a batch and before the commit, which resends that batch once.
- **Now playing** is sent from the API process when `onPlayStart` fires, best effort and without retries.

### Replay and history transfers

- **Imported history.** `userdata.history-import` reads a staged export incrementally and checks normalized recording credits and titles against the catalog. Matching album placements break ties. A batch commits its private import ledger, matched `plays` and progress together. The ledger deduplicates by user, source and fingerprint, and keeps unmatched metadata in private history to keep search results focused on the shared catalog. Scrobbling excludes imported plays. Replay aggregates matched and unmatched history, except early skips. API and worker processes share the data directory so either can reach staged uploads.
- **Replay.** `userdata/replay.ts` builds calendar windows in the requested IANA time zone. It aggregates listening rows by recording and album before joining catalog credits and genres. Local hourly buckets feed the clock, totals and streaks. Existing history invalidations also refresh Replay.

### Integrations

[Integrations](./server/integrations.md) owns user and server webhook subscriptions and the administrator's MQTT broker configuration. Event producers enqueue a signed delivery with an event ID that stays stable across pg-boss retries. HTTP destinations are checked as sockets resolve DNS and redirects are disabled. The API process runs the MQTT bridge and applies broker commands through the same playback session reducer as connected clients. Scoped native bearer tokens share the app-password lifecycle and are authorized against a route allowlist. The existing Subsonic credentials retain their original access.

### Radio

- `suggestAutoplay` (the seam) and the radio routes rank with `radio/ranking.ts`: profile the seeds (artists, album and artist genres, years, similar artists, and Deezer's radio of the two most recent seed artists), gather a few hundred candidates in one query from bounded pools (seed artists, similar artists, Deezer's radio, albums sharing a genre or era, tracks the user played within half an hour of a seed, liked tracks and artists, a few random albums, and the analysed tracks that sound most like the seeds), score them with the weights in `ranking.ts` plus noise, and pick under variety rules over any ten consecutive tracks, seeds included: two per artist, one per album, three by seed artists, no artist twice in a row.
- Sonic analysis (`radio/sonic.ts`, from the sonic module) adds three things, all with weights small next to the noise. A `sonic` feature: (1 − p)², where p is the share of the analysed library nearer the seeds' averaged timbre vector than the candidate, so it needs no calibration; a candidate with no analysis (on-demand ones) gets the average of the analysed candidates, so analysis never favours owned tracks. A pool of the nearest few percent of the library (at most 40), which count as related. And a transition cost at each pick from the previous track: a tempo jump past 3% (octave-folded, so double time is no jump), a key two or more Camelot steps away, an energy jump past 0.15; each only when both tracks know it with enough confidence. `POST /radio/sonic/:id` is the track radio in `mode: 'sonic'`: the `sonic` weight is 6 instead of 1.5, up to 120 neighbours are gathered, and unknown sound counts as 0. A seed with no analysis gets the ordinary mix and its analysis is queued at priority 0 (`analyzeSoon`). Autoplay after a sonic radio continues in the ordinary mode.
- A candidate is *related* when it is by a seed or similar artist, in Deezer's radio, shares a genre with the seeds (cosine at least `GENRE_RELATED`), or the user played it near a seed on at least two different days (one day is one session, or several people testing one account). Likes, popularity and owning a file only order candidates. Related ones are picked first, under the strict rules and then relaxed ones; unrelated ones (the random albums, a liked song of another genre) only fill a batch up to one window (`FILL_UP_TO`, ten), and past that the batch ends early: a radio that runs out continues through autoplay from its own last tracks. The rules drop last. An artist's tracks, in the pools and in the seed profile, are those it is credited on plus those it leads (`primary_artist_id`), since older rows and catalog stubs can lack credit rows. `suggestAutoplay` follows merge redirects of its seeds and exclusions first, so a queue entry holding a merged id still keeps its track out.
- For a requester (an admin, or a member with `canAcquire`), `on_demand` tracks from the seed-artist, similar-artist, radio and liked pools are gathered too and ranked together with the owned ones. What is on the server is mostly whatever was played lately, so having a file is no reason to suggest a track: it only breaks a near tie for the first pick (within `INSTANT_MARGIN`, the noise's range), so playback after the seeds starts without a fetch. The rest are fetched ahead while the first ones play. Everyone else gets owned tracks only, and nothing when none qualifies.
- Deezer's radio comes from enrichment's `artistRadioTracks` seam (`enrichment/radio.ts`): Deezer's `artist/<id>/radio` (the artist's Deezer id from `external_ids`, else an exact-name search, not linked), each track mapped to the row a page's popular tracks would use (`deezerRadioTrackRow`: by Deezer id, ISRC or the artist's title, else a provider-only stub with its album hint; its artist by `deezerArtistRow`'s rule). That brings artists the catalog has never heard of into a radio, and the artists it names count as similar artists (0.5, unless `similarArtists` ranks them higher). It runs before the similar-artist lookup so that lookup maps to the rows it wrote. The seam answers within the ranking's wait with the rows written so far and writes the rest in the background; one artist's rows are reused for an hour per process.
- Owned album pools sample albums with a present file linked to a recording. Co-listening uses non-skipped plays and limits its owned candidates after filtering for files. Two or more early skips of a recording by the listener in the last 30 days apply a small score penalty.
- Random sampling in SQL uses `uuid_hash_extended` with a salt drawn from the injected random source, so a seeded source repeats a result exactly.
- `similarArtists(artistId)` merges Deezer related artists (of the artist's Deezer page with the most fans, since search can link a namesake's page by name; else an exact name search) and ListenBrainz similar artists (with a server token and an artist MBID), mapped to catalog artists by MBID, else `name_key`. Deezer's suggestions the catalog lacks become artist stubs with their page and picture (`enrichment/deezer-rows.ts` `deezerArtistRows`, the rule search uses), so the rail does not depend on what someone happened to search; ListenBrainz's are left out. A source that is off or fails is skipped; lookups during ranking (Deezer's radio, then similar artists) share a 2.5-second wait, with at least half a second left for similar artists.
- A radio is up to 50 tracks starting with the seed track (fewer when the related ones run out) with context `{ type: 'radio', id: 'track:<id>' | 'artist:<id>' }`. Nothing is stored: when the radio runs out and autoplay is on, the session's history (the radio's last tracks) seeds the next batch, so it continues in the same direction.
- The seed obeys the queue's rule: a track with a file for everyone, an `on_demand` one for a requester, else 409 `not_playable`. An artist radio starts from the artist's playable track the user played most, then liked, then one with a file (so it plays at once), then the most popular; for a requester that includes its top tracks and discography on demand, so an artist with nothing on the server still has a radio. When nothing of the artist has a track list yet (albums found by search) and an `assume_available` provider would play them, it first fetches the track lists of two albums (studio albums, newest first) through `ensureAlbumDetail`, each within the page budget. Nothing playable is 409 `nothing_playable`.
- `canStartArtistRadio` answers the same question without fetching, for `ArtistDetail.radio`: clients offer an artist radio only when it is true.
- For a user who has explicit content off, no explicit track is a candidate, a seed or an artist radio's first track ([Explicit content](#explicit-content)).
- **Mixes** (`radio/mixes.ts`): the user's top 40 artists by completed plays over 90 days (weighted toward recent plays) are clustered by `affinity`, a noisy-or of genre cosine (genres and their words, so "Folk" meets "Indie Folk"), similar-artist scores (`similarArtists` of the 12 most played), co-listening (hours in which the user played both) and the `artistSoundAffinity` seam. The most played artist left starts a cluster and takes artists whose mean affinity to it is at least `LINKED`, up to eight; a cluster becomes a mix with enough plays. Each mix opens on the user's favourites by its artists (180 days) and interleaves them with `suggest` seeded by them (random choices seeded by user, day and slot), leaving out suggestions whose known genres have nothing to do with the mix (radio's fill), and no song in two mixes; a mix needs ten songs. Up to six are stored per user in slots that keep their ids (`mixes`), named after the slot and the two leading genres. A mix plays with context `{ type: 'mix', id }`.

### Sonic analysis

`modules/sonic` measures how each file sounds with Squirmy's own DSP (`sonic/dsp/`) on mono 22.05 kHz PCM that ffmpeg decodes (`decode.ts`, through `audioInput`, at nice 19). Each pipe chunk is analysed as it arrives, a few milliseconds of work, so memory stays flat and the event loop is never held; files are analysed up to their first 30 minutes.

- **Per frame** (2048 samples, hop 512, about 43 a second) one FFT gives a 40-band mel spectrum, 13 MFCCs, spectral flux (onset strength), centroid, flatness, rolloff, the zero-crossing rate and the level, and spectral peaks between 100 Hz and 5 kHz go into a 10-cent pitch-class histogram weighted by the frame's level.
- **Tempo** (`dsp/tempo.ts`): averaged autocorrelation of the smoothed onset envelope over nine-second windows, a log-normal prior at 120 BPM an octave wide (as librosa), then a comb over the whole track to refine the period (coarse, then fine) and a phase fitted to the first 30 seconds. Clarity (the autocorrelation at the period) is the confidence. **Key** (`dsp/key.ts`): tuning from the circular mean of the histogram, folded to 12 bins, correlated with the Krumhansl–Kessler profiles. **Levels**: the audible part (within 30 dB of the median 400 ms level), intro end and outro start (within 6 dB of it), loudness range from three-second levels. **Energy** and **danceability** are documented heuristics in `dsp/analyzer.ts`.
- **Timbre vector**: 34 raw descriptors (`VECTOR_LAYOUT`: MFCC means and deviations, spectral shape, onset rate, loudness range, pulse clarity, key strength, level). `vectors.ts` standardizes each over the library and weights each group (`GROUP_SHARES`), and keeps one vector per recording (its best analysed present file) in memory. Neighbours are found by brute force: 100,000 tracks are 13 MB and a few milliseconds per query. The index is checked against a signature at most every minute and rebuilt at most every five while analysis runs (always while it holds fewer than 500 vectors).

Storage: `sonic_analyses` (one row per file, cascading with it) holds the features, the file's audio hash and `ANALYSIS_VERSION`; a row with `version` null records that only the file's tags were read (analysis off), one with `error` that ffmpeg could not decode it. `sonic_hints` holds Deezer's tempo per recording. Tempo, key and mood tags live in `media_files.tags` (`FileTags.bpm`, `key` as written, `moods`): `library/tags.ts` reads them on probe, and `sonic.analyze` reads them again for files probed before it did, without a full probe (which would queue ingest for every album).

Jobs: `sonic.sweep` (every ten minutes and at worker start) queues up to 300 present files with probe stage 2 and loudness known that have no row, or (with `sonicAnalysisEnabled`) whose row is from another version or audio hash, oldest first at priority −30; then, with Deezer on, `sonic.deezer-tempo` for up to 100 owned recordings with a Deezer id and no tempo from tags or analysis, none still to come, rechecked after 90 days. `sonic.analyze` has one slot, so analysis takes one core at most. Switching the setting on queues a sweep at once (`queueSonicSweep`, from `PATCH /admin/settings`).

Reading it (`profile.ts`): tempo and key come from tags first (DJ software writes better ones than a generic analysis; confidence 0.9), then the analysis, then Deezer's tempo (0.5, often an octave off). For the hooks other features build on:

- **Daily Mixes**: `sonicIndex()` and `vectorOf` give every analysed recording's standardized vector, for clustering a user's listening; `sonicNeighbours(ids, { limit, exclude })` the nearest tracks to a set, with a 0..1 similarity by rank; `sonicPoints(ids)` tempo, key, energy and danceability for ordering a mix (with `transitionCost` in `radio/sonic.ts`).
- **DJ transitions and crossfades**: `fileTimings(recordingIds)` on the server, or `GET /tracks/:id/sonic` (`files[]`) in clients, gives each file's `bpm`, `beatOffsetMs` (beats at `beatOffsetMs + n·60000/bpm`), `audibleStartMs`, `audibleEndMs`, `introEndMs` and `outroStartMs`, matched to the playback descriptor's `fileId`. A crossfade can start at the outgoing file's `outroStartMs` and end at the incoming file's `introEndMs`, aligned to both beat grids when the tempos are within a few percent. Adding these to the playback descriptor is the natural next step for gapless clients.

**Why our own DSP.** It runs wherever Node and ffmpeg do (ARM64 and x86, nothing added to the image), is GPL like the rest of Squirmy, and costs about 0.4 s of CPU plus 0.2 s of decoding per four-minute track on Apple Silicon (several times that on a Pi 5, so a 20,000-track library takes about a day there). Rejected:

- **Essentia** (MTG's extractors, with or without TensorFlow models): AGPL-3.0, which GPLv3 §13 lets us combine with but which puts its network clause on the combination; no Linux aarch64 build on PyPI or as a static extractor, so ARM servers would need it built from source; Python and numpy add about 115 MB to the image, TensorFlow about 720 MB; its `MusicExtractor` took 4.4–5.1 s per four-minute track on the same Mac. Its pre-trained models (Discogs-EffNet, MusiCNN, MAEST, the mood and genre heads) are non-commercial (CC BY-NC-SA/ND), which conflicts with GPL redistribution.
- **Learned embeddings through ONNX Runtime** (CLAP, OpenL3, YAMNet, EfficientAT, CED): `onnxruntime-node` is MIT and has linux arm64 binaries (26 MB of its 308 MB package), and permissively licensed models exist, but they are trained for audio tagging rather than music similarity, add 20–500 MB of weights, and cost 0.7–3 s per track on Apple Silicon before preprocessing. The best music models (MERT, MuQ, MAEST) are non-commercial. A permissive model can be added later as another vector beside this one, behind its own switch.
- **pgvector**: not in the official `postgres:17` image that `compose.yaml` runs, and unnecessary at home-library scale with 34-dimension vectors. A future learned embedding of 512 dimensions would want it, with this brute-force path as the fallback when the extension is missing.
- **Deezer's tempo alone**: only single-track lookups carry it, it is often 0 or an octave off, and it covers only music Deezer has.

### Subsonic

`modules/subsonic` serves OpenSubsonic under `/rest` over the same services; [subsonic.md](./server/subsonic.md) lists what it supports.

- `router.ts` answers every method on GET and form POST, with or without `.view`. Handlers return plain objects that `serialize.ts` writes as XML or JSON(P). Failures are Subsonic error codes in a 200; service `AppError`s map to the closest code (404 is 70, 403 is 50).
- Every request authenticates with an app password (token, password or `apiKey`); there is no lockout, since app passwords cannot be guessed and are cheap to check.
- Ids carry their kind (`ar-`, `al-`, `tr-`, `pl-`, `ca-` for an artwork asset) and are checked on the way in. Music folders are library roots, numbered by a hash of the root id.
- Lists show the user's library restricted to tracks with a present file (`sql.ts`): a library file is a present collection file when the collection counts for the user (`collectionCounts`), or a present file whose recording or album the user saved (for a recording, that is the catalog's `inLibraryRecording` plus a present file); a library album is `inLibraryAlbum` with a library file, and its songs are its library files; artists are credited on a library album or track. Library albums are found from the library files, so search stubs cost nothing. Lookups by id (`getSong`, `stream`), starred songs and playlist entries need only a present file. `songs.ts`, `albums.ts` and `artists.ts` build response objects in batches with a fixed number of queries (`albums` and `artistRows` return only library rows); a song is shown through the present file `selectFile` would stream.
- `search3` and `search2` rank a query with the search module's library search (`searchLibrary`), so typos are tolerated as in the apps, and keep what is in the user's library or the server's collection (the `server` reach of `sql.ts`), so a search finds all of the server's music as Squirmy's own does. `getAlbum`, `getArtist` and `getMusicDirectory` reach the collection too: lookups by id. An empty `search3` (sync) and the other lists keep to the library. Sync clients page through everything with an empty `search3`. The page that starts where the user's previous one ended continues from its last key, so deep pages cost what the first does.
- `stream` serves originals and the streaming profiles through `openStream`. A bitrate below every profile, or a `timeOffset`, is an uncached live ffmpeg encode that stops immediately when its client disconnects. It takes a streaming encoder slot without waiting (`tryAcquireSlot`). Up to three such live encodes count toward the user's combined cap of four. A refusal is `transcoder_busy` (503) or `too_many_live_encodes` (429), sent as a Subsonic error before any header.
- Sized `getCoverArt` requests use cached JPEG renditions by default and WebP when explicitly accepted. Responses vary by `Accept`. Playlist IDs require the same visibility as the playlist itself.
- `getNowPlaying` shows the caller their own live playback and includes other accounts only when they have enabled `shareNowPlaying`. The setting defaults to off for existing and new users.
- For a user who has explicit content off, `songs.ts` leaves explicit songs out of every answer (by the file's own advisory, else the catalog's), and `stream` and `download` refuse them with error 50 ([Explicit content](#explicit-content)).
- `getAlbumList2`'s `frequent` orders albums by completed plays and `recent` by the latest play that was not an early skip, as Home counts them.
- The play queue is the session queue (`getSnapshot`, `replaceQueue`). The songs a client saved before its current one are remembered in memory while the session's current entry and queue are unchanged.

### Library pipeline

Jobs, in order. Each is idempotent and keyed by file or album group.

1. `library.scan` `{ rootId, paths? }` walks a root, or just the given paths, and compares `(rel_path, size, mtime)` with `media_files`: new files are inserted at `probe_stage 0`, changed ones reset to it, vanished ones get `missing_since` and returning ones lose it. A row is marked missing only while it still has the path the scan read and nothing is at that path when the scan writes: files move during a scan (Organize filing a delivery out of `_Incoming` while the watcher's scan of that folder runs), and a row marked missing by mistake makes its recording unplayable for a moment, long enough for the acquisition job checking that delivery to fail it. Probes are queued in bulk. The walk (sorted by UTF-8 bytes) and the rows (read in pages, `collate "C"`) are merged like two sorted lists, so memory and queries stay flat whatever the library size. Hidden entries, `@eaDir`, recycle bins and partial downloads are skipped; symlinks are followed only to files inside the root, also when the scanned path itself is a link or lies under a linked folder. Serving and every ffmpeg read resolve a file's links (`libraryPath`) and refuse one whose real path is outside its root's (403 `path_outside_root`). A root that cannot be read is skipped rather than marked missing. One scan per root at a time (the root id is the singleton key); `library.scan-all` runs nightly. A full scan asked for while a watcher or import scan of some paths holds the key is not dropped: a queued partial scan becomes the full scan, and a running one is followed by `library.scan-after`, which the partial scan's job runs as soon as it finishes (or, failing that, which queues the full scan on its own 15 minutes later).
2. `library.probe` reads tags and technical details with `music-metadata` (ffprobe fills gaps and takes over when it cannot parse), normalizes them into `FileTags`, reads ReplayGain (and Opus R128) into the `tag_*` columns, stores the embedded picture, sets `probe_stage 1` and the group key, then queues ingest for the group. A file nothing can read gets `probe_error` and is left alone until it changes.
3. `library.ingest` `{ rootId, groupKey }` creates or reuses local-only catalog rows (artists, album, release, recordings, release tracks) from the group's tags and links the files, in one transaction. Rows the files already use are reused unless another group has more files on them (or as many and an older file), so a group that loses a file keeps its rows whichever of the two is ingested first; rows with a MusicBrainz id in the tags are found by it or created with it, and are never renamed from tags afterwards. The album type comes from a release-type tag (`RELEASETYPE`, "MusicBrainz Album Type"), else a compilation flag, else a lone file without an album name is a single; otherwise it is "album" with `type_guessed` set, so a single delivered before its catalog row is known is not taken for an album. Files a provider delivered (their import belongs to an acquisition job) take their artists from the request, and tags only fill gaps: a delivery of one requested recording is credited as that recording (and its album as the requested album), whatever its tags spell; for other deliveries each tag credit resolves to the requested recordings' and album's artists by name, by the whole credit, or split into them when every part is one ("Grimes, VADAKIN"). A store's spelling used to mint a second artist beside the catalog's. A group with a matched or locked file is only relinked. Rows that end up unused (no files, no user data, no MusicBrainz id) are removed. Then album and artist art from the folder and files, lyrics (embedded or a `.lrc` sidecar), and `matching.match-album`. After this step the music is browsable and playable.
4. `library.analyze` (low priority) computes the audio hash and sets `probe_stage 2`. A new file whose hash matches a row whose file is gone is that row moved: the old row takes the new path and keeps its id, links and match state. Then `loudness.measure`, and once loudness is known `sonic.analyze` (see "Sonic analysis").
5. `matching.match-album` `{ rootId, groupKey }` (singleton key `<rootId>:<groupKey>`) upgrades local-only rows to MusicBrainz rows, opens a review, or leaves the files `unmatched`. The matcher tries the tagged release MBID, the tagged release-group MBID, an exact barcode lookup, an album artist and title search, and then ISRCs (after the search, since they cost up to five rate-limited requests). ISRC lookup samples up to five distinct codes and votes for releases with the same track count as the album’s files. Each stage can stop the search once the best candidate qualifies for automatic acceptance. If none qualifies and an AcoustID key is set, the matcher looks up fingerprints and scores all candidates with the added recording evidence. It applies the best qualifying release under the catalog lock, like ingest, or keeps up to five ranked candidates for review when the best score is plausible. `matching.sweep` re-queues groups still `pending` every ten minutes and at worker start. When `PATCH /admin/settings` switches MusicBrainz on, `queueNewlyPossibleMatching` (`matching/retry.ts`) queues a sweep at once; when an AcoustID key appears it queues `matching.retry-fingerprints`, which sets unlocked `unmatched` files with no known AcoustID back to `pending`, then sweeps. Both leave alone files in `_Incoming/<importId>/` while that import is processing and has no `duplicates_decided_at`, so no provider is asked about copies about to be deleted or about half an album; the import queues their matching once it has decided.
6. `enrichment.album` and `enrichment.artist` (queued by the match) fill in covers, images, bios, Deezer ids and lyrics; see "Enrichment".

Every ffmpeg and ffprobe call that reads a library, staged or delivered file puts `INPUT_GUARD` (`lib/ffmpeg.ts`, through `audioInput`) before the input: the `file` protocol only, and only the demuxers of the scanner's audio extensions, because ffmpeg picks a demuxer by content and a concat script, playlist or SDP named `x.flac` would otherwise open other files or sockets. fpcalc has no such options, so `acoustid.fingerprint` pipes samples from a guarded ffmpeg into `fpcalc -format s16le` and takes the duration from the guarded probe.

`library.purge-missing` runs daily and deletes files missing longer than `missingFileGraceDays`. The grouping and album artist rules are written out at the top of `modules/library/grouping.ts`. In short, the album grouping key is root id, parent directory (ignoring `CD1`/`Disc 2` subfolders), and `matchKey` of album artist and album. An album artist tag that is a track's several artists run together ("A, B", where the multi-value artists tag names A and B) credits those artists, never one artist named "A, B". Because the folder is part of the key, every acquisition delivery is a group of its own; acquisition places delivered files on the requested album itself (see "Acquisition") instead of leaving them to ingest and matching.

Watching: roots with `watch` on are watched while a worker runs, and changed paths are scanned after two quiet seconds. macOS and Windows use one recursive watch per root; Linux uses one inotify watch per folder. Network mounts and exhausted inotify limits fall back to the nightly scan.

Scans skip `_Incoming/<importId>` folders while that import is extracting or moving files into them, and organize leaves `_Incoming` out of its plans unless `includeIncoming` is set. Organize plans provider deliveries (`cached`) under `_Fetched/` with the root's template inside, and other files out of it. A filed delivery is moved again only when a path component the template fills from an artist credit is no longer what its credits give (`refileCredits`, `organize/refile.ts`): the acquisition repair runs it for each managed root on full runs and after placing anything, the batch is dropped when it moves nothing, and the mover removes the folders it empties. A file a scan finds under a managed root's `_Fetched/` with no row gets `source = 'provider:unknown'`, so a database restored without it keeps it as cache; nothing in a read-only root is ever cache. When move detection reconnects a cached row to a file moved out of `_Fetched/` (or into another root), the row takes the new file's source: the owner moved it to keep it.

Album tag edits use the organize module’s verified writer. A successful write preserves the packet hash, refreshes probe data and queues group ingest and matching in the same database transaction. Locked matches keep their links. Library duplicate removal revalidates the file and its surviving copy through the library deletion path. A low-priority worker checkpoints audio decode and hash results per file. See [library maintenance](./server/library.md#edit-album-tags).

### Imports

`modules/imports` brings music in through the server: web uploads, the inbox folder, and acquisition deliveries (which call `createImport`, `addImportFile`, `commitImport` and `failImport` from `modules/imports/index.ts`). Whatever the origin, an import is a row in `imports` and goes through the same steps:

```
receiving ──commit──▶ processing: extracting → moving → identifying → filing ──▶ completed
    │                                                                       └──▶ failed
    └── cancel, provider failure, or a day without files ──▶ failed
```

- **Receiving.** Files stream into `<data>/staging/<importId>/` through a byte counter, as a temporary dot file, and are linked into place in the same transaction that bumps the import's counters, so a concurrent commit or cancel sees all of a file or none of it. Names are checked first (`imports/paths.ts`): audio by the scanner's extension list, `cover.*` and `folder.*` images, `.lrc`, `.cue`, `.log` and `.zip` (`importFileKind` and `AUDIO_EXTENSIONS` in the contracts, so the web app marks a file the server would refuse before sending it); relative paths are normalized and must not be absolute or contain `..` or control characters, at most 8 levels and 1024 bytes. `importMaxFileBytes` and `importMaxBytes` bound files and imports (413). Nothing follows or creates a symbolic link. An upload that would leave less than 1 GiB free on the staging disk (`imports/space.ts`; the request's Content-Length counts, and a file is checked again every 256 MiB) is refused with 507 `insufficient_storage`, and `createImport` refuses a member's upload past `importMaxActivePerUser` receiving or processing ones (429 `too_many_imports`; admins exempt).
- **Target root.** `importRootId`, else the only enabled managed root; otherwise creating an import fails with `no_managed_root` or `import_root_not_set`.
- **`imports.process`** runs the steps; each is idempotent and records its outcome before the import moves on, so a retried job carries on after a crash. *Extracting* reads each zip in two passes with yauzl (check every entry, then extract into a temporary folder renamed into place); an archive with an unsafe path, a symbolic link, encryption, more than 10,000 entries, more bytes than the import may hold, or more than 20 times its own size (beyond 64 MiB) is refused whole, and one the disk has no room for fails the import, and nested zips are skipped. *Moving* uses organize's mover (rename, or copy, verify and delete) into `<root>/_Incoming/<importId>/`. *Identifying* queues a scan of that folder and watches `media_files`: it marks rows with `source` and `import_id`; once every file has its audio hash (or an error), it decides in one transaction which files are duplicates and deletes them, recording `imports.duplicates_decided_at` and the paths in `work`. A file is a duplicate when the library already has its audio, when an older import still processing has it, or when an earlier path in the same import does, so the outcome does not depend on the order analysis finished in. For an upload or inbox import, a provider delivery (cache) never counts as the library having the audio: the owner's copy is kept. For an acquisition import it also records the library files its duplicates were copies of (`work.copies`; only earlier provider deliveries not locked by "Fix match") and, on every pass from then on, hands the delivery to acquisition (`settleDelivery` in `acquisition/delivery.ts`), which checks it against the request and places what fits on the requested album before matching is awaited. Then it waits until the rest is ingested and matched, or for an hour, after which duplicates are decided from the hashes known by then and the rest is left for review. *Filing* plans and applies one organize batch for the import's own files still in its folder that are identified with confidence (matched, or placed by acquisition), removes the folder when no audio is left in it, refreshes wants and records the counts. `refileImport` runs the filing step again for a completed import, for files identified after it ended.
- **Completion** is read from the row; every status and step change publishes `import.updated` to the owner and admins.
- **Inbox.** One worker (an advisory lock) polls the inbox (`inboxPath`, else `SQUIRMY_INBOX_PATH`) and takes each top-level item once it has been unchanged and readable for five seconds, moving it into staging. What an import does not take, and failed inbox imports, go to `Not imported/<importId>/` in the inbox. The inbox may not overlap a library root or the data folder.
- **Uploads** (`imports/uploads.ts`) are the present files of finished `upload` and `inbox` imports (`media_files.import_id`), grouped by the import's user (none for the inbox) and album, newest first. `GET /me/uploads` lists the caller's, `GET /admin/uploads` everyone's. Deleting an album's or one file's uploads goes through `deleteLibraryFile` (`library/delete.ts`), the deleter the provider cache's eviction uses: under the catalog lock, only in a managed root, it removes the file from disk, its row and the local-only catalog rows it leaves unused, then the folder's sidecars and empty folders (anywhere in the root, not only `_Fetched/` and `_Incoming/`). The file must still be an upload of the scope when its row is locked, so a scanned file of the same song or another person's upload stays. When the album is left with no file, the uploader's own save of it goes in the same transaction (the upload made it); other people's saves stay, and keep the album. Afterwards the server announces availability, `deleted` for albums that are gone, and invalidates the library and Home for everyone, the uploaders' `uploads()` and admins' `admin()`. It cannot be undone.
- **`imports.sweep`** (every 15 minutes and at worker start) expires imports stuck receiving, re-queues processing ones and removes orphaned staging folders.

### Acquisition

`modules/acquisition` implements the server side of [provider-protocol.md](./provider-protocol.md). Nothing happens until an admin adds a provider.

- **Providers** are rows in `acquisition_providers`; the secret is encrypted with `encrypt('acquisition-provider-secret', …)`. A provider counts once it is enabled and has answered `capabilities`, which the server asks for when the provider is added, tested or given a new address or secret, and every five minutes for enabled providers (`acquisition.check`, `checkProviders`; an answer sets `last_ok_at` and clears `last_error` unless the provider is failing, a failure is kept as `last_error` as a failed resolve is, a busy answer is ignored, and none of it touches the failing streak). The enabled list is cached in memory for 30 seconds (and dropped on every change in that process), so `onDemandRecordings` costs nothing without one. Every call goes through `client.ts`: timeouts, the bearer secret, redirects only within the provider's origin, at most 4 MiB read, contract validation; failures are `ProviderCallError` and end up in `last_error` or the job's `error`.
- **Policy** is the `acquisition_policy` row of `server_settings` (`AcquisitionPolicy`): lossless preference, per-file limit, the cache limit (`storageQuotaBytes`), timeout, target root, and the delivery base URL (the policy's, else `PUBLIC_URL`, else localhost).
- **Coverage** (`onDemandRecordings`). An `assume_available` provider covers every recording without a miss that counts (below). A `must_resolve` provider covers recordings with a positive resolve newer than 30 days (`acquisition_offers`, free offers only). Recordings it has never answered for are collected in memory for a quarter second, queued as `acquisition.resolve` jobs of up to 100, and remembered for ten minutes so lists do not queue them again; when the answers arrive, the tracks that lit up and their albums are announced with `announceAvailability`. Album pages also queue optimistic coverage checks for unowned tracks, and prefetch jobs can resolve the next five queue entries together, with each recording’s album context. Optimistic checks reuse unexpired offers for an hour and the same day-long misses as playback. A busy resolve is retried and creates no misses. Optimistic misses use the same availability patch to gray out tracks live, and the queue’s existing unavailable outcome skips them. A provider's coverage is the admin's `coverage_override` when set (`PATCH` of the provider), else what it declared; a `capabilities` refresh only rewrites the declared one. `albumCoveredWithoutTracks` (the seam availability uses for albums with no track list, such as search results) is true while an `assume_available` provider is active.
- **Misses** (`misses.ts`). An empty resolve, a refusal, a failed or mismatched delivery, or a timeout after the provider took a job writes a row to `acquisition_misses` (one per provider and recording), and a miss grays the recording out for that provider for a day. It describes the provider as it was, so each row carries the provider's `miss_epoch` (`provider_epoch`) and `identity` (`provider_identity`, for the history), and only rows at the current epoch and younger than a day count (`currentMisses`, which coverage and the choice of provider for a request read). The epoch moves on (`forgetMisses`), so the older rows stop counting while staying until they expire, when: the provider's identity changes, that is its declared `version` (optional in `ProviderCapabilities`) and a hash of everything else it declares (`providerIdentity`), so a provider without a version still changes identity when an update changes its capabilities; it is turned back on; it is given a new address or secret; or an admin retries its unavailable tracks (`clearProviderMisses`). The first three also end its failing streak (below); a retry leaves the streak alone. The first identity recorded for a provider (also on upgrading to a server that records it) counts as a change. The tracks those misses grayed out are announced with `announceAvailability`, and the process that made the change forgets which of the provider's recordings it asked about recently, so a `must_resolve` provider is asked again at once. `AcquisitionProvider.unavailableTracks` counts the misses that count.
- **Requests** (`requestRecording` from sessions, the acquire routes). The user must be an admin or have `can_acquire` (checked before anything about other users' jobs is looked at), a provider without a recent miss must remain, there must be a root to file into, and a member may have at most 100 unfinished jobs (`acquire_limit_reached`, 429; joining a job in flight is free; admins have no limit). The cache limit never refuses a request. Each job stores its `origin`: `play` (the current entry), `prefetch` (one further down the queue), `download` (a device downloading) or `library` (an explicit request or a library save; the route default). Joining a job in flight with a sooner origin moves it up. An album request leaves out tracks another job is already fetching. Acquisition never adds to a library, whatever the origin: only the heart does (userdata's `PUT /me/likes`, which asks for the files itself as origin `library`). Fetched files are cache. One job per target is in flight: the `idempotency_key` is `recording:<id>` or `album:<id>` and gets the job id appended when the job ends. A request that cannot go ahead is answered as failed straight away, unless another job is fetching that recording.
- **Jobs.** `acquisition.start` picks an offer (fresh cached offers, else a resolve, providers in priority order), waits for a slot under the provider's `maxConcurrent`, claims the job with a new random token (only its SHA-256 is stored) and calls `acquire`. Counting the slots and claiming one happen under an advisory lock per provider, and a job claimed but not yet answered holds its slot, so jobs started together never overshoot. A provider that is busy gets the job again after 5 s, doubling up to a minute (or after its `Retry-After`, up to five minutes), with no miss and nothing counted against its health: busy is an acquire declined with `reason: "busy"`, a resolve or acquire answered 429 (or 503 with `Retry-After`; a bare 503 is more often a proxy in front of a provider that is down, so it counts as a failure), or a job the provider took and then failed as busy before any file arrived (`reason: "busy"` on `complete` or the job status). Older providers' wording counts too: an error starting "Provider is busy", or saying it was rate limited or got too many requests (`saysBusy` in `client.ts`). A job failed as busy goes back to `resolving` with its offer and is handed over again after a wait as long as its age, so the waits double. That holds even when the failure comes before the server has recorded that the provider took the job: the start then moves it to `queued` only while it still holds the slot it claimed; one that failed busy after files arrived fails without misses. A resolve job refused as busy is queued again the same way, five times at most. The policy's timeout ends a job no provider ever takes, also with no miss. An album job asks with the whole track list and marks tracks the server has, or that the job does not need, `wanted: false`. An album no provider offers whole, declines, or fails without delivering anything is fetched track by track instead (one recording job per missing track, the album job ends `failed` without misses). Deliveries stream into an import of kind `acquisition` (created on the first upload, filed into the policy's root) under the policy's per-file limit. `complete` commits the import, and `acquisition.finish` follows it: while it identifies, every delivered file that is ingested, hashed and not a copy of another library file is checked against the request (`verify.ts`, rules in the protocol document, merging rows with `mergeRecording` where a delivered file is plainly the requested recording) and what it satisfies is announced ready at once; when the import ends the check runs again and decides the job. A delivered file the import dropped as a copy of an earlier delivery counts through that file (`work.copies`), so a second request for a song the library has under another row succeeds and merges the two rows instead of failing with a miss. Free slots go to waiting jobs in start order (`play`, `prefetch`, `download`, `library`, oldest first within one): a job leaves a slot to the waiting jobs ahead of it, and a job ending wakes the first in line. Each upload is held to the job's budget: 1.25 × `maxFileBytes` per requested recording in all and four files per recording plus two (413 past either, which fails the job); empty audio is refused.
- **Placing deliveries** (`place.ts`, the one place that links a delivery to its request). A delivered file that is a requested recording goes on the album the request named (else, for a request without one, the album its file is already on when that is more than its tags, another album listing the recording, or the album a search stub hints at; with no hint either, as for Deezer's popular tracks, the album the file's own album tag names among its artists' albums, by edition-free title), on that album's own track for the recording. An album with no track list from a source has its detail fetched first; while a source could still answer, a young file waits (it plays meanwhile) and the sweep tries again, and without one the file goes on a track list built from the files in their own numbers (on an album its tags named that lists no track for it, a regional edition's bonus track, beside the album's own track list; on a requested album, as an extra with no track). A requested search stub that lists the recording only on a track list built from files gives way to the same album's other row (same artist, type and edition-free title) that lists it from a source, and is merged into that row once empty (`sameAlbumIds`). When the album lists the song under another row (a search stub and the MusicBrainz recording), the two are merged, but only when exactly one track is plainly the same recording and two catalog rows that carry ISRCs share one. `matching.placeFiles` (owned by matching) then links the files (`matched`, source `request`), removes or redirects the tags-built rows they left (never an album with a MusicBrainz id or a track list from a source, nor one with an id at another source unless the caller names it as the same album) and the credits of redirect recordings, so artists their tags ran together go, and resolves the group's review once every file in it is identified; the import files them as it files matches. Placement runs when the import has decided its duplicates (`settleDelivery`), while `acquisition.finish` follows a one-file delivery, at the end of the job, and from the repair.
- **Repair** (`repair.ts`). `acquisition.repair` (at worker start and daily at 04:25) and the sweep (over jobs of the last two hours) place deliveries of completed jobs that are still on rows built from their tags, as left by servers before placement existed, or on a file-built track list while their album, or another row that lists the recording from a source, has one by now, then file them with `refileImport`. The tags-built albums they leave become redirects, so likes, wants, playlist items and plays move to the real album (`mergeAlbum`). Only files a provider delivered for a job that completed, still linked to a recording it asked for, not locked and not matched by the matcher, are touched; jobs it could not place are skipped for five minutes. Groups of deliveries whose album is credited to a run-together artist are ingested again under today's grouping rules. A recording matching later links to another MusicBrainz id fails then: it gets a miss and its entries fail, except a current entry that is already playing. `acquisition.sweep` (every minute and at worker start) fails jobs past the timeout, polls providers of jobs quiet for a minute, re-queues the start of jobs stuck in `resolving` and the finish of jobs in `importing`, deletes expired misses and offers, and runs the repair over recent jobs.
- **The cache** (`evict.ts`). Every delivered file is cache (`media_files.cached`): Organize files it under `<root>/_Fetched/<template>`, matching never opens a review for a group of cached files only, Admin → Library stats count only collection files (a root's `cachedFileCount` says how many of its `fileCount` are cache), and `GET /admin/acquisition/usage` reports `cachedFiles`, `cachedBytes`, `pinnedBytes` and `limitBytes`, shown under Admin → Providers → Cache. When a job's import has ended, `discardUnrequested` deletes its delivered files that are not a requested recording (after merges), unless one is the only file of its recording and is pinned, counted by another import as a copy, or wanted by another job; the sweep repeats it for jobs ended in the last two hours. `acquisition.evict` (hourly at :17, and queued after a completion or upload while the cache is over its limit) deletes least recently used cached files (the later of the recording's last play and the file's arrival) until the cache is under 90% of `storageQuotaBytes`; 0 is unlimited. Never deleted: pinned files (`userdata/pins.ts`: a saved album or recording, a recording on a saved album's track list, a playlist item, a stored queue entry, a play in the last 24 hours, checked again for each file just before it goes), files in their first hour, files of imports still running, and anything outside a managed root. Deleting removes the file, its row and the local-only catalog rows it leaves (`removeOrphans`), then sidecars and empty folders inside `_Fetched/` or `_Incoming/` only; catalog albums and recordings stay, so the track is `on_demand` again.
- **Health** (`health.ts`). Failures a provider is answerable for count against it: a `ProviderCallError` while a job resolves, starts or is polled, a job it reports `failed`, and a job it took that times out (not a delivery the server's own checks refuse, and never a busy refusal, see "Jobs"). `noteProviderFailure` keeps the message in `last_error`, sets `failing_since` on the first one after a delivery, and adds the job's recordings to `failing_recordings`. With three different recordings there (`FAILING_AFTER`) the provider is failing: the misses recorded for them since `failing_since` are deleted, their availability announced and the sessions told they are playable again (`restored`), failed jobs record no more misses, their outcomes carry `outage`, and `AcquisitionProvider.failingSince` is set for the admin page. Jobs still go to it, so the first job that completes with a delivery (`noteProviderDelivered`) ends the streak, clears `last_error` and sets `last_ok_at`. A change to the provider (another identity, turned back on, a new address or secret) also ends it, with its misses (see "Misses"): those failures were the provider before the change.
- **Outcomes reach the sessions** through the `squirmy_acquisition` NOTIFY channel, which the API process applies with `markRecordingReady` / `markRecordingFailed`. A failed outcome carries its `cause` (`EntryFailure`), with the outage reason for `outage`:
  - `unavailable`: the provider does not have it. Every provider asked answered without a free offer, it declined or reported the job failed (both record a miss), the delivery was not the track, a miss that counts left no provider to ask (`not_available`), the track is gone, or the user may not fetch.
  - `outage`: the provider is failing (health), a provider could not be asked while resolving, the call to start the job failed, or no provider is enabled any more.
  - `error`: anything else: the server's own import failed, nothing was delivered in time, the job limit, a missing import root.

  Because sessions ask once per load, the API process also reconciles every 30 seconds while a provider is active: recordings of jobs that ended in the last ten minutes are marked ready when owned, and failed when not owned and no job is still on them (`unavailable` when a miss counts for them, else `error`).
- **Events.** Every status change publishes `acquisition.updated` to the requesting user and to admins.

The reference providers live in `adapters/`. `@squirmy/provider-kit` is the protocol's provider side (HTTP, secret, validation, idempotent jobs, streaming uploads; `ProviderBusyError` thrown from `resolve` answers 429 and from `fetch` fails the job with `reason: "busy"`, and a job that failed busy runs again when the server sends it again); `adapters/cold-storage` indexes a folder's tags and resolves by MusicBrainz id, ISRC, then artist, title and length; `adapters/mock` synthesizes quiet tones and can be slow, failing, wrong or priced. The server's tests run the mock in-process.

### External metadata

All clients live in `modules/metadata/` and go through `lib/http.ts`:

- `cachedFetch(provider, url, { ttlSeconds, … })` stores responses in `http_cache` and serves them until they expire. 404s are cached for at most six hours, 5xx never; 429/503 are retried honoring `Retry-After`. `cache: 'reload' | 'no-store'` bypasses the cache for one call.
- Bodies over 8 MiB fail the call with `ProviderError` and are not cached.
- Image links come from provider data, so `fetchImage` downloads through `requestPublic`: https only, at most three redirects followed by hand and checked the same way, and connections only to public addresses. `publicDispatcher` (an undici `Agent`) filters what each name resolves to at connect time, so a name cannot pass a check and then resolve to a private address; `lib/address.ts` has the list (loopback, RFC 1918, link-local, unique local, CGNAT, multicast, reserved, and IPv4-mapped and NAT64 forms of those). A refused URL is treated as an unusable image.
- `rateLimit(key, intervalMs)` reserves the next slot in the `rate_limits` table, so the limit holds across processes. MusicBrainz uses 1100 ms (only against `musicbrainz.org` and its subdomains, such as `beta.`; a mirror is not limited).
- User-Agent: `Squirmy/<version> ( https://github.com/IsaacThoman/squirmy )`, with the version from `lib/version.ts`: `SQUIRMY_VERSION` (release images), else `dev+<short commit>` from `SOURCE_COMMIT` (a build argument, or set at run time by Coolify) or read once at start from git, else `dev`.
- Every provider checks its toggle or key in `ServerSettings` and returns null or an empty list rather than throwing when it is off. `fetchImage` (`metadata/images.ts`) downloads an image for any provider and checks the switch of the source that owns the image's host (`imageSourceEnabled`), so a lazily listed remote image is not downloaded after its source is turned off. "Not found" is null too; a provider failure (network, timeout, 5xx, bad key) throws `ProviderError`.
- Album types: MusicBrainz's release-group types map through `musicbrainz.albumType` (a soundtrack, live or compilation secondary type wins over an album primary type; a single, EP or "Other" release stays one, so a song from a film is listed with the artist's singles and a film typed Other, such as Radiohead's Meeting People Is Easy, is no album; migration 0022 has artists that lead a MusicBrainz soundtrack fetch their discography again, so rows typed before are typed anew), Deezer's `record_type` through its client (`compile` is a compilation). Deezer has no soundtrack type: an album it files under Films/Games (genre 173, or the genres Films/Games or Soundtrack on the full album) or whose title says so in a soundtrack's own words ("(Original Motion Picture Soundtrack)", "Original Score", "Music from the Motion Picture"; `deezer.SOUNDTRACK_TITLE`) is typed `soundtrack` (`deezer.deezerSoundtrack`); a single stays a single, and a row with a MusicBrainz id keeps MusicBrainz's type. A Deezer-only row Deezer typed an album takes `soundtrack` when Deezer later says so; migration 0023 retyped stored rows by title or genres, and the release repair reads a composer's other Deezer-only albums from Deezer once for their genre (`retypeDeezerSoundtracks`).
- Other modules import the clients from `modules/metadata/index.ts`, e.g. `musicbrainz.getRelease(mbid)`.
- Tests never touch the network. `useHttpFixtures(provider)` from `src/test/http.ts` serves recorded responses from `src/test/http/<provider>/` and fails on any unrecorded request. `SQUIRMY_RECORD_HTTP=1` records missing fixtures from the real service.

### Enrichment

The catalog is a lazy cache of MusicBrainz. `enrichment/detail.ts` completes a row when a page opens it; jobs decorate owned music in the background.

- **Album detail** (`ensureAlbumDetail`). An album at `detail_level` 2 fetched in the last 30 days is left alone. With a release-group MBID the group is fetched, the canonical release chosen (`canonical.ts`, `standardRelease`: among the releases titled as the group is when any are, so an edition with a title of its own never stands for the album however many pressings it has; then best status present, then the most common track count, then the album's own mix before another (Dolby Atmos, spatial, instrumental: MusicBrainz lists those songs as recordings of their own, which no store copy or delivered file matched), uncensored before clean or edited pressings, CD or digital media, then the earliest date) and written through matching's `upsertRelease`. An album whose files are on a MusicBrainz edition keeps it as canonical; one whose files sit on a local edition (a local album merged into the group's row) takes the chosen release, and its files' recordings are fitted to the release's tracks. Without an MBID a Deezer id is bridged, most reliable first: the MusicBrainz URL relation of the Deezer page, the UPC as a barcode (accepted when its releases share one group), then a release-group search accepted only for one hit scoring 90 or more with the same title and artist. The bridge keeps the release too when the link or the barcode names one. The stub adopts the MBID, or is merged into the row that has it, unless it is another edition of the group: its track count differs from the group's own edition's, and a release of the group has its track count or its title names an edition the group's does not ("SOS Deluxe: LANA", "Midnights (3am Edition)", a deluxe "Watch the Throne"). Such a store album stays a row of its own with `edition_of_id` set to the group's row (created at level 1 when missing), the group's type, year and credits, and as its track list the group's release with its track count (link, then barcode, then track count) when there is one, else Deezer's; a release the group's row had shown moves to it, and the group's row picks its own again when next opened; an edition row made from MusicBrainz's titles (below) of that release or its track count, with no files and no Deezer id, is merged into it. A store copy that only lacks a track is the group's own edition. Of several Deezer albums on one row (the explicit and the clean version) the explicit one is built. With no match the track list comes from Deezer (provider-only rows with ISRCs); the album stays at level 1 and the bridge is retried after a day. A song is one row however many sources list it. Which track of the album a row from another source is follows `track-identity.ts`: a shared ISRC (with the title or the place, and lengths within 15 seconds, unless the ISRC is a source's own against rows without files), else the same edition-free title (`matchKey` folds case, curly and straight quotes and punctuation; guest credits and edition suffixes are dropped) with lengths within five seconds, at the same place or with no ISRC the other lacks entirely, else the same place with lengths within two seconds when neither title names another version and the track there is not listed elsewhere on the other list; each step counts only when exactly one track fits. A MusicBrainz release written onto an album that already lists the songs (Deezer's track list, one built from a delivery's tags, files filed under it) takes over those MBID-less rows (`standInsFor`, a track and a row that pick each other), so likes, plays and queue entries keep their ids. Recordings without an MBID that still stand in for a track of the canonical release are merged into its recording (`fit.ts`) when the release or a Deezer track list is written: tracks of the album's other track lists and the recordings of present files filed under it by those rules (an ISRC never alone), a recording with files on another album (the song's single) sharing an ISRC and the title with one track, a stub with no file sharing an ISRC with one track, and a loose stub of the album's artists (Deezer top tracks carry no ISRC) with the same edition-free title and a length within five seconds. Then a track with no file of its own whose song another release holds plays that copy, as a streaming app would (`joinHeldCopies`): the only recording with an MBID and present files that shares an ISRC and the title with it, within fifteen seconds of its length, takes the track (the track is merged into it, so its ids follow the redirect). PRIMA's "Red Bottoms" is MusicBrainz's Dolby Atmos recording on the album and the stereo one on the single the server has. That is the one merge of two MusicBrainz recordings; a track with a file keeps it, and `upsertRelease` writing a recording whose MBID row was merged away only adds its ISRCs to the row it was merged into. A detail run that writes nothing fits the album's files too, only when an indexed check finds a file on a stand-in, so a track fetched onto a complete album is folded in on the next visit. Deezer's track list is matched to the canonical release the same way (an ISRC counts alone): each match links the Deezer track id; a match that was not by ISRC adds Deezer's ISRC to a recording that carries other codes unless the track is a clean edit (Deezer marks it edited, or the album is not the explicit version), so a delivered stereo file of a song whose canonical release has codes of its own is the track that was asked for; and Deezer's explicit flag is copied onto recordings that have none when the ISRC matches or the Deezer album is the explicit version. Merges keep a flag the winner lacks. A track list only Deezer has gets each track's featured artists from the track's own entry (`creditDeezerTracks`; the album's track list names only the main artist), a collaboration album every main artist Deezer lists (`/album/{id}` contributors), and the album Deezer's year and date. Deezer's text is decoded of HTML entities.
- **Artist detail** (`ensureArtistDetail`, `hydrateArtist`). MusicBrainz answers a request a second and a big discography is many pages (Bach's is 62), so the run writes in the order a page can use it and tells the page when it has something worth showing (`usable`, see Bounds):
  1. **Deezer first.** With a Deezer page, its newest 200 albums become stubs with Deezer's date, type and cover, and rows that already carry a Deezer id gain a missing date, a stated type for a guessed one, or a cover: search names neither, so a first visit was yearless and alphabetical. For an artist with an MBID the MusicBrainz profile is fetched alongside; the pass waits up to 1.5 s for it to name the artist's own Deezer pages, else uses the row's page with the most fans. That is the first answer.
  2. **Profile.** The profile and genres, adopting the MBID (or merging into the row that has it). The name stays the one the row has when MusicBrainz lists it among the artist's names ("Kanye West" for Ye, "Hikaru Utada" for 宇多田ヒカル), takes MusicBrainz's spelling of the same name ("JAY‐Z" for "JAŸ-Z"), and is MusicBrainz's otherwise (`displayName`). Every Deezer page MusicBrainz links is linked. A page the row had by name alone that MusicBrainz does not list, when it lists others, is a namesake's: it moves to a stub of its own with the albums the first pass made from it (`detachDeezerArtist`). A Deezer stub bridged by name search to an artist whose Deezer pages are others is not bridged.
  3. **Image, bio, popular tracks.** None for a placeholder artist: its profile is stored without disambiguation or genres, and a web picture, bio or genres stored by older code are cleared (`clearPlaceholderProfile`; migration 0022 cleared existing rows). No writer of artist pictures (search, Deezer rows) gives a placeholder one. Otherwise the picture is chosen from the artist's own Deezer page (most fans), else fanart.tv, else Wikidata, as a lazy remote image, replacing one taken from a page search linked by name; a picture from the user's folders stays. `artists.image_picked_at` records a choice made with the profile; merges clear it. The bio is the English Wikipedia summary, with the separators of dropped parentheticals cleaned out (`wikidata.cleanExtract`). Popular tracks are Deezer's top tracks (a store's hits, with their albums), else ListenBrainz's most listened recordings (with a token), stored as the artist's ranked list in `artist_top_tracks` with a 0..1 `popularity` on each, with stubs for tracks the catalog lacks.
  4. **Discography.** The official discography (`release-group-status=website-default`), written a page of 100 groups at a time as level-1 album rows with a lazy Cover Art Archive cover (`/release-group/<mbid>/front-500`; none for MusicBrainz's placeholder artists, `musicbrainz.specialPurposeArtists`: Various Artists is credited on hundreds of thousands of compilations), adopting the album stubs search or Deezer made for the same groups (no MBID, no files, not an edition row, led by the group's first credit, else by another artist it credits, since Deezer lists an artist's features among its albums without their owner; the same title once store labels are dropped, `labelFreeKey`, so a deluxe or 3am edition stays its own; compatible type: EP and single are compatible, a stub typed album fits any long-form group since Deezer calls soundtracks, live albums and compilations albums, and a guessed type fits any; a title two groups share adopts nothing). Open pages are told after the first page and at most every 15 s after. Remix albums and DJ mixes are compilations (`musicbrainz.albumType`).

  A Deezer artist is bridged by URL relation, else an unambiguous exact-name search, where a Deezer namesake hint ("Nirvana (UK)") is not part of the name: the hit must be named like the part before it and fit the hint by country or disambiguation (`bridge.ts` `confidentArtist`). Otherwise Deezer's albums are its discography (up to 1,000).
- **One row per release** (`reconcile.ts`). Rows of one release arrive from writers that cannot see each other: search stubs written while the discography was fetched, stubs credited to a second row of the artist that the namesake bridge merges later (Grimes on the test instance), stubs of a track's album reference, rows built from a delivery's tags that a play kept alive after the file moved. `reconcileArtistAlbums` groups the albums an artist leads by `labelFreeKey`, so a deluxe or 3am edition never joins the standard album; a row with neither MBID, files nor `edition_of_id` merges into the row with one of those of the same type, else of the same family (EP and single; the rest), else any when its type is a guess, with years at most one apart; rows that no such row takes merge into the best of them. Rows with an MBID, files or `edition_of_id` are never merged here. It runs at the end of artist detail, after a namesake merge, from `enrichment.reconcile { artistId }` (queued by search when it writes album stubs), and as the release repair (`repair.ts`, `enrichment.reconcile` without an artist, at worker start and daily at 04:50): first editions merged into their group's row by older code are split off again (`editions.ts`: a Deezer album on a group's row whose track count differs and whose title names another edition moves to the row it was merged from, un-merged, or to a new edition row, with the track list Deezer built for it; up to 100 group rows a run), edition rows of one group that are one edition (the same name, track count and ISRCs in order, from their track list or Deezer's) are merged (`mergeDuplicateEditions`; the explicit and the clean version differ in ISRCs and stay apart), artists bridged by name to the wrong MusicBrainz artist are unlinked (`unlinkContradictedBridges`, below), then second Deezer pages are merged into their artists (below), then every artist with a loose row; artist rows built from a delivery's tags that only rows merged away still credit (no MBID, no provider id) are merged into the one other artist of their name, or removed when none or several share it and no like or rating points at them (`foldTagBuiltArtists`); names and titles stored with HTML entities are decoded and their keys recomputed; albums with a date get the year; up to 200 albums a run whose MusicBrainz recordings lack Deezer's explicit flag read their Deezer track list again; up to 200 artists whose popular tracks have no album fetch their top tracks again, so they get one, and up to 200 fetched artists with no ranked list get one; up to 100 artists with an MBID whose picture was not chosen from their profile (`image_picked_at` null) and is not from the user's folders have it chosen again; and up to 500 albums that list a song twice, the canonical track and, below it, a stand-in of another track list or a filed file with its title, an ISRC of it, or its place and length (`album-tracks.ts`), are fitted again, and with Deezer on those where that merged something read their Deezer track list again (up to 100); then up to 100 albums with a track that has no file while a recording of the album's artist with its title has one elsewhere read their Deezer track list again (so the track learns the store's code for the song) and are fitted, so the song plays from the release that holds it. Merges go through `mergeAlbum`, which moves files, editions, external ids, album hints, likes, ratings, wants, library saves, playlist items and plays. Each repair run ends with one info log line, `release repair finished`, holding its `RepairReport` counts and how long it took.
- **Popular tracks from Deezer** keep the album Deezer names for them as their album hint: the row with its Deezer id, else the album artist's row of the same `releaseKey` (owned and MusicBrainz first), else a stub with the track's cover and a guessed type. ListenBrainz's popular recordings take the artist's album of the release name it gives. Popularity is the last ranking's: recordings that left it lose theirs, so a song Deezer ranks under another track id is not listed twice. A featured artist is the row of that name when it is the only one and has no Deezer id yet, as search decides, rather than a second row beside the artist the discography credited.
- **Wrong bridges** (`namesakes.ts`, `unlinkContradictedBridges`). An artist with an MBID whose Deezer page carries a namesake hint the MusicBrainz artist does not fit (`contradictsHint`, `confidentArtist`'s rule: "Nirvana (UK)", the 1970s band, had become "Nirvana UK", a tribute band), or whose MusicBrainz disambiguation says tribute, cover band or karaoke while the page does not, is unlinked unless MusicBrainz itself links the page: the MBID moves to a row of its own with what MusicBrainz credits to it, and the row takes the page's name back at `detail_level` 0, to be bridged again. Candidates are artists whose name ends in a country word or whose disambiguation says they play others' music, up to 100 a run.
- **Second Deezer pages** (`artist-copies.ts`). Rows with an MBID are compared by what MusicBrainz credits them with (albums and recordings with an MBID) only: their other credits may be a namesake's, and counting them let one wrong merge pull in the next. A Deezer-only artist row that shares its name with another row is merged into it (`mergeArtist`: credits, likes, ratings, its Deezer id; the winner keeps its disambiguation and takes the loser's when it has none) when MusicBrainz links its Deezer page to that row's MBID, or the two share a release or two songs, counting the rows' credits and what each row's Deezer pages list (albums, popular tracks). A page MusicBrainz links to another artist, an empty page, or one with nothing in common is a namesake and stays apart; of several fitting rows only a sole MBID row is taken. It runs from `enrichment.reconcile { artistCopy }` (queued by search) and in the release repair, up to 300 rows a run: rows never checked first, and a row kept as a namesake (`artists.copy_checked_at`) only again after 30 days, so the batches reach every row instead of drawing the kept ones again each run.
- **Warming.** `warmDetail` (the seam's background form) starts a row's run without waiting for it; a catalog search warms its top result when that is an artist, so the page a user opens next joins a run already under way. At most two warm-ups run at once; more are skipped. Albums from a catalog search go through search's own queue instead (`search/warm.ts`), which keeps the ones it cannot start yet rather than skipping them.
- **Editions with a title of their own** (`named-editions.ts`). A release of a group that the cover names apart is an edition stores list as an album of its own: Tate McRae's deluxe "SO CLOSE TO WHAT???" is a release in the group of "So Close to What". `namedEditions` (`canonical.ts`) picks one release per such title (case, spacing, quote marks and dashes aside), as `chooseCanonicalRelease` would among that title's releases: only releases of the group's best status, of the album's own mix and uncensored; a title that differs from the standard one only in punctuation counts only with another track count; at most six. Pressings under the standard title (a Japanese bonus track, a store exclusive) are not editions here. Each edition the catalog lacks (no row holds the release, and no edition row of the group shows it or its track count) gets an edition row: `edition_of_id` set to the group's row, the release's title, its release as the track list (`upsertRelease` with `editionAlbumId`, so its songs are the group's recordings and play from the same copies), the release's date, and the release's Cover Art Archive front. Opening a group's row or one of its edition rows, when the group was not checked in the last 30 days (`albums.editions_checked_at`), queues `enrichment.editions { albumId }` for the group (`queueEditionCheck`, from the detail seam), so the page never waits for the release lookups; the job invalidates the group's and its editions' pages when it writes one.
- **Bounds.** One run per row is in flight per process and concurrent callers share it. A page waits at most four seconds from when the run started (so a visit that joins a run an earlier visit started waits only for what is left), then renders what is known with `detailPending: true` on `AlbumDetail`/`ArtistDetail`; the run carries on, invalidates the page when it lands, and `enrichment.album`/`enrichment.artist` is queued a minute later as a safety net. An album with a Deezer id and no track list yet gets Deezer's first: the page renders it (pending) while MusicBrainz is asked, and the Deezer edition becomes the MusicBrainz release when it is written. A release group with no Deezer id and no track list (one an artist page's discography listed) looks its Deezer copy up first (an album search for its credit and title: the same artist, the same title, else the same `releaseKey`, single or EP only for one) and takes the same path (`deezerStandIn`). An artist page renders once the Deezer pass is written, and the MusicBrainz discography fills in behind it with invalidations as it goes. The seam never throws: a `ProviderError` leaves what was written, and an optional source failing (image, bio, top tracks) only keeps the row below level 2 so the next visit retries.
- **Owned albums** (`enrichment.album`). After detail: a stored cover unless the album has one at least 500 px on its short side (Cover Art Archive release front, then release-group front, then Deezer), Deezer ids by UPC and ISRC, a Wikipedia description, and `enrichment.lyrics` for owned recordings without lyrics. `albums.enriched_at` records success.
- **Fallback covers** (`enrichment.cover`, `covers.ts`). An album whose cover the art route unassigned gets the first of: a folder image or embedded picture of a present file (as a scan picks them), then the cover of its Deezer page as a lazy image. The archive is not asked for another release of the group: the group front is one of theirs. The sweep queues albums without a cover that have files or a Deezer page, each once a day per process.
- **Lyrics** (`enrichment.lyrics`, and `GET /tracks/:id/lyrics` on demand): LRCLIB by title, artist, album and duration; no match stores a `none` row that is retried after 30 days. Lyrics from files are never replaced. A row keeps its lyrics as they came: sidecar `.ttml` is turned into Enhanced LRC when read (`ttmlToLrc`, `library/lyrics.ts`), and Enhanced LRC's word stamps stay in `synced`. `servedLyrics` answers with `synced` stripped to line stamps, for clients that read only lines, and `lines`, read by client-core's `parseLrc` with each word's time (`words`) and a line's `translation` (a second line at the same time).
- `enrichment.sweep` (every 30 minutes and at worker start) queues owned albums without `enriched_at`, their artists below level 2, and owned recordings without lyrics, 200 of each per run. While MusicBrainz is on, it then bridges up to 20 Deezer-only artists that share a name with another row (`namesakes.ts`, each tried once a day per process), by URL relation or an unambiguous exact-name search only, so Deezer's duplicate page of an artist is merged into the artist with the MBID without anyone opening it, and a real namesake stays apart.
- **Sources switched on later.** When `PATCH /admin/settings` switches a source on, `markEnrichmentStale` (`stale.ts`) clears `enriched_at` on owned albums (MusicBrainz, Cover Art Archive, Deezer, Wikidata) and drops artists of owned albums from level 2 to 1 (those, a fanart.tv key, a ListenBrainz token), and the sweep redoes them in its batches. Lyrics need nothing: no LRCLIB lookup is made or stored while it is off. `enrichment.new-releases` (weekly) refreshes library artists' discographies; Home's `new-releases` section lists albums from the last 120 days by library artists that have no present file. Neither counts MusicBrainz's placeholder artists (Various Artists on an owned compilation) as library artists.

## Clients

`client-core` holds everything both clients share and has no React, DOM or React Native imports:

- `reduceSession(state, { command, now, commandId, deviceId })`: the pure session reducer, also run by the server.
- `SessionClient`: owns the socket (through `createSocketTransport` from `@squirmy/client-core/socket`), the clock offset, optimistic commands and reconciliation; exposes a store (`getSnapshot`, `subscribe`) for `useSyncExternalStore`. `save()` and the `restore` option carry the last server state and the unsent commands across a relaunch; a restored session this device was playing comes back paused, at the saved position unless the server changed the session after the save (it paused it when the device went away), whose position is then kept rather than rewound to the save. On reconnect, commands made offline are followed by the engine's position, and tracks the device ended offline after the server gave up on it are preceded by a transfer back to it, so the server accepts them. A device the server gave up on while it played, or while it loaded the current entry to play it, takes the session back at the engine's position. `forgetPlayback(trackId?)` drops resolved descriptors (one track's, or all) so entries resolve again; the entries the engine holds keep their gain, and the preload is aimed again only when it is that track. An entry that only just became current loads at 0 rather than the few milliseconds its clock has run, since an exact seek that short makes a streaming player rebuffer; a preload the server refused is not asked for again until the target changes or playback is forgotten. `prepareTakeover()`, on a device that does not play, resolves the current entry and preloads it into the engine; a transfer here then loads from that buffer, and it is dropped when another entry becomes current. A load that failed for want of a connection starts, when it is retried, where its first try would have: the time spent offline is not time played. The snapshot's `outage` is the last `playback.unavailable` while the session is still paused on that failed entry: kept unseen until the pause arrives, forgotten once it plays or moves on. Its `away` is the active device while the live list leaves it out (online clients only), with that device as it was last listed (the client remembers the last 32 it saw), or none when it never was.
- `PlayerEngine`: the interface each platform implements (`load`, `preload`, `play`, `pause`, `seek`, `setGain`, `stop`, status events), with a `FakeEngine` for tests. `SessionClient` drives it when this device is active.
- `createApiClient({ baseUrl, getToken })`: typed fetch wrapper for every route, returning contract types.
- `TrackStore`: batched, cached `TrackSummary` hydration for queue entries. `refresh(trackId, albumId)` fetches one again while the cached copy stays on screen (asked while an answer is on its way, it asks again once that is in, since the answer may predate the change); `refreshTrack(trackId)` does that for every album the track is cached under, and `refreshInvalidated(keys)` for the tracks an `invalidate` names (`queryKeys.track`). `refreshFetchedTracks(client, store)` refreshes an entry once it turns from `preparing` to `ready`: an on-demand track gains its album and cover with its file; `patch` sets values the server announces on every cached copy.
- `planChanges`, `patchEntities` and `RealtimeBatch` (`changes.ts`): what a client does with the socket's `changes` and invalidations, shared by both apps.
- `readsUnavailable(entry, outage)` (`session/notices.ts`): whether a failed entry reads as "Not available". The one playback paused on in a provider outage does not; both apps' queue and track rows use it.
- `PlaybackNoticeWatcher`, `skipNotice`, `stopNotice` (`session/notices.ts`): what both apps tell a listener when songs cannot be had, from each snapshot and `SessionClient.failureOf(trackId)` (the last `playback.failed` for it). A song that was current or next and failed as `unavailable` joins the run of such songs since one last played, counted with the failed entries passed over to get there; the run is one notice that each skip replaces ("Skipped “Title” — not available", then "Skipped 3 songs — not available"; the web app's player status line shows the latest, iOS's notice shows one at a time). Any other failure is a notice of its own: "Couldn’t play “Title”" / "Skipped.". One notice for a stop the server explains (the snapshot's `outage`), which takes the run's place: "None of the remaining songs are available" for `exhausted`, "Several songs in a row aren’t available" / "Playback is paused." for `unavailable`, else "Can’t load music right now" with the reason and "Playback is paused."; after it nothing per song until playback resumes. Failures further down the queue are quiet, and nothing is told offline.
- `isPlayable(track, viewer)`, `albumPresentation`, `albumNote` and `canFetch`: the one rule for what a viewer can play and how unavailable music looks. An explicit track never plays for a viewer whose `allowsExplicit` is false (`explicitBlocked`), and `unavailableLabel` says why a gray track is gray. `mergeSearch(library, catalog, viewer, options)` turns the two search answers into one result set: `items`, one list of every kind ordered by the answers' `ranked` scores (what the viewer cannot play scored down, the viewer's playlists matched by name on the same scale, an older server's answers ordered by name match), with identical albums and songs under different ids listed once. `recent-searches.ts` handles recently viewed Search results stored on the device by both apps.
- Formatters (`formatDuration`, `formatTotalDuration`, `formatRemaining`, `formatReleaseDate` for calendar dates at the precision they have) and `creditParts(artistCredit, artists)`, which splits a credit into its artists and the words between them so both apps link each artist in the credit as written; the web app has no copies of them. Normalization math (`gainFor(mode, normalization, context)`, with the context's target loudness and whether a limiter follows the gain, so it need not stop at the song's peak), and artwork and stream URL helpers.

**Web** (`apps/web`): Vite, React 19, Tailwind 4, Radix primitives, TanStack Query, react-router. Colors are shadcn-style tokens declared as CSS custom properties in `src/index.css`: `background`, `foreground`, `card`, `popover`, `primary`, `secondary`, `muted`, `accent`, `destructive` (each surface with its `-foreground`), `border`, `input`, `ring`, and `sidebar` with `sidebar-foreground`, `sidebar-accent`, `sidebar-accent-foreground` and `sidebar-border`. A color theme replaces their values at runtime, so components style with the tokens; fixed colors are only for content (text over artwork, genre tiles, playlist covers). Two colors are mixed in `index.css` from the tokens rather than set by a theme: `faded-foreground` (gray text of music that does not play, 3:1) and `tint-muted-foreground` (secondary words over a collection header's artwork tint, 4.5:1); `headerTints` keeps a cover's color from going too light to tint a dark header. `input` is derived as the quietest color 3:1 off every surface a control sits on (`CONTROL_SURFACES`): it draws the edge of text fields and selects and the track of sliders. `color-themes.test.ts` checks those ratios, and 4.5:1 for text, in every theme and appearance. The palette is the web app's own and does not follow `apps/mobile/src/theme.ts`. Type is Inter, bundled with the app from `@fontsource-variable/inter`; nothing is loaded from a font service. `HTMLAudioElement` plus Web Audio gain implement `PlayerEngine`; the Media Session API mirrors the session.

- **Bootstrap.** One API client (same origin, `client: 'web'`) and one `QueryClient`. Before any route renders, `GET /setup/status` and `GET /auth/me` load. Guards: a server without an admin shows the setup wizard on every route; signed-out visitors go to `/login?next=…`; admin routes need the admin role. Signing in or out only changes the cached `me`, and the guards navigate. A 401 from any request signs out. Nothing else is said globally: every failure shows where it happened (below).
- **Feedback.** The app has no toasts, nor anything else that floats over the page to say what happened; `src/test/no-toasts.test.ts` and the lint config's `no-restricted-imports` refuse one. A change that shows (a filled heart, a playlist in the sidebar, a row gone) is its own confirmation. Where nothing else shows it, the control says so in place: a menu item's `done` ("Added to queue") for a moment before its menu closes (`components/ui/menu.tsx`; an `onSelect` that returns a promise keeps the menu open, with a spinner, and a rejection says why on the item), a sidebar playlist's "Added" after a drop, a field's "Saved". Failures show where they happened: beside the heart or Wantlist button (`LibraryFailures`), on the menu item, under a form (`FormError`) or a setting, in the dialog that asked (`ConfirmDialog` says a rejection above its buttons), on an admin row or panel (`InlineNote`). What cannot be undone (deleting a playlist, clearing the history) is asked first with `ConfirmDialog`. A query's first-load failure is the page's `QueryState`/`loadFailure`; a failed background refetch keeps what it had, and the shell's notice covers a lost connection.

The saved value carries the theme's stylesheet too (saved again at start when a release changed the theme's colors), and `public/appearance.js`, loaded blocking from `index.html` before the bundle, applies the class and that stylesheet, so a reload does not flash the wrong colors. It is a file rather than inline so the server's Content-Security-Policy can allow scripts from the server only. The script and `lib/appearance.ts` read the same value; change them together.
- **Density.** `lib/density.ts` keeps this browser's display density (`comfortable`, the default, or `compact`) in `localStorage` under `squirmy.density` and sets `data-density` on `<html>` (`public/appearance.js` does it before the app loads). `index.css`'s `compact:` variant applies only with a fine pointer, so touch screens keep 44 px rows. The sidebar has the navigation, the playlists (songs dropped on one of the user's own are added to it, on Liked Songs saved) and the account menu: Settings, Admin panel for admins, Log out. The tab's title (`lib/document-title.ts`, written by `PlayerProvider`) is the song while one plays; otherwise a page that names itself with `usePageTitle` ("Nothing here", "Page did not load") wins over a paused song. Album pages have no artist column: a song names its artists under its title only where its credit differs from the album's (`albumCredit`), as on iOS. The playing song has a quiet fill as well as its title in the action color.
- **Touch.** On a touch screen (`pointer-coarse:`) every control a finger uses has at least 44 × 44 px to press, set in the primitives rather than control by control: `IconButton`, `Switch` and link-styled buttons are pressed through a 44 px square centered on them (`touch-target` in `index.css`, a pseudo-element past the box, so they keep their look); `Button`, fields, selects, pills (`pillClass`), menu items and sliders grow to 44 px. Neighbors stay 44 px apart center to center, so no square covers another (a row of 40 px buttons gets an 8 px gap). `scripts/e2e-touch-targets.mjs` presses 17 points of the 44 px circle around every control on the main pages, on a phone and a tablet, and fails on any that lands elsewhere; its few exceptions (credit links inside a song row, a row's own play button, a line of linked words such as the player's credit, the sidebar's resize handle) say why. A song's menu opens with its whole title and credit there, since its row cuts them short. A dropdown's button (`DropdownMenu` in `components/ui/menu.tsx`, so every card's and row's ⋯) opens for a finger or a pen on the tap's click, not as it goes down as Radix does for a mouse, so a swipe that starts on it scrolls the page or the rail: the browser sends no click for a gesture it scrolled with, and one that moved more than 10 px is not a tap. The keyboard, a mouse, a right-click and a long press open menus as before. Controls that appear on hover are left out where nothing hovers (`pointer-fine:` shows them): a card's artwork opens its page, and a tap on a track row plays it. The page draws edge to edge (`viewport-fit=cover`), so the shell, the drawer, Now Playing and dialogs pad to `env(safe-area-inset-*)`. A dialog gives focus back to what had it when it opened (for a menu's item, the menu's button), even with no trigger, once its closing animation ends or its host removes it, and keeps the focused field in view as the keyboard shrinks the screen. Script-driven scrolling asks `scrollBehavior()` (`lib/motion.ts`), so Reduce Motion reaches it too.
- **Library.** One combined view (`components/views/LibraryView.tsx`, at `/library`), with filter chips All (Liked Songs first, then playlists, then albums), Playlists, Albums, Artists and Songs; the sorts of `library-state.ts` (Recently added, Title, Artist, Year; songs have no Year, artists and playlists no sort); a grid or list (songs are always a list); and "Find in your library", which filters what is loaded for one character and asks `/search/library` from two. The filter and layout are kept per browser (`squirmy.library.filter`, `squirmy.library.layout`). Only the lists the filter shows are loaded. `/library/albums`, `/artists`, `/songs` and `/playlists` redirect to `/library?filter=…`; a `?genre=` (from Search's genre tiles) shows as a removable chip and is kept across All, Albums and Songs (the songs on albums of that genre) but not Playlists or Artists, which take none. Under All the sort reads "Sort albums": Liked Songs and the playlists always lead. Below 768 px the chips leave the header for a wrapping row above the list. Each list fails on its own: a `LoadError` where it would be, with the chips, the toolbar and (under All) Liked Songs and the playlists still there. The sidebar has one **Library** entry.
- **Search.** `searchQuery` (`api/queries.ts`) is one search of the library or the catalog. The search page (`/search?q=…&type=…`) and `SearchDialog` (Cmd/Ctrl+K, fed by `SearchDialogHost` in `pages/shell.tsx`, which is also the command palette: `usePaletteCommands` in `components/layout/palette-commands.ts` builds the commands from the session and the shell's `ShellCommands`, `lib/fuzzy.ts` matches them, the best four from two letters follow the results under "Commands and places", and a query starting with ">" lists commands alone) both run both, with the same query keys, and draw their rows with `components/music/SearchRow.tsx`, so the two read the same. The dialog lists the first ten of the ranked list, then a row that opens `/search?q=…`, kept below the scrolling results; Enter on an artist, album or playlist opens it, and a song plays when it can (`isPlayable`), on its own so that autoplay follows it rather than the other songs found, else its album opens. With nothing typed it lists places to go, today's mixes among them (Home's `made-for-you` section, from the cache when Home was loaded). The page adds filter chips (All, Songs, Albums, Artists, Playlists, Lyrics, Credits) and each row's menu (`trackMenuEntries` for songs, `useResultMenus` for the rest). Its rows are list items with one control each (a link, or a song's play button described by its "Song · Artist" line), the heart and menu beside it rather than inside it; the arrow keys move focus from the field through the rows' controls and back. With nothing typed it lists recently viewed results (`lib/recent-searches.ts`, `localStorage` per user) and genres, or says what the page is for when there are neither.
- **Settings** are a dialog, not a page. `components/settings/SettingsDialog` is presentational, with the sections `playback`, `appearance`, `account`, `scrobbling`, `app-passwords` and `about`; `SettingsDialogHost` (`pages/settings.tsx`) gives it its data and is downloaded when the dialog first opens. Anything under the shell opens it with `useSettingsDialog().openSettings(section?)`. The routes `/settings` and `/settings/<section>` open it and redirect to `/`. Last.fm's callback lands on `/settings?lastfm=…`, which opens the Scrobbling section (`openSettings('scrobbling', { lastFm })`) and says there what Last.fm answered until the dialog closes. Each section says what its own controls did: a refused setting under the controls, "Saved" beside the browser's name, "Password changed" in Account.
- **Forms** validate with the contract schemas (`useFormSubmit`), show issues under their fields, and map known error codes onto fields.
- **Realtime.** `RealtimeProvider` opens one socket per signed-in user. `invalidate` and `changes` are collected for 100 ms (client-core's `RealtimeBatch`, which also drops keys a shorter one covers), then `applyChanges` (`realtime/apply-changes.ts`) patches every cached answer from the changes, keeping when it was loaded, and the named queries are refreshed once each. The player's `TrackStore` takes the same values (`useFreshSummaries` in `PlayerProvider`), so the queue and the player follow them too. Every reconnect refreshes all of them, and the shell shows a notice when the socket has been down for three seconds. The socket is in the context for `SessionClient`. It follows the page: `pagehide` and `freeze` close it, so the tab leaves the device list at once, and `pageshow` from the back/forward cache and `resume` open it again. A hidden tab stays connected and keeps answering the heartbeat, which runs from the socket's message handler rather than a throttled timer. When the page becomes visible or the browser comes online with no ping heard for 15 seconds (a laptop that slept), the socket is renewed.
- **Audio.** `WebPlayerEngine` alternates two `<audio>` elements, each through its own `GainNode`, so normalization can boost. When the browser refuses to start audio the entry goes to `error`, the player shows Play (its play/pause and Space call `unlock()`) and the shell offers "Enable audio", which does the same from the click. `EngineProvider` calls `warm()` on the first pointer or key press of the page, which opens the `AudioContext` before anything plays, so the first song is not held up by the output starting. `/dev/engine` drives it with tones from `scripts/dev-audio.mjs`; `scripts/e2e-engine.mjs` checks it against the contract in Chromium, `scripts/e2e-auth.mjs` walks the account flows against a fresh server, `scripts/e2e-admin.mjs` the admin flows (setup with a real folder, scans, reviews, Fix match, Organize on disk, the search index), `scripts/e2e-playback.mjs` playback on the demo library (transport, queue, likes, playlists, lyrics, gapless ends, two devices, a second user), `scripts/e2e-library.mjs` the heart and the combined Library (a refused save said beside its heart, a failed list or search recovering), `scripts/e2e-polish.mjs` a server started like the Docker image (setup with its configured folder, naming templates, search's top result, the queue showing a fetch as loading), and `scripts/e2e-imports-providers.mjs` adding music (uploads, the inbox, duplicates) and acquisition providers against the mock provider. They check each result where the app says it (a menu item, a field's "Saved", a panel's note, the player's status line), never in a toast.

- **Data.** Pages read through the hooks in `api/queries.ts`, keyed by `queryKeys`, so the server's invalidations refresh whatever is on screen. Page queries are `silent` and the page shows its own skeleton, error and "Nothing here" (404, and an id that is not a UUID, which is never sent). A read's three states go through `QueryState` (`components/ui/query-state.tsx`): the skeleton until the first answer, then `LoadError` (what did not load, the server's message and **Try again**) in the place of the page (`variant="page"`, a level 1 heading) or of the one panel that failed (`section`, the default), so the rest of the screen stays usable; a failed refetch keeps the last answer. Views that take data as props get the error from `loadFailure` (`load-failure.tsx`). An album whose songs are being looked up asks again every 3 s for a minute (`useAlbum`), and its `refetch` starts another minute. Library lists page by cursor as they scroll. Hearts and wants are optimistic. A heart applies as the same `patch` change the server then sends the user's devices (`applyChanges`), so every cached copy of the entity shows it, and a failure sets it back; the lists it moves (the library's, Liked Songs, Home) follow the server's invalidation. Wants set `wanted` with `patchEntity`. While the server has the wantlist off (`SetupStatus.wantlistEnabled`, read by `useWantlistEnabled` and carried in `LibraryActions.wantlistEnabled`), no sidebar item, search destination, bookmark, menu entry or album-page line mentions it, and `/wantlist` goes home.
- **Cache and prefetch.** `api/persist.ts` keeps the query cache in IndexedDB (`squirmy-cache`), one record per origin and user for 7 days, at most 250 queries, paged lists cut to their first page, and only allowlisted roots (home, library, albums, artists, tracks, likes, playlists, wants, settings, history; never `me`, search, lyrics, admin or playback URLs). It is restored before the first render and every restored query is marked stale, so screens show the last answer and refetch at once. The record names its user, who seeds `me` and the setup status as placeholders (`updatedAt: 0`) that are refetched straight away; a null `me`, any 401 or signing out deletes it. A new build discards old records. `api/prefetch.ts`: `usePrefetch` starts an album's or artist's request on a 100 ms hover, a focus or a press (cards, track-row links, search results, the ⌘K highlight), and `AlbumPreview`/`ArtistPreview` draw the real header from a summary already cached while the detail loads.
- **Session.** `PlayerProvider` (inside the signed-in routes) runs one `SessionClient` on the realtime socket with the page's engine. `resolvePlayback` asks for the user's `qualityWifi` and the codecs `canPlayType` confirms (Opus only in Ogg); `setNormalization` follows the user's mode. A `TrackStore` hydrates queue, history and autoplay entries; the current track also has its own query so its heart follows likes. Commands send track ids, album ids and durations only, never `none` tracks; `on_demand` ones go as `preparing`. What can be heard comes from `player/listening.ts`: on the playing tab only the engine playing the current entry is sound, so `PlayerState.waiting` (the spinner) covers a fetch, the stream being resolved or buffered and a load that fails offline, and `blocked` a play the browser held back; on other devices it follows the session's `stalled`. Playback position is a `PositionClock` that reads `Listening.position()` on animation frames while there is sound, so only the clocks and the lyrics re-render. The current track as song rows show it is a `NowPlayingStore` of its own: a row follows only its part of it (`useTrackPlayback`: current or not, playing, paused, waiting or failed), and track lists take only the player's commands (`useTrackActions`), so a volume, a seek or a queue change renders no rows and a new current track renders the row it leaves and the one it reaches; while waiting it stands where the music will start instead of counting through silence. A seek made while the current entry is `preparing` (the session ignores those) is kept there and sent once the entry is ready. Clear history is asked first (`ConfirmDialog` in the queue) and then sent at once. Space and the arrow keys (Shift+←/→ for the previous and next song) are left to a focused field, slider or menu, and to any dialog but Now Playing (`data-player-keys`). The provider also drives the Media Session (while this tab plays), the tab title, Space and the arrow keys, tells failures on the player's status line with client-core's `PlaybackNoticeWatcher` (a skipped song's notice waits 1.5 s and is dropped if the session stops meanwhile, so an outage shows only its stop notice; and skips a track the browser cannot play), and keeps the `TrackStore` fresh with `refreshFetchedTracks` and `refreshInvalidated`, so the queue, the player and the Media Session show a fetched song's album and cover.
- **Devices.** Each tab claims its device with a Web Lock on the id kept in `localStorage`: the first tab is the browser's device, a second one `<id>-2` under the same name, so tabs never play at once; a reloading tab waits briefly for its old page's lock and comes back as the same device. Names never carry a tab number: client-core `devices.ts` (`listedDevices`, `deviceLabel`) shows one row per browser, this browser's other tabs as "Another tab", the viewer's own device as "This browser" or "This iPhone", and a short id hint for two devices nothing else tells apart; web and iOS pickers both use it. The name (default from the user agent) is editable in the settings dialog and sent with a fresh hello (`SessionClient.rename`). While another device is active the player highlights the Devices button and the volume controls change that device's entry in `volumes`. Unmute restores the last volume heard on that device, whichever control muted it. Pointing at this tab in the picker calls `SessionClient.prepareTakeover()`, which resolves the current entry and has the engine buffer it as its preload, so the transfer that usually follows starts from that buffer. The devices picker (`components/player/Devices.tsx`) detaches this tab and rejoins (`detach`, `attach({ bringQueue })`), hides that where `canDetach` is false, and lists detached devices under "Playing separately" and never as transfer targets. The Devices button is also highlighted while detached.
- **Admin.** Pages in `pages/admin.tsx` (lazy) feed views in `components/admin/`. `AdminLayout` is one `PageHeader` titled Admin whose links are the sections (the review queue's carries the count of open reviews), with the server's version under each page. Scan progress comes from `scan.progress` events and invalidations; Organize and index imports report progress only in the database, so those screens poll while one runs. `components/admin/FixMatch.tsx` is the entry point other screens use for Fix match (the album page's menu offers it to admins); it loads its dialog on demand. Settings fields save on blur through `DraftField`, which shows the server's refusal under the field. Providers (`/admin/providers`) lists providers, the acquisition policy and every request, refreshed by `acquisition.updated`.
- **Adding music.** `/imports` (lazy, `pages/imports.tsx`) is for admins and members who may upload. `lib/upload.ts` sends the files picked or dropped (folders walked through directory entries, paths kept) a few per request through `imports.addFiles`, which uses `XMLHttpRequest` for progress and reads each file from disk as it goes; it pauses by aborting the request in flight, and a file the server already had is counted as sent on resuming. The upload belongs to the tab, not the page, and the page follows the import through `import.updated` to its albums (`GET /imports/:id/albums`).
- **Artist pages.** `ArtistView` draws each of `ArtistDetail.sections` as one `Rail` row with **See all** when its `total` is larger than its items (a key the app does not know shows under the section's `title`, with no link); a server that sends no `sections` gets `albums` grouped by type. **See all** opens `/artist/:id/releases/:section` (`ArtistReleasesView`), an infinite grid over `GET /artists/:id/releases` (`useArtistReleases`, under `queryKeys.artist(id)`). While `detailPending`, `useArtist` refetches every 5 s (at most 120 times) and the page says "Loading discography…".
- **What plays.** Every row, card and page uses client-core's rules (`isPlayable`, `albumPresentation`, `albumNote`, re-exported by `lib/catalog.ts`) with the viewer from `useViewer()`, which `OnDemandProvider` provides. Music that plays looks the same wherever its file is: no badge, no count, no word for fetching. What does not play is gray and says "Not available". A current entry that is `preparing`, or any the tab is still waiting to hear, looks like buffering (the spinner on its row and the play button) and after 8 s of waiting the player's subtitle says "Still loading…" (`use-still-loading.ts`). `OnDemandProvider` refreshes a track's own query when its fetch ends; its rows everywhere follow the server's availability `changes`, and the row of a current entry that failed is unavailable at once (`NowPlaying.failed`) rather than highlighted. The heart is the one library control (`SaveHeart`, and `librarySaveEntry` for the menu entry that mirrors it, both worded by client-core's `librarySave`): `LibraryActions.setSaved` patches `liked` (and `inLibrary` when saving) in every cached answer at once and puts it back when refused; the refusal is kept for a few seconds per item in `LibraryFailures` (`library-context.ts`), which the heart and the Wantlist buttons read to say it beside themselves (`IconButton`'s `failure`, a tooltip held open in the error color), and the provider's one live region names the item to screen readers. `setSaved`, `setWanted` and `addToPlaylist` also resolve or reject, for a menu entry that waits to say how it went. A collection item has the heart too; it only shows the viewer's own save. Track rows, the player bar and Now Playing link each credited artist to its own page (`ArtistLinks`).
- **Search.** `api/use-search.ts` runs `/search/library` (60 ms after typing pauses) and `/search/catalog` (250 ms) and merges them with client-core's `mergeSearch`, for the search page and ⌘K alike. The two are ranked together, so the list waits for the catalog's answer, or `CATALOG_WAIT_MS` (700 ms) after the library's, then shows what it has with a spinner at its end, and a later catalog answer joins where its rows rank. An answer is shown only for the query it answers; meanwhile the last results stay, faded, with nothing Enter would open. A filter's list is `useSearchPages`: pages of 30 of one kind (`type`, `offset`) from both routes, ranked together page by page, which end when a page adds nothing new (an older server ignores both parameters). Its pages stand in only for the same kind and a query typed on or deleted back, and faded results are `inert`. A next page that fails (after its one retry) ends the list with a `LoadError` and stops loading as the end comes into view until **Try again**. A catalog that could not be searched is said, with **Try again**, beside the library's results, never as "No results".

Catalog data reaches views through props typed with the contracts; session state and user actions come from `PlayerContext` and `LibraryContext`, whose providers are the only code that talks to `SessionClient` and the API. `/dev/kitchen-sink` shows every component state on the fixtures; the `/dev` pages exist only in development builds.

- **Accounts.** `AccountProvider` owns the auth state: it restores the stored session and opens the app from it at once (the `me` query confirms it in the background), creates the API client with the bearer token, and returns to sign-in on a 401. Every account signed in to stays saved: `AccountStore` (`src/account/accounts.ts`, pure, with the storage in `storage.ts`) keeps the list (server, user, last use) in app storage under `squirmy.accounts.v1` and each token in the keychain under its own id; on Apple TV, where tvOS may purge app storage, the list is in the keychain too. A launch moves an earlier version's single account (`squirmy.account.v1` and `squirmy.token`, or `squirmy.tv.account.v1`) into the list, removing the old record only once the new one is written. What each account keeps on the device is filed under `accountKey(server URL, user id)`. `switchTo` writes the leaving account's library (`CacheSaver.flush`), goes back to `restoring` (`switching`), which closes every screen, the player, the session socket and the managers, clears the query client, reads the next account's saved lists, and dispatches `restored` for it: nothing is asked of either server in between, and nothing built for one account sees the other's client. Signing out drops the token (and tells the server) but keeps the account and its data; `useAccountStorage` (`storageUsage.ts`) lists each account's downloads and cache for Settings → Storage and removes an account's downloads, or an account not in use with everything it keeps. The realtime socket is tagged with the server and token it was opened for, so the render that changes them never hands the old one on. The token and device id go through `Keychain` (`src/account/keychain.ts`), which never rejects: what the keychain refuses is kept in memory for the launch, and the account sheet (and sign-in, if it happens there) says the next launch will need a sign-in (`AccountContext.unsaved`). The server's name, version, invite rule and wantlist switch are read again from `GET /setup/status` whenever a server is chosen, and when the server invalidates it, so they stay current. While the wantlist is off (`useWantlistEnabled`), no screen, menu or Home row mentions it.
- **Data.** Query keys come from `queryKeys`; lists are infinite queries over the cursor pages. The cache is saved to app storage (expo-sqlite, through its async API, ten seconds after data changes and when the app leaves the screen) under keys of its own for each server and user, and kept when the account signs out or another one is opened; the single value earlier versions shared is moved to its account's keys when that account first reads it. It keeps the first page of each list and the 40 most recent album, artist, playlist and track pages from the last day, one line of JSON per query in two values: the lists, read before the splash hides, and the detail pages, read one per task after the first screen shows. A query over 512 KB is not saved, and the detail pages stay within 4 MB together. Every response that carries track summaries primes one `TrackStore`, which hydrates queue entries and the lock screen. Hearts apply at once through a queue kept in app storage (`LikeQueue`): every cached answer that shows the item is patched through `applyChanges`, as the server's `patch` will be (and Liked Songs gains or loses the track), the lists that move follow the server's invalidation, one that cannot reach the server is sent again on the next connection or, after a server error, with backoff, only the last change to an item is sent, and one the server refuses rolls back and shows on its heart. The playback session is saved in two halves, the queue half only when it changed.
- **Realtime.** `RealtimeProvider` opens one socket per signed-in session with `auth.token`, over WebSocket with a fallback to long-polling. `invalidate` refreshes the named queries, collected for 100 ms (and refetches a changed track's like); the echo of a change this device made only marks them stale. `changes` are applied at once (`data/changes.ts`, the web app's rule) and patch the `TrackStore` too; a heart `patch` from another device replaces the heart `LibraryProvider` remembered for that item (`remembersToDrop`), unless a change made here is still on its way, and a heart it sent is forgotten once the server has it, so later changes from other devices show. A reconnect marks everything stale and refetches what is on screen; lists not on screen keep their first page. Returning to the app refetches nothing by itself. The socket is renewed when the app returns after being suspended (no server ping for 15 seconds) and when the network type changes. In the background it stays open only while this phone plays, or loads or waits on a song it was told to play (`BackgroundPresence`, `data/presence.ts`): with nothing playing it closes 1.5 seconds after the app leaves the foreground, since iOS is about to suspend it and a suspended app should not be listed, and opens again when the app returns or playback starts here from the lock screen. A socket closed that way is not offline. A refused handshake rechecks `me`, so a revoked session signs out. The app is *offline* once the socket has been down for 2.5 seconds (a new socket gets 6 seconds to connect, unless a request fails first) and no request sent since it went down was answered; an answered request keeps the app online for 30 seconds more (`offlineAt`, `src/data/reachability.ts`).
- **Playback.** `PlaybackProvider` runs a `SessionClient` on that socket with the device's engine (its `canBoost` and `limiter`: true for the native engine, false for the classic one) and the user's normalization mode and target. `createPlayerEngine` reads the engine from the device setting `playbackEngine` (`src/player/engine/setting.ts`, kept with `accountItem(…, 'device')`): `classic`, the default, is `ExpoAudioEngine`; `native` is `NativeEngine`, and falls back to `classic` (saying so in the log) when the build has no `SquirmyAudioEngine` module or it fails to answer. Settings → Playback offers the choice in development and TestFlight builds (the module's `isTestFlight`), on the phone and the TV, and it applies at the next launch. The rest of this bullet is the classic engine; the native one is the next. `resolvePlayback` asks for the entry's album, the quality setting for the current network (Wi-Fi or cellular) and the codecs AVPlayer decodes. Components read the session through `usePlaybackState`; the position is polled with `usePosition` by the few components that show it. While another device is active the engine is stopped and the lock screen cleared. An engine error skips the track, or pauses when the next one fails too; either is said in the player's status line. iOS suspends a backgrounded app that plays nothing, and a suspended app neither starts the next song nor answers the server's heartbeat, so the engine loops a short silence whenever it should sound and nothing does: while the server fetches the current song (`holdAudioSession`) and while an entry it was told to play loads. A song chosen on another device is not the preload and starts from nothing, so the silence starts before the previous player is released: `expo-audio` keeps the audio session active for a player only from its first `play()`. The silence stops just before the new player is asked to play: over AirPlay a song did not start while the silence still played. Players never use AirPlay's external playback mode (`allowsExternalPlayback: false`), in which the receiver fetches a player's URL itself and cannot fetch the silence's local file; decoded on the phone, the sound still goes to AirPlay through the audio route. A player whose playhead has not moved 2 s after `play()` is paused and played again, then after 4 s and 8 s more. While the engine should sound and does not yet (loading, or buffering mid-song) it holds iOS background running time (`holdBackgroundTime`, about 30 s), so a song slow to start in the background can still be started. The engine logs each start (with the player's `timeControlStatus` and the output), its state changes, what the native player reports and the silence as `[engine]` lines, and route changes as `[audio]` lines.
- **Menus.** On iOS menus are the system's own (SwiftUI `Menu`, `ActionSheetIOS`). The other platforms' files show them with `useMenuSheet` (`src/MenuSheet.tsx`), a sheet from the bottom of any length: Android's `Alert` keeps three buttons and drops the rest.
- **No toasts.** The app has no notice or toast system, and `src/noToasts.test.mjs` (plain JavaScript, so the app's typecheck needs no Node types) fails if one comes back. A success shows as the change itself (the heart fills, the queue or playlist changes). A failure shows where it happened, for `failureShownMs` (8 s, `useBriefFailures` in `src/inlineFeedback.ts`) or until the next try, and is announced with `announce`: on the heart (`heartButton(liked, name, failure)` with `useLikeFailure`; `LibraryProvider` keeps `likeFailures` and `wantFailures`, the refused value by key, and the track menu's library and wantlist entries read them), on the button or under it (`FailureLine`, an artist's radio, Play all), on the playlist's page (`usePlaylistFailure`: removals and moves revert), or in the sheet (`SheetNote error`: adding to a playlist, which waits for the server and asks with an Alert before adding a duplicate, naming a playlist, detaching). Settings keep each scrobbling service's error (`useSettingsScreen().errors`) under its controls. Removing from the queue (`removeWithUndo`) and clearing it put **Undo** beside the line in Now Playing (`PlaybackStatus.action`) when the server can undo; Apple TV does not offer it yet. What playback has to say goes to `playbackStatus` (`src/player/playbackStatus.ts`), which the mini-player and Now Playing show in place of the artist: a one-off (a skip, a song that couldn't play, a detached session ending, a song-menu radio that didn't start) for 5 s, a pause it explains (an outage stop, nothing playable offline) until the session plays again; the newest shows.
- **Volume.** On iOS this phone's volume is the system output volume. `SessionPlayer.systemVolume` keeps this device's `volumes` entry out of the engine's gain (only normalization applies), the local `SquirmySystemVolume` module (in `modules/now-playing`) gives the level, its changes and an `MPVolumeView`-backed slider and setter, and `syncSystemVolume` (`src/player/systemVolume.ts`) keeps the session in step: button and slider changes are reported (throttled), a change from another device moves the system volume while this phone plays (not within a second of the phone's own report, so late answers do not pull it back), and becoming the playing device reports the system level. Where the module is missing (Android, an older build) the session volume drives the engine as before.
- **Now Playing's sliders.** The scrubber and another device's volume are `TransportSlider` (`src/player/`): React Native Gesture Handler owns the drag, `src/player/scrub.ts` the arithmetic (relative dragging, a tap commits nothing, the rubber band past the ends), and on iOS `SquirmyNowPlaying`'s `SliderBarView` draws the track as a thumbless `UISlider` that takes no touches. This phone's volume is the system `MPVolumeView` (`SystemVolumeView`), laid out so its track spans its bounds as the scrubber's does. `showRoutePicker` opens the system AirPlay and Bluetooth picker for the device sheet. Now Playing's spacing comes from `rhythm` (`src/player/layout.ts`), close to Apple Music's on a 6.1-inch iPhone and tighter in step with the height on shorter screens.
- **Now Playing's backdrop.** `player/AmbientArtwork.tsx` is the Apple TV's `Ambience` on the phone: the cover's ThumbHash in two layers turned on the UI thread by Reanimated, at the opacity the still blur had, under `playerGradient`. It turns only while Now Playing is up, the app is active and the music plays, and stands still under Reduce Motion.
- **Now Playing's motion.** Now Playing grows out of the mini-player on two springs (`src/player/transition.tsx`), on the UI thread: nothing re-renders while it moves. The panel's frame is the one layout that changes per frame. The artwork is laid out once at its size in the player and moved by a translate and a scale (`artworkTransform`, `src/player/artwork.ts`), its corner radius divided by the scale: expo-image redraws an image each time its view changes size, which soft-then-sharpened the artwork and held up the main thread. It keeps its decoded cover in memory and draws it without a resized copy, and `ArtworkPrefetch` decodes the covers either side of the current song (`upcomingArtworkEntries`) so a skip shows them at once. A Reanimated style reruns only for the shared values its own closure reads, so the styles read them and pass them to helpers. The lyrics and the queue are laid out on their first tap and then stay: every Fabric commit, one per frame of any animation, has each mounted scroll view walk its subviews (React Native's clipping pass), so content kept mounted makes every frame dearer, which is why the queue lays out only the rows near the view. The glass's blur intensity animates through `patches/expo-blur+58.0.6.patch`, which moves the effect's paused animator instead of rebuilding the effect and its backing store on every change.
- **Now Playing on iPad.** The artwork grows to fill its playback column (up to `tabletArtworkLimit`, `src/player/layout.ts`), and the artwork, the title and the transport are centred together as one block: the transport rises by half the room the artwork leaves. When the window can fit both columns (`tabletPaneWidth`), Lyrics and Queue share a trailing pane; one UI-thread value (`paneProgress`) moves the pane, resizes the playback column and places the artwork, passed into each style that reads it, since a Reanimated style reruns only for the shared values its own closure reads. The pane keeps its own scrolling and the transport stays visible. Narrow windows use the iPhone's single-column pages.
- **iOS queue.** `player/QueuePage.ios.tsx` is one React Native scroll view holding SwiftUI lists sized to their rows, so reordering stays native. The player hands it the song playing (`nowPlaying`), which scrolls with the page; the page reports how far it is from where it rests (`nowPlayingShift`), so the player's own artwork can take over from there when it leaves the page. Its headings stick by `translateY` on the UI thread from the scroll position (`player/queueScroll.ts`). They have no background, so each block of rows is cut down to the bottom of the heading pinned over it: the block's frame moves down and its contents move up by the same amount. The page rests on the song playing or a screen up into the history (`snapToOffsets`); with Reduce Motion it jumps there once it stops. Each list lays out only the rows near the view (`rowWindow`), at their place in a frame as tall as all of its rows: every row is a SwiftUI row with a React Native cover, and every Fabric commit has each mounted scroll view walk its subviews, so a queue laid out whole made each frame of any animation dearer. The window moves on whole chunks of rows as the page scrolls; reordering and the rows' menus count from its first row.
- **Fetched songs.** A summary taken while its song was on demand has no album or cover; when an entry turns from `preparing` to `ready` the provider refreshes it in the `TrackStore` (client-core's `refreshFetchedTracks`), so the mini-player, Now Playing and the lock screen show the cover.
- **Tab bar.** With the system's glass tab bar, `BrowseStack` draws `TabBarEdge` over its pages: content scrolling under the tab bar and the mini-player blurs and fades into the page colour, so their labels stay legible. `useTabChrome` (`src/tabChrome.ts`) gives the bottom padding a page needs to scroll its last row clear of both.
- **Top edge.** Pages scroll under the status bar and pushed pages also scroll under their floating glass buttons. `ScrollEdge` (`src/ScrollEdge.ios.tsx`) uses a low-intensity `expo-blur` view with a gradient mask on its native effect. The blur stays clear until content reaches the status bar and fades out within the safe area. iOS 26's own scroll edge effects are off everywhere: `modules/scroll-edges` hides them on every scroll view as it joins a window, and both stacks set `scrollEdgeEffects` to `hidden` (`noScrollEdgeEffects`) so they do not turn them on again. The page's own colour reaches the status bar. Collection pages bring it in as the cover scrolls up. Home and Library scroll their titles with their content. React Native handles screen insets for its scroll views. Embedded SwiftUI rows and controls ignore the container safe area so their content stays in the measured row as they pass the status bar. Search keeps its title and chips pinned, with a short fade where the list meets them. With Reduce Transparency, and off iOS, `EdgeFade` uses the page colour.
- **Native engine** (`modules/audio-engine`, designed in [audio-engine.md](./audio-engine.md)). The Swift core (`core/`, a package with no Expo dependency) has `Engine`, one process-wide object (`ios/SharedEngine.swift`) made on the first command, so it outlives a JavaScript reload and serves every scene. Each entry is a `Pipeline` on its own serial decode queue: its bytes (`FileByteSource` for a `file://` download; `ByteCache` for a stream: one sparse file in `Caches/squirmy-engine/` filled by a sequential `URLSession` download, with Range requests for what a decoder reads ahead of it, such as an MP4's index at the end, and a download that breaks resumes from where it stopped for about a minute), its decoder (`FileDecoder`, `AudioFile` with `ExtAudioFile`, for originals and downloads, which applies each file's own gapless information; `StreamDecoder`, `AudioFileStream` with `AudioConverter`, for every server transcode, which trims with the descriptor's numbers when there are any), and an `AVAudioConverter` to the output's rate. `NativeEngine` picks the decoder from the load's `media.transcoded`, which `SessionClient` passes from the descriptor. The feed loop (every 20 ms on the feed queue, which never waits for bytes) queues float stereo PCM 0.4 s ahead (10 s on AirPlay) to one `AVSampleBufferAudioRenderer` on an `AVSampleBufferRenderSynchronizer`, the next entry's first frame right after the current one's last, so consecutive files are gapless to the sample; `ended` goes out once the next entry's first frame plays. The renderer's clock runs on when it runs dry, so below 60 ms ahead with nothing decoded the engine stops it (`buffering`) and starts it again with 1 s decoded. A load or seek starts from a 5 ms fade-in, gain changes ramp over 10 ms, and every entry whose gain is not 1 then goes through `Limiter`, a true-peak limiter with a ceiling of -1 dBTP: peaks 4× oversampled (a windowed-sinc interpolator), the needed gain held 10 ms and averaged over the 1.5 ms before it, and a release of 50 to 150 ms, slower the deeper it was turning down. Its lookahead is the frames the feed loop queues next (`upcoming`), not a delay, so it changes no timing, and while nothing goes over its gain is exactly 1 and the samples pass bit for bit. An entry at unity gain (normalization off) passes untouched. Silence is queued while an entry loads and while `holdAudioSession` holds the session, which keeps the app running in the background without the classic engine's silent file. `AudioSessionController` sets `.playback` with the long-form route-sharing policy (and the config plugin `AVInitialRouteSharingPolicy`), and turns interruptions (`didBecomeInactive` and `resumptionRecommendation` from iOS 27), unplugged headphones, route changes and media-service resets into engine calls; the engine never resumes by itself, and says `interrupted` and `resumed` for the provider to turn into session commands. On every status the engine posts `SquirmyAudioClockDidChange`, which `NowPlayingModule` writes to the lock screen's elapsed time and rate without waiting for JavaScript. `swift test` in `core/` decodes split-tone fixtures (`core/scripts/make-fixtures.mjs`, from `apps/server/src/test/audio.ts`) and drives the engine on a fake output whose clock the test moves; the Apple apps workflow runs it.
- **Lock screen.** Buttons arrive through `connectNowPlaying` as callbacks; the provider turns them into session commands, never engine calls. The system's own pause (calls, unplugged headphones) becomes a session `pause`. The star (MPRemoteCommandCenter's `likeCommand`, which iOS draws as Apple Music's favorite) is the track's heart: `favoriteState` gives its state from the track summary and the provider's changed hearts, it is sent again when either changes (only the command, never the now playing info, so the elapsed time stays put), and a tap goes through `setLiked`, as the in-app heart does.
- **Downloads.** `DownloadManager` keeps each recording once per account, whatever albums, playlists, Liked Songs or single-song downloads list it, and drops it when none does. Files come from `GET /tracks/:id/playback?download=1` with the user's download quality, through `expo-file-system` background download tasks, into `Documents/downloads/` under a fresh UUID name; a completed file must match the announced size. Three run at a time; failures retry after 15 s, doubling, and are marked failed after five tries (a 404 at once); on cellular with Wi-Fi only they pause, keeping their resume data, and say so. The index is `downloads.db` (expo-sqlite): one row per account and recording with its file, quality, size, album context and times, plus the track summary, the descriptor (normalization) and retry state as JSON; collections keep their track ids and the album or playlist as last seen, so their pages open offline. Covers are kept at 600 px. Lyrics are kept in the row too (`lyrics`, null when the server has none): asked for when a file completes, by each sync for rows without them, and replaced by whatever the Lyrics page reads online for a downloaded track (`keepLyrics`); `useTrackLyrics` shows them at once and answers with them offline or when the request fails. Rows are written before files are deleted, and a launch sweep deletes files no row names and re-queues rows whose file is missing or short. Syncs (on reconnect, every six hours, and after `invalidate` of playlists, likes or albums) add tracks new to a downloaded collection, drop removed ones, flag what the server no longer has, and, at most daily per file, re-download a file the server replaced (`fileId` changed) while the old one keeps playing. Another account's downloads stay in the folder and the index while it is not in use (the launch sweep counts every account's rows), and the storage limit is the device's: `otherBytes` is what the other accounts hold. `removeAccountDownloads` removes an account's rows and only the files they named that no other row uses, so the running manager's transfers are untouched.
- **Downloading what the server does not have.** A download takes whatever plays for the user (`isPlayable`): for a requester (`canFetch`) an `on_demand` song gets a row in state `fetching`, and the manager asks for it with `POST /tracks/:id/acquire?origin=download` (an album downloaded whole is asked for once with `POST /albums/:id/acquire?origin=download`), which fetches without adding to the library and waits behind play and prefetch on the server. Requests go one at a time, 600 ms apart (the routes allow 120 a minute), and stop for 30 s when the server answers 429. The server announces an arrival or a miss with an `invalidate` of the track; `DownloadsProvider` gathers those for a second and `refreshTracks` reads their summaries: a `server` song is queued and downloads, a `none` one becomes `unavailable`. With no word the song is asked for again after a minute, doubling to 15 minutes (the answer says it is there, `409 already_available`, or that it cannot be had, 403 or 404 or a job that already failed), and it becomes `unavailable` after eight requests. These states, the request count and the next time to ask are in the row's JSON, so a relaunch carries on. Asking needs only a connection; Wi-Fi only and the storage limit hold back the download after it. Someone who may not fetch downloads only what the server has, as before. A collection keeps every track id it lists, also those with no row, so its status counts every song: "Downloading 2 of 3" while a song is being got, "Downloaded" only when all of them are on the phone, and otherwise "2 of 3 downloaded · 1 not available" (`downloadStatus`, `model.ts`), with Retry when a request could change it. A sync queues an `unavailable` song once the server has it.
- **Streaming cache.** `StreamingCache` keeps what was streamed and the next two `ready` entries in `Caches/streaming/` under a per-device limit (default 2 GB), indexed per account, recording and quality in `streaming-cache.db`. `plan` (`model.ts`, pure) chooses fetches once the outlook from `followSession` has been still for a second: on Wi-Fi also the stream being played, fetched a second time because `expo-audio` exposes no bytes; on cellular one at a time at the cellular quality, none with Data Saver; nothing while another device plays. Eviction is least recently played first and spares the entries about to play. `resolvePlayback` (`resolve.ts`) tries a download, a cached copy of at least the quality that would stream, the server, then a lesser copy; offline it takes a lesser copy without asking the server. Copies near the front are checked against the server daily. A launch drops purged rows and stray files. Other accounts' rows stay (`others()`) and count toward the device's limit: eviction (`evictionsAcross`) takes the least recently played row of any account, and covers another account uses are spared; `forgetAccount` removes an account's rows when it is removed from the device.
- **Search.** The Search tab is a `FlatList` of the ranked list (`useSearchList`, `src/library/useSearchList.ts`): song rows are the song lists' own, other results are `CollectionRow`s with a long-press menu and an ellipsis (`actions`). It waits for the catalog's answer or `catalogWaitMs` after the library's, keeping the last results on screen, and `keepOrder` keeps rows already shown for a query in place when the same query is answered again, so nothing moves under the finger. The segmented filters page one kind through `useSearchPages`, including server playlists, stored lyrics with excerpts and composer or producer credits. Older servers use the playlists the client can list. Results opened or played from Search are kept in the app's local storage per server and account (`useRecentSearches`). Offline, `useSearchList` answers from the phone (`useLocalSearch`, `src/library/`): `localLibrary` collects the downloads and what the saved query cache holds (the Library's lists, Liked Songs, playlists, history, Home and the album, artist and playlist pages), and `localSearch` ranks it with the server's name matching (`rank.ts`: whole name, word prefix, prefix, a later word, a typo, artist and title together), at the prominence of the viewer's own music, what can't play now scored down. The Library's **Find in your library** does the same over what the Library lists (`scope: 'library'`). Online, both ask the server as before; local results are not shown first, since the server's ranking would move them when it answered.
- **On demand.** `useAvailability().canPlay` is client-core's `isPlayable` plus the phone's own files (downloads and the streaming cache); offline only those play. A playable track looks the same wherever its file is (no mark); a gray one says "Not available", or offline "Not downloaded", or "Explicit content is off" (`unavailableReason`). An explicit download does not play for a user who has explicit content off. Fetching looks like buffering: `ExpoAudioEngine` counts a player that says it plays while its clock has stood still for 1.5 s as buffering (AVPlayer does that for a stream that has only begun to arrive), and `watchLoading` (`src/player/loading.ts`) follows how long the current entry has waited for audio (`preparing`, or the session `stalled`) and gives `useLoading`/`useTrackLoading` a phase: after 300 ms the play buttons and the current row show the spinner, after 8 s the subtitle reads "Still loading…". Queue rows show the artist whatever their state, "Not available" when failed. Failures are told with client-core's `PlaybackNoticeWatcher`, in the same words as the web app, in the player's status line (Now Playing puts a notice's `detail` on its quieter second line; VoiceOver hears both).
- **Browse pages.** An artist or album page draws its header at once from the summary of the tile or row that opened it (`findArtistSummary`, `findAlbumSummary` in `src/data/`), and an artist page answered with `detailPending` is asked for again every 3 s for a while. Rails are virtualized horizontal lists (`CollectionRail`), since each tile is a native view of its own; an artist page shows the server's `sections` (`releaseGroups`, `src/data/artists.ts`; from an older server, `albums` grouped by type, at most 20 tiles per heading) and 5 top songs. **See all** opens the `releases` or `songs` page of the tab's stack: a section's releases page from `GET /artists/:id/releases` (`useArtistReleases`), an older server's from the cached answer. Release tiles say `releaseSubtitle` (year and type, from client-core, as on web). Album pages list the songs first, with each song's length (client-core's `formatDuration`), a heading over each disc of a multi-disc album, then `formatReleaseDate` and a ℗ line, then the description; rows by the album's artist leave the artist out, and the menu leaves out Go to album. While the server is still looking up an album's songs (`detailPending` with none listed, `awaitsTrackList` in `src/data/albums.ts`, web's rule) the page asks again every 3 s for a minute, then says the songs are late and offers Check again, which asks for another minute. Collection pages have no Play or Shuffle buttons: songs play from their rows, and an album, a playlist, Liked Songs or Recently Played as a whole from its ⋯ menu (`playActions`, the head of `albumActions`; a playlist's adds Rename and Delete for its owner). An artist page shows top songs, the discography, similar artists, then About. A long press on a tile opens its menu (`collectionActions`, `src/library/collectionMenu.ts`), never the page. Song lists are native lists sized from their rows' measured heights (`onScrollGeometryChange`, iOS 18), so rows grow with the text size. Library's **Find in your library** asks `/search/library` and keeps only songs and artists with `inLibrary`. Albums carry no such flag, so it keeps the albums the Library lists (`useLibraryAlbumIds`, every id of `GET /library/albums` up to 2,000) or the viewer saved (`liked`), by `libraryAlbumMatches`; past 2,000 every album match stays.
- **Library.** The library is the server's collection plus what the user hearted, and only the heart adds: on track rows, album and artist pages and the player, plus one menu entry worded by client-core's `librarySave` ("Save to library" / "Remove from library"), the same rule as the web app's. A collection item has the heart too. A track's menu has a **Go to** entry for each credited artist. `LibraryProvider.setLiked` shows the change at once on every cached copy (the heart is the confirmation; there is no Undo), queues it while offline, sends the changes for one item in order, and sets it back when refused, with the failure on the heart for a few seconds. Only a request that never reached the server waits in the queue: no answer, or a gateway's 502, 503 or 504 (`isUnsent`, the same statuses `HttpReach` counts as unreachable). Any other answer, a 500 included, is a refusal, as on the web. Offline, the queue waits for the reconnect however long that takes; online, what could not be sent is tried again after 15 s, doubling, and after five tries it is given up and set back like a refusal (`likeRetryDelay`). A setback restores `inLibrary` too, to what the cache said before the heart changed it (client-core's `heartFields`, `cachedInLibrary` and `heartRollback`, which the web app uses as well). Album tiles are dimmed per `albumPresentation`, artist tiles never online; album pages show `albumNote` to viewers who can't fetch music, and the wantlist only on what the viewer can't play.
- **Offline.** `resolvePlayback` returns a downloaded file's descriptor (with its normalization) before asking the server, so downloads never stream; `SessionClient.forgetPlayback()` runs when a download arrives or goes, and `forgetPlayback(trackId)` when a cached file does. Offline, only downloads and cached tracks are playable (`canPlay`): other tracks are gray, as are albums, artists and playlists with nothing downloaded, actions that need the server are hidden, and a current entry that is neither downloaded nor cached is skipped. The session is saved (`SessionClient.save()`) with the summaries of its entries, and a relaunch restores it paused; commands made offline reach the server on reconnect. The **Offline** badge (`OfflineBadge`) shows beside the title of Home, Library and Search, beside the back button on every other page, and at the top of Now Playing.
- **Errors.** A page or sheet that throws while rendering shows a fallback in its place and leaves the rest of the app as it was: every route exports an `ErrorBoundary` (expo-router's), `PageError` for pages (the back button when there is somewhere to go back to, and Try again, as a page that failed to load shows) and `SheetError` for sheets (its close button and Try again); the root layout's `AppError` catches what fails outside them. Now Playing has its own (`PlayerErrorBoundary`): the music and the mini-player go on, and opening the player shows the error with Try again. React Native reports the error itself; `logRenderError` adds a warning saying which part of the app it replaced (`src/ScreenError.tsx`).

**Apple TV**

- **Build.** One `apps/mobile` makes both apps, and the generated `ios/` folder holds one of them at a time. `EXPO_TV=1` at prebuild makes it the tvOS project (`npm run tv:prebuild`; `npm run ios:prebuild` goes back). `app.config.js` then adds `@react-native-tvos/config-tv` with a tvOS 17.0 deployment target (Pods too), points expo-router at `tv-app/` instead of `app/`, and sets the landscape, always-dark splash. Xcode's bundling phase does not pass `EXPO_TV` on, so the config also recognises a tvOS build from Xcode's `PLATFORM_NAME`. There is no custom entry or Metro configuration. Both apps use the bundle ID `com.isaacthoman.squirmy`, one App Store Connect record with two platforms.
- **Why tvOS 17.** The system's context menus on focusable views and the menu buttons need it, and every Apple TV that ran tvOS 16 runs 17.
- **Routes.** `tv-app/` has the phone's gate (`connect`, `sign-in`, then `(tabs)`) and a transparent `devices` panel. `(tabs)` are expo-router's JavaScript tabs with no tab bar: Search, Home, Library, Now Playing, Settings. Search, Home and Library are stacks of the same album, artist, playlist, genre, releases and songs pages; Settings is a stack whose choices open as pushed lists. Route files only re-export screens from `src/tv/`.
- **Sidebar.** The system's media apps put their tabs in a sidebar since tvOS 26, which UIKit offers only to SwiftUI (`UITabBarController`'s sidebar mode is unavailable on tvOS), so `src/tv/Sidebar.tsx` draws one: a glass pill naming the tab at the top left of a tab's first page, which scrolls away with it, and a Liquid Glass panel of the tabs (a blur before tvOS 26). The focus engine does not move focus out of the screen on show (each tab and page is a view controller of its own), so the pill and the panel are drawn inside each tab's first screen (`Page` does it, other screens wrap themselves in `TabRoot`), with their state in `SidebarProvider`. Up from a page's first row lands on a focus guide under the pill and opens the panel; Menu on a tab's first page scrolls it back to its top, then opens the panel; with the panel open the system takes Menu and leaves the app; moving right closes it. Menu on a page pushed over a tab goes back natively. A screen with something of its own to close (Now Playing's lyrics or queue) takes Menu with `useMenuKey` meanwhile.
- **Focus.** `hasTVPreferredFocus` places a screen's first focus and is let go once that element is focused (`Focusable`), or it would pull focus back from the sidebar and menus. A long press opens the context menu, so `Focusable` gives every press a long press of its own, or its release would also select.
- **Kit.** `src/tv/theme.ts` has the tokens on the 1920 × 1080 canvas (an 80 pt gutter, 260 pt covers). `Focusable` grows the focused thing and lifts it on a shadow; `Artwork` draws covers with `tv-artwork`, so they move with focus as the system's posters do; `Lockup`, `CollectionLockup`, `Shelf` and `SongRow` build the pages; `Button` is a React Native button and `SystemButton` the native one; `Menu` and `menus.ts` give every song, album, artist and playlist the long-press menu the phone's long-press has. Screens use the phone's data and playback hooks (`src/data/`, `src/playback.tsx`, `src/library/`, `src/player/`), not copies.
- **Native modules.** `tv-artwork`, `tv-menu` and `tv-search` are local Expo modules for tvOS only; each JavaScript wrapper returns null in a build without its view, and the kit falls back to React Native parts. `now-playing` gives the TV its Now Playing info and the Siri Remote's commands, which become session commands as on the phone, and the system's AirPlay picker (`showRoutePicker`), which the playback device panel offers while the TV plays.
- **Playback.** The TV plays through the shared session like the phone. It streams at the Wi-Fi quality (Ethernet included), keeps no downloads, and treats its storage as a cache that tvOS may clear. The Keychain holds the saved accounts and their tokens, and Settings lists the others as household **Profiles** to switch to, add or remove. Servers advertise `supportsTvDevices` in `GET /setup/status`; a TV identifies itself as `tv` on those servers and `other` on older ones.
- **Settings.** `src/tv/Settings.tsx` uses the phone's `useSettingsScreen`. Connecting ListenBrainz or Last.fm needs a browser or a pasted token, so the TV shows their state, turns a connected one on or off, and sends the user to the phone or the web to connect. `src/account/settings.ts` loads `expo-web-browser` only when it is used, since tvOS has none.
- **Artwork.** `apps/mobile/assets/tv/render.mjs` draws the layered icon (the worm's eyes, its body, a violet back with rings of sound) and the Top Shelf images from the iOS icon's mascot layers in `assets/Squirmy.icon`. Run `node apps/mobile/assets/tv/render.mjs` from the repository root after changing them, then prebuild the TV project again; `brand-assets.cjs` lists the files for the config plugin.

## Testing

- `vitest` everywhere. A test file sits next to the code it tests as `*.test.ts`.
- **Database tests** call `useTestDatabase()` from `src/test/database.ts`, which clones a migrated template database for the file. They need `SQUIRMY_TEST_DATABASE_URL` (default `postgres://localhost:54329/postgres`). CI provides a Postgres service. Server tests default to at most eight workers to leave room in PostgreSQL’s connection limit for setup and dedicated connections.
- **Audio fixtures** are generated with ffmpeg by `src/test/audio.ts`: short, very quiet tones with real tags. No real music is committed. The native audio engine's Swift tests use a split sweep from it (`makeSplitTonePairs`), generated once and committed so `swift test` needs no ffmpeg.
- **Swift.** `swift test --package-path apps/mobile/modules/audio-engine/core` runs the native engine's core on macOS, where the same AVFoundation and AudioToolbox APIs exist.
- **HTTP fixtures** for external services are recorded JSON; no live calls in tests. A hand-written fixture may list `request.headers` that must match too, for requests that differ only in a header.
- **Before a change is done:** `npm run build:packages && npm run typecheck && npm run lint && npm test` all pass.

## Git

- Conventional Commits: `type(scope): imperative summary`. `feat` and `fix` drive releases.
- Branches are named like commits: `feat-library-scan`, `fix-range-requests`.
- Pull requests target `dev`. `main` receives merges from `dev`; semantic-release tags a version on every push to `main`.
- Every push to `main` is deployed to the test environment at once, without waiting for CI. So `main` changes only through a `dev` → `main` pull request whose checks have passed, never by a direct push. A fix made on `main` anyway is merged back into `dev` right away.
- When CI fails on `main`, it opens an issue. Either fix the problem on `dev` and open another `dev` → `main` pull request, or revert the merge commit on `main` (and merge that revert back into `dev`).

### TestFlight

After semantic-release publishes a version on `main`, CI builds and uploads iOS and tvOS from the release tag in separate jobs. Each build uses the release version and a UTC Unix timestamp as its build number. The tvOS job prebuilds with `EXPO_TV=1` and archives for `generic/platform=tvOS`; `apps/mobile/scripts/upload-testflight.sh ios|tvos` refuses to archive when `ios/` holds the other platform's project. If an upload fails, rerun the failed job from the release's CI run. The Apple apps workflow (`apple.yml`) compiles both apps, unsigned, on pull requests that change the mobile app or its shared dependencies, since they share `apps/mobile` and its native modules.

Use the Squirmy app record in App Store Connect with bundle ID `com.isaacthoman.squirmy`. In the app's sidebar, choose **Add Platform → tvOS** for the Apple TV build. The Apple Development certificate and the team's automatic signing cover both platforms; development signing needs at least one Apple TV registered to the team. In the repository's `testflight` GitHub Actions environment, allow deployments from `main` and set the `APPLE_TEAM_ID` variable to the Apple Developer team ID. Add these environment secrets:

- `APP_STORE_CONNECT_API_KEY_ID` and `APP_STORE_CONNECT_API_ISSUER_ID` for a team API key with access to automatic signing and TestFlight uploads.
- `APP_STORE_CONNECT_API_PRIVATE_KEY` with the complete contents of that key's `.p8` file.
- `IOS_DEVELOPMENT_CERTIFICATE_P12_BASE64` with a base64-encoded PKCS#12 export of the team's Apple Development certificate and private key, and `IOS_DEVELOPMENT_CERTIFICATE_PASSWORD` with its export password.

App Store Connect processes each upload before the build is available to testers. In the **TestFlight** tab, choose **tvOS** and add the build to the intended tester group. External testers receive access after Apple completes TestFlight App Review. Manage tester groups and any export compliance questions in App Store Connect.
