# Squirmy architecture

This is the technical contract for the codebase. [plan.md](./plan.md) says what the product does; this says how the code is laid out and which conventions every module follows. When code and this document disagree, fix one of them in the same change.

## Workspace

```
apps/mobile            @squirmy/mobile        Expo app
apps/web               @squirmy/web           Vite + React web app
apps/server            @squirmy/server        Fastify API, worker, realtime
packages/contracts     @squirmy/contracts     zod schemas and types for every API
packages/client-core   @squirmy/client-core   session reducer, session client, API client
adapters/kit           @squirmy/provider-kit  the provider side of the acquisition protocol
adapters/cold-storage  @squirmy/adapter-cold-storage  reference provider: a folder of your own files
adapters/mock          @squirmy/adapter-mock  provider for tests and demos: quiet tagged tones
```

npm workspaces, Node 22.13 or newer, TypeScript 6, ESM everywhere except the Expo app. `contracts` and `client-core` compile to `dist` with `tsc`; consumers import the built output, so run `npm run build:packages` (or the packages' `dev` watchers) before typechecking or running anything else. The adapters build the same way (`npm run build:adapters`); the root `typecheck`, `test` and `build` scripts build both. The server image installs only the server's workspaces; `adapters/cold-storage` and `adapters/mock` are separate services with their own READMEs, and `adapters/kit` is the library they share (a workspace package, not published to npm).

## Code conventions

- Relative imports end in `.js` in server and packages (NodeNext). No path aliases in server or packages.
- **Contracts first.** Every request and response body is a zod schema in `packages/contracts/src/<domain>.ts`, exported with its inferred type under the same name. Routes parse input with the schema and return objects that satisfy the response type.
- **Units.** Durations are integer milliseconds. Timestamps on the wire are ISO 8601 strings; the session protocol uses epoch milliseconds. Gains are dB; peaks are linear.
- **IDs.** UUIDv7 from `newId()`. Artwork asset ids are UUIDv4 from `newPublicId()`.
- **Errors.** Throw `AppError` (or the helpers in `lib/errors.ts`). The response body is `{ error: { code, message, details? } }`. Codes are stable snake_case strings.
- **Names in the API.** A *track* is a recording. `TrackSummary.id` is the recording id. An *album* is a release group. Clients never see files, releases or recordings as separate concepts, except `fileId` in the playback descriptor.
- **Text matching.** Use `matchKey`, `creditKey` and `sortKey` from `lib/text.ts` for every normalized comparison and for the `*_key` columns.
- **No module-level side effects.** Nothing connects, listens, schedules or reads config at import time. `db` connects on first use.
- **Comments** explain why, not what. No commented-out code.

## Server

```
apps/server/src/
  index.ts              entry: migrate, then start API and/or worker by SQUIRMY_ROLE
  app.ts                buildApp(): Fastify instance, plugins, auth hook, module routes
  config.ts             zod-parsed environment
  database/             client.ts (lazy db), schema.ts, migrate.ts
  lib/                  auth, errors, ids, text, crypto, settings, version, ffmpeg, http
  jobs/                 pg-boss wrapper: jobs.define, enqueue, schedule
  realtime/             socket.io server, rooms, publish/invalidate
  modules/<name>/       one folder per module; see the table below
  test/                 database harness, audio fixtures, factories, http fixtures
```

- **Boot.** `index.ts` migrates, runs each module's `jobs` hook in worker roles, starts jobs, then in API roles builds the app, attaches realtime and runs the `realtime` hooks, then runs every module's `start` hook and listens last. A failure at any step, a migration included, logs `[squirmy] failed to start` and undoes the steps done so far. SIGTERM and SIGINT undo them in reverse. A worker-only process opens no HTTP port.
- **HTTP.** Helmet with a Content-Security-Policy that allows scripts, connections and media from the server only (no inline scripts, no `eval`: the web app sets zod's `jitless` in `zod-config.ts`), cookies, multipart (streamed, up to 16 GiB per file), and CORS only for the Vite dev origins outside production. Each module's `routes` is registered in its own encapsulated scope under `/api/v1`.
- **Compression and revalidation.** `@fastify/compress` sends brotli (quality 4) or gzip for JSON, XML, JavaScript, CSS, SVG and text of 1 KiB or more; audio, images and ranged responses go as they are. `lib/conditional.ts` gives every successful JSON GET under `/api/v1` a weak `ETag` (a hash of the body) and `Cache-Control: private, no-cache`, unless the route set its own, and answers a matching `If-None-Match` (compared weakly) with an empty 304.
- **Web app.** When `SQUIRMY_WEB_DIST` is set the built app is served, with `index.html` as the fallback for unknown GET paths outside `/api`, `/rest`, `/socket.io`, `/health` and `/ready`. Hashed files under `assets/` are cached as immutable.
- `GET /health` answers without touching anything; `GET /ready` checks the database.

### Modules

Each module is a folder under `modules/` that exports one `ServerModule` from its `index.ts`. `modules/index.ts` lists them all statically. A module only edits files inside its own folder, its own contracts file, and its own tests.

```ts
export type ServerModule = {
  name: string
  /** HTTP routes. Called with an instance already prefixed with /api/v1. */
  routes?: (app: FastifyInstance) => void | Promise<void>
  /** Routes that need their own prefix (Subsonic's /rest). Called with the root instance. */
  rootRoutes?: (app: FastifyInstance) => void | Promise<void>
  /** Job handlers. Called in processes whose role includes the worker. */
  jobs?: (jobs: JobRegistry) => void | Promise<void>
  /** Socket handlers. Called in processes whose role includes the API. */
  realtime?: (realtime: Realtime) => void | Promise<void>
  /** Long-running loops (file watchers, schedulers). `stop` must undo `start`. */
  start?: (context: { role: 'all' | 'api' | 'worker' }) => void | Promise<void>
  stop?: () => void | Promise<void>
}
```

### Seams between modules

Modules reach each other in three ways, in this order of preference:

1. **Database state.** A module finds its own work by querying for rows that need it (files with no loudness, albums still `pending`). Sweeps make this robust to ordering and restarts. A module may also hold off on work by another module's recorded state: scans skip `_Incoming` folders of imports still moving files, and matching waits for an import to decide its duplicates.
2. **Jobs by name.** A module may enqueue another module's job (`enqueue('loudness.measure', { fileId })`). The job name and payload are that module's public interface.
3. **Seam functions.** A few direct calls are declared up front as seams: `enrichment/detail.ts` (`ensureAlbumDetail`, `ensureArtistDetail`), `acquisition/coverage.ts` (`onDemandRecordings`, `requestRecording`), `radio/suggest.ts` (`suggestAutoplay`). The owning module fills them in; callers never change. In the other direction, sessions exports `onPlayStart` (`sessions/plays.ts`), a subscription to plays opening on the active device, which scrobble uses for "now playing".

Beyond those, modules call each other's exported functions directly where sharing beats a copy: the catalog read helpers (`catalog/sql.ts`, `catalog/availability.ts`, `catalog/redirects.ts`, `catalog/summaries.ts`), `library/cleanup.ts`, `matching/merge.ts`, organize's planner and mover, and `search/keys.ts` are used across modules. Import them from the owning module and keep their signatures stable; the owner changes them with their callers.

### Configuration

Environment variables are parsed in `config.ts`; see that file for the full list. The ones a self-hoster sets: `DATABASE_URL` (required), `SQUIRMY_DATA_DIR`, `SQUIRMY_LIBRARY_PATHS` (read-only roots) and `SQUIRMY_MANAGED_LIBRARY_PATHS` (managed roots), `SQUIRMY_INBOX_PATH`, `PORT`, `PUBLIC_URL`, `TRUST_PROXY`, `SQUIRMY_ROLE`. `SQUIRMY_SECRET` is generated into the data directory on first boot when unset.

Operator settings that change at runtime (provider toggles, API keys, thresholds) live in the `server_settings` table and are edited in the admin UI. Shape: `ServerSettings` in contracts. Secrets are stored encrypted under separate keys and never returned. Feature switches clients need before signing in, such as `wantlistEnabled` (default off), are also reported by `GET /setup/status`; changing one invalidates `queryKeys.setupStatus()` and what it changes for every client.

### Artwork

Images are rows in `assets`. `storeImage(bytes)` stores an image now, de-duplicates by content, and queues `artwork.render` for a new one, which writes the 96, 300 and 600 px renditions from one read of the original. `GET /art/:id/:size` also answers `:size.webp`, which the web app uses so a CDN that caches by extension (Cloudflare) keeps art at the edge; responses are `public, max-age=31536000, immutable` with an `ETag` matched weakly. `remoteImage(url)` only records where an image lives; it is downloaded the first time `GET /art/:id/:size` asks for it, so search results for music you do not own can show covers without downloading every one. A failed download answers 404, is not cached, and is retried after an hour. A sized Cover Art Archive front (`.../front-500`) that answers 404 is fetched as the original (`.../front`, `coverart.originalFront`): archive.org derives the thumbnails some time after an upload, so a release of the last few days has only the original. When the source answers 404 or 410 (a release group the Cover Art Archive has no cover for), the asset is also unassigned from the albums and artists showing it, so their summaries stop handing out an id that cannot be served, `invalidate` names those albums and artists (from whichever process asked for the image), and each album gets `enrichment.cover`, which picks another cover; the discography does not offer that cover again for a week. Summaries leave out an asset that is `missing`, or `failed` and not yet due for a retry (`servable` in `catalog/summaries.ts`); Subsonic applies the same rule to its `coverArt` fields, image URLs and `getCoverArt` by entity id (`servableArt` in `subsonic/sql.ts`).

Lost originals rebuild themselves (`artwork/recover.ts`). When a file under `assets/` is gone, `readOriginal` (used by renditions and Subsonic's `getCoverArt`) reads it back from disk while the request waits: the folder image of a `folder:` source, or the pictures of the source file and of any present file whose `embedded_art_asset_id` it is. Only bytes with the stored SHA-256 are accepted, so an id never shows a different picture. A URL source is queued as `artwork.recover` and the request answers 404 without cache headers; the job downloads it again (a `remote_url` asset goes back to `remote` and is fetched as on its first request; any other must match its hash). An asset nothing rebuilds is `missing`, answers 404 at once, and is left alone. `artwork.sweep` (daily, 04:40) queues assets whose file is gone, `missing` assets whose file is back, and `missing` assets last tried a week ago.

### Authentication

- A session token is 32 random bytes, base64url. Only its SHA-256 is stored (`auth_sessions.token_hash`). Sessions last 180 days, sliding.
- Browsers get it in the `squirmy_session` cookie (httpOnly, SameSite=Lax, Secure when the request is HTTPS). Native clients send `Authorization: Bearer <token>`. The socket takes the same token from the cookie or from `auth.token`.
- Setup, login and register return `{ user, token }` to every client. A request with the header `X-Squirmy-Client: web` also gets the cookie; `GET /auth/me` renews it. Passing a `device` upserts the `devices` row.
- An `onRequest` hook resolves the token for `/api` routes and sets `request.user` (or null) and `request.authSessionId`. `/rest` authenticates each request with Subsonic credentials instead. Route code calls `requireUser(request)` or `requireAdmin(request)` from `lib/auth.ts`.
- **CSRF.** A cookie-authenticated request that is not GET/HEAD/OPTIONS must carry the header `X-Squirmy-Request: 1`. Bearer requests are exempt.
- Passwords are argon2id. Login is rate limited per address. Failed logins are counted before the password check (and taken back on success) per username and address, per username and IPv6 /48, and per username overall, where addresses with a recent success are exempt (`lib/failures.ts`); so concurrent attempts cannot slip past, a correct login never uses a budget, and one client cannot lock an account out for everyone. At most two argon2 runs at once (`withHashSlot`), with a bounded queue. Setup and register are limited per address, password changes per user. Subsonic has no lockout. Addresses are keyed by `lib/proxy.ts` `addressKey` (IPv6 per /64). Counters live in the API process's memory.
- Logging out, changing a password (other sessions), and an admin disabling a user or resetting their password end the affected sessions and close their sockets.
- App passwords for Subsonic clients are random secrets stored AES-GCM encrypted (Subsonic token auth needs the clear text) plus a SHA-256 `key_hash` for `apiKey` lookups. `modules/auth/service.ts` exports `verifyAppPassword` and `findAppPasswordByKey`. Creating one needs the account password, at most `APP_PASSWORD_LIMIT` (50) per user; a password change, an admin reset and disabling the account delete them (`revokeAppPasswords`). Devices are recorded through `rememberDevice`. Recording a new device also forgets the user's devices not seen for 180 days (as long as a session lasts) and keeps at most the 100 most recently seen.
- `lib/crypto.ts` derives purpose-specific keys from the root secret with HKDF and exposes `hashToken`, `sign`/`verify` (HMAC-SHA256) and `encrypt`/`decrypt` (AES-256-GCM, base64url output).

### Jobs

`jobs/` wraps pg-boss. Modules never import pg-boss directly.

```ts
jobs.define('library.probe', { concurrency: 4 }, async (data: ProbeJob) => { … })
await enqueue('library.probe', { fileId }, { singletonKey: fileId, priority: 0 })
await schedule('library.scan-all', '0 4 * * *')
```

- Queue names are `<module>.<verb>`.
- Handlers are idempotent: running one twice leaves the same result.
- `enqueue` accepts a transaction (`{ tx }`) so a row and its job commit together. It goes through pg-boss's Drizzle adapter, so the job insert runs on the caller's transaction; there is no outbox.
- `singletonKey` makes a duplicate a no-op while a job with that key is queued, retrying or active. Queues use pg-boss's `exclusive` policy and keyless jobs get a unique key, so only keyed jobs are deduplicated.
- A definition can choose `policy: 'stately'` instead: one queued and one active job per key, so a request made while a job runs is kept as a single follow-up (`library.ingest` uses it). The policy is fixed when the queue is created.
- `enqueueMany(name, items)` inserts many jobs in one statement with the same deduplication.
- Each concurrency slot is its own pg-boss worker and is woken as soon as its job finishes, so a backlog drains continuously rather than waiting out pg-boss's 30 second notify backstop between jobs.
- NOTIFY wakes workers when a job is inserted, not when a deferred one (`startAfter`) becomes due, so `enqueue` also wakes this process's workers for that queue just after the start time; a deferred job enqueued by another process still waits for the next poll.
- Failures retry with exponential backoff (default 3 retries). `timeoutSeconds` fails a job that runs too long.
- Every process starts pg-boss: `index.ts` calls `startJobs({ work })` with `work` true for worker roles. Modules' `jobs` hooks run only in worker roles; a process that enqueues a job it has no definition for creates the queue on first use.
- `getQueueStats()` counts jobs live; `GET /admin/jobs` returns it.
- Tests call `startJobs({ work: true })` and then `drainJobs()`, which resolves once no job of a defined queue is ready or active, running retries without waiting out the backoff.
- Priority orders jobs within one queue only. Each queue has its own worker slots, so heavy queues are bounded by their `concurrency` (loudness 1, analysis 2) rather than by priority. Background sweeps and safety-net jobs use negative priorities so on-demand jobs of the same queue run first.

### Realtime

`realtime/` owns the socket.io server. The session protocol is specified in `packages/contracts/src/session.ts`.

- `startRealtime(app)` attaches to the Fastify server before it listens; closing the app closes the socket server. Messages of 1 KiB or more are deflated (`perMessageDeflate`), mostly for `session:queue`, which carries the whole queue.
- The handshake takes the session token from `auth.token` or the `squirmy_session` cookie and is refused without a valid one. With the cookie, an `Origin` header must match the request's `Host`, `PUBLIC_URL`, or (with `NODE_ENV=development`) the Vite dev server. A socket is disconnected when its session expires; messages are capped at 1 MB.
- Each socket joins the room `user:<id>`. Admin sockets also join `admins`. Handlers passed to `onConnection` run after that; register socket listeners before the first `await`.
- `publish(target, event)` and `invalidate(target, keys)` are callable from any process. They `NOTIFY squirmy_events` with a JSON payload; the API process `LISTEN`s on a dedicated connection and forwards to rooms. `target` is `{ user: id }`, `'admins'`, `'all'`, or a list of them, which reaches each socket once however many of them it is in (an admin is in their own room and in `admins`). Keys that do not fit in one notification (8000 bytes) are split across several. `disconnectSockets(userId, { only | except })` closes sockets of revoked sessions the same way.
- `time:sync` is answered here; the `session:*` events belong to the `sessions` module.
- Every mutation that changes what another open screen shows calls `invalidate` with keys from `queryKeys`. The same call drops the API process's cached reads (see "Catalog read side"): at once in the calling process, and in the API process when the NOTIFY arrives, before the clients are told.

### HTTP API

All native routes are under `/api/v1`. ### Availability

Two separate questions, both answered in `modules/catalog/availability.ts`: can this be played (availability), and is it in this user's library (membership). A file existing answers the first and, on its own, never the second.

**Availability**, which every list and page uses:

- Track: `server` if a present (not missing) `media_files` row has its `recording_id`, whatever its source. Otherwise `on_demand` if an enabled acquisition provider covers it (coverage `assume_available`, or a cached positive resolve) and it is not in `acquisition_misses`. Otherwise `none`.
- Album: counts owned tracks on its track list (`albumTrackList`, below): the canonical release (else the album's release with the most tracks), plus owned recordings filed under the album that the release does not list. All owned is `full`, some is `partial`; none owned is `on_demand` when its tracks would be, else `none`. `trackCount` and `ownedTrackCount` count the same list, so an album with a present, linked file is never `none`.
- Clients present it by viewer with `isPlayable` and `albumPresentation` from client-core: for a *requester* (an admin, or a member with `canAcquire`) `on_demand` looks and plays like `server`; for anyone else it is unavailable. Requesters see no badge or count telling the two apart.

**Membership.** A user's library is the server's *collection* plus what that user *saved*:

- **Collection**: a present file whose `source` is not `provider:*` (scanned, uploaded, from the inbox). Shared: it is in every user's library, and only an admin takes it out, by deleting files. `collectionFile(alias)` is the condition.
- **Cache**: a file a provider delivered. `media_files.cached` is generated from `source like 'provider:%'`, so it cannot drift. Cache makes a track `server` and puts nothing in any library: a song sampled by pressing play stays out of Albums, Songs, Artists and Recently added.
- **Saved**: a row in `library_items (user_id, entity_type 'album' | 'recording', entity_id, created_at)`, written by `PUT /me/library/:type/:id` and deleted by `DELETE` (owner: userdata). A save needs no file, so a saved album is in the library at once. Removing deletes the row only: files stay as cache; likes, playlists and history stay. For a requester a save also asks acquisition for what is missing, as the `userdata.fetch-saved` job, best effort: the save never waits for it or fails on it. Liking does not save, and saving does not like.
- **Album** in a user's library: a collection file is linked to it (`media_files.album_id`), or the user saved it (`inLibraryAlbum`).
- **Track**: a collection file links its recording, or the user saved the recording, or a present file (cache included) links it and that file's album is saved by the user (`inLibraryRecording`). Songs of a saved album therefore appear as their files arrive.
- **Artist**: credited (`album_artists`) on an album in the user's library. Being featured on a track, or credited on cached music, does not count.
- Merges move saves as they move likes (the older row wins a collision), and the library's orphan cleanup and `search.cleanup` keep saved rows.
- The migration that introduced this turned completed album fetches with a requester into saves (with a track-only provider, seven or more track fetches of one album by one requester within a second, more than playing ever starts at once); other single-track fetches came from pressing play and were not carried over. On a server whose files all came from a provider, every library starts empty.

### Catalog read side

- `catalog/summaries.ts` builds every `TrackSummary`, `AlbumSummary` and `ArtistSummary`, in batches with a fixed number of queries. They leave out artwork the art route would answer 404 for: a `missing` asset, or a `failed` download inside the hour before it is tried again. Other modules (search, sessions, userdata) use these rather than writing their own. Subsonic builds its own, because its objects describe files (size, codec, path), but takes availability and redirects from the catalog. Summaries are per viewer: `TrackSummary.inLibrary` and `ArtistSummary.inLibrary` follow the viewer's membership (`artistSummaries` without a user answers for the collection alone); `AlbumSummary` carries none, and `AlbumDetail.library` is `collection` (which wins when the album is also saved), `saved` or null. `TrackSummary.library` says why a track is a member, the first of `collection`, `album` (a present file of it is on an album the viewer saved) and `saved`, or null (`recordingLibrary` in `availability.ts`): only a `saved` track leaves the library when its save is removed.
- Ids that come from clients follow `merged_into_id` redirects (`catalog/redirects.ts`, one primary-key lookup per hop, at most 16); the summary builders do it themselves, so stored queue and playlist ids keep working after a merge. `POST /tracks/summaries` answers a merged id with the row it was merged into and lists, in `requestedIds`, the id each summary was asked for, so `TrackStore` files it under the id the queue holds.
- **Cached reads** (`lib/read-cache.ts`). `GET /home`, `/library/*`, `/albums/:id`, `/artists/:id`, `/playlists` and `/playlists/:id` keep their serialized answer and its ETag in the API process, per user and URL, within `SQUIRMY_READ_CACHE_MB` (default 64, least recently used out first; off under test unless set). Each route names the `queryKeys` roots it depends on; an `invalidate` for one of them drops that user's entries (a user target) or everyone's (`all`, `admins`), a root the cache does not know drops everything, and `admin`, `settings`, `scrobbling`, `me` and `lyrics` drop nothing. A read that overlaps a drop is not stored. Entries expire after five minutes, which bounds what nothing announces; catalog searches (stubs credit artists and fill covers) and provider changes drop everything explicitly. Writes made in the background go through `invalidate` like any other, so a worker's reach the API process: an unassigned cover, album stubs a discography adopts (`upsertDiscography` names them, whichever job wrote it), an album hydration (announced even when a later step fails) and `search.cleanup` (each kind it deleted from, by root). Home is computed again two seconds after a drop when it was read in the last 15 minutes.
- Lists use keyset cursors (`catalog/pagination.ts`): opaque, tied to one ordering, and stable under ties and concurrent inserts. Title and artist orderings are `sortKey` over the stored `*_key` columns, backed by expression indexes in `schema.ts`.
- **Library lists** (`catalog/library.ts`) take the user and list their membership (above). Title, artist and year pages (and tracks by year, which place each library track by its newest present file, so a saved track waits for its file) have two shapes, picked per request by `libraryShape`, which counts members up to 2,000 on the membership indexes. A small library is read from its members (collection files by album or recording through the `media_files_collection_*` indexes, plus the user's saves) and sorted, so a catalog full of search stubs costs nothing. A large one walks the catalog's sort index and keeps members, about `limit` rows when most of the catalog is library.
- `recent` places an item at the later of its newest collection file's `added_at` and its save's `created_at` (for a track, also the save of an album holding a present file of it). It is a union of one walk per way in, each on its own index and keeping only the items whose time it holds, so each item appears once. Its orderings are `albums:recent2` and `tracks:recent2`; cursors from the old newest-file order are refused with `invalid_cursor`. `performance.test.ts` (10,000 albums, 150,000 tracks) and `stubs-performance.test.ts` (200,000 stubs around a library of 50 albums) check every page with EXPLAIN.
- Home's `recently-added` is the user's library albums by `recent`.
- An album's track list is `albumTrackList` (`catalog/pages.ts`), for the album page and Subsonic's `getAlbum`: the canonical release's tracks, then owned recordings filed under the album that the release does not list (bonus tracks, files matched with no track) in path order on the last disc, with no position. Subsonic numbers those after the disc's last track.

### Search

`modules/search/`. Both routes return `SearchResults` built with the catalog summary builders, so availability comes out the same as everywhere else. Queries whose `matchKey` is shorter than two characters answer nothing.

- **`top`** (`top.ts`, both routes): the single result a client can lead with, as `{ type, id }` naming an item of the lists, or null. Each result's name is compared with the query by `matchKey`, ignoring a leading "the", "a" or "an" on either side: the whole name, or for albums and tracks "artist title" and "title artist", equal to it (also once edition suffixes are dropped, `editionFreeKey`, since Deezer names most classic albums "… (Remastered 2009)") is the best match; starting with it is next; from five characters, a name one typo away comes last; anything else is never top. Ties go to the match with the article as typed, then to popularity when both sides have one (a track's `popularity`; an album's or artist's is the best of the returned tracks on it or by them, unknown when none came back), then to the item its list ranks higher (the provider's or the library's own order), then artist before album before track. `score` states the match on the 1..3 scale clients use to choose between the two routes' hints (`mergeSearch` in client-core): 3 the whole name as typed (edition suffixes ignored), 2 the whole name only with the article ignored, 1 a prefix or one typo; it follows the first two tie-breaks, so a higher score is always a hint this ranking would have put first. The field is optional in the contract, so older servers and clients are unaffected.

- **`GET /search/library`** (`library.ts`): owned music only (artists credited on an owned track or an album with a present file, albums with a present file, owned tracks). Candidates per kind come from bounded index lookups: a byte-order prefix btree on `name_key`/`title_key`; every split of the query into "artist title" or "title artist", looked up from that artist's rows; albums and tracks whose primary artist's name starts with the query; and, from three characters, trigram word similarity on `name_key` or the whole `match_key` (artist and title, so typos and word order are tolerated). Ranking: exact, then prefix (title, name or artist), then similarity; ties go to the user's plays among their last 1,000, then likes. Each kind is one query run with `enable_seqscan` off, because the planner prices `word_similarity` too low. `performance.test.ts` measures it on 10,000 albums and 150,000 tracks.
- **`GET /search/catalog`**: one provider per request (`providers.ts`), in this order: the local index when `isCatalogIndexReady()`, Deezer when enabled, MusicBrainz when enabled. A provider that throws falls through to the next; `provider` names the one that answered. Identical queries in flight share one provider call, and `cachedFetch` keeps search responses for a day. MusicBrainz free text matches titles only, so "artist title" queries are only understood by the other two. The route runs the library search for the same query and limit alongside the provider call and leaves out of its answer every artist, album and track that the library answer lists, so owned music the provider also found is not shown twice. It also lists one artist per name (`namesakes.ts`): an artist without an MBID is left out when the library answer, an artist of the answer with an MBID, or an earlier one has its name. Deezer has duplicate pages for some artists ("Boards of Canada" 1098 and 412310471), which are rows of their own until enrichment merges them; artists with MBIDs always stay. Its `top` is picked from what is left, with the same function and scale as the library's, so the client's comparison is between two separately ranked hints. After answering, it starts detail in the background: `warmDetail` for a top artist, and through `warm.ts` for up to five albums (a top album, then the first albums with no track list yet), two at a time across the process, a newer search's ahead of what an older one left waiting. Their pages are complete and their tracks playable by the time a user opens one.
- **Stub rows** (`materialize.ts`): results are stored before they are returned, in one transaction per response under the advisory lock `squirmy:search-stubs`. Each result is matched to an existing row by its `external_ids` row (`deezer`, or `musicbrainz` for MusicBrainz and local-index ids), then by MBID, then by key: for artists the one artist with that `name_key`, if exactly one exists and it has no other id from the provider; for albums and tracks the same artist (credit text or primary artist) and the same title once edition suffixes are dropped, owned rows first. Album types must agree unless the row is owned; track lengths must be within 10 s. Only then is a stub inserted:
  - artist: `name`, `name_key`, `detail_level` 0, `mbid` when known, an `external_ids` row, `image_asset_id` from `remoteImage`;
  - album: `title`, `artist_credit`, `primary_artist_id` and `album_artists`, `type`, `year`/`release_date`, `title_key`, `match_key`, `detail_level` 0, `mbid` (release group) when known, an `external_ids` row, `artwork_asset_id` from `remoteImage`, no releases;
  - recording: `title`, `artist_credit`, `primary_artist_id` and `recording_artists`, `duration_ms`, `title_key`, `match_key`, `explicit`, `popularity` (0..1), `isrcs`, `mbid` when known, an `external_ids` row, and `album_hint_id`, an album it appears on. Summaries use the hint only when no file or release track names an album.

  Existing rows only gain a missing external id, image or album hint. Credits without any provider id (the local index names some artists only as text) reuse the artist with that name and otherwise become a stub without an external id.
- **Edition suffixes** (`keys.ts`): a bracketed or dashed suffix is ignored for matching when all its words describe an edition (deluxe, expanded, remastered, anniversary, explicit, clean, bonus tracks, numbers…) and at least one is a strong word, so "OK Computer (Deluxe Edition)" and "Let It Be - Remastered 2009" find the plain titles while "(Live)", "(Remixes)", "(Radio Edit)" and "(Taylor's Version)" stay different albums and songs. Stored keys keep the full title. A catalog query that ends in edition words with at least one strong word ("ok computer deluxe") is also sent without them, and those results follow the whole query's: providers match every word, so an edition they name differently would otherwise find nothing.
- **`search.cleanup`** (daily): deletes stubs older than 30 days that never gained detail (albums and artists at `detail_level` 0 with no MusicBrainz releases, recordings on no release) and that nothing keeps: files, likes, ratings, wants, playlist items, plays, ids in stored playback sessions, acquisition jobs still running, album hints of kept recordings, credits, merges. Their `external_ids` go too; `assets` stay. The library's orphan cleanup leaves stubs alone.

### Playback and streaming

- Clients ask `GET /tracks/:id/playback` and receive a signed URL. The stream route accepts the signature instead of a session so `<audio>`, AVPlayer and downloads need no headers. Signatures bind the file id, profile, user id and an expiry of 12 hours.
- File choice: files of the recording that belong to the requested album first, then lossless over lossy, then higher bitrate. Both ids follow merges, so a queue entry that names an album merged away still gets that album's file.
- `chooseProfile` (`streaming/select.ts`) maps a quality to a profile. `original` serves the file when the client decodes its codec. Otherwise the target is the first profile the client decodes from the quality's preference list (`original` and `high`: `aac_256`, then `mp3_320`, `opus_128`, `mp3_192`; `data_saver`: `opus_128`, then `mp3_192`, `aac_256`, `mp3_320`). A lossy file at or below the target bitrate that the client decodes is served as is; one it cannot decode gets the smallest playable profile at or above its own bitrate. Encoder settings are in `streaming/profiles.ts`.
- Signed URLs carry `exp` (epoch seconds), `uid` and `sig`, an HMAC from `sign('stream', …)`. A request without a valid signature may use the session instead.
- A URL names the file, not its path, so it keeps working when organize files it: a file not at its row's path is looked for at the other end of a move that is running (organize renames on disk before it updates the row), and is marked missing only when it is in neither place. When the library root itself is not a readable folder (an unmounted drive or share) the request answers 503 `root_unavailable` and nothing is marked missing, as the scanner does.
- A transcode is written to the cache while it is streamed to the first requester; later requests get the cached file with Range support. A cached transcode is used only while the source's size and mtime are the ones it was made from, so a file replaced or retagged in place is encoded again. ffmpeg writes to a pipe, so every streamed byte is final: AAC 256k in ADTS (`.aac`), Opus 128k in Ogg, MP3 at constant bitrate without a Xing frame. Encoders: `aac`, `libopus`, `libmp3lame`.
- Requests for the same transcode share one ffmpeg per process; a client that leaves does not stop it. At most half the CPU cores (at least two) encode at once.
- Transcodes are built when a stream first asks for them; nothing is converted ahead of time. `streaming.evict` runs hourly and at worker start: it reconciles rows with files on disk and deletes least-recently-used transcodes beyond `transcodeCacheMaxBytes`, sparing those used in the last half hour so a track being played keeps answering Range requests.
- Normalization values: prefer measured loudness (`-18 − loudness_lufs` gives the gain); fall back to the file's ReplayGain tags. Album values come from `release_loudness`.
- Loudness is EBU R128 from ffmpeg's `ebur128` filter. `loudness.measure` `{ fileId }` stores a file's integrated loudness and true peak, then queues `loudness.album` `{ releaseId }`, which decodes the release's present files in track order through one concat filter, so gating covers the album as a whole. `loudness.sweep` (every 10 minutes and at worker start) queues files with no loudness in batches of 500 and releases whose file set changed. Silent and very short files store -70 LUFS, which yields no gain.

### Sessions

The server holds one shared session per user in memory, loaded on first use and persisted to `playback_sessions` on change (debounced one second, and flushed on shutdown), plus one session of its own for each detached device (see "Detaching" below). This assumes one API process: the copy in memory is the truth, so functions that change sessions (`markRecordingReady`, `replaceQueue`) must run in that process. Commands arrive on the socket, run through `reduceSession` from client-core, and the result is broadcast to the sockets in that session (socket.io room `session:<user>` for the shared one, `session:<user>/<device>` for a device's own): `session:state` on every change, `session:queue` only when the queue half changed (`queueChanged`), emitted just before the `session:state` of the same version. A socket joins a session room when its hello is answered; device lists and invalidations go to the `user:<id>` room as before.

- **Commands.** The server passes the envelope's `commandId` to the reducer (new entry ids derive from it), remembers recent command ids (the last hundred are stored with the session, so they survive a restart along with their effect) and acks a duplicate without applying it again, and acks a command before broadcasting its result. Server-issued commands use a fresh id. A user's commands, reports and hellos run one at a time, in arrival order, so each socket has a budget (`sessions/socket.ts`): 20 commands a second in bursts of 40, past which commands are acked `rate_limited`; 5 reports a second in bursts of 20; 5 hellos, then one every 5 seconds; 10 detaches and attaches together, then one every 2 seconds, past which they are acked `rate_limited`. Excess reports and hellos are dropped.
- **Trusted entries.** For `playTracks` and `enqueue` (and Subsonic's `savePlayQueue`) the server keeps only the track ids the client sent: it follows merges, takes durations from the database, drops tracks the user cannot play, and sets `ready` or `preparing` itself. Owned tracks are kept for everyone; `on_demand` ones only for a requester (an admin, or a member with `canAcquire`), so no one else gets an entry that would sit preparing and then fail.
- **Limits.** A session is copied and sent whole on every queue change, so it stays bounded. `playTracks` and `enqueue` carry at most `COMMAND_TRACK_LIMIT` (5,000) tracks, and the queue holds at most `QUEUE_LIMIT` (10,000) entries: an `enqueue` that would grow it past that, counted after untrusted tracks are dropped, is acked `queue_full` and the reducer ignores it, so optimistic clients agree. `replaceQueue` considers at most 5,000 ids from the current one on.
- **Device list.** The connected devices, sent on every hello and whenever one comes, goes or changes. Each socket gets the list as its own device sees it: `isCurrent` marks that device (over HTTP, the device the sign-in was made from). `lastSeenAt` is when the device last sent a hello, command, report or move; it moves on in memory and the list goes out again when what the others have is a minute or more behind, so a playing device costs at most one list a minute.
- **Active device.** The first device that can play and sends a command that starts playback while no device is active becomes active. `transfer` changes it, and only to a connected device that can play. Only the active device may send `trackEnded` and engine reports. A report that is more than a second off the computed position, or changes whether playback is stalled, becomes `syncPosition`.
- **Disconnects.** If the active device's last socket closes, the server waits 20 seconds, then applies `deviceLost` as of the moment it went away (pause at the position it had then, or at a later change's, and clear the active device), so neither the resume point nor the play counts the grace period. A session loaded after a restart gives its absent active device the same grace.
- **Plays.** A play row opens when an entry is current and running on the active device and closes when the entry changes or stops at its end. Listened time comes from the session's position arithmetic, so pauses and seeks add nothing. The open play is stored with the session (and written at shutdown under the id it was given when it opened), so a listen across a restart stays one row. Plays under five seconds are skips and leave no row; one counts as completed after half the track or four minutes. A play is written under the recording and album the track's summary resolves to when it closes (merges followed; the album of its file, else of a release), not the entry's ids, so it never lands on a merged-away row or on the catalog stub album an on-demand track was queued from. Writing one invalidates history and home.
- **On demand.** The current entry and the next five (`PREPARE_AHEAD`) that are `preparing` are requested from acquisition with `requestRecording`, current first and one after another, so jobs are created in queue order. Each request carries an origin, `play` for the current entry and `prefetch` for the rest (passed through for job ordering; acquisition does not read it yet); a prefetched entry that becomes current is asked for again as `play`, which joins the job in flight, and a queued request the session no longer wants by its turn is not sent. An entry stays `preparing` until the file is linked, then `setEntryState` flips it to `ready` or `failed`. A failed entry further down is only marked, without any notice, and skipped when reached. A failed current entry is skipped (a failure that comes after a current entry became ready leaves that entry playing), except the third in a row with no current entry ready in between (`FAILURES_BEFORE_PAUSE`; a new `playTracks` also restarts the count): then the session pauses on it, keeps the rest of the queue, publishes one `playback.unavailable` event to the sockets in that session, and requests nothing more until the user plays again, when `play` moves on from it. Every request gets an answer, so an entry never waits forever; see "Acquisition". A request that throws instead fails the session's entries of that recording, counted like any other failure.
- **Autoplay.** When the queue is nearly empty and autoplay is on, the radio module supplies `setAutoplayQueue`. `playTracks` empties the autoplay queue, so suggestions always follow what is playing rather than an earlier queue.
- **Detaching.** `session:detach` gives a device that can play a session of its own, copied from the shared one with `forkSession` (client-core); `session:attach` discards it, and with `bringQueue` first makes the shared session what it was (`bringSession`). The rules are in the "Detaching" section of `packages/contracts/src/session.ts`; the server's side of them:
  - Own sessions are rows of `detached_sessions` (one per device, cascading with the `devices` row), written before the device moves and then like shared ones, with `last_seen_at`. Once loaded, one stays in memory like a shared session (so it keeps its recent command ids) until shutdown or until it is discarded. Its device leaving while it plays gets the same grace period and `deviceLost`.
  - Which session a device is in is decided by its first socket's hello: the stored own session when there is one and the hello carries `detached` (either value), else the shared one. A hello without `detached` is from a client that cannot detach and discards a stored own session. Later sockets of a connected device join whichever session it is in, and when it moves, its other sockets get `session:moved`.
  - All of a user's sessions share the user's one serial queue, so detaching and attaching change both sessions in one step. The `detached_sessions` row is written (detach) or deleted (attach) before anything in memory changes, so a database error leaves the device where it was; the shared session is then written at once rather than a second later. The open play moves with the device: detaching while active carries it into the own session, bringing the queue back carries it into the shared one (closing the play the shared session had), and attaching without it closes it.
  - An own session runs everything above as the shared one does (trusted entries, fetching ahead, the pause after failed fetches, autoplay, plays), and its `playback.unavailable` goes to its device alone.
  - A device in its own session can transfer only to itself, and the shared session cannot transfer to a detached device. `DeviceInfo.detached` lists what each detached device plays, and the list is sent again when that changes.
  - Limits: eight own sessions per user. Detaching drops sessions unseen for seven days, then, if eight remain besides the device's own, the one whose device was seen longest ago among those not connected; with eight connected it is refused. Sessions unseen for seven days are discarded at the user's next returning hello or detach. There is no background sweep, so a user who never connects again keeps their rows until the user is deleted.

### Scrobbling

- **Connections** live on the user row under `settings.secrets.<listenbrainz|lastfm>`: the credential (ListenBrainz user token, Last.fm session key) encrypted with `encrypt('scrobble-credential', …)`, the account name, `since`, `needsAttention` and `lastError`. Connecting verifies the credential (`listenbrainz.validateToken`, Last.fm's web auth flow) and switches the user's `scrobbleListenBrainz`/`scrobbleLastFm` on; disconnecting switches it off and drops unsent rows. Reconnecting the same account keeps `since`, so plays waiting for it are still sent.
- **Last.fm web auth.** `POST /me/scrobbling/lastfm/start` returns Last.fm's approval URL with a callback carrying `state` = user id, expiry (10 minutes) and `sign('lastfm-connect-state', …)`. The callback base is `PUBLIC_URL`, else the request's origin.
- **Sweep.** `scrobble.sweep` (every minute and at worker start) inserts one `scrobble_deliveries` row per service for each completed play of the last 14 days that started at or after `since`: `pending` when the service is switched on, `skipped` when off. It then queues `scrobble.deliver` `{ userId, target }`, keyed by both, where rows are ready.
- **Delivery.** `scrobble.deliver` locks the oldest ready rows (`for update skip locked`) in the service's batch size (ListenBrainz 1000, Last.fm 50), submits them with the MusicBrainz recording, release, release group and artist ids when known, track number, duration, album and start time, and marks them `sent`. A failure counts an attempt and the row waits 1, 2, 4… minutes (at most 6 hours) for the next sweep; after 10 attempts it is `failed` and left alone. A rejected credential (ListenBrainz 401, Last.fm error 9) sets `needsAttention` instead, and rows wait for the user to reconnect.
- **Guarantees.** The row is the idempotency record: one per play and service, submitted while locked, so overlapping sweeps and deliveries send a play once. The one gap is a crash after a service accepted a batch and before the commit, which resends that batch once.
- **Now playing** is sent from the API process when `onPlayStart` fires, best effort and without retries.

### Radio

- `suggestAutoplay` (the seam) and the radio routes rank with `radio/ranking.ts`: profile the seeds (artists, album and artist genres, years), gather a few hundred owned candidates in one query from bounded pools (seed artists, similar artists, albums sharing a genre or era, tracks the user played within half an hour of a seed, liked tracks and artists, a few random albums), score them with the weights in `ranking.ts` plus noise, and pick under variety rules over any ten consecutive tracks, seeds included: two per artist, one per album, three by seed artists, no artist twice in a row. Rules relax only when nothing else fits. An artist's tracks, in the pools and in the seed profile, are those it is credited on plus those it leads (`primary_artist_id`), since older rows and catalog stubs can lack credit rows. `suggestAutoplay` follows merge redirects of its seeds and exclusions first, so a queue entry holding a merged id still keeps its track out.
- For a requester (an admin, or a member with `canAcquire`), `on_demand` tracks from the seed-artist, similar-artist and liked pools are gathered too and ranked together with the owned ones; the first two picks (`OWNED_FIRST`) are owned whenever an owned track qualifies, so they play at once while the later ones are fetched. Everyone else gets owned tracks only, and nothing when none qualifies.
- Random sampling in SQL uses `uuid_hash_extended` with a salt drawn from the injected random source, so a seeded source repeats a result exactly.
- `similarArtists(artistId)` merges Deezer related artists (Deezer id from `external_ids`, else an exact name search) and ListenBrainz similar artists (with a server token and an artist MBID), mapped to catalog artists by MBID, else `name_key`. A source that is off or fails is skipped; lookups during ranking give up after 2.5 seconds.
- A radio is 50 tracks starting with the seed track with context `{ type: 'radio', id: 'track:<id>' | 'artist:<id>' }`. Nothing is stored: when the radio runs out and autoplay is on, the session's history (the radio's last tracks) seeds the next batch, so it continues in the same direction.
- The seed obeys the queue's rule: a track with a file for everyone, an `on_demand` one for a requester, else 409 `not_playable`. An artist radio starts from the artist's playable track the user played most, then liked, then one with a file (so it plays at once), then the most popular; for a requester that includes its top tracks and discography on demand, so an artist with nothing on the server still has a radio. When nothing of the artist has a track list yet (albums found by search) and an `assume_available` provider would play them, it first fetches the track lists of two albums (studio albums, newest first) through `ensureAlbumDetail`, each within the page budget. Nothing playable is 409 `nothing_playable`.
- `canStartArtistRadio` answers the same question without fetching, for `ArtistDetail.radio`: clients offer an artist radio only when it is true.

### Subsonic

`modules/subsonic` serves OpenSubsonic under `/rest` over the same services; [subsonic.md](./server/subsonic.md) lists what it supports.

- `router.ts` answers every method on GET and form POST, with or without `.view`. Handlers return plain objects that `serialize.ts` writes as XML or JSON(P). Failures are Subsonic error codes in a 200; service `AppError`s map to the closest code (404 is 70, 403 is 50).
- Every request authenticates with an app password (token, password or `apiKey`); there is no lockout, since app passwords cannot be guessed and are cheap to check.
- Ids carry their kind (`ar-`, `al-`, `tr-`, `pl-`, `ca-` for an artwork asset) and are checked on the way in. Music folders are library roots, numbered by a hash of the root id.
- Lists show the user's library restricted to tracks with a present file (`sql.ts`): a library file is a present collection file, or a present cached file whose recording or album the user saved (for a recording, that is the catalog's `inLibraryRecording` plus a present file); a library album is `inLibraryAlbum` with a library file, and its songs are its library files; artists are credited on a library album or track. Library albums are found from the library files, so search stubs cost nothing. Lookups by id (`getSong`, `stream`), starred songs and playlist entries need only a present file. `songs.ts`, `albums.ts` and `artists.ts` build response objects in batches with a fixed number of queries (`albums` and `artistRows` return only library rows); a song is shown through the present file `selectFile` would stream.
- `search3` and `search2` rank a query with the search module's library search (`searchLibrary`), so typos are tolerated as in the apps, and keep what is in the user's library. Sync clients page through everything with an empty `search3`. The page that starts where the user's previous one ended continues from its last key, so deep pages cost what the first does.
- `stream` serves originals and the streaming profiles through `openStream`; a bitrate below every profile, or a `timeOffset`, is a live ffmpeg encode that is not cached. A live encode takes a streaming encoder slot without waiting (`tryAcquireSlot`) and at most `LIVE_ENCODES_PER_USER` (3) run per user; a refusal is `transcoder_busy` (503) or `too_many_live_encodes` (429), sent as a Subsonic error before any header.
- The play queue is the session queue (`getSnapshot`, `replaceQueue`). The songs a client saved before its current one are remembered in memory while the session's current entry and queue are unchanged.

### Library pipeline

Jobs, in order. Each is idempotent and keyed by file or album group.

1. `library.scan` `{ rootId, paths? }` walks a root, or just the given paths, and compares `(rel_path, size, mtime)` with `media_files`: new files are inserted at `probe_stage 0`, changed ones reset to it, vanished ones get `missing_since` and returning ones lose it. Probes are queued in bulk. The walk (sorted by UTF-8 bytes) and the rows (read in pages, `collate "C"`) are merged like two sorted lists, so memory and queries stay flat whatever the library size. Hidden entries, `@eaDir`, recycle bins and partial downloads are skipped; symlinks are followed only to files inside the root, also when the scanned path itself is a link or lies under a linked folder. Serving and every ffmpeg read resolve a file's links (`libraryPath`) and refuse one whose real path is outside its root's (403 `path_outside_root`). A root that cannot be read is skipped rather than marked missing. One scan per root at a time (the root id is the singleton key); `library.scan-all` runs nightly. A full scan asked for while a watcher or import scan of some paths holds the key is not dropped: a queued partial scan becomes the full scan, and a running one is followed by `library.scan-after`, which the partial scan's job runs as soon as it finishes (or, failing that, which queues the full scan on its own 15 minutes later).
2. `library.probe` reads tags and technical details with `music-metadata` (ffprobe fills gaps and takes over when it cannot parse), normalizes them into `FileTags`, reads ReplayGain (and Opus R128) into the `tag_*` columns, stores the embedded picture, sets `probe_stage 1` and the group key, then queues ingest for the group. A file nothing can read gets `probe_error` and is left alone until it changes.
3. `library.ingest` `{ rootId, groupKey }` creates or reuses local-only catalog rows (artists, album, release, recordings, release tracks) from the group's tags and links the files, in one transaction. Rows the files already use are reused unless another group has more files on them (or as many and an older file), so a group that loses a file keeps its rows whichever of the two is ingested first; rows with a MusicBrainz id in the tags are found by it or created with it, and are never renamed from tags afterwards. A group with a matched or locked file is only relinked. Rows that end up unused (no files, no user data, no MusicBrainz id) are removed. Then album and artist art from the folder and files, lyrics (embedded or a `.lrc` sidecar), and `matching.match-album`. After this step the music is browsable and playable.
4. `library.analyze` (low priority) computes the audio hash and sets `probe_stage 2`. A new file whose hash matches a row whose file is gone is that row moved: the old row takes the new path and keeps its id, links and match state. Then `loudness.measure`.
5. `matching.match-album` `{ rootId, groupKey }` (singleton key `<rootId>:<groupKey>`) upgrades local-only rows to MusicBrainz rows, opens a review, or leaves the files `unmatched`. It applies under the catalog lock, like ingest. `matching.sweep` re-queues groups still `pending` every ten minutes and at worker start. When `PATCH /admin/settings` switches MusicBrainz on, `queueNewlyPossibleMatching` (`matching/retry.ts`) queues a sweep at once; when an AcoustID key appears it queues `matching.retry-fingerprints`, which sets unlocked `unmatched` files with no known AcoustID back to `pending` in groups the matcher would fingerprint (no album artist and title to search by), then sweeps. Groups searched by their tags are not retried: the key could not change their answer. Both leave alone files in `_Incoming/<importId>/` while that import is processing and has no `duplicates_decided_at`, so no provider is asked about copies about to be deleted or about half an album; the import queues their matching once it has decided.
6. `enrichment.album` and `enrichment.artist` (queued by the match) fill in covers, images, bios, Deezer ids and lyrics; see "Enrichment".

Every ffmpeg and ffprobe call that reads a library, staged or delivered file puts `INPUT_GUARD` (`lib/ffmpeg.ts`, through `audioInput`) before the input: the `file` protocol only, and only the demuxers of the scanner's audio extensions, because ffmpeg picks a demuxer by content and a concat script, playlist or SDP named `x.flac` would otherwise open other files or sockets. fpcalc has no such options, so `acoustid.fingerprint` pipes samples from a guarded ffmpeg into `fpcalc -format s16le` and takes the duration from the guarded probe.

`library.purge-missing` runs daily and deletes files missing longer than `missingFileGraceDays`. The grouping and album artist rules are written out at the top of `modules/library/grouping.ts`. In short, the album grouping key is root id, parent directory (ignoring `CD1`/`Disc 2` subfolders), and `matchKey` of album artist and album. An album artist tag that is a track's several artists run together ("A, B", where the multi-value artists tag names A and B) credits those artists, never one artist named "A, B". Because the folder is part of the key, every acquisition delivery is a group of its own; acquisition places delivered files on the requested album itself (see "Acquisition") instead of leaving them to ingest and matching.

Watching: roots with `watch` on are watched while a worker runs, and changed paths are scanned after two quiet seconds. macOS and Windows use one recursive watch per root; Linux uses one inotify watch per folder. Network mounts and exhausted inotify limits fall back to the nightly scan.

Scans skip `_Incoming/<importId>` folders while that import is extracting or moving files into them, and organize leaves `_Incoming` out of its plans unless `includeIncoming` is set. Organize plans provider deliveries (`cached`) under `_Fetched/` with the root's template inside, and other files out of it. A filed delivery is moved again only when a path component the template fills from an artist credit is no longer what its credits give (`refileCredits`, `organize/refile.ts`): the acquisition repair runs it for each managed root on full runs and after placing anything, the batch is dropped when it moves nothing, and the mover removes the folders it empties. A file a scan finds under a managed root's `_Fetched/` with no row gets `source = 'provider:unknown'`, so a database restored without it keeps it as cache; nothing in a read-only root is ever cache. When move detection reconnects a cached row to a file moved out of `_Fetched/` (or into another root), the row takes the new file's source: the owner moved it to keep it.

### Imports

`modules/imports` brings music in through the server: web uploads, the inbox folder, and acquisition deliveries (which call `createImport`, `addImportFile`, `commitImport` and `failImport` from `modules/imports/index.ts`). Whatever the origin, an import is a row in `imports` and goes through the same steps:

```
receiving ──commit──▶ processing: extracting → moving → identifying → filing ──▶ completed
    │                                                                       └──▶ failed
    └── cancel, provider failure, or a day without files ──▶ failed
```

- **Receiving.** Files stream into `<data>/staging/<importId>/` through a byte counter, as a temporary dot file, and are linked into place in the same transaction that bumps the import's counters, so a concurrent commit or cancel sees all of a file or none of it. Names are checked first (`imports/paths.ts`): audio by the scanner's extension list, `cover.*` and `folder.*` images, `.lrc`, `.cue`, `.log` and `.zip`; relative paths are normalized and must not be absolute or contain `..` or control characters, at most 8 levels and 1024 bytes. `importMaxFileBytes` and `importMaxBytes` bound files and imports (413). Nothing follows or creates a symbolic link. An upload that would leave less than 1 GiB free on the staging disk (`imports/space.ts`; the request's Content-Length counts, and a file is checked again every 256 MiB) is refused with 507 `insufficient_storage`, and `createImport` refuses a member's upload past `importMaxActivePerUser` receiving or processing ones (429 `too_many_imports`; admins exempt).
- **Target root.** `importRootId`, else the only enabled managed root; otherwise creating an import fails with `no_managed_root` or `import_root_not_set`.
- **`imports.process`** runs the steps; each is idempotent and records its outcome before the import moves on, so a retried job carries on after a crash. *Extracting* reads each zip in two passes with yauzl (check every entry, then extract into a temporary folder renamed into place); an archive with an unsafe path, a symbolic link, encryption, more than 10,000 entries, more bytes than the import may hold, or more than 20 times its own size (beyond 64 MiB) is refused whole, and one the disk has no room for fails the import, and nested zips are skipped. *Moving* uses organize's mover (rename, or copy, verify and delete) into `<root>/_Incoming/<importId>/`. *Identifying* queues a scan of that folder and watches `media_files`: it marks rows with `source` and `import_id`; once every file has its audio hash (or an error), it decides in one transaction which files are duplicates and deletes them, recording `imports.duplicates_decided_at` and the paths in `work`. A file is a duplicate when the library already has its audio, when an older import still processing has it, or when an earlier path in the same import does, so the outcome does not depend on the order analysis finished in. For an upload or inbox import, a provider delivery (cache) never counts as the library having the audio: the owner's copy is kept. For an acquisition import it also records the library files its duplicates were copies of (`work.copies`; only earlier provider deliveries not locked by "Fix match") and, on every pass from then on, hands the delivery to acquisition (`settleDelivery` in `acquisition/delivery.ts`), which checks it against the request and places what fits on the requested album before matching is awaited. Then it waits until the rest is ingested and matched, or for an hour, after which duplicates are decided from the hashes known by then and the rest is left for review. *Filing* plans and applies one organize batch for the import's own files still in its folder that are identified with confidence (matched, or placed by acquisition), removes the folder when no audio is left in it, refreshes wants and records the counts. `refileImport` runs the filing step again for a completed import, for files identified after it ended.
- **Completion** is read from the row; every status and step change publishes `import.updated` to the owner and admins.
- **Inbox.** One worker (an advisory lock) polls the inbox (`inboxPath`, else `SQUIRMY_INBOX_PATH`) and takes each top-level item once it has been unchanged and readable for five seconds, moving it into staging. What an import does not take, and failed inbox imports, go to `Not imported/<importId>/` in the inbox. The inbox may not overlap a library root or the data folder.
- **`imports.sweep`** (every 15 minutes and at worker start) expires imports stuck receiving, re-queues processing ones and removes orphaned staging folders.

### Acquisition

`modules/acquisition` implements the server side of [provider-protocol.md](./provider-protocol.md). Nothing happens until an admin adds a provider.

- **Providers** are rows in `acquisition_providers`; the secret is encrypted with `encrypt('acquisition-provider-secret', …)`. A provider counts once it is enabled and has answered `capabilities`. The enabled list is cached in memory for 30 seconds (and dropped on every change in that process), so `onDemandRecordings` costs nothing without one. Every call goes through `client.ts`: timeouts, the bearer secret, redirects only within the provider's origin, at most 4 MiB read, contract validation; failures are `ProviderCallError` and end up in `last_error` or the job's `error`.
- **Policy** is the `acquisition_policy` row of `server_settings` (`AcquisitionPolicy`): lossless preference, per-file limit, the cache limit (`storageQuotaBytes`), timeout, target root, and the delivery base URL (the policy's, else `PUBLIC_URL`, else localhost).
- **Coverage** (`onDemandRecordings`). An `assume_available` provider covers every recording without a miss newer than a day (`acquisition_misses`). A `must_resolve` provider covers recordings with a positive resolve newer than 30 days (`acquisition_offers`, free offers only). Recordings it has never answered for are collected in memory for a quarter second, queued as `acquisition.resolve` jobs of up to 100, and remembered for ten minutes so lists do not queue them again; when the answers arrive, the tracks, their albums and searches are invalidated. A provider's coverage is the admin's `coverage_override` when set (`PATCH` of the provider), else what it declared; a `capabilities` refresh only rewrites the declared one. `albumCoveredWithoutTracks` (the seam availability uses for albums with no track list, such as search results) is true while an `assume_available` provider is active.
- **Requests** (`requestRecording` from sessions, the acquire routes). The user must be an admin or have `can_acquire` (checked before anything about other users' jobs is looked at), a provider without a recent miss must remain, there must be a root to file into, and a member may have at most 100 unfinished jobs (`acquire_limit_reached`, 429; joining a job in flight is free; admins have no limit). The cache limit never refuses a request. Each job stores its `origin`: `play` (the current entry), `prefetch` (one further down the queue), `download` (a device downloading) or `library` (an explicit request or a library save; the route default). Joining a job in flight with a sooner origin moves it up. An album request leaves out tracks another job is already fetching. Adding to a library is only ever the user's library action: `POST /albums/:id/acquire` with origin `library` (the default, which "Get this album" sends) also records a library save of the album for the user (`recordSave`, owned by userdata), even when the server already has every track. Origin `download`, track acquires, and playback and prefetch requests (which come from the sessions module) only fetch; their files are cache, and acquisition writes no `library_items` for them. One job per target is in flight: the `idempotency_key` is `recording:<id>` or `album:<id>` and gets the job id appended when the job ends. A request that cannot go ahead is answered as failed straight away, unless another job is fetching that recording.
- **Jobs.** `acquisition.start` picks an offer (fresh cached offers, else a resolve, providers in priority order), waits for a slot under the provider's `maxConcurrent`, claims the job with a new random token (only its SHA-256 is stored) and calls `acquire`. Counting the slots and claiming one happen under an advisory lock per provider, and a job claimed but not yet answered holds its slot, so jobs started together never overshoot. A provider that declines as busy (`reason: "busy"`, or an older provider's "Provider is busy") gets the job again after 5 s, doubling up to a minute, with no miss; the policy's timeout ends a job no provider ever takes, also with no miss. An album job asks with the whole track list and marks tracks the server has, or that the job does not need, `wanted: false`. An album no provider offers whole, declines, or fails without delivering anything is fetched track by track instead (one recording job per missing track, the album job ends `failed` without misses). Deliveries stream into an import of kind `acquisition` (created on the first upload, filed into the policy's root) under the policy's per-file limit. `complete` commits the import, and `acquisition.finish` follows it: while it identifies, every delivered file that is ingested, hashed and not a copy of another library file is checked against the request (`verify.ts`, rules in the protocol document, merging rows with `mergeRecording` where a delivered file is plainly the requested recording) and what it satisfies is announced ready at once; when the import ends the check runs again and decides the job. A delivered file the import dropped as a copy of an earlier delivery counts through that file (`work.copies`), so a second request for a song the library has under another row succeeds and merges the two rows instead of failing with a miss. Free slots go to waiting jobs in start order (`play`, `prefetch`, `download`, `library`, oldest first within one): a job leaves a slot to the waiting jobs ahead of it, and a job ending wakes the first in line. Each upload is held to the job's budget: 1.25 × `maxFileBytes` per requested recording in all and four files per recording plus two (413 past either, which fails the job); empty audio is refused.
- **Placing deliveries** (`place.ts`, the one place that links a delivery to its request). A delivered file that is a requested recording goes on the album the request named (else, for a request without one, the album its file is already on when that is more than its tags, another album listing the recording, or the album a search stub hints at; with no hint either, as for Deezer's popular tracks, the album the file's own album tag names among its artists' albums, by edition-free title), on that album's own track for the recording. An album with no track list from a source has its detail fetched first; while a source could still answer, a young file waits (it plays meanwhile) and the sweep tries again, and without one the file goes on a track list built from the files in their own numbers (on an album its tags named that lists no track for it, a regional edition's bonus track, beside the album's own track list; on a requested album, as an extra with no track). A requested search stub that lists the recording only on a track list built from files gives way to the same album's other row (same artist, type and edition-free title) that lists it from a source, and is merged into that row once empty (`sameAlbumIds`). When the album lists the song under another row (a search stub and the MusicBrainz recording), the two are merged, but only when exactly one track is plainly the same recording and two catalog rows that carry ISRCs share one. `matching.placeFiles` (owned by matching) then links the files (`matched`, source `request`), removes or redirects the tags-built rows they left (never an album with a MusicBrainz id or a track list from a source, nor one with an id at another source unless the caller names it as the same album) and the credits of redirect recordings, so artists their tags ran together go, and resolves the group's review once every file in it is identified; the import files them as it files matches. Placement runs when the import has decided its duplicates (`settleDelivery`), while `acquisition.finish` follows a one-file delivery, at the end of the job, and from the repair.
- **Repair** (`repair.ts`). `acquisition.repair` (at worker start and daily at 04:25) and the sweep (over jobs of the last two hours) place deliveries of completed jobs that are still on rows built from their tags, as left by servers before placement existed, or on a file-built track list while their album, or another row that lists the recording from a source, has one by now, then file them with `refileImport`. The tags-built albums they leave become redirects, so likes, wants, playlist items and plays move to the real album (`mergeAlbum`). Only files a provider delivered for a job that completed, still linked to a recording it asked for, not locked and not matched by the matcher, are touched; jobs it could not place are skipped for five minutes. Groups of deliveries whose album is credited to a run-together artist are ingested again under today's grouping rules. A recording matching later links to another MusicBrainz id fails then: it gets a miss and its entries fail, except a current entry that is already playing. `acquisition.sweep` (every minute and at worker start) fails jobs past the timeout, polls providers of jobs quiet for a minute, re-queues the start of jobs stuck in `resolving` and the finish of jobs in `importing`, deletes expired misses and offers, and runs the repair over recent jobs.
- **The cache** (`evict.ts`). Every delivered file is cache (`media_files.cached`): Organize files it under `<root>/_Fetched/<template>`, matching never opens a review for a group of cached files only, Admin → Library stats count only collection files, and `GET /admin/acquisition/usage` reports `cachedFiles`, `cachedBytes`, `pinnedBytes` and `limitBytes`. When a job's import has ended, `discardUnrequested` deletes its delivered files that are not a requested recording (after merges), unless one is the only file of its recording and is pinned, counted by another import as a copy, or wanted by another job; the sweep repeats it for jobs ended in the last two hours. `acquisition.evict` (hourly at :17, and queued after a completion or upload while the cache is over its limit) deletes least recently used cached files (the later of the recording's last play and the file's arrival) until the cache is under 90% of `storageQuotaBytes`; 0 is unlimited. Never deleted: pinned files (`userdata/pins.ts`: a saved or liked album or recording, a recording on a saved or liked album's track list, a playlist item, a stored queue entry, a play in the last 24 hours, checked again for each file just before it goes), files in their first hour, files of imports still running, and anything outside a managed root. Deleting removes the file, its row and the local-only catalog rows it leaves (`removeOrphans`), then sidecars and empty folders inside `_Fetched/` or `_Incoming/` only; catalog albums and recordings stay, so the track is `on_demand` again.
- **Outcomes reach the sessions** through the `squirmy_acquisition` NOTIFY channel, which the API process applies with `markRecordingReady` / `markRecordingFailed`. Because sessions ask once per load, the API process also reconciles every 30 seconds while a provider is active: recordings of jobs that ended in the last ten minutes are marked ready when owned, and failed when not owned and no job is still on them.
- **Events.** Every status change publishes `acquisition.updated` to the requesting user and to admins.

The reference providers live in `adapters/`. `@squirmy/provider-kit` is the protocol's provider side (HTTP, secret, validation, idempotent jobs, streaming uploads); `adapters/cold-storage` indexes a folder's tags and resolves by MusicBrainz id, ISRC, then artist, title and length; `adapters/mock` synthesizes quiet tones and can be slow, failing, wrong or priced. The server's tests run the mock in-process.

### External metadata

All clients live in `modules/metadata/` and go through `lib/http.ts`:

- `cachedFetch(provider, url, { ttlSeconds, … })` stores responses in `http_cache` and serves them until they expire. 404s are cached for at most six hours, 5xx never; 429/503 are retried honoring `Retry-After`. `cache: 'reload' | 'no-store'` bypasses the cache for one call.
- Bodies over 8 MiB fail the call with `ProviderError` and are not cached.
- Image links come from provider data, so `fetchImage` downloads through `requestPublic`: https only, at most three redirects followed by hand and checked the same way, and connections only to public addresses. `publicDispatcher` (an undici `Agent`) filters what each name resolves to at connect time, so a name cannot pass a check and then resolve to a private address; `lib/address.ts` has the list (loopback, RFC 1918, link-local, unique local, CGNAT, multicast, reserved, and IPv4-mapped and NAT64 forms of those). A refused URL is treated as an unusable image.
- `rateLimit(key, intervalMs)` reserves the next slot in the `rate_limits` table, so the limit holds across processes. MusicBrainz uses 1100 ms (only against `musicbrainz.org` and its subdomains, such as `beta.`; a mirror is not limited).
- User-Agent: `Squirmy/<version> ( https://github.com/IsaacThoman/squirmy )`, with the version from `lib/version.ts`: `SQUIRMY_VERSION` (release images), else `dev+<short commit>` from `SOURCE_COMMIT` (a build argument, or set at run time by Coolify) or read once at start from git, else `dev`.
- Every provider checks its toggle or key in `ServerSettings` and returns null or an empty list rather than throwing when it is off. `fetchImage` (`metadata/images.ts`) downloads an image for any provider and checks the switch of the source that owns the image's host (`imageSourceEnabled`), so a lazily listed remote image is not downloaded after its source is turned off. "Not found" is null too; a provider failure (network, timeout, 5xx, bad key) throws `ProviderError`.
- Other modules import the clients from `modules/metadata/index.ts`, e.g. `musicbrainz.getRelease(mbid)`.
- Tests never touch the network. `useHttpFixtures(provider)` from `src/test/http.ts` serves recorded responses from `src/test/http/<provider>/` and fails on any unrecorded request. `SQUIRMY_RECORD_HTTP=1` records missing fixtures from the real service.

### Enrichment

The catalog is a lazy cache of MusicBrainz. `enrichment/detail.ts` completes a row when a page opens it; jobs decorate owned music in the background.

- **Album detail** (`ensureAlbumDetail`). An album at `detail_level` 2 fetched in the last 30 days is left alone. With a release-group MBID the group is fetched, the canonical release chosen (`canonical.ts`: best status present, then the most common track count, then CD or digital media, then the earliest date) and written through matching's `upsertRelease`. An album whose files are on a MusicBrainz edition keeps it as canonical; one whose files sit on a local edition (a local album merged into the group's row) takes the chosen release, and its files' recordings are fitted to the release's tracks. Without an MBID a Deezer id is bridged, most reliable first: the MusicBrainz URL relation of the Deezer page, the UPC as a barcode (accepted when its releases share one group), then a release-group search accepted only for one hit scoring 90 or more with the same title and artist. The stub adopts the MBID, or is merged into the row that has it. With no match the track list comes from Deezer (provider-only rows with ISRCs); the album stays at level 1 and the bridge is retried after a day. Recordings without an MBID that stand in for a track of the canonical release are merged into its recording (`fit.ts`) when the release is written: a stub with no file sharing an ISRC with one track, a loose stub of the album's artists (Deezer top tracks carry no ISRC) with the same edition-free title and a length within five seconds, and the recording of a present file filed under the album by that title and length rule only. A detail run that writes nothing does the last part too, only when an indexed check finds such a file, so a track fetched onto a complete album is folded in on the next visit. Deezer track ids are linked by ISRC.
- **Artist detail** (`ensureArtistDetail`). With an MBID: profile and genres, every Deezer page MusicBrainz links, the official discography (`release-group-status=website-default`) as level-1 album rows with a lazy Cover Art Archive cover (`/release-group/<mbid>/front-500`; none for MusicBrainz's placeholder artists, `musicbrainz.specialPurposeArtists`: Various Artists is credited on hundreds of thousands of compilations), adopting the album stubs search or Deezer made for the same groups (no MBID, no files, same primary artist, same `editionFreeKey` title, compatible type; a title two groups share adopts nothing), an image (the one the artist has, else Deezer, fanart.tv, Wikidata, all lazy), the English Wikipedia summary as bio, and a 0..1 `popularity` from ListenBrainz (with a token) or Deezer's top tracks, with stubs for tracks the catalog lacks. A Deezer artist is bridged by URL relation, else an unambiguous exact-name search; otherwise its Deezer albums become stubs.
- **Warming.** `warmDetail` (the seam's background form) starts a row's run without waiting for it; a catalog search warms its top result when that is an artist, so the page a user opens next joins a run already under way. At most two warm-ups run at once; more are skipped. Albums from a catalog search go through search's own queue instead (`search/warm.ts`), which keeps the ones it cannot start yet rather than skipping them.
- **Bounds.** One run per row is in flight per process and concurrent callers share it. A page waits at most four seconds from when the run started (so a visit that joins a run an earlier visit started waits only for what is left), then renders what is known with `detailPending: true` on `AlbumDetail`/`ArtistDetail`; the run carries on, invalidates the page when it lands, and `enrichment.album`/`enrichment.artist` is queued a minute later as a safety net. An album with a Deezer id and no track list yet gets Deezer's first: the page renders it (pending) while MusicBrainz is asked, and the Deezer edition becomes the MusicBrainz release when it is written. The seam never throws: a `ProviderError` leaves what was written, and an optional source failing (image, bio, top tracks) only keeps the row below level 2 so the next visit retries.
- **Owned albums** (`enrichment.album`). After detail: a stored cover unless the album has one at least 500 px on its short side (Cover Art Archive release front, then release-group front, then Deezer), Deezer ids by UPC and ISRC, a Wikipedia description, and `enrichment.lyrics` for owned recordings without lyrics. `albums.enriched_at` records success.
- **Fallback covers** (`enrichment.cover`, `covers.ts`). An album whose cover the art route unassigned gets the first of: a folder image or embedded picture of a present file (as a scan picks them), then the cover of its Deezer page as a lazy image. The archive is not asked for another release of the group: the group front is one of theirs. The sweep queues albums without a cover that have files or a Deezer page, each once a day per process.
- **Lyrics** (`enrichment.lyrics`, and `GET /tracks/:id/lyrics` on demand): LRCLIB by title, artist, album and duration; no match stores a `none` row that is retried after 30 days. Lyrics from files are never replaced.
- `enrichment.sweep` (every 30 minutes and at worker start) queues owned albums without `enriched_at`, their artists below level 2, and owned recordings without lyrics, 200 of each per run. While MusicBrainz is on, it then bridges up to 20 Deezer-only artists that share a name with another row (`namesakes.ts`, each tried once a day per process), by URL relation or an unambiguous exact-name search only, so Deezer's duplicate page of an artist is merged into the artist with the MBID without anyone opening it, and a real namesake stays apart.
- **Sources switched on later.** When `PATCH /admin/settings` switches a source on, `markEnrichmentStale` (`stale.ts`) clears `enriched_at` on owned albums (MusicBrainz, Cover Art Archive, Deezer, Wikidata) and drops artists of owned albums from level 2 to 1 (those, a fanart.tv key, a ListenBrainz token), and the sweep redoes them in its batches. Lyrics need nothing: no LRCLIB lookup is made or stored while it is off. `enrichment.new-releases` (weekly) refreshes library artists' discographies; Home's `new-releases` section lists albums from the last 120 days by library artists that have no present file. Neither counts MusicBrainz's placeholder artists (Various Artists on an owned compilation) as library artists.

## Clients

`client-core` holds everything both clients share and has no React, DOM or React Native imports:

- `reduceSession(state, { command, now, commandId, deviceId })`: the pure session reducer, also run by the server.
- `SessionClient`: owns the socket (through `createSocketTransport` from `@squirmy/client-core/socket`), the clock offset, optimistic commands and reconciliation; exposes a store (`getSnapshot`, `subscribe`) for `useSyncExternalStore`. `save()` and the `restore` option carry the last server state and the unsent commands across a relaunch; a restored session this device was playing comes back paused. On reconnect, commands made offline are followed by the engine's position, and tracks the device ended offline after the server gave up on it are preceded by a transfer back to it, so the server accepts them. `forgetPlayback(trackId?)` drops resolved descriptors (one track's, or all) so entries resolve again; the entries the engine holds keep their gain, and the preload is aimed again only when it is that track. An entry that only just became current loads at 0 rather than the few milliseconds its clock has run, since an exact seek that short makes a streaming player rebuffer; a preload the server refused is not asked for again until the target changes or playback is forgotten.
- `PlayerEngine`: the interface each platform implements (`load`, `preload`, `play`, `pause`, `seek`, `setGain`, `stop`, status events), with a `FakeEngine` for tests. `SessionClient` drives it when this device is active.
- `createApiClient({ baseUrl, getToken })`: typed fetch wrapper for every route, returning contract types.
- `TrackStore`: batched, cached `TrackSummary` hydration for queue entries.
- `isPlayable(track, viewer)`, `albumPresentation`, `albumNote` and `canFetch`: the one rule for what a viewer can play and how unavailable music looks. `mergeSearch(library, catalog, viewer)` turns the two search answers into one result set.
- Formatters (`formatDuration`), normalization math (`gainFor(mode, normalization, context)`), and artwork and stream URL helpers.

**Web** (`apps/web`): Vite, React 19, Tailwind 4, Radix primitives, TanStack Query, react-router. Colors are shadcn-style tokens declared as CSS custom properties in `src/index.css`: `background`, `foreground`, `card`, `popover`, `primary`, `secondary`, `muted`, `accent`, `destructive` (each surface with its `-foreground`), `border`, `input`, `ring`, and `sidebar` with `sidebar-foreground`, `sidebar-accent`, `sidebar-accent-foreground` and `sidebar-border`. A color theme replaces their values at runtime, so components style with the tokens; fixed colors are only for content (text over artwork, genre tiles, playlist covers). The palette is the web app's own and does not follow `apps/mobile/src/theme.ts`. Type is Inter, bundled with the app from `@fontsource-variable/inter`; nothing is loaded from a font service. `HTMLAudioElement` plus Web Audio gain implement `PlayerEngine`; the Media Session API mirrors the session.

- **Color themes.** `COLOR_THEMES` in `lib/color-themes.ts`: Squirmy (the default), Pulpo, Ocean, Forest and Ember, each with `light` and `dark` colors named by role. A theme sets at least `background`, `text` and `action`. `resolvePalette` derives the roles it leaves out (surfaces, hover, muted text, borders, the sidebar's colors, focus, error, the text on `action`) from those three, mostly by mixing background and text in OKLab (`lib/color.ts`), and `paletteVariables` maps the roles onto the tokens. `colorThemeStylesheet` is empty for the default theme: its colors are written out in `index.css`, which is what shows before any script runs, so the two blocks there (`:root` and `.dark`) must equal what `paletteVariables` gives for it; `lib/color-themes.test.ts` fails when they differ. A saved id that no longer exists falls back to the default.
- **Shell.** `ShellPage` (`pages/shell.tsx`) wraps every signed-in route in `AppShell`: the sidebar, `<main>` (the one scroll container, from `useScrollContainer()`, back at the top on every navigation), the queue panel beside it and the player bar under it. Now Playing is a full-screen dialog. The player bar is a row of the layout, not fixed over the page, so pages leave no room for it; `--player-height` on `<html>` tells toasts and notices where the player ends. The sidebar has the navigation, the playlists (songs dropped on one of the user's own are added to it, on Liked Songs liked) and the account menu: Settings, Admin panel for admins, Log out. It folds to a 52 px rail, and its open width is dragged between 200 and 385 px (default 264), never leaving the page less than 480 px. Both are kept per browser in `localStorage` (`squirmy.sidebar.collapsed`, `squirmy.sidebar.width`, in `sidebar-state.ts`), and the width is applied as `--sidebar-width` so a drag does not re-render the app. Below 768 px the sidebar is a modal drawer, opened by a button at the page's top left, the player is `MiniPlayer`, and the queue is only in Now Playing. From 768 px the queue panel floats over the page's right side, and from 1280 px it is a column beside it. The shell owns three shortcuts: Cmd/Ctrl+K (search dialog), Cmd/Ctrl+B (fold the sidebar, or open the drawer) and Cmd/Ctrl+, (settings).
- **Pages.** A page is a `PageHeader` (a sticky bar with the `<h1>`, links between the page's sections as `HeaderLink`s, and its controls) over a `Page`, which pads to the shell's `--gutter` (16 px, 24 px from 768 px). Album, artist, playlist and Liked Songs pages start with their artwork header and have no bar; they keep their first content clear of the drawer button on phones.

The search page runs both. `SearchDialog` (Cmd/Ctrl+K), fed by `SearchDialogHost` in `pages/shell.tsx`, runs only the library one, with the same query key, so the two share answers. It lists up to three artists, four albums and five songs, the answer's `top` first, then a row that opens `/search?q=…`. Enter on an artist or album opens it; a song plays when it can (`isPlayable`), else its album opens. With nothing typed it lists places to go.
- **Settings** are a dialog, not a page. `components/settings/SettingsDialog` is presentational, with the sections `playback`, `appearance`, `account`, `scrobbling`, `app-passwords` and `about`; `SettingsDialogHost` (`pages/settings.tsx`) gives it its data and is downloaded when the dialog first opens. Anything under the shell opens it with `useSettingsDialog().openSettings(section?)`. The routes `/settings` and `/settings/<section>` open it and redirect to `/`. Last.fm's callback lands on `/settings?lastfm=…`, which becomes a toast and opens the Scrobbling section.
- **Forms** validate with the contract schemas (`useFormSubmit`), show issues under their fields, and map known error codes onto fields.
- **Realtime.** `RealtimeProvider` opens one socket per signed-in user. `invalidate` refreshes the named queries, every reconnect refreshes all of them, and the shell shows a notice when the socket has been down for three seconds. The socket is in the context for `SessionClient`.
- **Audio.** `WebPlayerEngine` alternates two `<audio>` elements, each through its own `GainNode`, so normalization can boost. When the browser refuses to start audio the entry goes to `error` and the shell offers "Enable audio", which calls `unlock()` from the click. `/dev/engine` drives it with tones from `scripts/dev-audio.mjs`; `scripts/e2e-engine.mjs` checks it against the contract in Chromium, `scripts/e2e-auth.mjs` walks the account flows against a fresh server, `scripts/e2e-admin.mjs` the admin flows (setup with a real folder, scans, reviews, Fix match, Organize on disk, the search index), `scripts/e2e-playback.mjs` playback on the demo library (transport, queue, likes, playlists, lyrics, gapless ends, two devices, a second user), `scripts/e2e-polish.mjs` a server started like the Docker image (setup with its configured folder, naming templates, search's top result, the queue showing a fetch as loading), and `scripts/e2e-imports-providers.mjs` adding music (uploads, the inbox, duplicates) and acquisition providers against the mock provider.

- **Data.** Pages read through the hooks in `api/queries.ts`, keyed by `queryKeys`, so the server's invalidations refresh whatever is on screen. Page queries are `silent` and the page shows its own skeleton, error and "Nothing here" (404). Library lists page by cursor as they scroll. Likes and wants are optimistic: `patchEntity` sets `liked`/`wanted` on every cached copy of the entity, and a failure sets it back. While the server has the wantlist off (`SetupStatus.wantlistEnabled`, read by `useWantlistEnabled` and carried in `LibraryActions.wantlistEnabled`), no sidebar item, search destination, bookmark, menu entry or album-page line mentions it, and `/wantlist` goes home.
- **Cache and prefetch.** `api/persist.ts` keeps the query cache in IndexedDB (`squirmy-cache`), one record per origin and user for 7 days, at most 250 queries, paged lists cut to their first page, and only allowlisted roots (home, library, albums, artists, tracks, likes, playlists, wants, settings, history; never `me`, search, lyrics, admin or playback URLs). It is restored before the first render and every restored query is marked stale, so screens show the last answer and refetch at once. The record names its user, who seeds `me` and the setup status as placeholders (`updatedAt: 0`) that are refetched straight away; a null `me`, any 401 or signing out deletes it. A new build discards old records. `api/prefetch.ts`: `usePrefetch` starts an album's or artist's request on a 100 ms hover, a focus or a press (cards, track-row links, search results, the ⌘K highlight), and `AlbumPreview`/`ArtistPreview` draw the real header from a summary already cached while the detail loads.
- **Session.** `PlayerProvider` (inside the signed-in routes) runs one `SessionClient` on the realtime socket with the page's engine. `resolvePlayback` asks for the user's `qualityWifi` and the codecs `canPlayType` confirms (Opus only in Ogg); `setNormalization` follows the user's mode. A `TrackStore` hydrates queue, history and autoplay entries; the current track also has its own query so its heart follows likes. Commands send track ids, album ids and durations only, never `none` tracks; `on_demand` ones go as `preparing`. Playback position is a `PositionClock` that reads `getPositionMs()` on animation frames while playing, so only the clocks and the lyrics re-render. The provider also drives the Media Session (while this tab plays), the tab title, Space and the arrow keys, and tells failures (`player/fetch-failures.ts`): once for a song that was current or next and could not be had, once for `playback.unavailable` and then nothing until a song plays, never for fetches further down the queue (and skips a track the browser cannot play).
- **Devices.** Each tab claims its device with a Web Lock on the id kept in `localStorage`: the first tab is the browser's device, a second one `<id>-2` ("Chrome on macOS (2)"), so tabs never play at once; a reloading tab waits briefly for its old page's lock and comes back as the same device. The name (default from the user agent) is editable in the settings dialog and sent with a fresh hello (`SessionClient.rename`). While another device is active the shell shows "Playing on …" with "Play here", and the volume controls change that device's entry in `volumes`. The devices picker (`components/player/Devices.tsx`) detaches this tab and rejoins (`detach`, `attach({ bringQueue })`), hides that where `canDetach` is false, and lists detached devices under "Playing separately" and never as transfer targets; while detached the player shows "Only on this device" where "Playing on …" would be.
- **Admin.** Pages in `pages/admin.tsx` (lazy) feed views in `components/admin/`. `AdminLayout` is one `PageHeader` titled Admin whose links are the sections (the review queue's carries the count of open reviews), with the server's version under each page. Scan progress comes from `scan.progress` events and invalidations; Organize and index imports report progress only in the database, so those screens poll while one runs. `components/admin/FixMatch.tsx` is the entry point other screens use for Fix match (the album page's menu offers it to admins); it loads its dialog on demand. Settings fields save on blur through `DraftField`, which shows the server's refusal under the field. Providers (`/admin/providers`) lists providers, the acquisition policy and every request, refreshed by `acquisition.updated`.
- **Adding music.** `/imports` (lazy, `pages/imports.tsx`) is for admins and members who may upload. `lib/upload.ts` sends the files picked or dropped (folders walked through directory entries, paths kept) a few per request through `imports.addFiles`, which uses `XMLHttpRequest` for progress and reads each file from disk as it goes; it pauses by aborting the request in flight, and a file the server already had is counted as sent on resuming. The upload belongs to the tab, not the page, and the page follows the import through `import.updated` to its albums (`GET /imports/:id/albums`).
- **What plays.** Every row, card and page uses client-core's rules (`isPlayable`, `albumPresentation`, `albumNote`, re-exported by `lib/catalog.ts`) with the viewer from `useViewer()`, which `OnDemandProvider` provides. Music that plays looks the same wherever its file is: no badge, no count, no word for fetching. What does not play is gray and says "Not available". A current entry that is `preparing` looks like buffering (the spinner on its row and the play button) and after 8 s the player's subtitle says "Still loading…" (`use-still-loading.ts`). `OnDemandProvider` refreshes a track when its fetch ends. Add to library / Remove from library (`LibraryActions.setInLibrary`) patch `inLibrary` and `library` in every cached answer at once; track menus offer them per client-core's `trackLibraryToggle`, so a collection song, or one of an album the user added, has neither. Track rows, the player bar and Now Playing link each credited artist to its own page (`ArtistLinks`).
- **Search.** `api/use-search.ts` runs `/search/library` (60 ms after typing pauses) and `/search/catalog` (250 ms) and merges them with client-core's `mergeSearch`, for the search page and ⌘K alike. An answer is shown only for the query it answers; while the next one loads, the last library answer stays (faded, no top result) only if what is typed starts with its query. Catalog rows append after library rows, and the search page keeps skeleton room for them, so rows on screen do not move.

Catalog data reaches views through props typed with the contracts; session state and user actions come from `PlayerContext` and `LibraryContext`, whose providers are the only code that talks to `SessionClient` and the API. `/dev/kitchen-sink` shows every component state on the fixtures; the `/dev` pages exist only in development builds.

- **Accounts.** `AccountProvider` owns the auth state: it restores the stored session and opens the app from it at once (the `me` query confirms it in the background), creates the API client with the bearer token, and returns to sign-in on a 401. The token and device id go through `Keychain` (`src/account/keychain.ts`), which never rejects: what the keychain refuses is kept in memory for the launch, and the app says once that the next launch will need a sign-in. The server's name, version, invite rule and wantlist switch are read again from `GET /setup/status` whenever a server is chosen, and when the server invalidates it, so they stay current. While the wantlist is off (`useWantlistEnabled`), no screen, menu or Home row mentions it.
- **Data.** Query keys come from `queryKeys`; lists are infinite queries over the cursor pages. The cache is saved to app storage (expo-sqlite, through its async API, ten seconds after data changes and when the app leaves the screen) per server and user, restored before the splash hides, and removed on sign-out. It keeps the first page of each list and the 40 most recent album, artist, playlist and track pages from the last day. Every response that carries track summaries primes one `TrackStore`, which hydrates queue entries and the lock screen. Likes apply at once through a queue kept in app storage (`LikeQueue`): every cached answer that shows the item is patched (and Liked Songs gains or loses the track), one that cannot reach the server is sent again on the next connection or, after a server error, with backoff, only the last change to an item is sent, and one the server refuses rolls back with a notice. The playback session is saved in two halves, the queue half only when it changed.
- **Realtime.** `RealtimeProvider` opens one socket per signed-in session with `auth.token`, over WebSocket with a fallback to long-polling. `invalidate` refreshes the named queries (and refetches a changed track's like); the echo of a change this device made only marks them stale. A reconnect marks everything stale and refetches what is on screen; lists not on screen keep their first page. Returning to the app refetches nothing by itself. The socket is renewed when the app returns after being suspended (no server ping for 30 seconds) and when the network type changes. A refused handshake rechecks `me`, so a revoked session signs out. The app is *offline* once the socket has been down for 2.5 seconds.
- **Playback.** `PlaybackProvider` runs a `SessionClient` on that socket with `ExpoAudioEngine` (`canBoost: false`) and the user's normalization mode. `resolvePlayback` asks for the entry's album, the quality setting for the current network (Wi-Fi or cellular) and the codecs AVPlayer decodes. Components read the session through `usePlaybackState`; the position is polled with `usePosition` by the few components that show it. While another device is active the engine is stopped and the lock screen cleared. An engine error skips the track with a notice, or pauses when the next one fails too.
- **Volume.** On iOS this phone's volume is the system output volume. `SessionPlayer.systemVolume` keeps this device's `volumes` entry out of the engine's gain (only normalization applies), the local `SquirmySystemVolume` module (in `modules/now-playing`) gives the level, its changes and an `MPVolumeView`-backed slider and setter, and `syncSystemVolume` (`src/player/systemVolume.ts`) keeps the session in step: button and slider changes are reported (throttled), a change from another device moves the system volume while this phone plays (not within a second of the phone's own report, so late answers do not pull it back), and becoming the playing device reports the system level. Where the module is missing (Android, an older build) the session volume drives the engine as before.
- **Lock screen.** Buttons arrive through `connectNowPlaying` as callbacks; the provider turns them into session commands, never engine calls. The system's own pause (calls, unplugged headphones) becomes a session `pause`.
- **Downloads.** `DownloadManager` keeps each recording once per account, whatever albums, playlists, Liked Songs or single-song downloads list it, and drops it when none does. Files come from `GET /tracks/:id/playback?download=1` with the user's download quality, through `expo-file-system` background download tasks, into `Documents/downloads/` under a fresh UUID name; a completed file must match the announced size. Three run at a time; failures retry after 15 s, doubling, and are marked failed after five tries (a 404 at once); on cellular with Wi-Fi only they pause, keeping their resume data, and say so. The index is `downloads.db` (expo-sqlite): one row per account and recording with its file, quality, size, album context and times, plus the track summary, the descriptor (normalization) and retry state as JSON; collections keep their track ids and the album or playlist as last seen, so their pages open offline. Covers are kept at 600 px. Rows are written before files are deleted, and a launch sweep deletes files no row names and re-queues rows whose file is missing or short. Syncs (on reconnect, every six hours, and after `invalidate` of playlists, likes or albums) add tracks new to a downloaded collection, drop removed ones, flag what the server no longer has, and, at most daily per file, re-download a file the server replaced (`fileId` changed) while the old one keeps playing. Sign-out and switch-server remove the account's downloads after saying so.
- **Streaming cache.** `StreamingCache` keeps what was streamed and the next two `ready` entries in `Caches/streaming/` under a per-device limit (default 2 GB), indexed per account, recording and quality in `streaming-cache.db`. `plan` (`model.ts`, pure) chooses fetches once the outlook from `followSession` has been still for a second: on Wi-Fi also the stream being played, fetched a second time because `expo-audio` exposes no bytes; on cellular one at a time at the cellular quality, none with Data Saver; nothing while another device plays. Eviction is least recently played first and spares the entries about to play. `resolvePlayback` (`resolve.ts`) tries a download, a cached copy of at least the quality that would stream, the server, then a lesser copy; offline it takes a lesser copy without asking the server. Copies near the front are checked against the server daily. A launch drops purged rows, stray files and other accounts' rows; sign-out and switch-server empty it.
- **Search.** `searchView` (`src/library/search.ts`) is client-core's `mergeSearch` (one result set: library rows first in their order, catalog rows appended, what the viewer can't play last per kind) without a gray top result. While the catalog answer is on its way, kinds the library had nothing for are held open by placeholders of the same height, and `keepOrder` keeps rows already shown for a query in place when the same query is answered again, so nothing moves under the finger. An old query's answer is never mixed with a new one's.
- **On demand.** `useAvailability().canPlay` is client-core's `isPlayable` plus the phone's own files (downloads and the streaming cache); offline only those play. A playable track looks the same wherever its file is (no mark); a gray one says "Not available", or offline "Not downloaded" (`unavailableReason`). Fetching looks like buffering: `watchLoading` (`src/player/loading.ts`) follows how long the current entry has waited for audio (`preparing`, or the session `stalled`) and gives `useLoading`/`useTrackLoading` a phase: after 300 ms the play buttons and the current row show the spinner, after 8 s the subtitle reads "Still loading…". Queue rows show the artist whatever their state, "Not available" when failed. `failureNotices` (`player/session.ts`) gives one notice per failed entry that was current or next, and a session paused on a failed entry, or the `playback.unavailable` event, gives a single "Can't load music right now" and silences per-track notices until the user plays again.
- **Library.** The library is the server's collection plus the user's own additions, and only a manual action adds: the album page's + button (a check for a `collection` album, which cannot be removed) and Add to library / Remove from library in track menus, shown only when the server reports membership (`AlbumDetail.library`, `TrackSummary.inLibrary`) and never for a track whose `library` is `collection` or `album`, which removing would not take out (client-core's `trackLibraryToggle`, the same rule as the web app's). A track's menu has a **Go to** entry for each credited artist. `LibraryProvider.setSaved` shows the change at once on every cached copy, confirms it with an Undo notice, sends the changes for one item in order, and sets it back with a notice when refused. Album tiles are dimmed per `albumPresentation`, artist tiles never online; album pages show `albumNote` to viewers who can't fetch music, and the wantlist only on what the viewer can't play.
- **Offline.** `resolvePlayback` returns a downloaded file's descriptor (with its normalization) before asking the server, so downloads never stream; `SessionClient.forgetPlayback()` runs when a download arrives or goes, and `forgetPlayback(trackId)` when a cached file does. Offline, only downloads and cached tracks are playable (`canPlay`): other tracks are gray, as are albums, artists and playlists with nothing downloaded, actions that need the server are hidden, and a current entry that is neither downloaded nor cached is skipped. The session is saved (`SessionClient.save()`) with the summaries of its entries, and a relaunch restores it paused; commands made offline reach the server on reconnect.

## Testing

- `vitest` everywhere. A test file sits next to the code it tests as `*.test.ts`.
- **Database tests** call `useTestDatabase()` from `src/test/database.ts`, which clones a migrated template database for the file. They need `SQUIRMY_TEST_DATABASE_URL` (default `postgres://localhost:54329/postgres`). CI provides a Postgres service.
- **Audio fixtures** are generated with ffmpeg by `src/test/audio.ts`: short, very quiet tones with real tags. No real music is committed.
- **HTTP fixtures** for external services are recorded JSON; no live calls in tests. A hand-written fixture may list `request.headers` that must match too, for requests that differ only in a header.
- **Before a change is done:** `npm run build:packages && npm run typecheck && npm run lint && npm test` all pass.

## Git

- Conventional Commits: `type(scope): imperative summary`. `feat` and `fix` drive releases.
- Branches are named like commits: `feat-library-scan`, `fix-range-requests`.
- Pull requests target `dev`. `main` receives merges from `dev`; semantic-release tags a version on every push to `main`.
- Every push to `main` is deployed to the test environment at once, without waiting for CI. So `main` changes only through a `dev` → `main` pull request whose checks have passed, never by a direct push. A fix made on `main` anyway is merged back into `dev` right away.
- When CI fails on `main`, it opens an issue. Either fix the problem on `dev` and open another `dev` → `main` pull request, or revert the merge commit on `main` (and merge that revert back into `dev`).
